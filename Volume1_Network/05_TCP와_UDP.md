# 05. TCP와 UDP

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- TCP와 UDP의 제공 기능과 차이를 설명할 수 있다.
- 메시지 특성에 따라 전송 프로토콜을 선택할 수 있다.
- TCP의 스트림 특성과 UDP의 데이터그램 특성을 설명할 수 있다.

## 1. 개요

TCP(Transmission Control Protocol)는 연결을 설정한 뒤 신뢰성 있고 순서가 보장된 바이트 스트림을 제공한다. UDP(User Datagram Protocol)는 연결 설정 없이 독립적인 데이터그램을 전달하며 도착과 순서를 보장하지 않는다.

둘은 IP 위에서 프로세스 간 통신을 제공하는 전송 계층 프로토콜이다. IP의 최선형 전달만으로 부족한 기능을 어떤 방식으로 보완할지에 차이가 있다. TCP는 운영체제가 신뢰성과 혼잡 제어를 제공한다. UDP는 기본 기능을 최소화하고 필요한 정책을 애플리케이션이 선택하게 한다.

## 2. 왜 필요한가

데이터의 가치와 시간 민감도는 서비스마다 다르다. 아이템 구매 요청은 누락과 순서 오류를 허용하기 어렵다. 반면 초당 여러 번 보내는 캐릭터 위치는 오래된 패킷을 재전송해 최신 위치를 늦추는 것이 더 나쁠 수 있다.

TCP와 UDP는 단순히 “안전하지만 느림”과 “불안전하지만 빠름”으로 나눌 수 없다. TCP의 연결·재전송 비용과 UDP 위에 직접 구현할 신뢰성 비용을 포함해 요구사항에 맞게 선택해야 한다.

## 3. 핵심 동작 원리

### TCP

TCP는 연결 지향 프로토콜이다. 연결 설정 후 데이터를 순서 번호가 있는 세그먼트로 전송한다. 수신자는 확인 응답을 보내고, 송신자는 손실로 판단한 데이터를 재전송한다. 수신 측 처리 능력에 맞추는 흐름 제어와 네트워크 상태에 맞추는 혼잡 제어도 수행한다.

TCP가 제공하는 것은 **바이트 스트림**이다. 응용 프로그램이 세 번 `Send`해도 상대가 세 번 `Receive`한다는 보장은 없다. 메시지 길이 또는 구분자를 응용 프로토콜에 포함해야 한다.

```text
Send: [A][B]   [C]
          TCP byte stream
Recv: [A]   [B][C]
```

TCP는 순서를 맞추기 위해 앞선 데이터가 손실되면 뒤 데이터가 도착해도 애플리케이션 전달을 기다릴 수 있다. 이를 전송 계층의 Head-of-Line Blocking 관점에서 설명할 수 있다.

### UDP

UDP는 연결 설정 없이 데이터그램을 보낸다. 각 데이터그램의 메시지 경계는 유지된다. 하나의 데이터그램이 도착하면 하나의 단위로 읽지만, 데이터그램 자체가 유실되거나 중복되거나 순서가 바뀔 수 있다.

```text
Send: [Position #10] [Position #11] [Position #12]
Recv: [Position #10]                [Position #12]
```

UDP에는 TCP의 연결 상태, 재전송, 순서 정렬, 흐름·혼잡 제어가 없다. 필요하다면 애플리케이션이 시퀀스 번호, 확인 응답, 재전송, 전송률 조절을 구현한다. 모든 UDP 애플리케이션이 이 기능을 전부 구현할 필요는 없다.

### 체크섬과 MTU

TCP는 체크섬으로 전송 중 오류를 검출한다. UDP 체크섬은 IPv4에서는 0으로 설정해 생략할 수 있지만 IPv6에서는 원칙적으로 필수다. 체크섬을 사용하더라도 도착이나 비즈니스 처리 성공을 보장하는 것은 아니다.

큰 UDP 데이터그램은 IP 단편화를 유발할 수 있다. 한 조각만 유실되어도 전체 데이터그램을 사용할 수 없으므로 게임 서버는 경로 MTU를 고려해 작은 단위로 설계하는 편이 안전하다. TCP는 바이트 스트림을 세그먼트로 나누지만 애플리케이션은 여전히 과도한 메시지 크기와 지연을 관리해야 한다.

### 포트와 통신 대상 식별

TCP와 UDP는 모두 포트 번호를 사용해 호스트 안의 통신 대상을 구분한다. 다만 상태를 관리하는 방식은 다르다.

TCP 연결은 일반적으로 출발지 IP·포트와 목적지 IP·포트의 4-튜플로 구분한다. 따라서 서버가 하나의 TCP 포트에서 대기하더라도 클라이언트 주소와 임시 포트가 다르면 여러 연결을 동시에 유지할 수 있다. 연결마다 순서 번호, 송수신 버퍼, 흐름·혼잡 제어 상태가 독립적으로 관리된다.

UDP 서버는 보통 하나의 소켓으로 여러 송신자의 데이터그램을 받는다. `recvfrom` 계열 API는 데이터와 함께 송신자 주소를 알려 준다. 서버는 이 주소와 인증된 세션 식별자를 이용해 논리적인 상대를 구분할 수 있다. NAT 환경에서는 외부 IP와 포트 매핑이 바뀔 수 있으므로 주소만으로 사용자 신원을 판단하면 안 된다.

### 송수신 버퍼와 역압력

TCP의 `send`가 성공했다는 사실은 상대 애플리케이션이 데이터를 처리했다는 뜻이 아니다. 데이터가 로컬 운영체제의 송신 버퍼에 들어간 것일 수 있다. 상대가 늦게 읽으면 수신 윈도가 줄고, 결국 송신 측도 더 보내기 어려워진다. 이 흐름은 손실을 막는 데 필요하지만 느린 클라이언트의 서버 송신 큐가 계속 커지지 않도록 애플리케이션 수준의 상한도 필요하다.

UDP도 소켓 수신 버퍼가 가득 차면 데이터그램이 폐기될 수 있다. 또한 애플리케이션이 데이터그램보다 작은 버퍼로 읽으면 API와 운영체제에 따라 초과 부분이 잘릴 수 있다. UDP가 메시지 경계를 보존한다는 것은 한 데이터그램을 여러 번의 수신으로 자동 이어 읽을 수 있다는 뜻이 아니다. 최대 데이터그램 크기와 수신 버퍼 크기를 프로토콜에서 함께 정해야 한다.

## 4. 쉬운 예시

로그인 요청은 인증 결과를 정확히 받아야 하고 빈도가 낮으므로 TCP가 자연스럽다. 이동 위치는 다음 갱신이 곧 오며 오래된 값의 가치가 낮으므로 UDP가 적합할 수 있다. 그러나 턴제 게임의 이동 명령은 순서와 누락 방지가 중요하므로 TCP를 선택할 수도 있다. 데이터 이름이 아니라 요구사항이 기준이다.

전투 게임에서 이동, 스킬 사용, 채팅을 모두 같은 방식으로 보낼 필요도 없다. 이동 스냅샷에는 증가하는 시퀀스 번호를 붙여 오래된 UDP 데이터그램을 버릴 수 있다. 스킬 사용은 유실 시 재전송하되 같은 명령 ID가 다시 오면 중복 실행하지 않도록 만들 수 있다. 채팅과 로그인은 TCP 채널로 보내 구현을 단순화할 수 있다.

```text
Login / Chat     ── TCP ──> 순서·재전송을 전송 계층에 맡김
Movement #120   ── UDP ──> 최신성 우선, 오래된 번호 폐기
Skill command 7 ── UDP ──> ACK·제한적 재전송·중복 제거
```

이 구조에서 UDP를 쓴 스킬 명령이 TCP와 완전히 같은 보장을 얻는 것은 아니다. 애플리케이션이 필요한 메시지에만 보장을 추가하는 선택이다.

## 5. 비슷한 개념과 비교

| 구분 | TCP | UDP |
|---|---|---|
| 연결 설정 | 필요 | 없음 |
| 데이터 형태 | 바이트 스트림 | 데이터그램 |
| 도착·순서 보장 | 재전송과 순서 정렬 제공 | 제공하지 않음 |
| 흐름·혼잡 제어 | 제공 | 애플리케이션 책임 |
| 메시지 경계 | 보존하지 않음 | 보존 |
| 대표 용도 | 로그인, API, 결제, 채팅 | 실시간 위치, 음성, 일부 게임 트래픽 |

UDP 위에서도 QUIC처럼 신뢰성과 혼잡 제어를 구현할 수 있다. 따라서 UDP를 사용한다는 사실만으로 서비스가 비신뢰적이라고 단정할 수 없다.

## 6. 장점과 단점

TCP는 검증된 신뢰성 기능을 운영체제가 제공해 애플리케이션 구현이 단순해진다. 반면 연결 상태와 재전송 비용이 있고, 손실 시 뒤 데이터 전달이 지연될 수 있다.

UDP는 연결 설정이 없고 메시지별 정책을 직접 정할 수 있다. 최신 데이터 우선 처리와 멀티캐스트 같은 선택이 가능하다. 반면 신뢰성, 보안, 혼잡 제어가 필요하면 애플리케이션 구현과 검증 부담이 커진다.

## 7. 게임 서버·백엔드 실무 예시

게임 서버는 트래픽을 성격별로 분리할 수 있다.

- 로그인·결제·인벤토리: TCP와 요청 ID, 멱등성 처리
- 채팅: 순서와 도착이 중요해 TCP가 일반적
- 실시간 이동: UDP와 시퀀스 번호로 오래된 패킷 폐기
- 중요한 전투 이벤트: UDP 위 선택적 확인 응답 또는 TCP 채널 사용

UDP를 택해도 무제한으로 보내면 네트워크 혼잡을 악화시킨다. 서버는 클라이언트별 전송률, 패킷 크기, 재전송 상한을 관리해야 한다. 또한 UDP는 출발지 주소 위조가 상대적으로 쉬우므로 세션 토큰과 인증 절차가 필요하다.

### 선택 절차

전송 프로토콜을 정할 때는 다음 순서로 판단할 수 있다.

1. 데이터 유실을 허용할 수 있는지 확인한다.
2. 모든 메시지의 순서가 중요한지, 메시지 종류별 순서만 중요한지 구분한다.
3. 늦게 도착한 과거 데이터에 가치가 있는지 확인한다.
4. 연결 설정과 유지 비용, NAT 환경을 고려한다.
5. UDP를 선택했다면 인증, 혼잡 제어, 재전송과 중복 제거 중 필요한 기능을 정한다.
6. 패킷 손실률, RTT, 서버 큐 길이와 p99 지연으로 실제 동작을 검증한다.

TCP를 선택해도 응용 계층 책임은 남는다. 요청의 최대 크기, 메시지 프레이밍, 타임아웃, 재접속, 멱등성, 느린 클라이언트의 송신 큐 정책을 설계해야 한다. UDP를 선택하면 여기에 세션 식별, 시퀀스 번호, 필요한 신뢰성과 전송률 제어가 추가된다.

### 보안과 증폭 공격

UDP는 연결 설정 없이 출발지 주소가 담긴 데이터그램을 처리하므로 출발지 IP가 위조된 요청에 응답하면 제3자를 향한 증폭 공격에 악용될 수 있다. 인증 전에는 요청보다 훨씬 큰 응답을 보내지 않고, 짧은 검증 토큰이나 Cookie 방식으로 상대가 해당 주소에서 응답을 받을 수 있는지 확인할 수 있다. TCP의 핸드셰이크도 모든 공격을 막는 것은 아니지만, 주소 위조만으로 연결을 완성하기는 UDP보다 어렵다.

## 8. 자주 하는 오해

- “UDP는 언제나 TCP보다 빠르다”: 연결과 재전송 비용은 적지만 직접 구현한 신뢰성이나 네트워크 조건에 따라 결과가 달라진다.
- “TCP면 메시지가 한 번만 처리된다”: TCP는 바이트 전달을 보장하지만 요청 재시도로 인한 비즈니스 중복은 막지 않는다.
- “UDP는 손상된 데이터도 그대로 전달한다”: 체크섬을 사용하는 경우 오류가 검출된 데이터그램은 폐기된다. UDP에서 애플리케이션이 주로 다룰 문제는 손실·중복·순서 뒤바뀜이다.
- “실시간 게임은 전부 UDP다”: 장르와 메시지 요구사항에 따라 TCP만 사용하거나 혼합할 수 있다.
- “TCP는 패킷 경계를 보존한다”: TCP는 바이트 스트림이므로 프레이밍이 필요하다.

## 9. 면접 질문

### Q1. TCP와 UDP의 차이를 설명해 주세요.

TCP는 연결 후 신뢰성 있고 순서가 보장된 바이트 스트림을 제공하며 흐름·혼잡 제어를 수행한다. UDP는 연결 없이 데이터그램을 전달하고 도착과 순서를 보장하지 않는다. 대신 애플리케이션이 필요한 전송 정책을 직접 선택할 수 있다.

### Q2. 게임 서버에서 TCP와 UDP를 어떻게 선택하나요?

누락 허용 여부, 순서, 최신성, 구현 복잡도를 기준으로 선택한다. 로그인과 결제는 TCP가 적합하고, 오래된 위치보다 최신 위치가 중요한 실시간 갱신은 UDP가 적합할 수 있다.

### Q3. TCP에서도 메시지 프레이밍이 필요한 이유는 무엇인가요?

TCP는 메시지가 아니라 연속된 바이트를 제공한다. 송수신 호출 경계가 보존되지 않으므로 길이 필드나 구분자로 메시지 경계를 정의해야 한다.

### Q4. UDP로 신뢰성 있는 통신을 만들 수 있나요?

가능하다. 시퀀스 번호, 확인 응답, 선택적 재전송을 응용 계층에서 구현할 수 있다. 다만 혼잡 제어와 예외 처리까지 검증해야 하므로 복잡도가 증가한다.

### Q5. TCP의 `send` 성공은 무엇을 의미하나요?

일반적으로 로컬 소켓이 데이터를 받아들였다는 뜻이며 상대 애플리케이션의 수신이나 비즈니스 처리를 보장하지 않는다. 처리 완료가 필요하면 응용 계층 응답을 별도로 정의해야 한다.

### Q6. UDP에서 메시지 경계를 보존한다는 의미는 무엇인가요?

각 송신 데이터그램이 독립된 수신 단위로 유지된다는 뜻이다. TCP처럼 여러 송신이 하나의 스트림으로 합쳐지지는 않지만, 데이터그램 유실과 수신 버퍼보다 큰 데이터의 절단 가능성은 별도로 처리해야 한다.

## 10. 예상 꼬리질문

- UDP 데이터그램이 MTU를 넘으면 어떤 문제가 생기나요?
- TCP를 사용해도 멱등성이 필요한 이유는 무엇인가요?

- QUIC은 UDP를 어떻게 활용하나요?
- UDP 서버가 출발지 주소만으로 사용자를 식별하면 안 되는 이유는 무엇인가요?

## 11. 30초 모범답변

> TCP는 연결을 맺고 재전송과 순서 제어를 통해 신뢰성 있는 바이트 스트림을 제공하며, UDP는 연결 없이 독립적인 데이터그램을 전달합니다. TCP는 메시지 경계를 보존하지 않고 UDP는 보존하지만 도착과 순서를 보장하지 않습니다. 게임 서버에서는 로그인처럼 정확성이 중요한 데이터에는 TCP를, 오래된 값보다 최신성이 중요한 위치 갱신에는 UDP를 고려합니다.

## 12. 1~2분 확장답변

> TCP와 UDP는 IP 위에서 프로세스 간 통신을 제공하는 전송 계층 프로토콜입니다. TCP는 연결을 설정하고 순서 번호, 확인 응답, 재전송으로 신뢰성과 순서를 보장하며 흐름 제어와 혼잡 제어도 제공합니다. 대신 바이트 스트림이라 응용 계층에서 메시지 경계를 정의해야 하고, 손실된 앞 데이터 때문에 뒤 데이터 전달이 기다릴 수 있습니다. UDP는 연결 설정과 이런 보장이 없는 대신 데이터그램 경계를 유지하고 메시지별로 지연과 신뢰성 정책을 직접 설계할 수 있습니다. 게임에서는 로그인과 인벤토리는 TCP, 빈번한 위치 갱신은 UDP처럼 선택할 수 있지만 장르와 데이터 요구사항을 기준으로 판단해야 합니다.

## 13. 핵심 요약

- TCP는 신뢰성과 순서가 보장된 바이트 스트림을 제공한다.
- UDP는 메시지 경계를 유지하지만 도착, 순서, 중복 방지를 보장하지 않는다.
- TCP에는 프레이밍이 필요하고 UDP에는 큰 데이터그램의 단편화 위험이 있다.
- 프로토콜 선택 기준은 정확성, 최신성, 지연, 구현 비용이다.
- UDP에서도 필요한 데이터에만 신뢰성을 추가할 수 있다.

## 한 줄 정리

> TCP는 전달 보장을 전송 계층에 맡기는 선택이고, UDP는 필요한 전달 정책을 애플리케이션이 직접 선택하는 방식이다.
