# 08. TIME_WAIT와 CLOSE_WAIT


## 학습 목표

- TIME_WAIT가 능동 종료 측에 생기는 이유(마지막 ACK 재전송·지연 패킷 소멸 대기)를 설명할 수 있다.
- CLOSE_WAIT가 수동 종료 측에 생기는 이유와 누수 원인(close() 미호출)을 설명할 수 있다.
- TIME_WAIT 과다와 CLOSE_WAIT 과다를 구분해 각각의 점검 항목을 설명할 수 있다.
- 게임 서버에서 소켓 생명주기와 세션 생명주기를 분리해야 하는 이유를 설명할 수 있다.

## 1. 개요

TIME_WAIT는 TCP(Transmission Control Protocol) 연결을 능동적으로 종료하고 마지막 ACK(Acknowledgment)를 보낸 쪽이 일정 시간 유지하는 상태다. CLOSE_WAIT는 상대의 FIN(Finish)을 받아 수신 종료를 확인했지만 로컬 애플리케이션이 아직 소켓을 닫지 않은 상태다.

둘 다 TCP 종료 과정의 정상 상태일 수 있다. 다만 지속적으로 많이 쌓이면 서로 다른 원인을 조사해야 한다.

## 2. 왜 필요한가

TIME_WAIT는 마지막 ACK가 유실되었을 때 상대의 FIN 재전송에 다시 ACK하고, 이전 연결의 지연 세그먼트가 같은 4-튜플의 새 연결에 섞이지 않도록 기다린다. CLOSE_WAIT는 상대가 송신을 끝냈어도 로컬 애플리케이션이 남은 처리와 송신을 마칠 기회를 준다.

## 3. 핵심 동작 원리

```text
Active Closer                              Passive Closer
  FIN_WAIT_1 -- FIN ---------------------> ESTABLISHED
             <------- ACK ---------------- CLOSE_WAIT
  FIN_WAIT_2                              (앱 close 대기)
             <------- FIN ---------------- LAST_ACK
  TIME_WAIT -- ACK ----------------------> CLOSED
     |
  일정 시간 후 CLOSED
```

### TIME_WAIT

능동 종료 측이 마지막 ACK를 보낸 뒤 진입한다. 상대가 마지막 ACK를 받지 못하면 FIN을 재전송할 수 있으므로 다시 ACK할 수 있어야 한다. 또한 네트워크에 남은 이전 세그먼트의 수명보다 충분히 기다려 같은 연결 식별자의 재사용 위험을 줄인다.

TIME_WAIT가 있다는 사실만으로 누수는 아니다. 짧은 TCP 연결을 많이 만들고 먼저 닫는 서버나 프록시에서는 자연스럽게 많을 수 있다. 문제는 임시 포트 고갈, 새 연결 실패, 비정상적인 연결 생성 패턴과 함께 나타나는지다.

TIME_WAIT 유지 시간은 TCP가 지연 세그먼트의 최대 수명을 고려하는 개념과 관련된다. 흔히 `2MSL`로 설명하지만 실제 운영체제의 유지 시간과 설정은 구현마다 다를 수 있다. 면접에서는 특정 초 값을 외우기보다 마지막 ACK 재전송과 이전 연결 세그먼트 제거라는 목적을 설명하는 편이 정확하다.

같은 로컬 IP·포트와 원격 IP·포트 조합을 즉시 재사용하면 이전 연결의 늦은 세그먼트를 새 연결 데이터로 오해할 위험이 있다. TIME_WAIT는 이 4-튜플 재사용을 일정 시간 제한한다. 다른 원격 주소나 포트를 사용하는 새 연결까지 모두 막는 것은 아니다.

### CLOSE_WAIT

상대 FIN을 받은 운영체제는 애플리케이션의 `recv()`에 EOF를 알린다. 애플리케이션이 `close()`할 때까지 CLOSE_WAIT가 유지된다. 따라서 오래 누적되면 보통 종료 이벤트를 처리하지 않았거나 예외 경로에서 소켓 자원을 닫지 않은 애플리케이션 문제를 의심한다.

CLOSE_WAIT를 커널 설정으로 짧게 없애는 것이 근본 해결은 아니다. 애플리케이션의 소유권과 종료 경로를 찾아야 한다.

상대가 FIN을 보내면 로컬 TCP는 이전까지 받은 바이트 뒤에 EOF를 제공한다. 애플리케이션은 남은 데이터를 모두 읽은 뒤 `recv()`가 0을 반환하는 방식으로 정상 종료를 알 수 있다. 이를 오류로만 처리하거나 읽기 Loop를 빠져나간 뒤 소켓을 닫지 않으면 CLOSE_WAIT가 남는다.

비동기 서버에서는 수신 Callback, Timeout, 인증 실패와 서버 종료가 동시에 같은 Session을 정리하려 할 수 있다. 종료 책임을 한 곳에 모으고 한 번만 실행되는 상태 전환을 사용해야 한다. 그렇지 않으면 닫기 누락뿐 아니라 이중 해제와 오래된 Callback의 상태 접근도 발생할 수 있다.

### 누가 먼저 닫았는가

TIME_WAIT는 일반적으로 먼저 종료한 능동 종료 측에 생기고, CLOSE_WAIT는 FIN을 받은 수동 종료 측에 생긴다. 클라이언트와 서버 역할만으로 결정되지 않는다. 서버가 먼저 연결을 닫으면 서버에 TIME_WAIT가 생길 수 있다.

## 4. 쉬운 예시

게임 서버가 유휴 클라이언트를 먼저 끊으면 서버가 능동 종료 측이 되어 TIME_WAIT가 생길 수 있다. 반대로 클라이언트가 종료해 FIN을 보냈는데 서버 코드가 수신 0바이트를 무시하고 소켓을 닫지 않으면 서버에 CLOSE_WAIT가 쌓인다.

API 서버가 매 요청마다 외부 서비스에 새 TCP 연결을 만들고 응답 후 먼저 닫는다면 API 서버 쪽에 TIME_WAIT가 빠르게 늘 수 있다. HTTP 지속 연결과 Connection Pool을 사용하면 연결 생성·종료율을 낮출 수 있다. 다만 Pool의 연결이 영원히 유효한 것은 아니므로 유휴 시간, 최대 수명과 실패 연결 제거가 필요하다.

### 코드로 보는 CLOSE_WAIT 누수와 수정

```java
// BAD: 예외 경로에서 close() 누락 → CLOSE_WAIT 누수
public class SessionHandler {
    private SocketChannel socket;

    public void handleSession() {
        try {
            while (true) {
                ByteBuffer buf = ByteBuffer.allocate(1024);
                int read = socket.read(buf);
                if (read == -1) {
                    // EOF: 상대가 FIN을 보냄 → CLOSE_WAIT 진입
                    // close() 없으면 CLOSE_WAIT 영구 유지
                    return; // ← 소켓 미종료 누수
                }
                process(buf);
            }
        } catch (IOException e) {
            log.error("IO error", e);
            // close() 없음 → CLOSE_WAIT 누수
        }
    }
}

// GOOD: try-with-resources로 항상 close 보장
public class SessionHandler {
    public void handleSession(SocketChannel socket) {
        try (SocketChannel ch = socket) { // close() 자동 호출
            while (true) {
                ByteBuffer buf = ByteBuffer.allocate(1024);
                int read = ch.read(buf);
                if (read == -1) break; // EOF → loop 종료 → 자동 close()
                process(buf);
            }
        } catch (IOException e) {
            log.error("IO error", e); // close() 자동 호출됨
        }
    }
}
```

```text
TIME_WAIT 과다 진단:
ss -ant | grep TIME_WAIT | wc -l    ← 개수 확인
→ 짧은 연결 + 서버가 먼저 닫음 → 연결 재사용(Keep-Alive, Pool) 검토

CLOSE_WAIT 과다 진단:
ss -ant | grep CLOSE_WAIT | wc -l   ← 개수 확인 + 시간 경과 관찰
→ 수 늘어나고 줄지 않음 → close() 누락 코드 경로 추적
```

## 5. 비슷한 개념과 비교

| 구분 | TIME_WAIT | CLOSE_WAIT |
|---|---|---|
| 위치 | 능동 종료 측 | FIN 수신 측 |
| 의미 | 마지막 ACK 재전송과 지연 패킷 소멸 대기 | 애플리케이션의 로컬 종료 대기 |
| 정상 해소 | 타이머 만료 | 애플리케이션 `close()` |
| 과다 시 점검 | 짧은 연결, 포트 고갈, 종료 주체 | 소켓 누수, EOF·예외 처리 |

FIN_WAIT_2가 오래 유지되면 상대가 FIN을 보내지 않거나 종료 처리가 멈춘 상황을 확인한다. 상태 이름만 보지 말고 연결 종료의 어느 단계인지 이해해야 한다.

## 6. 장점과 단점

**TIME_WAIT 존재 이유(장점)**
- 마지막 ACK 유실 시 상대 FIN 재전송에 다시 ACK할 수 있다.
- 이전 연결의 지연 세그먼트가 새 연결에 섞이지 않도록 보호한다.

**TIME_WAIT 단점**
- 많은 짧은 연결에서 임시 포트를 점유해 고갈 위험.
- 2MSL 동안 같은 4-튜플 재사용 불가.

**CLOSE_WAIT 존재 이유(장점)**
- 수신 종료 후에도 로컬이 남은 데이터를 전송할 시간을 제공.

**CLOSE_WAIT 단점**
- 애플리케이션이 `close()`를 호출하지 않으면 영구 유지 → 소켓 누수.
- 파일 디스크립터 고갈, 메모리 누수로 이어질 수 있다.

## 7. 게임 서버·백엔드 실무 예시

운영 중 상태가 급증하면 시계열로 연결 생성률, 종료 주체, 오류율을 함께 본다. TIME_WAIT가 많다면 요청마다 새 연결을 만드는지, 연결 풀과 keep-alive를 사용할 수 있는지 확인한다. CLOSE_WAIT가 많다면 소켓을 소유한 프로세스와 호출 스택을 찾고 다음 경로를 점검한다.

- `recv()`가 0을 반환했을 때 종료하는가?
- 타임아웃과 예외 경로에서도 `Dispose` 또는 `close()`가 실행되는가?
- 세션 객체와 소켓의 소유권이 명확한가?
- 비동기 작업 취소 시 종료 코드가 빠지지 않는가?

무작정 TIME_WAIT 재사용 설정을 바꾸면 지연 패킷 충돌 위험이나 다른 운영 문제를 만들 수 있다. 먼저 연결 패턴을 개선한다.

### 상태 수를 해석하는 방법

상태의 절대 개수만으로 장애를 판단하지 않는다. 초당 새 연결 수가 높으면 정상 종료만으로도 TIME_WAIT가 많이 보일 수 있다. 다음 항목을 같은 시간축에서 확인한다.

- 초당 연결 생성·종료 수와 어느 쪽이 먼저 닫는지
- 새 연결 실패율과 임시 포트 사용량
- 프로세스의 열린 파일 수와 소켓 메모리
- CLOSE_WAIT의 체류 시간과 소유 코드 경로
- 배포·장애 시 FIN과 RST 비율 변화

예를 들어 TIME_WAIT 수는 많지만 새 연결 오류와 포트 압박이 없다면 즉시 조정할 필요가 없을 수 있다. 반대로 CLOSE_WAIT 수가 적더라도 같은 연결이 장시간 남아 있고 계속 증가한다면 누수를 의심해야 한다.

## 8. 자주 하는 오해

- **”TIME_WAIT는 서버 버그다”**: 능동 종료 측에서 발생하는 정상 TCP 상태다. 짧은 연결이 많으면 당연히 많이 보인다. 포트 고갈·새 연결 실패를 동반할 때만 조치가 필요하다.
- **”CLOSE_WAIT는 기다리면 운영체제가 정리한다”**: CLOSE_WAIT는 애플리케이션이 `close()`를 호출해야만 해제된다. TIME_WAIT는 2MSL 타이머 후 자동 정리되지만 CLOSE_WAIT는 코드 수정 없이 영구 유지된다.
- **”TIME_WAIT는 클라이언트에만 생긴다”**: 서버가 먼저 FIN을 보내면(유휴 연결 정리, 배포 시 드레이닝) 서버에 TIME_WAIT가 생긴다. 능동 종료 주체가 기준이다.
- **”상태 수가 많으면 무조건 장애다”**: 절대 숫자보다 추세와 자원 고갈 여부가 중요하다. TIME_WAIT 수천 개도 포트 고갈·연결 실패가 없으면 정상일 수 있다.
- **”RST로 강제 종료하면 TIME_WAIT를 건너뛴다”**: RST는 TIME_WAIT를 우회하지만 미처리 데이터가 손실될 수 있고, 상대에서 연결 오류로 보인다. 의도적 사용이 아니면 원인부터 찾아야 한다.
- **”CLOSE_WAIT는 소켓 개수에만 영향을 준다”**: CLOSE_WAIT 소켓은 파일 디스크립터를 점유해 `ulimit` 상한을 소비한다. 대량 누수 시 새 연결 수락 불가, 파일 열기 실패로 이어진다.
- **”연결 풀 크기를 늘리면 CLOSE_WAIT가 줄어든다”**: 풀 크기 증가는 CLOSE_WAIT 원인(close() 누락)을 숨기고 파일 디스크립터 고갈 시점을 늦출 뿐이다. 코드 경로 추적이 근본 해결이다.


## 9. 면접 질문

### Q1. TIME_WAIT가 필요한 이유는 무엇인가요?

마지막 ACK가 유실되면 상대가 FIN을 재전송하므로 다시 ACK할 수 있어야 한다. 또한 이전 연결의 지연 세그먼트가 사라질 시간을 확보해 같은 4-튜플의 새 연결과 섞이는 위험을 줄인다.

### Q2. CLOSE_WAIT가 많이 쌓이면 무엇을 의심하나요?

상대 FIN은 받았지만 로컬 애플리케이션이 소켓을 닫지 않은 상태이므로 EOF나 예외 처리 누락, 소켓 자원 누수를 우선 확인한다.

### Q3. TIME_WAIT와 CLOSE_WAIT는 어느 쪽에 생기나요?

TIME_WAIT는 일반적으로 능동 종료 측, CLOSE_WAIT는 상대 FIN을 받은 수동 종료 측에 생긴다. 서버와 클라이언트 역할이 아니라 종료 주체가 기준이다.

### Q4. TIME_WAIT가 많을 때 무엇부터 확인하나요?

연결 생성률과 능동 종료 주체, 새 연결 실패, 임시 포트 압박을 먼저 확인한다. 짧은 연결이 원인이라면 연결 재사용과 Pooling을 검토하고 커널 설정 변경은 영향 범위를 검증한 뒤 판단한다.

### Q5. CLOSE_WAIT를 코드에서 어떻게 줄일 수 있나요?

EOF, Timeout, 예외와 취소를 포함한 모든 종료 경로에서 소켓을 한 번만 닫도록 소유권을 명확히 한다. 비동기 Callback이 남아 있다면 종료 상태를 확인해 오래된 작업이 Session에 접근하지 않게 한다.

### Q6. 게임 서버에서 소켓 생명주기와 세션 생명주기를 분리해야 하는 이유는 무엇인가요?
소켓은 TCP 연결이 끊기면 사라지지만 게임 세션(플레이어 상태, 캐릭터 위치)은 재접속을 위해 유지해야 할 수 있습니다. FIN 수신 즉시 세션을 삭제하면 짧은 네트워크 단절로 끊긴 플레이어가 게임을 처음부터 다시 시작해야 합니다. 세션에 재접속 토큰과 유예 시간(예: 30초)을 두어 새 소켓으로 이전 세션을 복구할 수 있게 합니다. CLOSE_WAIT 누수 방지를 위해 소켓은 항상 즉시 닫고, 세션 보존은 별도 타이머로 관리합니다.

## 10. 예상 꼬리질문

- `recv()`가 0을 반환하면 무엇을 의미하나요?
  > 상대방이 FIN을 보내 송신 종료를 알린 것으로, TCP 스트림에서 더 이상 읽을 데이터가 없음을 의미한다. 애플리케이션은 이 시점에 소켓을 닫아야 하며, 닫지 않으면 CLOSE_WAIT 상태가 지속된다.
- 짧은 연결이 많을 때 TIME_WAIT를 줄이는 방법은 무엇인가요?
  > 근본적으로는 HTTP Keep-Alive나 연결 풀로 연결 재사용 횟수를 높여 새 연결 생성 자체를 줄이는 것이 우선이다. 운영체제의 `tcp_tw_reuse` 설정으로 조건에 맞는 TIME_WAIT 소켓을 재사용할 수 있지만, 영향 범위를 검증한 뒤 적용해야 한다.
- FIN_WAIT_2는 어떤 상태인가요?
  > 능동 종료 측이 FIN을 보내고 ACK를 받았지만 상대방의 FIN은 아직 받지 못한 상태다. 상대 애플리케이션이 데이터를 다 보낸 뒤 FIN을 보낼 때까지 기다린다. 이 상태가 오래 지속되면 상대가 FIN을 보내지 않거나 종료 처리가 지연된 상황을 의심한다.
- 연결 풀은 어떤 비용과 상태를 줄이나요?
  > TCP 3-Way Handshake와 TLS 핸드셰이크 비용을 줄이고, 연결 생성·종료 반복으로 발생하는 TIME_WAIT 누적을 완화한다. 또한 운영체제의 임시 포트 소비를 줄여 포트 고갈 위험도 낮춘다.
- RST 종료는 TIME_WAIT와 어떤 관계가 있나요?
  > RST로 강제 종료하면 정상 4-Way FIN 절차를 건너뛰어 TIME_WAIT 상태가 생기지 않는다. 그러나 미처리 데이터가 유실될 수 있고 상대방 입장에서는 연결 오류로 인식된다. TIME_WAIT 회피를 목적으로 RST를 의도적으로 사용하는 것은 권장하지 않는다.
- 서버와 클라이언트 중 어느 쪽이 TIME_WAIT를 갖는지 어떻게 판단하나요?
  > 역할(서버/클라이언트)이 아니라 누가 먼저 FIN을 보냈는지, 즉 능동 종료 측이 TIME_WAIT를 갖는다. `ss -ant`로 TIME_WAIT 소켓의 로컬 주소와 원격 주소를 확인해 어느 쪽이 먼저 종료했는지 판단한다.
- CLOSE_WAIT 소켓의 누수를 실시간으로 확인하는 방법은 무엇인가요?
  > `ss -ant | grep CLOSE_WAIT`로 개수를 확인하고 시간 경과에 따른 증가 추세를 관찰한다. 개수가 줄지 않고 계속 늘어나면 소켓을 소유한 프로세스의 호출 스택(Java라면 jstack)을 분석해 close() 누락 코드 경로를 찾는다.

## 11. 30초 모범답변

> TIME_WAIT는 능동 종료 측이 마지막 ACK 재전송과 이전 연결의 지연 패킷 소멸을 위해 유지하는 상태입니다. CLOSE_WAIT는 상대 FIN을 받았지만 로컬 애플리케이션이 아직 소켓을 닫지 않은 상태입니다. TIME_WAIT는 짧은 연결이 많으면 정상적으로 늘 수 있지만, CLOSE_WAIT가 오래 누적되면 EOF나 예외 경로에서 `close()`가 빠진 코드부터 확인합니다.

## 12. 1~2분 확장답변

> TCP 종료에서 먼저 FIN을 보내고 마지막 ACK까지 보낸 능동 종료 측은 TIME_WAIT에 들어갑니다. 마지막 ACK가 유실되면 상대가 FIN을 재전송할 수 있고, 이전 연결의 지연 세그먼트가 새 연결에 섞이지 않도록 기다려야 하기 때문입니다. 반면 FIN을 받은 쪽은 ACK 후 CLOSE_WAIT가 되며 애플리케이션이 남은 처리를 마치고 소켓을 닫으면 FIN을 보냅니다. 따라서 CLOSE_WAIT 누적은 보통 애플리케이션 종료 처리 누락을 나타냅니다. 운영에서는 상태 수만 보지 않고 연결 생성률, 포트 고갈, 오류율과 소켓 소유 코드를 함께 확인합니다.

## 13. 핵심 요약

- TIME_WAIT는 능동 종료 측(먼저 FIN을 보낸 쪽)에 생긴다. 서버·클라이언트 역할이 아니라 종료 주체가 기준이다.
- TIME_WAIT 목적: ① 마지막 ACK 유실 시 재전송 대응 ② 이전 연결의 지연 세그먼트가 새 연결에 섞이지 않도록 2MSL 대기.
- CLOSE_WAIT는 상대 FIN 수신 후 애플리케이션이 `close()`를 호출할 때까지 유지된다. 타이머로 자동 해소되지 않는다.
- CLOSE_WAIT 장기 누적 → EOF 처리 누락, 예외 경로 close() 누락. try-with-resources로 방지.
- TIME_WAIT 과다 → 짧은 연결 반복 패턴. 연결 재사용(Keep-Alive, Pool)으로 감소.
- CLOSE_WAIT 과다 → 파일 디스크립터 고갈 → 새 연결 수락 불가. 절대 숫자보다 추세(계속 증가)를 본다.
- 게임 서버: 소켓 생명주기(TCP 연결)와 세션 생명주기(플레이어 상태) 분리. FIN 수신 즉시 세션 삭제 금지, 재접속 유예 시간 운영.
- `ss -ant | grep CLOSE_WAIT` 로 실시간 확인. 증가 추세면 close() 누락 코드 경로를 jstack 또는 heap dump로 추적.

## 한 줄 정리

> TIME_WAIT는 TCP가 안전하게 끝나기 위한 대기이고, CLOSE_WAIT는 애플리케이션이 끝내 주기를 기다리는 상태다.
