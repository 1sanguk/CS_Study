# 04. Port와 Socket


## 학습 목표

이 문서를 읽은 뒤 다음을 설명할 수 있어야 한다.

- 포트(Port)가 필요한 이유와 포트 번호의 범위를 설명할 수 있다.
- 소켓(Socket)을 운영체제가 제공하는 통신 끝점으로 설명할 수 있다.
- TCP 서버와 클라이언트의 소켓 생성부터 종료까지 흐름을 설명할 수 있다.
- 하나의 서버 포트로 여러 클라이언트를 처리할 수 있는 이유를 설명할 수 있다.
- 리스닝 소켓과 연결 소켓, TCP 소켓과 UDP 소켓의 차이를 구분할 수 있다.

---

## 1. 개요

포트(Port)는 한 호스트 안에서 네트워크 데이터를 받을 애플리케이션 또는 통신 끝점을 구분하는 16비트 번호다. 소켓(Socket)은 애플리케이션이 운영체제의 네트워크 기능을 사용하기 위한 통신 끝점이자 프로그래밍 인터페이스다.

IP(Internet Protocol) 주소가 네트워크에서 목적지 호스트를 찾는다면, 포트 번호는 그 호스트 안에서 데이터를 받을 프로세스를 구분한다. 실제로 운영체제는 프로토콜, 로컬·원격 주소와 포트, 소켓 상태 등을 함께 사용해 데이터를 알맞은 소켓으로 전달한다.

```text
Internet
   |
   | 목적지 IP: 203.0.113.10
   v
Server Host
   ├─ TCP 443  → Web/API Server
   ├─ TCP 7777 → Game Server
   └─ UDP 9000 → Realtime Game Server
```

같은 서버 IP를 여러 프로그램이 공유할 수 있는 이유는 전송 계층의 프로토콜과 포트가 통신 대상을 추가로 구분하기 때문이다.

## 2. 왜 필요한가

### 한 호스트에서 여러 네트워크 서비스를 실행한다

서버 한 대에서는 웹 API, 게임 서버, 관리 도구, 데이터베이스 프록시 등 여러 프로세스가 실행될 수 있다. IP 주소만으로는 도착한 데이터를 어느 프로세스에 넘길지 결정할 수 없다. 전송 계층은 목적지 포트 번호를 사용해 알맞은 소켓으로 데이터를 역다중화한다.

### 애플리케이션이 프로토콜 구현 세부사항을 직접 처리하지 않게 한다

애플리케이션이 네트워크 인터페이스, IP 헤더, TCP 재전송을 모두 직접 구현하는 것은 비효율적이다. 운영체제는 네트워크 프로토콜 스택을 제공하고, 애플리케이션은 소켓 API로 연결하거나 대기하고 데이터를 주고받는다.

### 여러 통신을 독립적인 상태로 관리한다

게임 서버 포트 7777에 플레이어 수천 명이 접속하더라도 각 TCP 연결은 독립적인 송수신 상태를 갖는다. 운영체제는 연결마다 버퍼, 순서 번호, 상태 정보를 관리한다. 애플리케이션은 연결별 소켓을 통해 플레이어 데이터를 구분할 수 있다.

## 3. 핵심 동작 원리

### 3.1 포트 번호의 구조

TCP와 UDP의 포트 번호는 각각 16비트이므로 범위는 0부터 65535까지다. 같은 숫자라도 TCP 7777과 UDP 7777은 서로 다른 전송 프로토콜의 포트 공간에 속한다.

| 범위 | 일반적 이름 | 용도 |
|---|---|---|
| 0~1023 | 잘 알려진 포트(Well-known Ports) | HTTP 80, HTTPS 443 등 널리 정해진 서비스 |
| 1024~49151 | 등록 포트(Registered Ports) | 등록된 애플리케이션·서비스 |
| 49152~65535 | 동적·사설 포트(Dynamic/Private Ports) | 클라이언트 임시 포트 등에 사용 |

이 분류는 포트의 일반적인 용도를 나타낸다. 운영체제의 실제 임시 포트 범위는 설정에 따라 다를 수 있다. 또한 특정 서비스가 관례적인 포트를 사용한다고 해서 그 포트에서 해당 서비스만 실행할 수 있는 것은 아니다.

서버는 일반적으로 알려진 고정 포트에서 연결을 기다린다. 클라이언트는 서버에 연결할 때 운영체제가 선택한 임시 포트(Ephemeral Port)를 출발지 포트로 사용한다.

```text
Client 192.0.2.10:53124  ---->  Server 203.0.113.10:7777
                     임시 포트                 서비스 포트
```

포트는 물리적인 단자가 아니다. 운영체제가 전송 계층 데이터를 소켓에 전달하기 위해 사용하는 논리적 번호다.

### 3.2 소켓이란 무엇인가

소켓은 프로세스가 네트워크 통신을 수행하기 위해 운영체제로부터 얻는 통신 끝점이다. 애플리케이션은 소켓에 대해 연결, 송신, 수신, 종료 같은 작업을 요청한다. 운영체제는 소켓과 연결된 프로토콜 상태와 송수신 버퍼를 관리한다.

프로세스는 소켓을 파일 디스크립터나 핸들 형태로 참조한다. C#에서는 `Socket` 객체나 이를 감싼 `TcpClient`, `TcpListener` 등을 사용할 수 있다. 프로그래밍 언어의 객체는 운영체제 소켓 자원을 가리키므로 사용 후 적절히 닫아야 한다.

소켓을 단순히 `IP:Port`라고만 정의하면 부족하다. TCP 연결 소켓은 로컬 주소뿐 아니라 상대 주소와 연결 상태도 갖는다. 반면 리스닝 소켓이나 아직 연결되지 않은 UDP 소켓은 상태와 식별 방식이 다르다.

### 3.3 TCP 연결을 구분하는 4-튜플

TCP 연결은 보통 다음 네 값의 조합인 **4-튜플(4-tuple)**로 구분한다.

```text
(출발지 IP, 출발지 Port, 목적지 IP, 목적지 Port)
```

전송 프로토콜까지 명시해야 하는 문맥에서는 TCP 또는 UDP를 포함한 5-튜플이라고 표현하기도 한다.

```text
Client A 192.0.2.10:51001 ─┐
                            ├──> Game Server 203.0.113.10:7777
Client B 192.0.2.20:52002 ─┘
```

두 연결은 서버 IP와 서버 포트가 같지만 클라이언트 IP 또는 클라이언트 포트가 다르다. 따라서 운영체제는 서로 다른 TCP 연결로 구분할 수 있다. 이것이 하나의 서버 포트로 여러 클라이언트를 동시에 처리할 수 있는 핵심 이유다.

같은 클라이언트가 동일한 서버에 여러 연결을 만들 수도 있다. 운영체제가 각 연결에 서로 다른 임시 포트를 할당하면 4-튜플이 달라진다.

### 3.4 TCP 서버 소켓의 생명주기

TCP 서버의 기본 흐름은 다음과 같다.

```text
Server
  socket()
     |
  bind(IP, Port)
     |
  listen(backlog)
     |
  accept()  <---------------- Client connect()
     |
     +---- 새 연결 소켓 반환
     |
  recv() / send()
     |
  close()
```

1. `socket()`으로 TCP 소켓을 생성한다.
2. `bind()`로 소켓에 로컬 IP와 포트를 연결한다.
3. `listen()`으로 연결 요청을 받을 리스닝 소켓으로 전환한다.
4. `accept()`로 완료된 연결을 꺼내 새 연결 소켓을 얻는다.
5. 새 연결 소켓으로 클라이언트와 데이터를 주고받는다.
6. 통신이 끝나면 연결 소켓을 닫는다.

`accept()`가 리스닝 소켓 자체를 연결 소켓으로 바꾸는 것은 아니다. 리스닝 소켓은 계속 같은 포트에서 새 연결을 받고, `accept()`는 특정 클라이언트와 통신할 새 소켓을 반환한다.

```text
TCP 7777 Listening Socket
       |
       +-- accept() --> Connected Socket A --> Client A
       +-- accept() --> Connected Socket B --> Client B
       +-- accept() --> Connected Socket C --> Client C
```

`listen(backlog)`의 backlog는 서버가 아직 `accept()`하지 못한 연결을 운영체제가 대기시킬 수 있는 큐와 관련된 값이다. 정확한 동작과 상한은 운영체제에 따라 다를 수 있다. backlog를 게임의 최대 동시 접속자 수로 해석해서는 안 된다.

### 3.5 TCP 클라이언트 소켓의 생명주기

클라이언트는 소켓을 생성하고 서버의 IP와 포트로 `connect()`를 호출한다. 로컬 IP와 임시 포트를 직접 지정하지 않았다면 운영체제가 적절한 값을 선택한다. TCP 연결 설정이 완료되면 송수신을 시작한다.

```text
Client                                  Server
 socket()                               socket()
    |                                      |
 connect(server:7777) ----------------> bind(:7777)
    |                                   listen()
    | <---------- 연결 성립 ----------- accept()
 send()/recv() <---------------------> send()/recv()
    |                                      |
 close() ------------------------------ close()
```

`connect()`가 성공했다는 것은 TCP 연결이 성립했다는 뜻이다. 게임 로그인이나 인증이 성공했다는 뜻은 아니다. 애플리케이션 계층의 로그인 요청과 검증은 그 이후에 수행된다.

### 3.6 바인드할 IP의 의미

서버가 `0.0.0.0:7777`에 바인드하면 일반적으로 호스트의 모든 IPv4 로컬 인터페이스에서 해당 포트의 연결을 받겠다는 뜻이다. `127.0.0.1:7777`에 바인드하면 로컬 루프백을 통한 접속만 받는다. 특정 인터페이스의 IP에 바인드하면 그 주소로 들어오는 연결만 대상으로 한다.

```text
0.0.0.0:7777       모든 IPv4 로컬 인터페이스
127.0.0.1:7777     같은 호스트 내부에서만 접근
10.0.1.20:7777     해당 로컬 주소로 들어온 연결
```

바인드 주소는 서버 노출 범위와 장애 분석에 중요하다. 프로세스가 실행 중이고 포트가 열려 보여도 루프백에만 바인드했다면 외부 클라이언트는 연결할 수 없다. IPv6의 모든 인터페이스 주소는 `::`로 표현하며, IPv4와 함께 처리되는 방식은 운영체제 설정에 따라 다를 수 있다.

### 3.7 송수신 버퍼와 부분 처리

소켓의 `send()`는 보낸 바이트가 즉시 상대 애플리케이션에 도착했다는 뜻이 아니다. 보통 데이터가 우선 운영체제의 송신 버퍼로 복사되거나 등록되고, 프로토콜 스택이 이후 전송한다.

TCP는 바이트 스트림이므로 다음을 고려해야 한다.

- 한 번의 송신 데이터가 여러 번의 수신으로 나뉠 수 있다.
- 여러 번의 송신 데이터가 한 번의 수신에서 함께 보일 수 있다.
- `send()`가 요청한 전체 바이트를 한 번에 처리하지 못할 수 있다.
- `recv()`가 0을 반환하는 것은 일반적으로 상대가 정상적으로 송신 방향을 종료했음을 뜻한다.

따라서 응용 계층은 길이 필드 또는 구분자 같은 패킷 프레이밍(Packet Framing)을 정의하고, 필요한 바이트가 모일 때까지 버퍼링해야 한다.

### 3.8 UDP 소켓의 동작

UDP 서버는 보통 소켓을 생성하고 로컬 IP와 포트에 바인드한 뒤 `recvfrom()`으로 데이터그램과 송신자 주소를 받는다. TCP처럼 연결마다 `accept()`가 새 소켓을 만들지 않는다.

```text
Client A ---- UDP Datagram ----┐
                               v
Client B ---- UDP Datagram --> Server UDP Socket :9000
                               ^
Client C ---- UDP Datagram ----┘
```

하나의 UDP 소켓이 여러 송신자의 데이터그램을 받을 수 있다. 각 데이터그램은 메시지 경계를 보존하지만 도착, 순서, 중복 방지를 보장하지 않는다.

UDP에서도 `connect()`를 사용할 수 있다. 이 경우 TCP 연결이 생기는 것은 아니다. 운영체제에 기본 상대 주소를 지정하고 다른 발신자의 데이터 수신을 제한하거나 관련 오류를 받기 쉽게 하는 효과가 있다. UDP의 비연결 특성과 API의 `connect()` 호출을 구분해야 한다.

## 4. 쉬운 예시

게임 서버가 `203.0.113.10:7777`에서 TCP 연결을 기다린다고 하자.

1. 서버는 `203.0.113.10:7777`에 소켓을 바인드하고 리스닝한다.
2. 플레이어 A는 `192.0.2.10:51001`에서 서버로 연결한다.
3. 플레이어 B는 `192.0.2.20:52002`에서 같은 서버로 연결한다.
4. 서버의 `accept()`는 플레이어마다 별도의 연결 소켓을 반환한다.
5. 서버는 연결 소켓을 세션(Session) 객체와 연결해 플레이어별 수신 버퍼와 인증 상태를 관리한다.

```text
Listening Socket :7777
       |
       ├─ Socket A: 203.0.113.10:7777 ↔ 192.0.2.10:51001
       |     └─ Session A: accountId=1001
       |
       └─ Socket B: 203.0.113.10:7777 ↔ 192.0.2.20:52002
             └─ Session B: accountId=1002
```

소켓은 네트워크 연결 상태를 나타내고, 게임 세션은 인증된 사용자와 게임 상태 같은 응용 정보를 담는다. 둘은 관련 있지만 같은 개념이 아니다.

## 5. 비슷한 개념과 비교

### 포트와 소켓

| 구분 | 포트 | 소켓 |
|---|---|---|
| 의미 | 프로세스·통신 끝점을 구분하는 논리적 번호 | 운영체제가 제공하는 통신 끝점 |
| 형태 | 0~65535의 16비트 번호 | 파일 디스크립터, 핸들, 객체로 참조 |
| 역할 | 수신 데이터를 알맞은 애플리케이션으로 분배 | 연결 설정과 실제 송수신 수행 |
| 상태 | 번호 자체는 연결 상태를 갖지 않음 | 프로토콜, 주소, 버퍼, 연결 상태 등을 가짐 |

포트는 소켓을 구성하는 주소 정보 중 하나다. 소켓과 포트를 같은 것으로 설명하면 여러 연결 소켓이 하나의 서버 포트를 공유하는 구조를 설명하기 어렵다.

### 리스닝 소켓과 연결 소켓

| 구분 | 리스닝 소켓 | 연결 소켓 |
|---|---|---|
| 목적 | 새 TCP 연결 요청 수신 | 특정 상대와 데이터 송수신 |
| 생성 흐름 | `bind()` 후 `listen()` | `accept()` 결과 또는 성공한 `connect()` |
| 상대 | 특정 상대에 연결되지 않음 | 특정 원격 IP·포트와 연결 |
| 개수 | 보통 서비스 주소당 하나 | 클라이언트 연결마다 생성 |

### 소켓과 세션

소켓은 운영체제 수준의 통신 자원이다. 세션은 애플리케이션에서 정의하는 논리적인 대화나 사용자 상태다. TCP 연결이 끊겨도 재접속 토큰을 사용해 기존 게임 세션을 복구할 수 있다. 반대로 하나의 TCP 연결 안에서 인증 전·후의 세션 상태가 달라질 수 있다.

## 6. 장점과 단점

### 장점

- 포트를 이용해 하나의 호스트에서 여러 네트워크 서비스를 동시에 운영할 수 있다.
- 소켓 API가 운영체제와 프로토콜 세부사항을 감싸 다양한 언어에서 일관된 통신 모델을 제공한다.
- TCP 연결마다 독립적인 소켓 상태와 버퍼를 관리할 수 있다.
- 서버는 하나의 서비스 포트로 여러 클라이언트 연결을 구분할 수 있다.
- TCP와 UDP 등 요구사항에 맞는 소켓 유형을 선택할 수 있다.

### 단점과 고려 사항

- 소켓은 파일 디스크립터, 버퍼, 커널 메모리 같은 유한한 자원을 사용한다.
- 연결 종료와 예외 상황에서 소켓을 정리하지 않으면 자원 누수가 발생한다.
- 연결마다 스레드를 하나씩 만들면 대규모 접속에서 메모리와 문맥 교환 비용이 커질 수 있다.
- TCP 스트림의 부분 송수신과 메시지 경계를 애플리케이션이 처리해야 한다.
- 방화벽, NAT, 로드 밸런서가 IP와 포트 기반 연결에 영향을 줄 수 있다.

## 7. 게임 서버·백엔드 실무 예시

### 다중 접속 게임 서버

게임 서버는 리스닝 소켓 하나로 연결을 받고, 연결마다 별도 세션 객체를 만든다. 세션에는 소켓, 수신 버퍼, 계정 ID, 현재 상태를 연결한다. 비동기 I/O나 이벤트 기반 모델을 사용하면 소수의 스레드로 많은 연결을 처리할 수 있다.

```text
I/O Event Loop
   ├─ Socket A readable → Session A 패킷 파싱 → Work Queue
   ├─ Socket B writable → Session B 송신 버퍼 처리
   └─ Listening Socket  → 새 연결 accept
```

소켓이 읽을 수 있다는 이벤트와 실제 게임 로직 실행을 분리하면 네트워크 I/O 스레드가 긴 전투 계산이나 DB 작업에 막히는 것을 줄일 수 있다.

### 서비스별 포트 분리

로그인 서버, 게임 서버, 관리 서버가 서로 다른 포트를 사용할 수 있다. 하지만 포트 번호만으로 보안을 제공할 수는 없다. 관리 포트는 외부에 공개하지 않고 사설 네트워크, 방화벽, 인증을 함께 적용해야 한다.

로드 밸런서가 앞에 있다면 클라이언트는 로드 밸런서의 IP와 포트로 연결한다. 백엔드 서버가 보는 원격 IP는 구성에 따라 로드 밸런서 주소일 수 있다. 원래 클라이언트 주소가 필요하다면 신뢰할 수 있는 전달 방식과 위조 방지 정책을 사용해야 한다.

### 포트 고갈과 연결 관리

클라이언트나 프록시가 동일한 목적지로 매우 많은 연결을 만들면 사용 가능한 임시 포트와 4-튜플 조합이 제한될 수 있다. 연결을 불필요하게 매 요청마다 새로 만들지 않고 풀링하거나 재사용하는 이유 중 하나다.

게임 서버에서는 재접속 시 이전 소켓과 새 소켓의 소유권을 명확히 해야 한다. 오래된 연결에서 늦게 도착한 이벤트가 새 세션 상태를 덮어쓰지 않도록 연결 세대 번호나 세션 토큰을 검증할 수 있다.

### 연결 실패를 분석하는 순서

1. 서버 프로세스가 실행 중인가?
2. 의도한 IP와 포트에 실제로 바인드하고 리스닝 중인가?
3. 루프백 주소에만 바인드한 것은 아닌가?
4. 클라이언트가 올바른 IP, 포트, TCP/UDP 프로토콜을 사용하는가?
5. 방화벽, 보안 그룹, NAT, 로드 밸런서가 해당 트래픽을 허용하는가?
6. TCP 연결 후 애플리케이션 핸드셰이크와 인증이 성공하는가?

“포트가 열렸다”는 표현은 문맥을 확인해야 한다. 프로세스가 리스닝 중인지, 방화벽이 통과시키는지, 외부에서 실제 연결 가능한지는 서로 다른 검사다.

## 8. 자주 하는 오해

### “포트 하나에는 클라이언트 하나만 연결할 수 있다”

TCP 연결은 서버 포트 하나가 아니라 출발지와 목적지의 IP·포트 조합으로 구분한다. 클라이언트의 주소나 임시 포트가 다르면 같은 서버 포트에 여러 연결을 만들 수 있다.

### “accept하면 리스닝 소켓이 사라진다”

`accept()`는 특정 클라이언트용 연결 소켓을 새로 반환한다. 리스닝 소켓은 계속 새 연결 요청을 받는다.

### “TCP 연결 성공은 로그인 성공이다”

TCP 연결 성공은 전송 계층의 통신 경로가 만들어졌다는 뜻이다. 계정 인증, 프로토콜 버전 확인, 캐릭터 선택은 응용 계층에서 별도로 처리한다.

### “한 번 send하면 상대도 한 번 recv한다”

TCP는 메시지가 아닌 바이트 스트림이다. 송신과 수신 호출의 경계가 보존되지 않으므로 응용 계층 프레이밍이 필요하다.

### “UDP는 connect를 호출할 수 없다”

UDP 소켓에도 `connect()` API를 사용할 수 있다. 다만 TCP 연결 설정이 일어나는 것은 아니며 기본 상대 주소를 운영체제에 지정하는 의미에 가깝다.

### “127.0.0.1에서 접속되면 외부에서도 접속된다”

루프백 접속 성공은 같은 호스트 내부 경로가 동작한다는 뜻이다. 서버가 루프백에만 바인드했거나 외부 방화벽이 차단하면 다른 호스트에서는 접속할 수 없다.

### “포트 번호가 서비스의 보안을 결정한다”

잘 알려지지 않은 포트로 바꾸는 것은 자동 스캔의 잡음을 줄일 수 있지만 접근 통제를 대신하지 못한다. 인증과 방화벽 정책이 필요하다.

## 9. 면접 질문

### Q1. 포트와 소켓의 차이를 설명해 주세요.

포트는 호스트 안에서 네트워크 데이터를 받을 애플리케이션을 구분하는 16비트 논리 번호다. 소켓은 프로세스가 운영체제 네트워크 기능을 사용하기 위한 통신 끝점이다. 소켓은 프로토콜, 로컬·원격 주소, 버퍼, 연결 상태를 포함할 수 있으며 포트는 그 주소 정보의 일부다.

### Q2. 하나의 서버 포트에 여러 클라이언트가 연결할 수 있는 이유는 무엇인가요?

TCP 연결은 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트의 4-튜플로 구분한다. 서버 IP와 포트가 같아도 클라이언트 IP나 임시 포트가 다르면 별개의 연결이다. 서버는 리스닝 소켓으로 연결을 받고 클라이언트마다 새 연결 소켓을 얻는다.

### Q3. TCP 서버 소켓의 동작 순서를 설명해 주세요.

서버는 소켓을 생성하고 `bind()`로 로컬 IP와 포트를 지정한다. `listen()`으로 연결 요청을 대기하고 `accept()`로 각 클라이언트의 연결 소켓을 얻는다. 이후 연결 소켓으로 송수신하고 통신이 끝나면 닫는다.

### Q4. 리스닝 소켓과 연결 소켓은 어떻게 다른가요?

리스닝 소켓은 특정 서비스 주소에서 새 TCP 연결 요청을 받는다. 연결 소켓은 `accept()`가 반환하며 특정 클라이언트와 실제 데이터를 주고받는다. 리스닝 소켓 하나에서 여러 연결 소켓이 만들어질 수 있다.

### Q5. TCP 소켓과 UDP 소켓의 차이는 무엇인가요?

TCP 서버는 연결을 리스닝하고 `accept()`로 클라이언트별 연결 소켓을 만든다. TCP는 순서 있는 바이트 스트림을 제공한다. UDP는 보통 하나의 바인드된 소켓으로 여러 발신자의 데이터그램을 받으며 메시지 경계는 보존하지만 도착과 순서는 보장하지 않는다.

### Q6. `0.0.0.0`과 `127.0.0.1`에 바인드하는 차이는 무엇인가요?

`0.0.0.0`은 일반적으로 호스트의 모든 IPv4 로컬 인터페이스에서 연결을 받겠다는 뜻이다. `127.0.0.1`은 루프백 주소이므로 같은 호스트 내부에서만 접근할 수 있다. 외부 공개 범위를 고려해 적절한 주소를 선택해야 한다.

TCP 서버는 `socket`, `bind`, `listen` 순서로 준비하고 `accept`를 호출해 클라이언트별 연결 소켓을 얻습니다. 리스닝 소켓은 계속 새 연결을 받고 실제 데이터는 연결 소켓으로 주고받습니다. TCP 연결은 출발지 IP와 포트, 목적지 IP와 포트의 4-튜플로 구분되므로 서버 포트 7777 하나에도 여러 클라이언트가 연결할 수 있습니다. TCP는 바이트 스트림이라 송수신 호출 경계가 보존되지 않으므로 게임 프로토콜에서 길이 필드 같은 프레이밍을 정의해야 합니다. 소켓은 네트워크 자원이고 세션은 인증 사용자 같은 응용 상태이므로 둘의 생명주기도 분리해서 관리해야 합니다.

## 13. 핵심 요약

- 포트는 호스트 안의 애플리케이션·통신 끝점을 구분하는 16비트 논리 번호다.
- 소켓은 애플리케이션이 운영체제 네트워크 기능을 사용하는 통신 끝점이다.
- TCP 연결은 출발지와 목적지의 IP·포트 조합인 4-튜플로 구분한다.
- 서버는 `socket → bind → listen → accept` 순서로 연결을 받는다.
- 리스닝 소켓은 새 연결을 받고, 연결 소켓은 특정 클라이언트와 데이터를 주고받는다.
- TCP는 바이트 스트림이므로 응용 계층에서 메시지 경계를 정의해야 한다.
- UDP 서버는 일반적으로 하나의 소켓으로 여러 송신자의 데이터그램을 받는다.
- 소켓과 게임 세션은 서로 다른 계층의 상태이므로 생명주기를 분리해 관리해야 한다.
