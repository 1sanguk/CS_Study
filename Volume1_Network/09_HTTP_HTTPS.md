# 09. HTTP와 HTTPS

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- HTTP 요청·응답 구조와 핵심 특성을 설명할 수 있다.
- HTTPS가 기밀성, 무결성, 서버 인증을 제공하는 방식을 설명할 수 있다.
- 상태 코드, 멱등성, 연결 재사용을 API 설계에 적용할 수 있다.

## 1. 개요

HTTP(Hypertext Transfer Protocol)는 클라이언트와 서버가 요청과 응답을 교환하는 응용 계층 프로토콜이다. HTTPS는 HTTP 통신을 TLS로 보호해 암호화, 무결성 검증, 인증을 제공한다.

```text
HTTP:  Application Data → TCP
HTTPS: Application Data → TLS → TCP
HTTP/3: Application Data → QUIC(UDP 기반)
```

## 2. 왜 필요한가

다양한 클라이언트와 서버가 메서드, URI, 헤더, 본문, 상태 코드라는 공통 규칙으로 통신해야 한다. 공개 네트워크에서는 내용 도청, 변조, 가짜 서버 접속 위험이 있으므로 TLS 보호가 필요하다.

## 3. 핵심 동작 원리

### 요청과 응답

```text
POST /v1/login HTTP/1.1
Host: api.game.example
Content-Type: application/json
Content-Length: ...

{"token":"..."}

HTTP/1.1 200 OK
Content-Type: application/json

{"sessionId":"abc"}
```

요청은 메서드, 대상 경로, 헤더, 선택적 본문으로 구성된다. 응답은 상태 코드, 헤더, 선택적 본문으로 구성된다.

대표 메서드의 의미는 다음과 같다.

- GET: 자원 조회
- POST: 처리 요청 또는 하위 자원 생성
- PUT: 지정 자원의 전체 생성·교체
- PATCH: 자원의 부분 변경
- DELETE: 자원 삭제

안전한 메서드는 서버 상태 변경을 의도하지 않는다. 멱등한 메서드는 같은 요청을 여러 번 수행해도 의도된 최종 상태가 한 번 수행한 것과 같다. GET, PUT, DELETE는 명세 의미상 멱등하지만 POST는 일반적으로 그렇지 않다. 실제 구현이 의미를 지켜야 한다.

### 상태 코드

| 범위 | 의미 | 예시 |
|---|---|---|
| 2xx | 성공 | 200 OK, 201 Created, 204 No Content |
| 3xx | 리다이렉션·캐시 | 301, 304 Not Modified |
| 4xx | 클라이언트 요청 문제 | 400, 401, 403, 404, 409, 429 |
| 5xx | 서버 처리 문제 | 500, 502, 503, 504 |

401은 인증 정보가 없거나 유효하지 않은 상황, 403은 인증되었더라도 권한이 없는 상황에 사용한다. 502는 게이트웨이가 잘못된 업스트림 응답을 받은 경우, 504는 업스트림 응답 시간 초과와 관련된다.

### 무상태성과 상태 관리

HTTP는 각 요청이 필요한 정보를 포함하는 무상태(Stateless) 프로토콜로 설계된다. 이는 서버가 어떤 상태도 저장할 수 없다는 뜻이 아니다. 로그인 세션을 서버나 Redis에 저장할 수 있지만, 요청을 처리할 때 쿠키나 토큰으로 어떤 세션인지 식별해야 한다.

### 연결과 버전

HTTP/1.1은 지속 연결을 통해 하나의 TCP 연결을 재사용한다. 여러 요청을 새 연결로 반복하면 TCP와 TLS 핸드셰이크 비용이 커진다. HTTP/2는 하나의 연결에서 여러 스트림을 다중화하고 헤더 압축을 제공한다. 그러나 TCP 손실은 연결의 여러 스트림에 영향을 줄 수 있다. HTTP/3는 UDP 기반 QUIC을 사용해 스트림 단위 손실 영향을 줄이고 연결 설정을 개선한다.

HTTP/1.1에서 요청을 순차 처리하면 앞 요청이 늦을 때 뒤 요청도 기다릴 수 있다. 여러 연결로 완화할 수 있지만 연결 수가 늘어난다. HTTP/2는 스트림을 다중화해 응용 계층의 순차 대기를 줄이지만 하나의 TCP 연결에서 패킷이 손실되면 TCP 순서 복구가 여러 스트림 전달에 영향을 줄 수 있다. HTTP/3의 QUIC은 스트림별 순서 공간을 사용해 한 스트림 손실이 다른 스트림의 전달을 같은 방식으로 막지 않게 한다.

### 캐시와 조건부 요청

HTTP 캐시는 응답을 재사용해 서버 부하와 지연을 줄인다. `Cache-Control`은 저장 가능 여부와 유효 시간을 지시할 수 있다. `ETag`나 `Last-Modified`를 받은 클라이언트는 다음 요청에 `If-None-Match`나 `If-Modified-Since`를 보내 변경 여부를 확인한다. 자원이 바뀌지 않았다면 서버는 본문 없이 `304 Not Modified`로 응답할 수 있다.

개인정보나 인증별 응답을 공유 캐시에 잘못 저장하면 다른 사용자에게 노출될 수 있다. 캐시 Key에 영향을 주는 헤더와 `Vary`, private·no-store 정책을 요구사항에 맞게 설정한다. 게임 공지와 정적 패치 정보는 캐시하기 좋지만 인벤토리와 구매 결과는 훨씬 보수적으로 다룬다.

### HTTPS와 TLS

TLS 연결 설정에서 서버는 인증서를 제시한다. 클라이언트는 인증서의 서명 체인, 도메인 일치, 유효기간 등을 검증한다. 키 교환으로 양쪽이 세션 키를 만들고, 이후 대칭키 암호로 데이터를 효율적으로 암호화하며 인증 태그로 변조를 검출한다.

```text
Client                       HTTPS Server
  | ---- 지원 버전·암호군 ----> |
  | <--- 인증서·키 교환 정보 --- |
  | ---- 키 교환·검증 완료 ----> |
  | === 암호화된 HTTP 요청 ===> |
```

HTTPS는 전송 구간을 보호한다. 서버 내부 로그, 데이터베이스 저장, 클라이언트 단말이 안전하다는 뜻은 아니다. 인증서 검증을 끄면 암호화되어도 중간자 공격을 막기 어렵다.

클라이언트는 신뢰하는 인증 기관으로 이어지는 인증서 체인뿐 아니라 접속한 호스트 이름과 인증서의 이름이 일치하는지, 인증서가 유효 기간 안에 있는지 확인한다. 검증 실패를 개발 편의를 위해 무시하는 코드는 운영 환경에 남지 않게 해야 한다.

로드 밸런서나 리버스 프록시에서 TLS를 종료할 수도 있다. 이 경우 클라이언트와 프록시 구간은 암호화되지만 프록시와 백엔드 구간을 평문으로 둘지 다시 TLS로 보호할지는 별도 결정이다. 내부망이라는 이유만으로 자동 안전하다고 보지 않고 위협 모델과 인증 요구에 따라 정한다.

## 4. 쉬운 예시

아이템 구매 API가 응답 전에 연결이 끊기면 클라이언트는 서버 처리 여부를 모를 수 있다. 같은 POST를 그대로 재시도하면 중복 지급 가능성이 있다. 클라이언트가 고유 요청 ID를 보내고 서버가 처리 결과를 저장해 같은 ID의 요청에 동일 결과를 반환하도록 멱등성을 설계한다.

## 5. 비슷한 개념과 비교

| 구분 | HTTP | HTTPS |
|---|---|---|
| 애플리케이션 의미 | 동일 | 동일 |
| 전송 보호 | 기본 제공 없음 | TLS 암호화·무결성·인증 |
| 기본 포트 | 80 | 443 |
| 인증서 | 불필요 | 서버 인증에 사용 |

쿠키는 클라이언트가 요청에 함께 보내는 작은 데이터다. 세션은 서버가 관리하는 논리적 상태를 뜻할 수 있다. 토큰은 인증 정보나 참조 값을 자체 형식으로 전달한다. 세 개념은 서로 대체되는 동일 개념이 아니다.

## 6. 장점과 단점

HTTP는 표준화된 의미, 풍부한 도구, 프록시와 캐시 지원이 강점이다. 무상태 요청은 서버 수평 확장에 유리하다. 반면 반복 헤더와 요청·응답 모델은 고빈도 실시간 양방향 통신에 비효율적일 수 있다.

HTTPS는 공개망에서 필수적인 보호를 제공한다. TLS 핸드셰이크와 암복호화 비용이 있지만 연결 재사용과 현대 하드웨어로 완화되며, 보안을 위해 감수해야 할 기본 비용이다.

## 7. 게임 서버·백엔드 실무 예시

로그인, 상점, 랭킹 조회는 HTTPS API에 적합하다. 장시간 양방향 게임 플레이는 TCP/UDP 전용 프로토콜이나 WebSocket을 고려할 수 있다.

API 운영에서는 다음을 함께 설계한다.

- 요청 ID로 로그를 추적한다.
- 타임아웃은 연결, 업스트림, 전체 요청 예산으로 나눈다.
- 429와 재시도 지침으로 과부하를 제어한다.
- 재시도에는 지수 백오프와 무작위 지연을 적용한다.
- 결제·지급 요청에는 멱등성 키를 사용한다.
- 토큰과 개인정보를 URL이나 로그에 노출하지 않는다.

### 타임아웃과 재시도의 의미

HTTP 클라이언트가 시간 초과를 받았다는 사실만으로 서버가 요청을 처리하지 않았다고 결론 내릴 수 없다. 서버는 아이템 지급을 커밋했지만 응답이 돌아오는 중 끊겼을 수 있다. 클라이언트가 같은 요청을 다시 보내면 중복 지급 위험이 있다.

변경 요청에는 클라이언트가 생성한 멱등성 키를 포함할 수 있다. 서버는 키와 처리 결과를 원자적으로 기록하고 같은 키의 재요청에는 기존 결과를 반환한다. 조회 요청도 무제한 즉시 재시도하면 장애 서버에 부하를 더하므로 재시도 가능 오류를 구분하고 지수 백오프, 무작위 지연과 전체 시간 예산을 사용한다.

프록시를 거치면 `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`이 서로 다른 장애 단서를 준다. 다만 제품별 응답 정책이 다를 수 있으므로 요청 ID로 프록시와 백엔드 로그를 연결해 실제 처리 지점을 확인한다.

## 8. 자주 하는 오해

- “HTTPS면 서버가 안전하다”: 전송 구간 보호이며 서버 취약점은 별도다.
- “HTTP는 상태를 저장할 수 없다”: 요청 자체가 무상태이며 서버 세션은 가능하다.
- “POST는 재시도하면 안 된다”: 멱등성 키 등 안전장치가 있으면 재시도 가능하다.
- “401은 권한 없음이다”: 인증 실패는 401, 권한 부족은 주로 403이다.
- “TLS는 비대칭키로 모든 본문을 암호화한다”: 키 교환 후 효율적인 대칭키를 사용한다.

## 9. 면접 질문

### Q1. HTTP 요청과 응답 구조를 설명해 주세요.

요청은 메서드, URI, 헤더와 선택적 본문으로 구성된다. 응답은 상태 코드, 헤더와 선택적 본문으로 구성된다. 헤더에는 콘텐츠 형식, 인증, 캐시 정책 같은 메타데이터가 담긴다.

### Q2. HTTP와 HTTPS의 차이는 무엇인가요?

HTTPS는 HTTP를 TLS로 보호한다. 인증서로 서버 신원을 검증하고 키를 합의한 뒤 암호화와 무결성 검증을 적용해 도청과 변조, 중간자 공격을 방어한다.

### Q3. 무상태란 무엇인가요?

각 요청이 처리에 필요한 정보를 포함해 이전 요청의 연결 상태에 의존하지 않는 성질이다. 서버 세션을 금지하는 뜻은 아니며 요청이 세션 식별자를 전달할 수 있다.

### Q4. 멱등성이 왜 중요한가요?

타임아웃 후 요청을 재시도할 때 중복 변경을 막기 위해 중요하다. 결제나 아이템 지급은 고유 요청 ID와 처리 결과 저장으로 멱등하게 만들 수 있다.

### Q5. HTTP/1.1, HTTP/2, HTTP/3의 핵심 차이는 무엇인가요?

HTTP/1.1은 지속 연결을 사용하고, HTTP/2는 하나의 TCP 연결에서 스트림을 다중화한다. HTTP/3는 QUIC 위에서 동작해 스트림 간 손실 영향을 줄이고 연결 설정을 개선한다.

### Q6. HTTP 캐시의 조건부 요청은 어떻게 동작하나요?

클라이언트가 이전 응답의 ETag나 수정 시간을 조건 헤더로 보낸다. 자원이 변경되지 않았다면 서버는 본문 없이 304를 반환해 전송량을 줄일 수 있다.

## 11. 30초 모범답변

> HTTP는 메서드와 URI, 헤더, 본문으로 요청하고 상태 코드와 헤더, 본문으로 응답하는 응용 계층 프로토콜입니다. HTTPS는 여기에 TLS를 적용해 인증서 기반 서버 인증, 암호화, 무결성 검증을 제공합니다. 게임 백엔드에서는 로그인과 상점 API에 HTTPS를 사용하고, 아이템 지급처럼 재시도 가능한 요청은 멱등성 키로 중복 처리를 막습니다.

## 12. 1~2분 확장답변

> HTTP는 클라이언트가 자원에 대한 요청을 보내고 서버가 응답하는 무상태 응용 프로토콜입니다. 메서드는 작업 의도를, 상태 코드는 처리 결과를 표현합니다. 무상태는 서버가 세션을 저장할 수 없다는 뜻이 아니라 각 요청이 세션을 식별할 정보를 포함해야 한다는 뜻입니다. HTTPS는 TLS 핸드셰이크에서 인증서를 검증하고 키를 합의한 뒤 대칭키로 HTTP 데이터를 암호화하고 무결성을 확인합니다. HTTP/1.1은 연결 재사용을, HTTP/2는 스트림 다중화를, HTTP/3는 QUIC 기반 전송을 제공합니다. 실무에서는 타임아웃과 재시도뿐 아니라 결제나 아이템 지급의 멱등성을 응용 계층에서 보장해야 합니다.

## 13. 핵심 요약

- HTTP는 표준 요청·응답 의미를 제공하는 응용 계층 프로토콜이다.
- HTTPS는 TLS로 기밀성, 무결성, 서버 인증을 제공한다.
- 무상태는 서버가 상태를 절대 저장하지 않는다는 뜻이 아니다.
- 상태 코드와 메서드 의미를 일관되게 사용해야 한다.
- 재시도되는 변경 요청에는 멱등성 설계가 필요하다.

## 한 줄 정리

> HTTP가 요청과 응답의 공통 언어라면, HTTPS는 그 대화를 TLS로 안전하게 보호한 방식이다.
