# 11. DNS, ARP, ICMP


## 학습 목표

- DNS, ARP, ICMP의 역할과 동작 범위를 구분할 수 있다.
- 도메인 조회부터 로컬 프레임 전송까지의 흐름을 설명할 수 있다.
- 세 프로토콜을 활용한 계층별 장애 분석 순서를 설명할 수 있다.
- DNS TTL 조정과 드레이닝을 게임 서버 이전에 적용할 수 있다.

## 1. 개요

DNS(Domain Name System)는 도메인 이름을 IP 주소 등 자원 정보로 변환한다. ARP(Address Resolution Protocol)는 IPv4 로컬 네트워크에서 다음 대상 IP에 대응하는 MAC 주소를 알아낸다. ICMP(Internet Control Message Protocol)는 IP 전달 중 오류와 진단 정보를 운반한다.

세 프로토콜은 모두 통신을 돕지만 대상 계층과 범위가 다르다.

## 2. 왜 필요한가

사람과 서비스는 변경 가능한 IP보다 도메인 이름을 사용하기 쉽다. 실제 프레임을 보내려면 현재 링크의 MAC 주소가 필요하다. IP 패킷이 목적지에 갈 수 없거나 TTL이 만료되면 원인을 알릴 제어 메시지도 필요하다. DNS, ARP, ICMP가 각각 이 문제를 해결한다.

## 3. 핵심 동작 원리

### DNS 이름 해석

```text
Application
   | game.example 조회
   v
Stub Resolver → Recursive Resolver
                    |
                    +→ Root → TLD → Authoritative DNS
                    |
                응답 캐시 후 IP 반환
```

애플리케이션은 운영체제 리졸버에 이름 해석을 요청한다. 캐시에 없으면 재귀 리졸버가 권한 서버 계층을 따라 조회하거나 자신의 캐시를 이용한다. 응답에는 TTL이 있어 일정 시간 캐시할 수 있다.

대표 레코드는 다음과 같다.

- A: 이름을 IPv4 주소에 연결
- AAAA: 이름을 IPv6 주소에 연결
- CNAME: 다른 정규 이름을 가리키는 별칭
- MX: 메일 서버 지정
- TXT: 텍스트 기반 검증·정책 정보

DNS는 일반적으로 UDP 53을 사용하지만 큰 응답, 영역 전송, 일부 상황에서는 TCP도 사용한다. DNS over HTTPS나 TLS처럼 암호화된 전달 방식도 있다.

TTL을 낮추면 변경 반영이 빨라질 수 있지만 조회량이 증가한다. TTL이 끝나도 모든 클라이언트가 즉시 같은 순간에 바뀌는 것은 아니며 캐시와 연결 재사용을 고려해야 한다.

#### 재귀 조회와 반복 조회

클라이언트의 스텁 리졸버는 보통 재귀 리졸버에게 최종 답을 요구한다. 재귀 리졸버는 캐시에 답이 없으면 루트와 TLD 서버가 알려 주는 다음 권한 서버를 따라 반복적으로 조회한다. 루트 서버가 서비스 IP를 직접 알려 주는 것이 아니라 이름 공간의 위임 경로를 제공하는 구조다.

존재하지 않는 이름이라는 응답도 부정 캐시(Negative Cache)에 저장될 수 있다. 따라서 잘못 만든 레코드를 바로 고쳐도 일부 리졸버에서는 일정 시간 `NXDOMAIN`이 계속 보일 수 있다. 장애 분석에서는 정상 응답 TTL뿐 아니라 부정 응답과 어느 리졸버를 조회했는지도 확인한다.

DNS 응답이 전통적인 UDP 크기 범위를 넘으면 잘리거나 TCP로 재시도할 수 있다. EDNS(Extension Mechanisms for DNS)는 더 큰 UDP 응답 등 확장 정보를 협상한다. 경로에서 큰 UDP 조각이 차단되면 작은 질의는 되는데 특정 도메인만 실패하는 현상도 생길 수 있다.

### ARP 주소 해석

호스트가 같은 IPv4 서브넷의 목적지나 기본 게이트웨이로 Ethernet 프레임을 보내려면 MAC 주소가 필요하다.

```text
Host A: "192.168.1.1을 가진 장비는 누구인가?"
  | -------- ARP Request (broadcast) --------> LAN
  | <------- ARP Reply: MAC=AA:BB:... -------- Gateway
  |
ARP Cache 저장 후 해당 MAC으로 프레임 전송
```

목적지가 다른 네트워크라면 최종 서버의 MAC이 아니라 기본 게이트웨이의 MAC을 알아낸다. ARP 결과는 캐시에 보관되며 만료되거나 갱신된다. IPv6는 ARP 대신 ICMPv6 기반 Neighbor Discovery를 사용한다.

### ICMP 오류와 진단

ICMP는 IP와 함께 동작하며 포트 기반 애플리케이션 데이터 프로토콜이 아니다. 대표 메시지에는 Echo Request/Reply, Destination Unreachable, Time Exceeded가 있다.

`ping`은 Echo 요청과 응답으로 대상까지의 왕복과 기본 IP 연결성을 확인한다. `traceroute` 계열 도구는 TTL을 점차 늘려 중간 라우터의 Time Exceeded 응답을 관찰한다. 운영체제와 도구에 따라 UDP, ICMP, TCP 탐사 패킷을 사용할 수 있다.

ICMP가 차단되거나 응답 우선순위가 낮을 수 있다. ping 실패만으로 서버 중단을, 성공만으로 게임 포트와 애플리케이션 정상을 단정할 수 없다.

ICMP는 경로 MTU 탐색에도 중요하다. IPv4에서 라우터가 단편화할 수 없는 큰 패킷을 받거나 IPv6에서 패킷이 다음 링크 MTU보다 크면 송신자에게 관련 ICMP 오류를 보낸다. 이 메시지가 차단되면 송신자는 크기를 줄여야 한다는 사실을 모르고, 연결은 되었지만 큰 응답만 멈추는 PMTU 블랙홀 증상이 나타날 수 있다. 보안을 이유로 ICMP 전체를 막기보다 필요한 유형과 속도를 통제하는 편이 적절하다.

## 4. 쉬운 예시

클라이언트가 `login.game.example`에 접속한다.

1. DNS로 로드 밸런서 IP를 얻는다.
2. 목적지가 외부 네트워크이므로 ARP로 기본 게이트웨이 MAC을 얻는다.
3. 게이트웨이 프레임 안에 최종 목적지 IP 패킷을 넣어 보낸다.
4. 경로 문제 발생 시 라우터가 ICMP 오류를 보낼 수 있다.
5. IP 도달 후 TCP 포트 연결과 HTTPS 로그인을 수행한다.

```java
// Java에서 DNS 조회: 이름 → IP 목록
InetAddress[] addresses = InetAddress.getAllByName("login.game.example");
for (InetAddress addr : addresses) {
    System.out.println(addr.getHostAddress()); // 여러 A 레코드 반환 가능
}
// 주의: JVM은 기본적으로 결과를 캐시한다 (networkaddress.cache.ttl JVM 속성으로 제어)
// DNS TTL이 60초여도 JVM 캐시가 30분이면 변경이 늦게 반영됨
```

```bash
# DNS 조회 및 장애 분석 명령어
dig login.game.example A         # DNS A 레코드 조회 + TTL 확인
dig @8.8.8.8 login.game.example  # 특정 리졸버로 조회 (캐시 우회 비교)
nslookup login.game.example      # Windows/공통 DNS 조회

# ARP 캐시 확인
ip neigh show                    # Linux: ARP 캐시 목록
arp -n                           # MAC 주소 테이블 확인

# ICMP 진단
ping -c 4 login.game.example     # IP 연결성 확인
traceroute login.game.example    # 경로 홉별 응답 시간
```

```text
접속 장애 계층별 확인 순서:
1. dig → DNS가 올바른 IP를 반환하는가?
2. ip neigh → 게이트웨이 ARP 해석이 되는가?
3. ping → ICMP 경로가 살아있는가?
4. telnet host 443 → TCP 포트가 열려있는가?
5. curl -v https://login.game.example → 애플리케이션이 응답하는가?
```

## 5. 비슷한 개념과 비교

| 구분 | DNS | ARP | ICMP |
|---|---|---|---|
| 질문 | 이름의 주소는? | 로컬 IP의 MAC은? | IP 전달 상태·오류는? |
| 범위 | 분산 이름 시스템 | 로컬 링크 | IP 네트워크 |
| 캐시 | DNS TTL 캐시 | ARP 캐시 | 일반적 주소 캐시 역할 아님 |
| 대표 도구 | dig, nslookup | arp, ip neigh | ping, traceroute |

DNS는 도메인을 IP로 바꾸고, ARP는 이미 선택된 다음 홉 IP를 링크 주소로 바꾼다. 서로 다른 해석 과정이다.

## 6. 장점과 단점

**DNS의 장점**

- 이름과 실제 서버 주소를 분리해 서버 이전·확장이 클라이언트 변경 없이 가능하다.
- TTL 기반 캐시와 분산 위임으로 전 세계 규모로 확장된다.
- 여러 A 레코드 반환으로 단순 접속 분산이 가능하다.

**DNS의 단점**

- TTL 기반 캐시 때문에 변경 반영이 즉시 일어나지 않는다.
- JVM·OS 캐시가 DNS TTL보다 길면 갱신이 더 늦어진다.
- 권한 DNS 장애 시 영향이 광범위하다. 단일 실패점이 될 수 있다.

**ARP의 장점**

- 설정 없이 로컬 링크에서 자동 MAC 주소 해석이 이루어진다.

**ARP의 단점**

- 브로드캐스트 기반이라 대규모 네트워크에서 비효율적이다.
- ARP 스푸핑으로 트래픽을 가로채는 공격에 취약하다.

**ICMP의 장점**

- ping·traceroute로 IP 연결성과 경로를 빠르게 진단한다.
- 경로 MTU 탐색(PMTUD)에 필수적인 오류 메시지를 제공한다.

**ICMP의 단점**

- 방화벽·라우터에서 필터링될 수 있어 결과가 불완전하다.
- ping 성공·실패가 애플리케이션 포트 상태를 보장하지 않는다.

## 7. 게임 서버·백엔드 실무 예시

게임 서버 이전 시 DNS 레코드만 바꾸면 새 연결의 목적지를 전환할 수 있다. 그러나 기존 캐시와 열린 TCP 연결은 이전 서버를 계속 사용할 수 있다. 사전에 TTL을 조정하고 이전 서버를 드레이닝하며 양쪽 상태를 관찰한다.

접속 장애는 다음 순서로 나눌 수 있다.

- 도메인이 의도한 IP를 반환하는가?
- 클라이언트와 재귀 리졸버 캐시에 오래된 값이 있는가?
- 로컬 게이트웨이에 대한 ARP가 해결되는가?
- 라우팅과 ICMP 오류가 어떤 상태인가?
- 실제 TCP/UDP 포트와 애플리케이션이 응답하는가?

ARP 스푸핑은 공격자가 거짓 ARP 응답으로 트래픽을 자신에게 유도하는 방식이다. 스위치 보안 기능과 암호화된 상위 프로토콜을 함께 사용한다. HTTPS는 트래픽이 잘못 유도되더라도 인증서 검증으로 가짜 서버와의 안전하지 않은 통신을 막는 데 도움을 준다.

### DNS 기반 분산의 한계

하나의 이름에 여러 A·AAAA 레코드를 반환해 접속을 분산할 수 있지만 DNS 자체는 각 게임 서버의 실시간 부하와 연결 성공을 보장하지 않는다. 클라이언트나 리졸버가 응답 순서를 고정해서 사용하거나 오래 캐시할 수도 있다. 빠른 장애 제외가 필요하다면 헬스 체크가 있는 로드 밸런서, 클라이언트의 주소 순회와 재시도 정책을 함께 설계한다.

DNS 조회가 성공해도 IPv4와 IPv6 경로 품질은 다를 수 있다. 운영에서는 A와 AAAA 결과, 실제 선택 주소, 각 주소 계열의 연결 시간을 구분해서 기록한다.

## 8. 자주 하는 오해

- **”DNS는 IP 주소만 반환한다”**: A(IPv4)·AAAA(IPv6) 외에 CNAME·MX·TXT 등 다양한 레코드 타입이 있다.
- **”DNS는 항상 UDP로 동작한다”**: 큰 응답이나 영역 전송 시 TCP를 사용하며, DNS over HTTPS/TLS 같은 암호화 방식도 있다.
- **”외부 서버의 MAC 주소를 ARP로 구한다”**: ARP는 로컬 링크에서만 동작한다. 외부 목적지라면 기본 게이트웨이 IP의 MAC을 구한다.
- **”ping 성공이면 서버가 정상이다”**: ICMP는 통과해도 TCP 포트나 애플리케이션이 응답하지 않을 수 있다. ping은 IP 연결성 확인이지 서비스 정상 확인이 아니다.
- **”DNS TTL을 0으로 하면 즉시 전환된다”**: JVM·OS·ISP 재귀 리졸버 캐시가 TTL과 무관하게 값을 보관할 수 있다. 기존 TCP 연결도 계속 이전 주소를 사용한다.
- **”DNS 여러 A 레코드 반환이 로드 밸런서를 대체한다”**: DNS는 서버의 실시간 부하·장애 상태를 모른다. 헬스 체크 없이 죽은 서버 IP가 반환될 수 있다.
- **”ICMP를 전부 차단해야 보안이 강화된다”**: 필요한 ICMP 유형까지 막으면 경로 MTU 탐색(PMTUD)이 실패해, 연결은 되지만 큰 패킷만 전달 안 되는 블랙홀 현상이 발생한다.


## 9. 면접 질문

### Q1. DNS 조회 과정을 설명해 주세요.

애플리케이션이 로컬 리졸버에 요청하고 캐시에 없으면 재귀 리졸버가 루트, TLD, 권한 서버의 정보를 따라 조회한다. 결과는 TTL 동안 캐시되어 이후 조회 비용을 줄인다.

### Q2. ARP는 언제 사용하나요?

IPv4 로컬 링크에서 다음 홉 IP에 대응하는 MAC 주소를 알아낼 때 사용한다. 외부 목적지라면 보통 기본 게이트웨이 IP의 MAC 주소를 해석한다.

### Q3. ICMP의 역할은 무엇인가요?

IP 패킷 전달 중 목적지 도달 불가나 TTL 만료 같은 오류와 진단 정보를 전달한다. ping과 traceroute에 활용되지만 차단 가능성 때문에 결과만으로 애플리케이션 상태를 단정하지 않는다.

### Q4. DNS 전환이 즉시 적용되지 않는 이유는 무엇인가요?

재귀 리졸버와 운영체제, 애플리케이션에 TTL 기반 캐시가 있고 기존 연결도 유지될 수 있기 때문이다.

### Q5. ICMP를 전부 차단하면 어떤 문제가 생길 수 있나요?

ping만 실패하는 데 그치지 않고 목적지 도달 불가, TTL 만료, 경로 MTU 탐색에 필요한 오류 정보도 사라질 수 있다. 큰 패킷만 전달되지 않는 블랙홀 같은 장애의 진단과 복구가 어려워진다.

### Q6. 게임 서버 이전 시 DNS 전환을 어떻게 안전하게 수행하나요?

이전 1~2일 전부터 TTL을 낮게(60초 이하) 조정해 캐시 영향 범위를 줄인다. 이전 당일 새 서버로 레코드를 변경하고 이전 서버는 즉시 내리지 않고 드레이닝하며 기존 연결을 처리한다. DNS 변경 후에도 JVM·OS 캐시와 기존 TCP 연결로 이전 주소가 사용될 수 있으므로 양쪽 서버 지표를 동시에 모니터링한다.

## 11. 30초 모범답변

> DNS는 도메인 이름을 IP 같은 자원 정보로 변환하고, ARP는 IPv4 로컬 링크에서 다음 홉 IP의 MAC 주소를 알아냅니다. ICMP는 목적지 도달 불가나 TTL 만료 같은 IP 전달 오류와 진단 정보를 제공합니다. 게임 접속 장애에서는 DNS 결과, 게이트웨이 ARP, 라우팅 진단, 실제 서비스 포트를 계층별로 확인해야 합니다.

## 12. 1~2분 확장답변

> DNS는 분산된 이름 시스템으로 재귀 리졸버가 권한 서버를 조회하고 TTL 동안 결과를 캐시합니다. IP를 얻은 호스트는 같은 링크의 목적지나 외부로 나갈 기본 게이트웨이의 MAC 주소를 ARP로 알아내 프레임을 보냅니다. 패킷 전달 중 경로가 없거나 TTL이 만료되면 ICMP가 오류 정보를 전달할 수 있고 ping과 traceroute가 이를 진단에 활용합니다. 다만 DNS 캐시, ARP의 로컬 범위, ICMP 필터링을 이해해야 하며 어떤 한 도구의 결과만으로 게임 애플리케이션 전체 상태를 판단하면 안 됩니다.

## 13. 핵심 요약

- DNS는 이름을 IP 등 자원 정보로 해석한다. A·AAAA 외에 CNAME·MX·TXT 등 다양한 레코드가 있다.
- ARP는 IPv4 로컬 링크에서만 동작한다. 외부 목적지라면 기본 게이트웨이의 MAC을 구한다.
- ICMP는 IP 전달 오류(목적지 도달 불가·TTL 만료)와 진단(ping·traceroute)을 담당한다.
- DNS 변경은 TTL 기반 캐시와 기존 TCP 연결 때문에 즉시 일괄 반영되지 않는다. JVM 캐시도 별도 확인이 필요하다.
- ping 성공은 TCP 포트·애플리케이션 정상을 보장하지 않는다. 장애 분석은 계층별로 수행한다.
- ICMP를 전부 차단하면 PMTUD 실패로 큰 패킷만 전달 안 되는 블랙홀 현상이 생길 수 있다.
- DNS 여러 A 레코드 반환은 로드 밸런서를 대체하지 않는다. 실시간 헬스 체크가 없다.
- 서버 이전 전 TTL을 낮추고, 이전 후 드레이닝하며, 양쪽 서버 지표를 동시에 모니터링한다.
- ping 결과는 실제 서비스 포트의 상태와 다를 수 있다.
- 부정 캐시와 ICMP 필터링도 변경 전파와 경로 장애에 영향을 준다.

## 한 줄 정리

> DNS가 목적지 IP를 찾고 ARP가 첫 링크의 다음 장비를 찾으며 ICMP가 IP 전달의 문제를 알려 준다.
