# 10. WebSocket

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- WebSocket의 등장 이유와 HTTP와의 차이를 설명할 수 있다.
- HTTP Upgrade부터 양방향 프레임 교환까지의 흐름을 설명할 수 있다.
- 실시간 서비스에서 연결 유지, 느린 클라이언트 큐 관리, 확장 문제를 설명할 수 있다.
- 재접속 시 이벤트 ID와 세션 토큰으로 누락·중복 이벤트를 복구하는 방법을 설명할 수 있다.

## 1. 개요

WebSocket은 하나의 연결에서 클라이언트와 서버가 필요할 때마다 메시지를 주고받는 전이중(Full-duplex) 응용 계층 프로토콜이다. 최초 연결은 HTTP 핸드셰이크로 시작하지만 전환 후에는 HTTP 요청·응답이 아니라 WebSocket 프레임을 교환한다.

## 2. 왜 필요한가

일반 HTTP는 클라이언트 요청에 서버가 응답하는 구조다. 채팅, 알림, 실시간 매치 상태처럼 서버가 즉시 데이터를 밀어야 하면 짧은 폴링은 불필요한 요청을 만들고 긴 폴링은 연결과 재요청 관리가 복잡하다. WebSocket은 장시간 연결을 재사용해 양방향 메시지를 낮은 오버헤드로 교환한다.

## 3. 핵심 동작 원리

### 연결 전환

```text
Client                                      Server
  | GET /chat HTTP/1.1                        |
  | Upgrade: websocket                        |
  | Connection: Upgrade --------------------> |
  | <--- HTTP/1.1 101 Switching Protocols --- |
  | ===== WebSocket frame 양방향 교환 ======= |
```

클라이언트는 업그레이드 요청과 임의 키를 보낸다. 서버는 WebSocket을 지원하면 규칙에 따라 계산한 응답 값을 돌려준다. 이 검증은 서버가 프로토콜 전환을 이해했음을 확인하지만 사용자 인증을 대신하지 않는다.

TLS로 보호되는 WebSocket은 `wss://`, 평문은 `ws://` 스킴을 사용한다. 공개 서비스에서는 일반적으로 `wss://`를 사용한다.

### 프레임과 메시지

WebSocket은 텍스트와 바이너리 메시지를 지원한다. 하나의 메시지가 여러 프레임으로 분할될 수 있다. 제어 프레임에는 연결 종료, Ping, Pong이 있다. 브라우저가 보내는 프레임은 마스킹되지만 서버 프레임은 일반적으로 마스킹하지 않는다. 마스킹은 암호화가 아니며 보안에는 TLS가 필요하다.

TCP 위에서 동작하므로 순서와 신뢰성을 얻지만 TCP의 스트림 손실 지연도 영향을 준다. WebSocket 프레임이 메시지 경계를 제공하므로 애플리케이션은 프레임 위에서 JSON 또는 바이너리 메시지 규약을 정의한다.

### 연결 유지와 종료

장시간 아무 데이터가 없으면 NAT, 프록시, 로드 밸런서가 유휴 연결을 제거할 수 있다. Ping/Pong 또는 애플리케이션 하트비트로 연결 상태를 확인한다. 단순히 주기적으로 트래픽만 보내는 것이 아니라 응답 기한, 재접속, 중복 처리 정책을 정해야 한다.

정상 종료는 Close 프레임과 상태 코드를 교환한 뒤 TCP 연결을 닫는다. 네트워크 단절에서는 정상 종료 프레임을 받지 못할 수 있으므로 타임아웃으로 감지한다.

### 백프레셔와 송신 큐

서버가 만드는 속도보다 클라이언트가 읽는 속도가 느리면 소켓 송신 버퍼와 애플리케이션 큐가 쌓인다. 이를 방치하면 한 사용자의 느린 연결이 메모리를 계속 소비하고, 결국 프로세스 전체의 지연이나 장애로 번질 수 있다. 따라서 연결별 큐 크기와 대기 시간을 제한하고 한도를 넘었을 때의 정책을 정한다.

정책은 메시지 성격에 따라 달라진다. 결제 결과나 채팅처럼 빠지면 안 되는 이벤트는 일정 시간 보관한 뒤 연결을 종료하고 재접속 복구를 유도할 수 있다. 캐릭터 좌표나 인원 수처럼 최신 상태만 중요하다면 이전 값을 버리고 가장 최근 값으로 합친다. 모든 메시지를 같은 방식으로 큐에 쌓는 설계는 단순하지만 서비스 의미를 반영하지 못한다.

```text
이벤트 생성 속도 100 msg/s
          |
          v
   [연결별 송신 큐] ----> 느린 클라이언트 20 msg/s
     80 msg/s 누적
          |
   제한·병합·종료 정책 필요
```

이 다이어그램은 TCP의 흐름 제어가 송신 속도를 늦출 수는 있어도 애플리케이션 메모리 증가까지 자동으로 해결하지는 않는다는 뜻이다.

## 4. 쉬운 예시

채팅 클라이언트가 로그인 후 WebSocket을 연다. 클라이언트가 채팅 메시지를 보내면 서버는 권한과 내용을 검증한 뒤 같은 방의 연결들에 즉시 전송한다. 새 메시지가 없을 때는 HTTP 폴링 요청을 반복하지 않는다.

```text
Client A ─┐
Client B ─┼─ WebSocket Gateway ─ Chat Service
Client C ─┘          |
                 연결·방 구독 관리
```

```java
// Spring WebSocket: 연결 인증 + 메시지 브로드캐스트
@Component
public class GameWebSocketHandler extends TextWebSocketHandler {

    private final Map<String, WebSocketSession> sessions = new ConcurrentHashMap<>();
    private final Map<String, String> sessionToRoom = new ConcurrentHashMap<>();

    @Override
    public void afterConnectionEstablished(WebSocketSession session) throws Exception {
        // 쿼리 파라미터로 단기 토큰 전달 (URL 로그 노출 주의: 장기 자격증명 금지)
        String token = extractToken(session.getUri().getQuery());
        Player player = authService.validate(token);
        if (player == null) {
            session.close(CloseStatus.POLICY_VIOLATION);
            return;
        }
        sessions.put(player.getId(), session);
        sessionToRoom.put(player.getId(), player.getRoomId());
    }

    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) throws Exception {
        ChatMessage msg = objectMapper.readValue(message.getPayload(), ChatMessage.class);
        String roomId = sessionToRoom.get(session.getId());

        // 같은 방의 모든 연결에 브로드캐스트
        sessions.values().stream()
            .filter(s -> roomId.equals(sessionToRoom.get(s.getId())) && s.isOpen())
            .forEach(s -> {
                try {
                    s.sendMessage(message);
                } catch (IOException e) {
                    // 연결 상태 오류는 afterConnectionClosed에서 정리됨
                }
            });
    }

    @Override
    public void afterConnectionClosed(WebSocketSession session, CloseStatus status) {
        sessions.values().remove(session);
        sessionToRoom.values().remove(session.getId());
    }
}
```


## 5. 비슷한 개념과 비교

| 구분 | HTTP 폴링 | SSE | WebSocket |
|---|---|---|---|
| 방향 | 요청마다 클라이언트 주도 | 서버→클라이언트 | 양방향 |
| 연결 | 반복 또는 긴 요청 | 장시간 HTTP 연결 | 장시간 전용 연결 |
| 데이터 | 일반 HTTP | 주로 텍스트 이벤트 | 텍스트·바이너리 |
| 적합 | 변경이 드문 조회 | 알림·피드 | 채팅·실시간 상호작용 |

SSE(Server-Sent Events)는 서버에서 브라우저로 단방향 이벤트를 보내며 HTTP 재연결 의미가 단순하다. 클라이언트 송신이 일반 HTTP로 충분하면 SSE가 더 단순할 수 있다.

## 6. 장점과 단점

**WebSocket의 장점**

- 하나의 연결을 재사용하므로 반복 HTTP 요청의 연결·헤더 오버헤드가 없다.
- 서버가 이벤트 발생 즉시 클라이언트로 메시지를 밀 수 있는 진정한 양방향 통신이다.
- 텍스트·바이너리 모두 지원하고 브라우저 내장 API로 추가 라이브러리 없이 사용 가능하다.

**WebSocket의 단점**

- 서버가 많은 장기 연결 상태를 유지해야 하므로 파일 디스크립터·메모리 관리가 필요하다.
- 일반 HTTP 캐시·프록시를 그대로 적용하기 어렵다.
- 프록시 유휴 타임아웃, 하트비트, 재접속, 인증 만료를 별도로 설계해야 한다.
- 수평 확장 시 연결 위치와 서버 간 이벤트 전달 구조가 필요하다.

## 7. 게임 서버·백엔드 실무 예시

WebSocket 게이트웨이를 여러 대로 확장하면 연결은 특정 인스턴스에 붙는다. 다른 서버에서 발생한 이벤트를 해당 연결로 전달하려면 메시지 브로커나 분산 구독 구조가 필요하다. 단순한 로드 밸런싱만으로 인스턴스 간 사용자 위치를 공유할 수는 없다.

느린 클라이언트의 송신 큐에는 상한을 둔다. 중요한 채팅은 보존하되 덮어쓸 수 있는 상태 갱신은 최신 값으로 합칠 수 있다. 인증 토큰은 연결 시 검증하고 만료·권한 변경 정책을 정한다. 브라우저의 `Origin`도 허용 목록과 비교해 의도하지 않은 사이트의 연결을 제한한다.

재접속 후에는 마지막으로 처리한 이벤트 ID를 보내 누락분을 복구할 수 있다. 메시지 ID로 중복을 제거한다. TCP 연결 자체는 이전 애플리케이션 세션을 자동 복구하지 않는다.

### 인증과 세션 수명주기

연결 시점의 인증 성공이 연결 전체 기간의 권한을 영구히 보장하지는 않는다. 토큰이 만료되거나 계정이 정지되고, 사용자가 길드나 채팅방에서 나갈 수 있다. 서버는 연결 수명과 인증 수명을 분리해 생각해야 한다. 짧은 연결 토큰을 발급하거나, 만료 전에 재인증 메시지를 요구하거나, 권한 변경 이벤트를 받아 구독을 즉시 해제하는 방식이 가능하다.

브라우저 WebSocket API는 임의의 HTTP 헤더 설정이 제한되므로 쿠키, URL의 단기 토큰, 최초 애플리케이션 메시지 등으로 인증 정보를 전달한다. URL 토큰은 접근 로그와 모니터링 도구에 남을 수 있으므로 장기 자격 증명을 넣지 않는다. 쿠키를 사용한다면 `Origin` 검증과 SameSite 정책을 함께 고려한다.

### 운영에서 관찰할 지표

단순 연결 수만 보면 품질 문제를 놓치기 쉽다. 연결 성공·실패율, 비정상 종료 코드, Ping 왕복 시간, 연결별 송신 큐 크기, 드롭 메시지 수, 재접속률, 인스턴스별 연결 편차를 함께 관찰한다. 배포 직후 비정상 종료와 재접속이 급증하면 프로토콜 호환성이나 연결 드레이닝 문제를 의심할 수 있다.

서버를 종료할 때 기존 연결을 즉시 끊기보다 신규 연결 유입을 막고, Close 프레임이나 재접속 안내를 보낸 뒤 제한 시간 동안 연결을 비우는 드레이닝(Draining)을 적용할 수 있다. 클라이언트는 지수 백오프와 무작위 지연을 사용해 모든 사용자가 동시에 재접속하는 현상을 줄인다.

## 8. 자주 하는 오해

- **”WebSocket은 UDP처럼 동작한다”**: 일반적으로 TCP 위에서 순서 있는 신뢰성 통신을 한다. 손실·순서 역전이 없지만 TCP HoL Blocking은 영향을 준다.
- **”101 응답이면 인증도 완료된다”**: 101은 프로토콜 전환 승인일 뿐이다. 연결 시 토큰·쿠키 검증을 별도로 수행해야 한다.
- **”Ping만 보내면 끊김 없이 연결이 유지된다”**: Ping은 단순 생존 확인이다. Pong 응답 기한 설정, 무응답 시 연결 종료, 지수 백오프 재접속 정책이 필요하다.
- **”WebSocket은 HTTP/2 스트림이다”**: 완전히 별개의 프로토콜이다. WebSocket은 HTTP/1.1 Upgrade로 전환하며, HTTP/2와는 전환·프레이밍 방식이 다르다.
- **”연결 서버를 늘리면 자동 확장된다”**: 장기 연결은 특정 인스턴스에 고정된다. 다른 인스턴스에서 발생한 이벤트를 전달하려면 메시지 브로커나 분산 구독이 필요하다.
- **”WebSocket이 메시지를 정확히 한 번 전달을 보장한다”**: TCP는 바이트 전달을 보장하지만 처리 후 응답 전 연결이 끊기면 클라이언트는 처리 여부를 모른다. 중요한 명령에는 메시지 ID로 중복 감지를 설계해야 한다.
- **”재접속하면 이전 WebSocket 세션이 자동 복구된다”**: 재접속은 새 TCP 연결이다. 세션 토큰, 마지막 이벤트 순번을 서버에 전달해야 인증 상태와 누락 이벤트를 복구할 수 있다.


## 9. 면접 질문

### Q1. WebSocket은 왜 사용하나요?

HTTP 폴링의 반복 요청 없이 하나의 연결에서 서버와 클라이언트가 실시간으로 양방향 메시지를 교환하기 위해 사용한다.

### Q2. WebSocket 연결 과정은 어떻게 되나요?

클라이언트가 HTTP Upgrade 요청을 보내고 서버가 101 응답으로 전환을 승인한다. 이후 같은 연결에서 HTTP 메시지가 아닌 WebSocket 프레임을 교환한다.

### Q3. WebSocket 서버를 확장할 때 무엇을 고려하나요?

장기 연결의 인스턴스 위치, 서버 간 이벤트 전달, 로드 밸런서 유휴 시간, 하트비트, 느린 소비자 큐, 재접속과 중복 제거를 고려한다.

### Q4. WebSocket과 SSE는 어떻게 선택하나요?

양방향·바이너리 통신이 중요하면 WebSocket을, 서버에서 브라우저로 단방향 텍스트 이벤트만 필요하면 SSE를 고려한다.

### Q5. 느린 WebSocket 클라이언트는 어떻게 처리하나요?

연결별 송신 큐에 크기와 시간 제한을 둔다. 최신 값만 중요한 상태 갱신은 병합하거나 버리고, 보존이 필요한 이벤트는 재접속 복구 저장소로 넘긴 뒤 기준을 넘은 연결을 종료한다. 이를 통해 한 연결의 지연이 서버 전체 메모리 문제로 확산되는 것을 막는다.

### Q6. 재접속하면 이전 WebSocket 세션이 이어지나요?

아니다. TCP와 WebSocket 관점에서는 새로운 연결이다. 애플리케이션이 세션 토큰, 마지막 이벤트 순번, 메시지 ID를 이용해 인증 상태와 누락 이벤트를 복구하고 중복 처리를 막아야 한다.

## 10. 예상 꼬리질문

- `ws://`와 `wss://`의 차이는 무엇인가요?
- Ping/Pong은 왜 필요한가요?
- 느린 클라이언트의 송신 큐를 어떻게 관리하나요?
- 재접속 시 메시지 누락과 중복을 어떻게 처리하나요?
- WebSocket 연결에서 인증 만료를 어떻게 다루나요?
- 서버 배포 중 연결 폭주를 어떻게 줄이나요?
- WebSocket에서도 메시지 ID가 필요한 이유는 무엇인가요?

## 11. 30초 모범답변

> WebSocket은 하나의 연결에서 클라이언트와 서버가 전이중으로 메시지를 교환하는 프로토콜입니다. HTTP Upgrade 요청과 101 응답으로 시작한 뒤 WebSocket 프레임을 주고받습니다. 채팅과 실시간 알림에 적합하지만 장기 연결 위치, 하트비트, 느린 클라이언트, 재접속 시 누락과 중복을 서버가 관리해야 합니다.

## 12. 1~2분 확장답변

> WebSocket은 HTTP 폴링의 반복 요청 비용을 줄이고 서버가 즉시 데이터를 밀 수 있도록 만든 양방향 프로토콜입니다. 최초에는 HTTP Upgrade로 협상하고 이후 텍스트·바이너리와 Ping/Pong, Close 프레임을 교환합니다. 일반적으로 TCP 위에서 동작하므로 순서와 신뢰성을 얻습니다. 운영에서는 프록시의 유휴 타임아웃 때문에 하트비트가 필요하고, 서버 확장 시 어느 인스턴스가 사용자 연결을 갖는지 추적해 메시지 브로커로 이벤트를 전달해야 합니다. 재접속은 새 연결이므로 이벤트 ID와 세션 토큰으로 누락·중복과 인증을 처리해야 합니다.

## 13. 핵심 요약

- WebSocket은 HTTP Upgrade·101 응답으로 시작해 하나의 연결에서 전이중 프레임을 교환한다.
- `wss://`는 TLS를 포함한 WebSocket이다. 공개 서비스에서는 필수다.
- 프로토콜 전환(101)은 인증이 아니다. 연결 시 토큰·쿠키 검증을 별도로 수행한다.
- Ping/Pong + 응답 기한 + 재접속 정책(지수 백오프)이 갖춰져야 진정한 연결 유지다.
- 느린 클라이언트의 송신 큐에는 상한을 둔다. 최신 값만 중요하면 병합, 보존이 필요하면 재접속 복구 저장소로 넘긴다.
- 수평 확장 시 장기 연결은 인스턴스에 고정된다. 서버 간 이벤트 전달에는 메시지 브로커가 필요하다.
- 재접속은 새 TCP 연결이다. 이벤트 순번과 세션 토큰으로 누락·중복을 앱 계층에서 복구한다.
- TCP는 바이트 전달을 보장하지만 메시지 처리 정확히 한 번은 보장하지 않는다. 중요한 명령에는 메시지 ID가 필요하다.

## 한 줄 정리

> WebSocket은 HTTP로 문을 연 뒤 하나의 연결을 재사용해 실시간 양방향 메시지를 주고받는 방식이다.
