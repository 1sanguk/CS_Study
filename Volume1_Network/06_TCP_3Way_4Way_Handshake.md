# 06. TCP 3-Way·4-Way Handshake

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- TCP 연결 설정에 세 단계가 필요한 이유를 설명할 수 있다.
- TCP 종료가 일반적으로 네 단계인 이유를 설명할 수 있다.
- SYN, ACK, FIN과 시퀀스 번호의 의미를 설명할 수 있다.

## 1. 개요

TCP 3-Way Handshake는 양쪽이 송수신 가능한지 확인하고 초기 시퀀스 번호를 교환해 연결 상태를 만드는 과정이다. 4-Way Handshake는 각 방향의 송신을 독립적으로 종료하는 과정이다.

## 2. 왜 필요한가

TCP는 이전 연결의 지연된 세그먼트와 새 연결을 구분하고, 양쪽의 초기 시퀀스 번호를 알아야 한다. 한쪽이 보내기만 가능하고 받지 못하는 상태도 확인해야 한다. 연결 종료에서는 전이중 통신의 두 방향을 따로 닫아 아직 보낼 데이터가 있는 쪽을 보호해야 한다.

## 3. 핵심 동작 원리

### 연결 설정

```text
Client                                    Server
  | -------- SYN, seq=x ----------------> |
  | <--- SYN+ACK, seq=y, ack=x+1 -------- |
  | -------- ACK, ack=y+1 --------------> |
  |              ESTABLISHED              |
```

1. 클라이언트가 자신의 초기 시퀀스 번호 `x`와 SYN을 보낸다.
2. 서버는 이를 확인하고 자신의 `y`를 담은 SYN과 `x+1` ACK를 보낸다.
3. 클라이언트는 `y+1` ACK를 보내 서버의 SYN도 확인한다.

두 번만 주고받으면 서버는 자신의 응답이 클라이언트에게 도착했는지 확인할 수 없다. 세 번째 ACK를 통해 양쪽 송수신 경로와 초기 번호 교환을 확인한다. SYN은 시퀀스 번호 공간을 하나 소비한다.

서버는 SYN을 받은 연결과 최종 ACK까지 받은 연결을 별도 큐로 관리할 수 있다. SYN Flood는 최종 ACK를 보내지 않는 요청을 대량으로 만들어 서버 자원을 소모시키는 공격이다. SYN cookie 같은 완화 기법이 사용될 수 있다.

### 연결 설정 중 패킷이 유실되면

핸드셰이크 세그먼트도 IP 위에서 전달되므로 유실될 수 있다. 클라이언트가 보낸 SYN이 유실되거나 서버의 SYN+ACK가 도착하지 않으면 송신 측은 타이머에 따라 재전송한다. 재전송을 정해진 횟수 이상 실패하면 `connect()`는 시간 초과로 끝날 수 있다.

마지막 ACK가 유실되어도 클라이언트는 연결이 성립했다고 생각할 수 있다. 서버는 아직 최종 ACK를 확인하지 못했으므로 SYN+ACK를 재전송한다. 클라이언트가 이를 받으면 ACK를 다시 보낼 수 있다. 클라이언트가 곧바로 보낸 데이터가 서버에 도착하면 그 세그먼트의 ACK 정보로 서버가 연결 성립을 확인할 수도 있다.

연결 거부와 시간 초과는 증상이 다르다. 닫힌 TCP 포트에 도달해 RST를 받으면 일반적으로 연결 거부가 빠르게 반환된다. 방화벽이 패킷을 조용히 버리거나 경로가 끊기면 재전송을 반복한 뒤 시간 초과가 발생할 수 있다. 다만 중간 장비 정책에 따라 달라질 수 있으므로 패킷 캡처와 서버 리스닝 상태를 함께 확인한다.

### 주요 연결 상태

```text
Client: CLOSED → SYN_SENT → ESTABLISHED
Server: LISTEN → SYN_RECEIVED → ESTABLISHED
```

클라이언트는 SYN을 보낸 뒤 `SYN_SENT`, 서버는 SYN을 받고 SYN+ACK를 보낸 뒤 `SYN_RECEIVED` 상태가 된다. 최종 ACK가 확인되면 `ESTABLISHED`가 된다. 이 상태 이름을 알면 연결이 클라이언트 송신 전인지, 서버의 반쯤 열린 큐에서 멈췄는지 범위를 좁힐 수 있다.

### 연결 종료

```text
Active Closer                              Passive Closer
  | -------- FIN ------------------------> |
  | <------- ACK ------------------------- |
  |          상대의 남은 송신 가능          |
  | <------- FIN ------------------------- |
  | -------- ACK ------------------------> |
  | TIME_WAIT                              |
```

FIN은 “나는 더 보낼 데이터가 없다”는 뜻이다. FIN을 받은 쪽은 ACK한 뒤에도 반대 방향으로 데이터를 보낼 수 있다. 준비가 끝나면 자신의 FIN을 보낸다. 따라서 일반적으로 FIN과 ACK가 따로 오가며 네 단계가 된다. 상대가 즉시 종료할 수 있으면 ACK와 FIN이 한 세그먼트에 함께 담겨 단계가 줄어 보일 수 있다.

능동 종료 측은 마지막 ACK 유실에 대비하고 이전 연결의 지연 패킷이 사라질 시간을 확보하기 위해 TIME_WAIT에 머문다. 강제 종료에는 RST가 사용될 수 있으며, 이는 정상적인 FIN 종료와 달리 남은 데이터를 잃을 수 있다.

종료 상태는 다음과 같이 진행된다.

```text
Active:  ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
Passive: ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
```

수동 종료 측이 `CLOSE_WAIT`에 오래 머문다면 상대 FIN은 받았지만 로컬 애플리케이션이 아직 소켓을 닫지 않았다는 뜻이다. 종료 이벤트나 예외 경로에서 `close()`가 누락되지 않았는지 확인한다. `TIME_WAIT`는 타이머가 끝나면 운영체제가 정리하지만 `CLOSE_WAIT`는 애플리케이션의 종료 호출이 필요하다는 차이가 있다.

양쪽이 거의 동시에 FIN을 보내는 동시 종료도 가능하다. 이 경우 양쪽이 FIN을 보내고 받은 상태를 거쳐 TIME_WAIT로 갈 수 있다. 따라서 실제 상태 전이는 누가 먼저 닫았는지와 FIN·ACK가 결합되었는지에 따라 전형적인 네 단계 그림과 다르게 보일 수 있다.

### 반쪽 종료

한쪽이 FIN을 보낸 뒤 수신은 계속할 수 있는 상태를 반쪽 종료(Half-close)라고 한다. 예를 들어 클라이언트가 요청 송신을 끝냈지만 서버의 긴 응답을 계속 받을 수 있다.

## 4. 쉬운 예시

게임 클라이언트의 TCP `connect()`는 3-Way Handshake가 끝나야 성공한다. 하지만 이것은 로그인 성공이 아니다. 이후 프로토콜 버전과 토큰을 검증한다. 종료 시 클라이언트가 먼저 FIN을 보내도 서버는 버퍼에 남은 마지막 응답을 전송한 후 FIN을 보낼 수 있다.

## 5. 비슷한 개념과 비교

| 구분 | 연결 설정 | 연결 종료 |
|---|---|---|
| 일반 단계 | 3단계 | 4단계 |
| 핵심 플래그 | SYN, ACK | FIN, ACK |
| 목적 | 양방향 확인과 초기 번호 교환 | 양방향 송신 독립 종료 |
| 관련 상태 | SYN_SENT, SYN_RECEIVED | FIN_WAIT, CLOSE_WAIT, TIME_WAIT |

RST는 즉시 연결을 중단한다. FIN은 이전에 보낸 바이트를 정상 전달한 뒤 한 방향 송신을 닫는 절차다.

## 6. 장점과 단점

핸드셰이크는 오래된 연결과 새 연결을 구분하고 양방향 통신 준비를 확인한다. 정상 종료는 남은 데이터를 보존한다. 반면 연결 설정에는 최소 한 번의 왕복 지연이 들고, 연결 상태와 종료 상태가 서버 자원을 사용한다.

## 7. 게임 서버·백엔드 실무 예시

로그인 서버와 짧은 연결을 매 요청마다 새로 만들면 핸드셰이크 비용이 반복된다. 연결 재사용이나 풀링은 이 비용을 줄인다. 게임 서버는 TCP 연결 직후 일정 시간 안에 인증 메시지가 오지 않으면 연결을 정리해 미인증 소켓의 자원 점유를 제한할 수 있다.

종료 처리에서는 네트워크 끊김과 정상 FIN을 구분해야 한다. FIN을 받았어도 게임 세션을 즉시 삭제하기보다 짧은 재접속 유예 시간을 둘 수 있다. 소켓 생명주기와 사용자 세션 생명주기는 분리한다.

### 운영에서 함께 볼 지표

연결 설정 장애는 SYN 전송 수, SYN+ACK 응답 수, 최종 ACK 완료 수를 나누어 본다. SYN은 도착하지만 연결 완료율이 낮다면 클라이언트 경로, 방화벽, SYN 큐 포화 가능성을 확인한다. 연결 시간은 네트워크 RTT뿐 아니라 서버 앞단의 프록시와 TLS 설정 시간까지 분리해 측정한다.

종료 장애는 정상 FIN, RST, 타임아웃 비율을 구분한다. 배포 때 RST가 급증하면 연결 드레이닝 없이 프로세스를 종료했을 수 있다. 클라이언트가 모바일 네트워크를 전환하면 정상 FIN 없이 연결이 사라질 수 있으므로 서버는 하트비트와 유휴 타임아웃으로 죽은 연결을 정리한다.

재시도는 즉시 반복하지 않는다. 많은 클라이언트가 동시에 끊긴 뒤 같은 간격으로 연결하면 서버 복구 시점에 SYN과 인증 요청이 몰린다. 지수 백오프와 무작위 지연을 적용하고, 연결 성공 후에도 인증 요청 전송률을 제한한다.

## 8. 자주 하는 오해

- “3-Way가 로그인까지 확인한다”: TCP 연결만 확인한다.
- “종료는 반드시 네 패킷이다”: FIN과 ACK가 합쳐질 수 있다.
- “FIN을 보내면 양방향이 즉시 닫힌다”: 한 방향 송신 종료다.
- “TIME_WAIT는 서버에만 생긴다”: 일반적으로 능동 종료 측에 생긴다.
- “RST와 FIN은 같다”: RST는 비정상적·즉시 중단 성격이다.

### 최종 실무 판단 기준

- **요구 확인**: 3-Way Handshake는 양방향 통신과 초기 시퀀스 번호를 확인한다. 이 내용을 적용하기 전에 데이터 규모, 호출 빈도와 허용 지연을 수치로 확인한다. 같은 기술도 요청량과 정확성 요구가 달라지면 적합한 선택이 달라질 수 있다.
- **정확성 경계**: 종료는 각 송신 방향을 독립적으로 닫아 일반적으로 4단계다. 정상 흐름만 설명하지 않고 중복, 역순, 동시 실행과 부분 실패에서 어떤 불변식을 지켜야 하는지 함께 명시한다.
- **비용 비교**: FIN은 정상적인 한 방향 종료이고 RST는 즉시 연결을 중단한다. 평균 복잡도나 처리량 하나만 보지 않고 Memory, CPU, I/O, Lock 대기와 구현 복잡도까지 비교한다.
- **장애 대응**: TCP 3-Way·4-Way Handshake 관련 구성 요소가 느려지거나 중단됐을 때 Timeout, Retry 상한, Backpressure와 복구 순서를 정한다. Retry가 중복 부작용이나 연쇄 부하를 만들지 검증한다.
- **운영 검증**: TCP 3-Way·4-Way Handshake에서는 기능 Test와 함께 경계값, Peak 부하와 장애 주입 Test를 수행한다. 처리 시간 p95·p99, 오류율, Queue와 Resource 사용량을 관찰하고 변경 전후 결과를 비교한다.

TCP 3-Way·4-Way Handshake 답변에서는 이 기준으로 답하면 개념 정의에 그치지 않고 선택 조건, Trade-off와 실무 검증 방법까지 논리적으로 연결할 수 있다.

## 9. 면접 질문

### Q1. TCP 연결 설정이 3-Way인 이유는 무엇인가요?

양쪽이 상대의 SYN과 초기 시퀀스 번호를 받았음을 확인해야 한다. 세 번째 ACK로 서버의 SYN이 클라이언트에 도착했다는 사실까지 확인해 양방향 통신 준비를 검증한다.

### Q2. TCP 종료가 일반적으로 4-Way인 이유는 무엇인가요?

TCP는 전이중 통신이므로 각 방향의 송신을 독립적으로 닫는다. FIN을 받은 쪽이 남은 데이터를 보낸 뒤 별도로 FIN을 보낼 수 있어 ACK와 FIN이 나뉜다.

### Q3. SYN Flood는 무엇인가요?

공격자가 SYN을 대량 전송하고 최종 ACK를 완료하지 않아 반쯤 열린 연결 자원을 소모시키는 공격이다. 큐 조정, SYN cookie, 전송률 제한 등으로 완화한다.

### Q4. FIN과 RST의 차이는 무엇인가요?

FIN은 기존 데이터를 정상 처리하며 한 방향 송신을 종료한다. RST는 연결 상태가 유효하지 않거나 즉시 중단할 때 사용되어 미처리 데이터가 손실될 수 있다.

### Q5. 연결 시 SYN 또는 SYN+ACK가 유실되면 어떻게 되나요?

송신 측은 재전송 타이머에 따라 해당 세그먼트를 다시 보낸다. 재전송이 계속 실패하면 연결 시도는 시간 초과로 종료된다. 즉 TCP 연결 설정 자체도 IP 전달 실패를 재전송으로 보완한다.

### Q6. CLOSE_WAIT가 오래 유지되는 이유는 무엇인가요?

상대의 FIN은 받았지만 로컬 애플리케이션이 소켓을 닫지 않았기 때문이다. EOF, 예외, 취소 경로에서 종료 처리가 누락되었는지 확인해야 한다.

## 11. 30초 모범답변

> TCP 3-Way Handshake는 양쪽의 송수신 가능 여부를 확인하고 초기 시퀀스 번호를 교환하는 과정입니다. SYN, SYN+ACK, ACK 세 단계로 서버 응답이 클라이언트에 도착한 사실까지 확인합니다. 종료는 전이중의 두 방향을 FIN과 ACK로 각각 닫기 때문에 일반적으로 네 단계이며, 능동 종료 측은 마지막 ACK 유실과 지연 패킷에 대비해 TIME_WAIT를 거칩니다.

## 12. 1~2분 확장답변

> 클라이언트가 SYN과 초기 번호를 보내면 서버가 자신의 SYN과 클라이언트 SYN에 대한 ACK를 함께 보냅니다. 클라이언트가 서버 SYN에 ACK하면 양쪽이 상대 번호와 양방향 경로를 확인해 연결됩니다. 두 단계만으로는 서버가 자신의 응답 도착을 확인할 수 없습니다. 종료 시 FIN은 한 방향의 송신 종료만 의미합니다. FIN을 받은 쪽은 ACK 후 남은 데이터를 보낼 수 있고, 준비되면 자신의 FIN을 보냅니다. 마지막 ACK를 보낸 능동 종료 측은 재전송 대응과 이전 연결 패킷 제거를 위해 TIME_WAIT에 머뭅니다.

## 13. 핵심 요약

- 3-Way Handshake는 양방향 통신과 초기 시퀀스 번호를 확인한다.
- 종료는 각 송신 방향을 독립적으로 닫아 일반적으로 4단계다.
- FIN은 정상적인 한 방향 종료이고 RST는 즉시 연결을 중단한다.
- TCP 연결 성공은 게임 로그인 성공과 다르다.
- 능동 종료 측은 일반적으로 TIME_WAIT를 거친다.

## 한 줄 정리

> TCP는 세 단계로 양방향 연결을 확인하고, 종료할 때는 두 송신 방향을 각각 닫는다.
