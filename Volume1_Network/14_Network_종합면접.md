# 14. Network 종합면접


## 학습 목표

- 네트워크 핵심 개념을 계층과 데이터 흐름으로 연결해 설명할 수 있다.
- 게임 서버 접속·지연·연결 누수 문제를 구조적으로 진단할 수 있다.
- 대표 면접 질문에 1~3분 동안 논리적으로 답할 수 있다.
- TCP(Transmission Control Protocol)·UDP(User Datagram Protocol) 선택, HTTP(HyperText Transfer Protocol)·WebSocket 선택, 상태 있는 게임 서버 확장을 설계 질문으로 설명할 수 있다.

## 1. 개요

네트워크 면접은 용어 암기보다 “클라이언트의 메시지가 서버 프로세스까지 어떻게 가는가”를 연결해 설명하는 능력을 본다. 좋은 답변은 계층, 주소, 전송 보장, 응용 프로토콜, 운영 장애를 하나의 흐름으로 묶는다.

```text
도메인
  ↓ DNS
서버 IP와 라우팅
  ↓ ARP로 다음 홉 MAC
TCP/UDP + Port
  ↓ Socket
HTTP/WebSocket/게임 프로토콜
  ↓
로드 밸런서와 게임 서버 로직
```

## 2. 핵심 연결 흐름

클라이언트가 `https://api.game.example/login`에 접속한다고 하자.

1. DNS(Domain Name System)로 도메인의 IP(Internet Protocol)를 얻는다.
2. 라우팅 테이블로 목적지가 로컬인지 외부인지 판단한다.
3. 외부라면 ARP(Address Resolution Protocol)로 기본 게이트웨이 MAC(Media Access Control) 주소를 알아낸다.
4. HTTPS(HTTP over TLS) 서버의 TCP 443 포트로 3-Way Handshake를 수행한다.
5. TLS(Transport Layer Security)가 인증서를 검증하고 암호화 키를 합의한다.
6. HTTP 로그인 요청을 보낸다.
7. 로드 밸런서가 정상 백엔드를 선택한다.
8. 서버는 인증 후 게임 세션과 접속 주소를 반환한다.

이 과정에서 IP는 호스트를, 포트는 프로세스의 통신 끝점을, MAC은 현재 링크의 다음 인터페이스를 찾는다. TCP 연결 성공과 로그인 성공은 다른 계층의 사건이다.

## 3. 주제별 핵심 답변 지도

| 주제 | 반드시 말할 핵심 | 실무 연결 |
|---|---|---|
| OSI·TCP/IP | 역할 분리와 캡슐화 | 장애 계층 분류 |
| IP·라우팅 | 접두사와 다음 홉 | 왕복 경로 확인 |
| Port·Socket | 프로세스 구분과 통신 끝점 | 4-튜플·다중 접속 |
| TCP·UDP | 신뢰성·순서와 정책 선택 | 로그인 대 위치 갱신 |
| TCP 제어 | ACK·재전송·두 윈도 | 지연과 느린 소비자 |
| HTTP·HTTPS | 요청·응답과 TLS | 멱등성·인증서 |
| WebSocket | 장기 양방향 연결 | 재접속·수평 확장 |
| DNS·ARP·ICMP | 이름·링크·진단 | 계층별 장애 분석 |
| NAT·MTU | 주소 변환·크기 한도 | P2P·UDP 단편화 |
| LB·Proxy | 분산·대리 | 헬스 체크·드레이닝 |

## 4. 장애 분석 시나리오

장애 분석에서는 먼저 증상의 범위를 고정한다. 전체 사용자와 특정 통신사 중 어디에서 발생하는지, IPv4와 IPv6 중 한 경로인지, 신규 연결과 기존 연결 중 어느 쪽인지, 단일 서버와 전체 서버 중 어디인지 나눈다. 그다음 클라이언트 시각, 로드 밸런서 로그, 서버 로그, 메트릭, 필요하면 패킷 캡처의 시간을 맞춘다. 한 계층의 추측을 사실처럼 말하지 않고 관측 결과로 다음 검사를 선택한다.

### 서버에 접속할 수 없다

```text
DNS 결과 확인
  ↓
IP 경로와 게이트웨이 확인
  ↓
TCP/UDP 포트와 방화벽 확인
  ↓
TLS 인증서와 핸드셰이크 확인
  ↓
HTTP·게임 프로토콜과 인증 확인
```

연결 시간 초과와 연결 거부를 구분한다. 시간 초과는 패킷 차단이나 경로 문제 가능성이 있고, 즉시 거부는 대상 호스트에 리스닝 소켓이 없거나 RST가 온 상황일 수 있다. 단정하지 않고 로그와 패킷을 확인한다.

### 간헐적으로 지연된다

평균만 보지 않고 p95·p99 지연, 패킷 손실, 재전송, RTT(Round-Trip Time), 서버 큐, GC와 DB 지연을 시간축으로 맞춘다. TCP 손실로 인한 재전송인지, 수신 윈도 정체인지, 네트워크 혼잡인지, 애플리케이션 작업 지연인지 분리한다.

### 작은 메시지는 되지만 큰 메시지는 실패한다

MTU(Maximum Transmission Unit)와 단편화, PMTUD ICMP(Internet Control Message Protocol) 차단, 프록시 본문 제한, 응용 버퍼 상한을 확인한다. VPN과 터널이 추가 헤더로 실제 경로 MTU를 줄였는지도 본다.

### CLOSE_WAIT가 쌓인다

상대 FIN을 받은 뒤 애플리케이션이 소켓을 닫지 않은 상태다. EOF, 예외, 취소 경로의 자원 정리를 점검한다. TIME_WAIT와 원인이 다르다.

### WebSocket이 일정 시간 후 끊긴다

로드 밸런서와 NAT(Network Address Translation)의 유휴 타임아웃, Ping/Pong 주기, 이벤트 루프 정체, 인증 만료를 확인한다. 재접속에는 백오프와 무작위 지연을 적용해 동시 재접속 폭주를 막는다.

## 5. 설계 선택 질문

### 게임에 TCP와 UDP 중 무엇을 선택하는가

“게임이므로 UDP”라고 답하지 않는다. 메시지마다 다음을 묻는다.

- 누락을 허용할 수 있는가?
- 순서가 중요한가?
- 오래된 데이터에도 가치가 있는가?
- 재전송 지연과 구현 복잡도 중 무엇을 감수할 것인가?
- 혼잡 제어와 보안을 어떻게 제공할 것인가?

로그인, 채팅, 결제는 TCP가 자연스럽다. 빈번한 위치 갱신은 UDP와 시퀀스 번호를 고려한다. 중요한 전투 이벤트에는 선택적 신뢰성을 추가할 수 있다.

### HTTP와 WebSocket 중 무엇을 선택하는가

조회와 짧은 명령, 캐시 가능한 API(Application Programming Interface)는 HTTP가 단순하다. 서버가 빈번하게 이벤트를 밀고 양방향 메시지가 필요하면 WebSocket을 고려한다. 단방향 알림이면 SSE도 후보가 된다.

### 상태 있는 게임 서버를 어떻게 확장하는가

로그인 API는 무상태화해 로드 밸런서 뒤에서 쉽게 분산할 수 있다. 게임 룸은 특정 서버가 권위 상태를 가질 수 있으므로 매치메이커나 디렉터리가 룸 위치와 용량을 관리한다. 장애 복구에는 스냅샷, 이벤트 저장, 재접속 정책 등 요구 수준에 맞는 방법을 선택한다.

### 면접 답변 구성법

대표 질문에는 정의, 필요한 이유와 핵심 동작, 비교와 장단점, 게임 서버 사례의 순서로 답하면 안정적이다. 예를 들어 TCP 질문에 “연결 지향 프로토콜”만 답하면 부족하다. 순서 번호와 ACK·재전송, 흐름·혼잡 제어를 말하고 UDP와 비교한 뒤 로그인과 위치 갱신 사례를 연결한다.

세부 구현이 기억나지 않을 때는 아는 범위를 명시하고 원리에서 추론한다. 부정확한 숫자나 “항상 TCP가 느리다” 같은 절대적인 표현으로 빈칸을 채우지 않는다. 면접관의 꼬리질문에는 최초 선택의 조건이 바뀌었는지 확인하고 그에 따라 선택이 달라질 수 있음을 설명한다.

## 6. 자주 하는 오해

- **"TCP 연결 성공 = 애플리케이션 처리 성공"**: TCP 3-Way Handshake 완료는 소켓 연결만 의미한다. TLS 협상, HTTP 응답, 비즈니스 로직 처리 성공은 각각 다른 계층의 사건이다.
- **"ping 성공이면 서비스가 정상이다"**: ICMP는 허용되어도 TCP 포트나 애플리케이션이 응답하지 않을 수 있다. 계층별로 독립 확인이 필요하다.
- **"NAT·사설 IP는 보안 기능이다"**: NAT는 주소 변환만 수행한다. 접근 제어는 방화벽과 보안 정책으로 별도 구성해야 한다.
- **"HTTPS면 서버와 저장 데이터도 안전하다"**: HTTPS는 전송 구간만 보호한다. 서버 내부 취약점, DB 노출, 로그 노출은 별개 문제다.
- **"로드 밸런서가 상태 있는 세션을 자동 이동한다"**: 세션 고정(Sticky Session)을 사용해도 서버 장애 시 세션은 손실된다. 상태 복구는 외부 저장소나 재접속 정책으로 설계해야 한다.
- **"평균 지연이 낮으면 괜찮다"**: p99·p999 꼬리 지연, 패킷 손실, 재전송 이벤트를 함께 관찰해야 한다. 평균은 실제 사용자 경험을 숨길 수 있다.
- **"포트 하나에는 연결 하나만 가능하다"**: 소켓은 4-튜플(로컬 IP·포트, 원격 IP·포트)로 구분된다. 서버 포트 443 하나에 수만 개의 클라이언트 연결이 공존할 수 있다.


## 7. 면접 질문

### Q1. 브라우저나 게임 클라이언트가 도메인으로 서버에 접속하는 과정을 설명해 주세요.

DNS로 IP를 얻고 라우팅 테이블에서 다음 홉을 결정한다. 외부 목적지라면 ARP로 게이트웨이 MAC을 알아내 프레임을 보낸다. TCP라면 3-Way Handshake 후 TLS와 응용 프로토콜을 진행한다. 목적지 포트를 기준으로 운영체제가 서버 소켓에 데이터를 전달한다.

### Q2. TCP와 UDP를 게임 서버 관점에서 비교해 주세요.

TCP는 재전송, 순서, 흐름·혼잡 제어를 제공하는 바이트 스트림이라 정확성이 중요한 로그인과 채팅에 유리하다. UDP는 데이터그램 경계를 보존하고 전송 정책을 직접 설계할 수 있어 최신성이 중요한 위치 갱신에 적합할 수 있다. 요구사항별로 혼합한다.

### Q3. TCP 흐름 제어와 혼잡 제어의 차이는 무엇인가요?

흐름 제어는 수신 윈도로 느린 수신자의 버퍼를 보호한다. 혼잡 제어는 혼잡 윈도로 중간 네트워크 용량에 맞춰 전송량을 조절한다.

### Q4. TIME_WAIT와 CLOSE_WAIT를 설명해 주세요.

TIME_WAIT는 능동 종료 측이 마지막 ACK와 지연 패킷을 안전하게 처리하기 위해 기다리는 상태다. CLOSE_WAIT는 상대 FIN을 받았으나 로컬 애플리케이션이 아직 소켓을 닫지 않은 상태다.

### Q5. HTTPS는 어떻게 안전한 통신을 제공하나요?

TLS가 인증서로 서버 신원을 검증하고 키 교환으로 세션 키를 만든다. 이후 대칭키 암호화와 무결성 검증으로 도청과 변조를 방어한다.

### Q6. 로드 밸런서의 L4와 L7 차이는 무엇인가요?

L4는 IP·포트와 연결 정보를 기준으로 TCP/UDP를 분산한다. L7은 HTTP 경로와 헤더 같은 응용 정보를 읽어 서비스별 정책과 라우팅을 적용한다.

### Q7. 큰 UDP 패킷을 피해야 하는 이유는 무엇인가요?

경로 MTU를 넘으면 IP 단편화될 수 있고 조각 하나만 유실되어도 전체 데이터그램이 사라진다. 응용 계층에서 안전한 크기로 나누는 것이 손실 제어에 유리하다.

## 8. 예상 꼬리질문
- TCP에서 메시지 경계를 어떻게 정의하나요?
  > TCP는 바이트 스트림이므로 프로토콜 자체에 메시지 경계가 없다. 애플리케이션이 헤더에 길이 필드를 포함하거나 구분자(예: 개행 문자)를 사용해 메시지 경계를 직접 정의해야 한다.
- 하나의 서버 포트에 여러 클라이언트가 연결되는 이유는 무엇인가요?
  > 소켓은 로컬 IP·포트, 원격 IP·포트의 4-튜플로 고유하게 구분되기 때문이다. 서버 포트가 443으로 동일해도 원격 IP나 포트가 다르면 서로 다른 소켓으로 처리된다. 따라서 포트 하나에 수만 개의 클라이언트 연결이 동시에 공존할 수 있다.
- ACK는 애플리케이션 처리 완료를 뜻하나요?
  > 그렇지 않다. TCP ACK는 해당 바이트 시퀀스가 수신 측 TCP 스택에 도달했음을 의미할 뿐이다. 애플리케이션이 데이터를 읽었는지, 비즈니스 로직을 처리 완료했는지는 ACK와 별개다.
- DNS 변경이 즉시 반영되지 않는 이유는 무엇인가요?
  > 재귀 리졸버, 운영체제 캐시, JVM 캐시 등이 TTL 기반으로 이전 값을 보관하기 때문이다. TTL을 0으로 설정해도 일부 리졸버는 최소값을 강제 적용한다. 기존 TCP 연결도 DNS 변경과 무관하게 이전 서버를 계속 사용한다.
- 재접속 폭주를 어떻게 줄이나요?
  > 클라이언트가 지수 백오프와 무작위 지연(Jitter)을 적용해 재접속 간격을 점진적으로 늘린다. 이를 통해 서버 배포나 장애 직후 모든 클라이언트가 동시에 재접속하는 Thundering Herd 현상을 분산한다.
- 느린 클라이언트의 송신 큐를 어떻게 처리하나요?
  > 연결별 송신 큐에 크기와 시간 상한을 설정한다. 최신 값만 의미 있는 상태 갱신은 이전 값을 버리고 병합한다. 보존이 필요한 이벤트는 재접속 복구 저장소로 넘기고, 한도를 초과한 연결은 종료해 메모리 소비가 서버 전체로 번지지 않게 한다.
- 요청은 도착하지만 응답이 없을 때 무엇을 확인하나요?
  > 서버 애플리케이션이 요청을 받아 처리하고 있는지(로그, 스레드 덤프), 응답을 생성했는데 네트워크 역방향 경로가 막혔는지, 응답이 로드 밸런서나 프록시에서 차단됐는지, 비대칭 라우팅으로 응답 경로가 달라졌는지 순으로 계층별로 확인한다.

## 9. 30초 모범답변

> 네트워크 통신은 DNS로 IP를 찾고, 라우팅과 링크 계층을 거쳐 목적지 호스트에 도달한 뒤 포트와 소켓으로 서버 프로세스에 전달됩니다. TCP는 신뢰성 있는 스트림을, UDP는 단순한 데이터그램을 제공하므로 메시지의 정확성과 최신성에 따라 선택합니다. 실무 장애에서는 DNS, IP 경로, 전송 연결, TLS, 응용 프로토콜 순으로 범위를 좁히고 왕복 경로와 서버 큐도 함께 확인합니다.

## 10. 1~2분 확장답변

> 클라이언트가 도메인으로 접속하면 DNS로 IP를 얻고 라우팅 테이블로 다음 홉을 결정합니다. 같은 링크에서는 ARP로 MAC 주소를 알아내고, 라우터들은 목적지 IP의 최장 접두사 경로로 패킷을 전달합니다. 서버 호스트에서는 포트와 소켓이 대상 프로세스를 구분합니다. TCP는 핸드셰이크 후 순서 번호, ACK, 재전송과 흐름·혼잡 제어로 신뢰성 있는 스트림을 제공하며 UDP는 메시지별 정책을 애플리케이션에 맡깁니다. HTTPS는 TLS로 인증·암호화하고 WebSocket은 장기 양방향 연결을 제공합니다. 게임 서버 설계에서는 로그인과 결제는 신뢰성을, 위치 갱신은 최신성을 우선할 수 있습니다. 장애 분석은 계층별로 하되 NAT, MTU, 로드 밸런서, 응답 경로와 애플리케이션 처리까지 연결해서 봅니다.

## 11. 핵심 요약

- 네트워크 답변은 이름(DNS) → 주소(IP/MAC) → 경로(라우팅) → 전송(TCP/UDP) → 응용(HTTP/WS) 흐름으로 연결한다.
- IP는 호스트, 포트는 통신 끝점(프로세스), MAC은 현재 링크의 다음 인터페이스를 찾는다.
- TCP·UDP 선택은 "게임이니 UDP"가 아니라 정확성·순서·최신성·지연 요구로 메시지별로 결정한다.
- TCP 연결 성공과 비즈니스 처리 성공은 다른 계층의 사건이다. 혼동하지 않는다.
- 장애 분석은 DNS → IP 경로 → 포트·방화벽 → TLS → 응용 프로토콜 순으로 계층별 증거로 좁힌다.
- 평균 지연만 보지 말고 p99·손실·재전송을 시간축에 맞춰 관찰한다.
- NAT, MTU, 프록시 재시도, 장기 연결 드레이닝은 운영 환경에서 함께 고려한다.
- 면접 답변은 정의 → 핵심 동작 → 비교/장단점 → 게임 서버 실무 사례 순서로 구성한다.

## 한 줄 정리

> 네트워크 면접의 핵심은 프로토콜을 외우는 것이 아니라 데이터가 목적지 프로세스까지 가는 과정과 실패 지점을 논리적으로 연결하는 것이다.
