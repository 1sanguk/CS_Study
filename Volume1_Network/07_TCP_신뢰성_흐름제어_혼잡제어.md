# 07. TCP 신뢰성·흐름 제어·혼잡 제어


## 학습 목표

- TCP(Transmission Control Protocol)가 순서 번호·ACK(Acknowledgment)·재전송으로 손실과 순서 뒤바뀜을 처리하는 방식을 설명할 수 있다.
- 흐름 제어(rwnd)와 혼잡 제어(cwnd)의 대상과 목적을 구분할 수 있다.
- 슬라이딩 윈도가 처리량을 높이는 원리와 실제 송신량이 min(rwnd, cwnd)에 제한되는 이유를 설명할 수 있다.
- 게임 서버에서 느린 클라이언트 송신 큐를 관리해야 하는 이유와 방법을 설명할 수 있다.

## 1. 개요

TCP(Transmission Control Protocol) 신뢰성은 순서 번호, 확인 응답, 재전송, 체크섬을 이용해 애플리케이션에 순서 있는 바이트 스트림을 제공하는 기능이다. 흐름 제어는 수신자가 감당할 수 있는 양에 맞추고, 혼잡 제어는 네트워크가 감당할 수 있는 양에 맞춘다.

## 2. 왜 필요한가

IP는 패킷 도착, 순서, 중복 방지를 보장하지 않는다. 또한 빠른 송신자가 느린 수신자의 버퍼를 넘칠 수 있고, 여러 송신자가 네트워크 용량보다 많이 보내면 라우터 큐가 가득 차 손실과 지연이 증가한다. TCP는 이 문제를 종단에서 제어한다.

## 3. 핵심 동작 원리

### 순서 번호와 확인 응답

TCP는 바이트에 순서 번호를 부여한다. 수신자는 일반적으로 다음에 기대하는 바이트 번호를 ACK로 알린다. 중복 세그먼트는 순서 번호로 감지하고, 순서가 바뀐 데이터는 버퍼링해 올바른 순서로 애플리케이션에 전달한다.

```text
Sender                         Receiver
  | -- bytes 100~199 --------> |
  | <------- ACK 200 --------- |
  | -- bytes 200~299 --X       |
  | -- bytes 300~399 --------> |
  | <------- ACK 200 --------- |
  | -- bytes 200~299 재전송 --> |
  | <------- ACK 400 --------- |
```

재전송은 타이머 만료 또는 중복 ACK 같은 손실 신호로 시작할 수 있다. 실제 알고리즘은 구현과 옵션에 따라 다르지만, 면접에서는 ACK가 오지 않거나 손실을 추정하면 재전송한다고 설명하면 충분하다.

### 누적 ACK와 선택적 확인

기본 TCP ACK는 누적 확인 방식이다. `ACK 400`은 일반적으로 399번 바이트까지 연속으로 받았고 다음에는 400번을 기대한다는 뜻이다. 중간 데이터가 빠진 상태에서 뒤 세그먼트가 도착하면 수신자는 다음 기대 번호를 반복해서 ACK할 수 있다. 송신자는 이런 중복 ACK를 손실 신호로 활용할 수 있다.

선택적 확인 응답(SACK, Selective Acknowledgment) 옵션을 사용하면 수신자가 연속되지 않게 도착한 바이트 범위도 알려 줄 수 있다. 송신자는 이미 도착한 범위를 불필요하게 다시 보내지 않고 빠진 부분을 중심으로 재전송할 수 있다. 손실이 여러 군데 발생하거나 윈도가 큰 네트워크에서 효율적이다.

### 재전송 타임아웃

재전송 타임아웃(RTO)을 너무 짧게 잡으면 단순한 지연을 손실로 오해해 중복 전송한다. 너무 길면 실제 손실 복구가 늦어진다. TCP는 관찰한 RTT(Round-Trip Time)와 변동성을 바탕으로 RTO를 조정한다. 타임아웃이 반복되면 재전송 간격을 늘려 혼잡한 네트워크에 더 많은 트래픽을 즉시 쏟지 않도록 한다.

ACK를 받았다는 것은 상대 TCP가 해당 바이트를 수신했다는 의미다. 서버 로직이 패킷을 파싱했거나 DB 반영을 끝냈다는 의미는 아니다. 결제나 아이템 지급 완료를 확인하려면 응용 계층의 성공 응답과 요청 ID가 필요하다.

### 슬라이딩 윈도

매 세그먼트마다 ACK를 기다리면 긴 왕복 시간에서 처리량이 낮다. TCP는 확인되지 않은 데이터를 일정 범위까지 연속 전송한다. ACK가 오면 허용 범위가 앞으로 이동하므로 슬라이딩 윈도라고 한다.

```text
[ACK 완료][전송했으나 미확인][전송 가능][아직 전송 불가]
                ---- window ----
```

실제 송신 가능량은 수신 윈도와 혼잡 윈도의 영향을 함께 받는다.

단순화하면 송신 측이 네트워크에 내보낼 수 있는 미확인 데이터는 `min(rwnd, cwnd)`의 제한을 받는다. 수신 버퍼가 작으면 `rwnd`가 병목이고, 경로 혼잡을 우려하면 `cwnd`가 병목이다. 여기에 이미 전송했지만 아직 확인되지 않은 바이트를 고려해 새로 보낼 수 있는 양을 계산한다.

긴 RTT 경로에서 높은 처리량을 내려면 네트워크에 동시에 떠 있을 수 있는 데이터가 충분해야 한다. 필요한 양은 대략 대역폭과 RTT의 곱인 대역폭-지연 곱(Bandwidth-Delay Product)으로 생각할 수 있다. 윈도가 이 값보다 지나치게 작으면 회선 대역폭이 남아도 ACK를 기다리느라 충분히 활용하지 못한다.

### 흐름 제어

수신자는 자신의 수신 버퍼 여유를 수신 윈도(rwnd)로 광고한다. 송신자는 이를 넘지 않게 미확인 데이터를 제한한다. 목적은 빠른 송신자가 느린 수신자의 버퍼를 압도하지 않게 하는 것이다.

수신 윈도가 0이면 송신자는 일반 데이터를 멈추고, 윈도가 다시 열렸는지 확인하는 동작을 수행한다. 애플리케이션이 소켓 데이터를 너무 늦게 읽으면 네트워크가 정상이어도 흐름 제어로 전송이 정체될 수 있다.

### 혼잡 제어

혼잡 제어는 수신 호스트가 아니라 중간 네트워크의 수용 능력을 고려한다. TCP는 혼잡 윈도(cwnd)를 관리하며 손실, 지연 같은 신호를 바탕으로 전송량을 조절한다.

- 느린 시작: 작은 윈도에서 시작해 ACK를 받으며 빠르게 증가한다.
- 혼잡 회피: 임계점 이후 더 완만하게 증가한다.
- 손실 반응: 혼잡 신호로 판단하면 윈도를 줄인다.
- 빠른 재전송·회복: 중복 ACK로 손실을 추정해 타임아웃 전에 복구할 수 있다.

현대 운영체제는 다양한 혼잡 제어 알고리즘을 사용한다. 세부 증가 공식보다 “네트워크 혼잡을 감지해 송신량을 조절한다”는 목적이 핵심이다.

손실이 항상 혼잡만을 의미하는 것은 아니다. 무선 환경에서는 신호 문제로도 손실될 수 있다. 그러나 전통적인 TCP는 종단에서 원인을 완벽히 구분하기 어려워 손실을 혼잡 신호로 해석하고 전송량을 줄일 수 있다. 이 때문에 같은 서버라도 유선 데이터센터와 모바일 네트워크에서 처리량과 지연 분포가 다르게 나타난다.

### Head-of-Line Blocking

TCP는 순서 있는 스트림을 제공하므로 앞 바이트가 손실되면 뒤 바이트가 도착해도 애플리케이션 전달이 기다릴 수 있다. 게임의 중요하지 않은 위치 갱신과 중요한 이벤트를 한 연결에 섞으면 위치 손실이 다른 메시지 지연에 영향을 줄 수 있다.

## 4. 쉬운 예시

서버가 클라이언트에 대량의 맵 데이터를 보내는 동안 클라이언트가 느리게 읽으면 수신 윈도가 줄어든다. 동시에 공유 네트워크에 트래픽이 몰리면 혼잡 윈도도 줄 수 있다. 전자는 클라이언트 처리 능력, 후자는 네트워크 상태 문제다.

### 코드로 보는 송신 큐 관리와 흐름 제어

```java
// BAD: 무제한 송신 큐 → 느린 클라이언트가 서버 메모리 점유
public class GameSession {
    private final Queue<byte[]> sendQueue = new LinkedList<>(); // 크기 제한 없음

    public void sendState(byte[] stateSnapshot) {
        sendQueue.offer(stateSnapshot); // 클라이언트가 느리면 계속 쌓임
    }
}

// GOOD: 최대 큐 크기 + 오래된 위치 스냅샷 교체
public class GameSession {
    private static final int MAX_QUEUE = 64;
    private final ArrayDeque<GameMessage> sendQueue = new ArrayDeque<>();

    public void sendPositionSnapshot(PositionSnapshot snapshot) {
        // 위치 스냅샷은 최신 값으로 교체 (오래된 값 유지 불필요)
        sendQueue.removeIf(m -> m.type() == MessageType.POSITION_SNAPSHOT);
        if (sendQueue.size() < MAX_QUEUE) {
            sendQueue.offer(new GameMessage(MessageType.POSITION_SNAPSHOT, snapshot.serialize()));
        }
        // 상한 초과 시 연결 종료 또는 QoS 저하 정책 적용
    }
}
```

```text
흐름 제어와 혼잡 제어 동시 영향:
클라이언트가 느리게 읽음 → rwnd 감소 → TCP 송신 정체
                                          ↓
                              서버 OS 송신 버퍼 가득 참
                                          ↓
                              write() 블록 또는 애플리케이션 큐 증가
                                          ↓
                              서버 메모리 증가 (주의)
```

## 5. 비슷한 개념과 비교

| 구분 | 흐름 제어 | 혼잡 제어 |
|---|---|---|
| 보호 대상 | 수신자 버퍼 | 네트워크 전체 |
| 주요 기준 | 수신 윈도 rwnd | 혼잡 윈도 cwnd |
| 문제 | 송신자가 수신자보다 빠름 | 전체 트래픽이 경로 용량 초과 |
| 신호 | 수신자가 광고한 여유 | 손실, ACK, 지연 등 |

오류 검출은 체크섬으로 데이터 손상을 감지하는 기능이고, 신뢰성은 손실·중복·순서를 처리해 스트림을 제공하는 더 넓은 개념이다.

## 6. 장점과 단점

**TCP 신뢰성 장점**
- 재전송·순서·중복 제거를 운영체제가 처리해 애플리케이션 구현이 단순하다.
- 체크섬으로 데이터 손상을 감지한다.
- SACK으로 여러 손실 구간 효율적 재전송이 가능하다.

**TCP 신뢰성 단점**
- 앞선 바이트 손실 시 뒤 데이터 전달이 대기(Head-of-Line Blocking).
- 재전송 타이머와 RTO 계산 오버헤드.

**흐름 제어 장점**
- 수신 버퍼 넘침을 방지해 데이터 손실 없이 안정적 전송.

**흐름 제어 단점**
- 애플리케이션이 소켓을 느리게 읽으면 rwnd가 0이 돼 전송이 정체.
- OS 송신 버퍼 정체가 애플리케이션 레벨 메모리 증가로 이어질 수 있음.

**혼잡 제어 장점**
- 네트워크 전체 혼잡을 방지해 모든 연결의 공평한 대역폭 사용을 도움.

**혼잡 제어 단점**
- 느린 시작(Slow Start)으로 초기 처리량이 낮음.
- 무선 환경에서 신호 손실을 혼잡으로 오판해 불필요하게 전송률 감소.

## 7. 게임 서버·백엔드 실무 예시

게임 서버의 송신 큐가 계속 증가한다면 단순히 네트워크가 느리다고 결론 내리지 않는다. 클라이언트가 읽지 않는지, 서버 로직이 과도하게 생성하는지, 경로 혼잡인지 구분한다. 큐 상한을 두고 중요도 낮은 상태 갱신을 합치거나 폐기해 느린 클라이언트 하나가 메모리를 계속 점유하지 않게 한다.

대용량 패치와 실시간 제어 메시지를 한 TCP 연결에 섞으면 작은 메시지가 대용량 데이터 뒤에서 기다릴 수 있다. 연결이나 서비스 경로를 분리하고 우선순위를 설계할 수 있다.

### 작은 메시지와 전송 지연

TCP 구현은 작은 데이터를 모아 보내기 위한 Nagle 알고리즘을 사용할 수 있고, 수신 측은 ACK를 잠시 모으는 지연 ACK를 사용할 수 있다. 두 동작이 결합되면 작은 요청과 응답 중심 프로토콜에서 예상하지 못한 지연이 보일 수 있다. `TCP_NODELAY`로 Nagle 알고리즘을 끌 수 있지만 패킷 수가 늘어날 수 있으므로 무조건 적용하지 않는다. 먼저 메시지를 적절히 배치하고 실제 RTT·패킷 수·p99 지연을 비교한다.

### 느린 클라이언트 진단

```text
게임 로직 생성률 > 소켓 실제 전송률
          ↓
애플리케이션 송신 큐 증가
          ↓
메모리 증가·오래된 상태 전송·지연 확대
```

서버는 연결별 송신 큐 크기와 가장 오래된 메시지의 대기 시간을 관찰한다. 위치 스냅샷처럼 덮어쓸 수 있는 데이터는 최신 값으로 합친다. 반드시 전달해야 하는 데이터가 상한을 넘으면 연결을 종료하거나 품질을 낮추는 정책이 필요하다. TCP가 흐름 제어를 제공해도 애플리케이션 메모리까지 자동으로 보호하지는 않는다.

## 8. 자주 하는 오해

- **”흐름 제어와 혼잡 제어는 같다”**: 흐름 제어는 수신자 버퍼를, 혼잡 제어는 중간 네트워크를 보호한다. 제어 신호(rwnd vs cwnd)와 보호 대상이 다르다.
- **”ACK는 애플리케이션 처리 완료다”**: TCP 스택이 바이트를 수신했다는 의미일 뿐이다. 서버 파싱·DB 반영·비즈니스 처리 완료는 응용 계층 응답으로 확인해야 한다.
- **”TCP면 지연이 일정하다”**: 패킷 손실 시 재전송 대기, 혼잡 제어에 따른 전송률 감소로 p99 지연이 크게 튈 수 있다. 특히 무선 환경에서 더 두드러진다.
- **”수신 윈도가 크면 언제나 빠르다”**: 실제 전송량은 `min(rwnd, cwnd)`에 제한된다. rwnd가 커도 네트워크 혼잡이 cwnd를 줄이면 처리량이 제한된다.
- **”순서 보장은 항상 장점이다”**: 실시간 게임에서 오래된 위치 데이터가 손실되면 최신 위치도 그 뒤에서 대기(HoL Blocking). 실시간 최신성에는 오히려 단점이 될 수 있다.
- **”TCP가 흐름 제어를 하므로 서버 메모리는 안전하다”**: TCP 흐름 제어는 OS 송신 버퍼를 보호한다. 애플리케이션이 추가로 유지하는 송신 큐(게임 메시지 큐)는 TCP가 관리하지 않는다. 별도 상한이 없으면 메모리 누수.
- **”Nagle 알고리즘은 끄면 항상 좋다”**: `TCP_NODELAY`로 Nagle을 끄면 작은 패킷 수가 늘어 네트워크 오버헤드가 증가할 수 있다. 먼저 메시지 배치를 최적화하고 실제 p99와 패킷 수를 측정한 뒤 적용을 결정해야 한다.

## 9. 면접 질문

### Q1. TCP는 어떻게 신뢰성을 제공하나요?

바이트 순서 번호와 체크섬으로 순서와 오류를 확인하고, ACK가 없거나 손실 신호가 나타나면 재전송한다. 중복을 제거하고 순서대로 재조립해 애플리케이션에 바이트 스트림을 제공한다.

### Q2. 흐름 제어와 혼잡 제어의 차이는 무엇인가요?

흐름 제어는 수신자가 광고한 윈도로 수신 버퍼 초과를 막는다. 혼잡 제어는 혼잡 윈도를 조절해 중간 네트워크 용량을 초과하지 않도록 한다.

### Q3. 슬라이딩 윈도가 필요한 이유는 무엇인가요?

ACK를 하나씩 기다리지 않고 여러 데이터를 연속 전송해 왕복 지연이 있어도 처리량을 높이기 위해서다. ACK가 오면 전송 가능한 범위가 앞으로 이동한다.

### Q4. TCP의 Head-of-Line Blocking은 무엇인가요?

앞선 바이트가 손실되면 뒤 데이터가 도착해도 순서 보장을 위해 애플리케이션 전달을 기다리는 현상이다.

### Q5. 실제 TCP 송신량은 어떤 윈도의 영향을 받나요?

수신자가 광고하는 수신 윈도와 송신자가 관리하는 혼잡 윈도의 작은 값에 주로 제한된다. 전자는 수신 버퍼를, 후자는 네트워크를 보호한다.

### Q6. SACK은 왜 필요한가요?

수신자가 순서가 끊긴 상태로 이미 받은 구간을 알려 송신자가 빠진 범위를 중심으로 재전송하게 한다. 여러 손실이 있을 때 불필요한 재전송을 줄일 수 있다.

## 11. 30초 모범답변

> TCP는 순서 번호, ACK, 체크섬과 재전송으로 순서 있는 바이트 스트림을 제공합니다. 흐름 제어는 수신자가 광고한 윈도로 수신 버퍼를 보호하고, 혼잡 제어는 네트워크 상태에 따라 혼잡 윈도를 조절합니다. 실제 송신량은 두 윈도의 영향을 받으며, 손실 시 재전송과 순서 대기로 게임 메시지 지연이 커질 수 있습니다.

## 12. 1~2분 확장답변

> TCP는 각 바이트에 순서 번호를 부여하고 수신자가 다음 기대 번호를 ACK로 알리게 합니다. 손실을 타이머나 중복 ACK로 추정하면 재전송하고, 중복과 순서 뒤바뀜을 처리합니다. 처리량을 높이기 위해 여러 세그먼트를 연속 전송하는 슬라이딩 윈도를 사용합니다. 이때 흐름 제어의 수신 윈도는 느린 수신자의 버퍼를 보호하고, 혼잡 제어의 혼잡 윈도는 중간 네트워크가 감당할 수 있도록 전송량을 조절합니다. 게임 서버에서는 송신 큐와 윈도 정체를 관찰하고 느린 클라이언트의 불필요한 상태 갱신을 합치거나 제한해야 합니다.

## 13. 핵심 요약

- 순서 번호·ACK·체크섬·재전송이 TCP 신뢰성의 핵심이다. SACK으로 여러 손실 구간을 효율적으로 재전송한다.
- 슬라이딩 윈도는 ACK를 하나씩 기다리지 않고 여러 세그먼트를 연속 전송해 RTT가 커도 처리량을 높인다.
- 흐름 제어(rwnd): 수신자 버퍼 보호. 혼잡 제어(cwnd): 네트워크 보호. 실제 송신량은 `min(rwnd, cwnd)`.
- ACK는 TCP 스택이 바이트를 수신했다는 의미다. 애플리케이션 처리 완료·DB 반영은 응용 계층 응답으로 확인.
- 순서 보장은 손실 시 뒤 데이터 지연(Head-of-Line Blocking)을 만든다. 실시간 최신성에는 단점.
- 게임 서버의 애플리케이션 송신 큐는 TCP 흐름 제어가 보호하지 않는다. 별도 상한과 오래된 스냅샷 교체 정책이 필요하다.
- 무선 환경에서 신호 손실을 혼잡으로 오판해 불필요하게 cwnd가 감소할 수 있다.
- Nagle 알고리즘 비활성화(TCP_NODELAY)는 패킷 수를 늘릴 수 있으므로 p99와 패킷 수를 측정한 후 적용한다.

## 한 줄 정리

> TCP는 재전송으로 신뢰성을 만들고, 수신자와 네트워크가 감당할 수 있는 범위에서 전송량을 조절한다.
