# 13. Load Balancer와 Reverse Proxy

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 로드 밸런서와 리버스 프록시의 역할과 관계를 설명할 수 있다.
- L4와 L7 로드 밸런싱의 차이를 설명할 수 있다.
- 헬스 체크, 세션 고정, 연결 드레이닝을 운영에 적용할 수 있다.

## 1. 개요

로드 밸런서(Load Balancer)는 들어오는 트래픽을 여러 백엔드에 분산해 처리량과 가용성을 높이는 구성 요소다. 리버스 프록시(Reverse Proxy)는 클라이언트 앞에서 요청을 받은 뒤 내부 서버로 전달하고 응답을 대신 반환하는 프록시다.

리버스 프록시가 로드 밸런싱 기능을 제공할 수 있고, 로드 밸런서도 프록시 방식으로 동작할 수 있어 두 용어의 범위는 겹친다. 초점은 트래픽 분산과 대리 요청 처리 중 어디에 있느냐의 차이다.

## 2. 왜 필요한가

단일 서버는 용량과 장애 면에서 한계가 있다. 여러 서버를 직접 클라이언트에 노출하면 주소 변경, 인증서, 라우팅 정책 관리가 복잡하다. 앞단 구성 요소가 단일 진입점을 제공하고 정상 서버 선택, TLS 종료, 경로 라우팅, 관찰 기능을 맡으면 백엔드를 확장하고 교체하기 쉽다.

## 3. 핵심 동작 원리

```text
Clients
   |
   v
Load Balancer / Reverse Proxy
   ├─ Backend A
   ├─ Backend B
   └─ Backend C
```

### L4와 L7

L4 로드 밸런서는 주로 IP, 포트, TCP/UDP 연결 정보를 기준으로 전달한다. 프로토콜 내용에 대한 이해가 적어 범용적이고 오버헤드가 낮다. TCP 게임 연결이나 UDP 트래픽 분산에 사용할 수 있다.

L7 로드 밸런서는 HTTP 호스트, 경로, 헤더, 쿠키 같은 응용 정보를 읽어 라우팅한다. `/login`은 로그인 서비스, `/ranking`은 랭킹 서비스로 보낼 수 있다. TLS를 종료하면 인증서 관리와 HTTP 정책을 중앙화할 수 있지만 복호화 지점의 보안과 백엔드 구간 보호를 고려해야 한다.

### 분산 알고리즘

- Round Robin: 서버를 순서대로 선택
- Weighted Round Robin: 용량에 따라 가중치 적용
- Least Connections: 활성 연결이 적은 서버 선택
- Hash 기반: 클라이언트나 키를 해시해 서버 선택

요청 수가 같아도 처리 비용이 다를 수 있다. 긴 게임 연결에서는 단순 요청 수보다 활성 연결, 서버 부하, 방 수용량을 함께 고려한다.

### 헬스 체크

로드 밸런서는 백엔드가 요청을 받을 수 있는지 주기적으로 확인한다. TCP 포트 연결만 확인하는 검사는 프로세스가 리스닝하는지만 볼 수 있다. HTTP readiness 검사는 필수 의존성과 요청 처리 준비 상태까지 확인할 수 있다.

헬스 체크가 너무 얕으면 고장 난 서버로 트래픽을 보내고, 너무 무거우면 자체 부하와 연쇄 장애를 만든다. 생존 여부와 트래픽 수신 준비 상태를 분리하는 것이 좋다.

### 세션 고정과 상태

세션 고정(Sticky Session)은 같은 클라이언트 요청을 같은 백엔드로 보내는 방식이다. 메모리 세션을 쉽게 유지하지만 서버 장애와 확장 시 재분배가 어렵고 부하가 치우칠 수 있다. 가능한 경우 상태를 외부 저장소에 두거나 토큰으로 전달해 어느 서버든 처리하도록 설계한다.

게임 룸처럼 특정 프로세스가 권위 상태를 갖는 경우에는 단순 고정이 아니라 매치 디렉터리가 룸 위치를 관리하고 재접속을 해당 서버로 안내하는 구조가 필요할 수 있다.

### 드레이닝과 타임아웃

서버 배포 시 새 연결을 중단하고 기존 연결이 끝날 시간을 주는 연결 드레이닝(Connection Draining)이 필요하다. HTTP 요청은 비교적 짧지만 WebSocket과 게임 TCP 연결은 오래 유지되므로 종료 예고, 재접속 안내, 최대 유예 시간이 필요하다.

프록시에는 연결, 요청, 업스트림, 유휴 타임아웃이 있다. 값이 서비스 특성과 맞지 않으면 정상적인 장기 연결이 끊기거나 장애 응답이 너무 늦어진다.

### 재시도와 멱등성

프록시는 백엔드 연결 실패나 일부 오류에 다른 서버로 재시도할 수 있다. 조회 요청에는 유용하지만 처리 결과를 확인하지 못한 변경 요청을 재전송하면 결제나 아이템 지급이 중복될 수 있다. HTTP 메서드 이름만 믿지 말고 실제 작업의 멱등성, 요청 본문 전송 여부, 멱등성 키를 고려해 재시도 범위를 정한다.

재시도 횟수와 시간 제한이 과하면 장애 중인 백엔드에 원래 요청보다 많은 부하가 생긴다. 전체 요청 기한 안에서 짧게 제한하고, 백엔드 퇴출과 회로 차단, 클라이언트 재시도 정책까지 합산해 증폭을 막는다.

```text
Client 1 request
   └─ Proxy retry 3회
         └─ Service retry 3회
               = 최대 9번의 하위 호출
```

각 계층의 재시도는 독립적으로는 작아 보여도 곱해질 수 있다는 의미다.

## 4. 쉬운 예시

HTTPS 로그인 요청은 L7 로드 밸런서에서 TLS를 종료하고 정상 로그인 서버 중 하나로 전달한다. 매치 성공 후 클라이언트는 할당된 게임 서버 주소로 L4 연결을 만든다. 로그인 서버는 무상태로 확장하기 쉽지만 게임 룸은 상태 위치를 별도로 추적한다.

## 5. 비슷한 개념과 비교

| 구분 | Forward Proxy | Reverse Proxy | Load Balancer |
|---|---|---|---|
| 대신하는 쪽 | 클라이언트 | 서버 | 여러 백엔드 앞단 |
| 주 목적 | 클라이언트 접근 중계 | 서버 은닉·정책·TLS | 부하 분산·가용성 |
| 대상이 보는 상대 | 프록시 클라이언트 | 리버스 프록시 | 로드 밸런서 또는 원주소 전달 |

API Gateway는 인증, 사용량 제한, API 조합 등 응용 정책에 더 초점을 둔다. 리버스 프록시와 기능이 겹칠 수 있으나 개념적 역할은 다르다.

## 6. 장점과 단점

장점은 수평 확장, 장애 서버 제외, 단일 진입점, TLS와 정책 중앙화, 점진적 배포다. 단점은 앞단 자체가 중요한 장애 지점이 되고, 추가 홉과 비용이 생기며, 원본 클라이언트 정보와 장기 연결 상태를 관리해야 한다는 점이다. 로드 밸런서 자체도 다중화해야 한다.

## 7. 게임 서버·백엔드 실무 예시

클라이언트 IP가 필요하면 신뢰할 수 있는 프록시가 전달한 헤더나 Proxy Protocol을 사용한다. 외부 입력 헤더를 그대로 신뢰하면 위조 가능하다. 신뢰 경계를 명확히 한다.

서버가 과부하인데 헬스 체크에는 성공할 수 있다. readiness에서 큐 길이와 수용 여부를 반영하거나 매치메이커가 서버 용량을 관리한다. 모든 서버를 동시에 비정상으로 판정하면 남은 서버에 부하가 몰리는 연쇄 장애가 생길 수 있어 퇴출 속도와 복구 기준을 조절한다.

헬스 체크는 한 번의 실패로 즉시 퇴출하고 한 번의 성공으로 즉시 복구하기보다 연속 성공·실패 임계값을 둘 수 있다. 이는 순간적인 네트워크 흔들림 때문에 서버가 계속 들어왔다 나가는 플래핑(Flapping)을 줄인다. 반대로 임계값이 너무 크면 실제 장애 감지가 늦어지므로 검사 주기와 함께 복구 목표에 맞춘다.

과부하 시에는 모든 요청을 받아 큐를 무한히 늘리는 것보다 빠르게 거절해 상위 계층이 대체 경로나 백오프를 선택하게 하는 편이 낫다. 로드 밸런서는 서버별 활성 연결뿐 아니라 지연, 오류율, 명시적인 수용 가능 용량을 사용할 수 있다. 게임 룸 배치는 일반 HTTP 분산보다 도메인 상태가 중요하므로 전용 매치 디렉터리가 적합하다.

배포 시에는 다음 순서를 사용할 수 있다.

```text
readiness 실패 처리 → 새 트래픽 중단 → 기존 연결 드레이닝
→ 프로세스 종료·배포 → 준비 완료 → 트래픽 재개
```

## 8. 자주 하는 오해

- “로드 밸런서가 있으면 장애가 없다”: 앞단과 의존성도 다중화해야 한다.
- “Round Robin이면 부하가 동일하다”: 요청 비용과 연결 시간이 다르다.
- “헬스 체크 성공은 완전 정상이다”: 검사 범위만 통과한 것이다.
- “Sticky Session이 상태 문제를 해결한다”: 장애·재분배 문제를 남긴다.
- “리버스 프록시와 로드 밸런서는 완전히 별개다”: 제품 기능은 겹칠 수 있다.

### 최종 실무 판단 기준

- **요구 확인**: 로드 밸런서는 트래픽 분산, 리버스 프록시는 서버 대리와 정책이 중심이다. 이 내용을 적용하기 전에 데이터 규모, 호출 빈도와 허용 지연을 수치로 확인한다. 같은 기술도 요청량과 정확성 요구가 달라지면 적합한 선택이 달라질 수 있다.
- **정확성 경계**: L4는 연결 정보, L7은 응용 정보를 이용한다. 정상 흐름만 설명하지 않고 중복, 역순, 동시 실행과 부분 실패에서 어떤 불변식을 지켜야 하는지 함께 명시한다.
- **비용 비교**: 헬스 체크 깊이와 서버 퇴출 정책이 가용성에 영향을 준다. 평균 복잡도나 처리량 하나만 보지 않고 Memory, CPU, I/O, Lock 대기와 구현 복잡도까지 비교한다.
- **장애 대응**: Load Balancer와 Reverse Proxy 관련 구성 요소가 느려지거나 중단됐을 때 Timeout, Retry 상한, Backpressure와 복구 순서를 정한다. Retry가 중복 부작용이나 연쇄 부하를 만들지 검증한다.
- **운영 검증**: Load Balancer와 Reverse Proxy에서는 기능 Test와 함께 경계값, Peak 부하와 장애 주입 Test를 수행한다. 처리 시간 p95·p99, 오류율, Queue와 Resource 사용량을 관찰하고 변경 전후 결과를 비교한다.

Load Balancer와 Reverse Proxy 답변에서는 이 기준으로 답하면 개념 정의에 그치지 않고 선택 조건, Trade-off와 실무 검증 방법까지 논리적으로 연결할 수 있다.

## 9. 면접 질문

### Q1. 로드 밸런서와 리버스 프록시의 차이는 무엇인가요?

로드 밸런서는 여러 백엔드에 트래픽을 분산하는 목적이 중심이고, 리버스 프록시는 서버 대신 요청을 받아 전달하며 서버 은닉, TLS, 캐시, 정책을 제공한다. 하나의 제품이 두 기능을 함께 수행할 수 있다.

### Q2. L4와 L7 로드 밸런서의 차이는 무엇인가요?

L4는 IP·포트와 연결 정보를 기준으로 TCP/UDP를 전달한다. L7은 HTTP 경로, 호스트, 헤더 같은 응용 정보를 읽어 세밀한 라우팅과 정책을 적용한다.

### Q3. 세션 고정의 장단점은 무엇인가요?

메모리 상태를 가진 서버에 같은 사용자를 보내기 쉽다. 반면 부하 불균형, 서버 장애 시 세션 손실, 확장과 재분배 어려움이 생긴다.

### Q4. 연결 드레이닝은 왜 필요한가요?

배포나 서버 제거 시 새 연결은 막고 기존 요청과 장기 연결이 정상적으로 끝나거나 재접속할 시간을 주어 사용자 오류와 데이터 손실을 줄이기 위해서다.

### Q5. 로드 밸런서 재시도에서 무엇을 주의해야 하나요?

이미 처리되었을 가능성이 있는 비멱등 요청을 다시 보내면 중복 변경이 생길 수 있다. 전체 요청 기한과 멱등성 키를 사용하고, 여러 계층의 재시도가 곱해져 장애 부하를 키우지 않도록 한 계층에서 제한적으로 수행한다.

## 11. 30초 모범답변

> 로드 밸런서는 요청이나 연결을 여러 백엔드에 분산해 처리량과 가용성을 높이고, 리버스 프록시는 서버 대신 요청을 받아 TLS 종료, 라우팅, 캐시 같은 정책을 수행합니다. L4는 IP와 포트 중심, L7은 HTTP 경로와 헤더 중심으로 동작합니다. 운영에서는 헬스 체크, 타임아웃, 원본 주소 전달과 장기 연결의 드레이닝을 함께 설계해야 합니다.

## 12. 1~2분 확장답변

> 로드 밸런서는 단일 진입점에서 정상 백엔드로 트래픽을 분산합니다. L4는 TCP·UDP 연결 정보를, L7은 HTTP 의미를 이용해 경로별 라우팅과 TLS 종료를 할 수 있습니다. 리버스 프록시는 서버를 대신해 요청을 받고 보안과 캐시, 헤더 정책을 적용하며 로드 밸런싱 기능도 포함할 수 있습니다. 백엔드 선택에는 Round Robin, 가중치, 최소 연결 등을 사용하지만 게임의 장기 연결과 룸 상태는 별도 용량 정보가 필요합니다. 헬스 체크는 준비 상태를 제대로 반영해야 하며 배포 때는 새 트래픽을 끊고 기존 연결을 드레이닝해야 합니다.

## 13. 핵심 요약

- 로드 밸런서는 트래픽 분산, 리버스 프록시는 서버 대리와 정책이 중심이다.
- L4는 연결 정보, L7은 응용 정보를 이용한다.
- 헬스 체크 깊이와 서버 퇴출 정책이 가용성에 영향을 준다.
- 세션 고정은 편리하지만 부하와 장애 문제를 남긴다.
- 장기 연결 서비스의 배포에는 연결 드레이닝이 필요하다.
- 재시도는 멱등성과 전체 시간 예산 안에서 제한해야 한다.

## 한 줄 정리

> 로드 밸런서와 리버스 프록시는 서버 앞의 단일 진입점에서 트래픽을 고르고 보호하며 백엔드 확장을 가능하게 한다.
