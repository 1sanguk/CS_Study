# 05. Dynamic Programming

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 겹치는 부분 문제와 최적 부분 구조가 모두 존재하는지 확인하고 DP 적용 가능 여부를 판단할 수 있다.
- 상태, 점화식, 초기값, 계산 순서를 체계적으로 설계할 수 있다.
- 재귀 깊이·공간 제약·순서 의존성을 고려해 Memoization과 Tabulation 중 어느 방식이 적합한지 선택할 수 있다.
- 0/1 Knapsack과 게임 자원 배분 문제에서 공간 최적화 방향을 판단할 수 있다.

## 1. 개요

Dynamic Programming은 큰 문제를 부분 문제로 나누고, 같은 부분 문제의 답을 저장해 한 번만 계산하는 설계 방식이다. 보통 DP라고 부른다.

단순 재귀는 서로 다른 경로에서 같은 상태를 반복 계산할 수 있다.

```text
fib(5)
├─ fib(4)
│  ├─ fib(3)
│  └─ fib(2)
└─ fib(3)        ← 이미 계산한 상태 반복
   ├─ fib(2)
   └─ fib(1)
```

`fib(3)`, `fib(2)` 같은 결과를 저장하면 상태 수에 비례한 계산으로 줄어든다. 그러나 DP의 핵심은 단순 Cache가 아니라 문제를 올바른 상태와 점화식으로 표현하는 것이다.

## 2. DP가 성립하는 구조

### 겹치는 부분 문제

재귀적으로 문제를 풀 때 같은 입력 상태가 여러 번 등장한다. 결과를 저장하면 반복 작업을 제거할 수 있다. 모든 분할 정복이 DP인 것은 아니다. Merge Sort의 왼쪽과 오른쪽 부분 문제는 보통 겹치지 않아 Memoization 이득이 없다.

### 최적 부분 구조

큰 문제의 최적해가 작은 부분 문제의 최적해로 구성된다. 예를 들어 제한된 Capacity에서 최대 가치를 구할 때 마지막 물건을 선택했는지에 따라 더 작은 Capacity의 최적값을 사용한다.

최적 부분 구조는 Greedy에도 등장하지만 DP는 하나의 현재 선택을 즉시 확정하지 않는다. 가능한 상태와 전이의 결과를 비교한다.

## 3. DP 설계의 다섯 단계

```text
1. State 정의
      ↓
2. Transition·점화식
      ↓
3. Base Case
      ↓
4. 계산 순서·구현 방식
      ↓
5. 정답 위치와 복잡도
```

### 상태 정의

상태는 “이 값이 무엇을 의미하는가”를 문장으로 설명해야 한다.

```text
dp[i] = i번째 단계까지 도달하는 최소 비용
dp[i][w] = 앞의 i개 물건만 고려하고 Capacity w일 때 최대 가치
```

상태가 미래 결정을 위한 정보를 빠뜨리면 서로 다른 상황을 같은 칸에 합쳐 오답이 난다. 반대로 불필요한 정보까지 넣으면 차원이 늘어 Memory와 시간이 폭증한다.

### 점화식

현재 상태가 어떤 이전 상태와 선택으로 만들어지는지 정의한다. 최소·최대·경우의 수 등 목적에 따라 `min`, `max`, 합을 사용한다.

### 초기값

가장 작은 문제와 도달 불가능 상태를 정의한다. 최솟값 DP에서 모든 칸을 0으로 두면 “비용 0으로 도달 가능”하다는 잘못된 의미가 될 수 있어 충분히 큰 INF를 사용한다.

### 계산 순서

현재 상태가 참조하는 이전 상태가 먼저 계산되어야 한다. Top-down 재귀는 의존 순서를 호출이 해결하지만, Bottom-up은 Loop 방향을 직접 정해야 한다.

### 정답 위치

정답이 `dp[n]`인지, 마지막 행의 최댓값인지, 모든 종료 상태의 최소인지 확인한다. DP Table을 채웠다고 문제가 끝난 것은 아니다.

## 4. 쉬운 예시: 계단 오르기

한 번에 1칸 또는 2칸 이동해 `n`번째 칸에 도달하는 방법 수를 구해 보자.

```text
dp[i] = i번째 칸에 도달하는 방법 수

마지막 이동이 1칸: dp[i-1]
마지막 이동이 2칸: dp[i-2]

dp[i] = dp[i-1] + dp[i-2]
dp[0] = 1
dp[1] = 1
```

`dp[0]=1`은 아무것도 하지 않는 한 가지 방법을 뜻한다. 이런 의미를 먼저 정하면 초기값을 암기하지 않아도 된다.

```text
i:       0  1  2  3  4  5
dp[i]:   1  1  2  3  5  8
```

게임 서버에서 행동력 1 또는 2를 소모해 n번째 퀘스트에 도달하는 경로 수를 구하는 구현이다.

```java
// 행동력 1 또는 2를 소모해 퀘스트 n번에 도달하는 경로 수
int countQuestPaths(int n) {
    if (n <= 1) return 1;
    int[] dp = new int[n + 1];
    dp[0] = 1; // 시작 상태: 소모 없이 출발 지점, 경우 1가지
    dp[1] = 1;
    for (int i = 2; i <= n; i++) {
        dp[i] = dp[i - 1] + dp[i - 2]; // 행동력 1 또는 2 소모 이동
    }
    return dp[n];
}
```

상태 `n+1`개를 각각 O(1)에 계산하므로 시간 O(n), 배열 공간 O(n)이다. 직전 두 값만 필요하므로 변수 두 개로 보조 공간을 O(1)로 줄일 수 있다.

## 5. Top-down Memoization

원래 재귀 구조를 유지하고 상태 결과를 Cache한다.

```csharp
long Solve(int i)
{
    if (i <= 1) return 1;
    if (computed[i]) return memo[i];

    computed[i] = true;
    memo[i] = Solve(i - 1) + Solve(i - 2);
    return memo[i];
}
```

### 장점

- 점화식을 재귀 형태로 자연스럽게 옮길 수 있다.
- 시작 상태에서 실제로 도달하는 상태만 계산한다.
- 상태 의존 순서를 직접 정하기 어려울 때 편하다.

### 단점

- 재귀 호출과 Function Frame 비용이 있다.
- 깊이가 크면 Stack Overflow가 날 수 있다.
- Cache 미계산 표시와 유효 값이 충돌하지 않게 해야 한다.

결과가 0이나 -1일 수 있는데 해당 값을 “미계산” Sentinel로 쓰면 상태를 반복 계산하거나 오답이 난다. 별도 `computed` 배열 또는 구분 불가능하지 않은 Sentinel을 사용한다.

## 6. Bottom-up Tabulation

작은 상태부터 Table을 채운다.

```csharp
long Climb(int n)
{
    if (n <= 1) return 1;

    long[] dp = new long[n + 1];
    dp[0] = 1;
    dp[1] = 1;

    for (int i = 2; i <= n; i++)
        dp[i] = dp[i - 1] + dp[i - 2];

    return dp[n];
}
```

### 장점

- 재귀 Stack이 없고 반복문이라 상수 비용이 작다.
- 계산 순서와 Memory Layout을 통제하기 쉽다.
- Rolling Array 같은 공간 최적화가 명확하다.

### 단점

- 실제로 필요하지 않은 상태까지 모두 계산할 수 있다.
- 복잡한 의존 관계의 순서를 잘못 정하면 미계산 값을 읽는다.

Top-down과 Bottom-up은 본질적으로 같은 상태 Graph를 다른 순서로 평가한다. 하나가 항상 더 우수한 것은 아니다.

## 7. 시간·공간 복잡도 분석

DP의 시간 복잡도는 보통 다음으로 계산한다.

```text
시간 = 계산하는 상태 수 × 상태 하나당 전이 수
공간 = 저장하는 상태 수 + 재귀 Stack·보조 자료구조
```

`dp[i][w]`가 `n × W`개이고 각 상태에서 선택·미선택 두 전이를 O(1)에 비교하면 시간 O(nW), 공간 O(nW)다.

이 O(nW)는 입력 값 W에 비례한다. W가 Binary로 주어질 때 입력 비트 길이는 log W이므로 엄밀히 다항 시간이라고 부르기 어려워 Pseudo-polynomial이라고 한다. Capacity가 10⁹이면 O(nW)는 현실적으로 불가능하다.

Top-down은 도달 상태가 적으면 전체 Table보다 적게 계산할 수 있지만 최악에는 같은 상태 수를 방문한다. Hash Map Memo를 사용하면 배열보다 유연하지만 Hash와 Allocation 비용이 있다.

## 8. 0/1 Knapsack

각 물건을 최대 한 번 선택하고 총 무게가 Capacity `W`를 넘지 않게 최대 가치를 구한다.

```text
dp[i][w] = 앞의 i개 물건만 고려하고 Capacity w일 때 최대 가치

물건 i를 선택하지 않음: dp[i-1][w]
선택 가능할 때 선택:     dp[i-1][w-weight[i]] + value[i]

dp[i][w] = max(두 선택)
```

```text
             선택 안 함
dp[i][w]  ←  dp[i-1][w]
   ↑
   └──── dp[i-1][w-weight] + value  선택
```

시간 O(nW), 공간 O(nW)다. 현재 행은 이전 행만 참조하므로 2개 행 O(W)로 줄일 수 있다. 더 나아가 1차원 배열 하나를 사용할 수 있다.

```csharp
for (int i = 0; i < n; i++)
{
    for (int w = capacity; w >= weight[i]; w--)
    {
        dp[w] = Math.Max(dp[w],
                         dp[w - weight[i]] + value[i]);
    }
}
```

Capacity를 큰 값부터 역순으로 순회하는 이유는 같은 물건을 이번 Iteration에서 갱신한 값으로 다시 사용하지 않기 위해서다. 작은 값부터 순회하면 물건 하나를 여러 번 고를 수 있어 Unbounded Knapsack 의미가 된다.

```text
0/1 Knapsack:     w를 큰 쪽 → 작은 쪽
Unbounded:        w를 작은 쪽 → 큰 쪽
```

Loop 방향이 문제의 선택 가능 횟수를 표현한다.

## 9. 최솟값 DP와 INF

최소 비용을 구할 때 도달 불가능 상태를 INF로 초기화한다.

```text
dp[start] = 0
나머지 dp = INF

dp[next] = min(dp[next], dp[current] + cost)
```

`INF + cost`가 Overflow해 작은 음수가 되지 않도록 현재 상태가 INF인지 먼저 확인하거나 충분히 넓은 정수형을 사용한다. INF를 자료형 최댓값 그대로 두고 더하는 것은 위험하다.

경우의 수 DP는 값이 매우 커질 수 있다. 문제에서 Modulo를 요구하면 덧셈·곱셈마다 적용하고, 정확한 큰 수가 필요하면 Big Integer 또는 Overflow 정책을 정한다.

## 10. 상태 설계의 충분성과 최소성

상태는 과거 전체를 저장하지 않고 미래 결정에 필요한 요약만 담아야 한다.

예를 들어 “연속으로 같은 Skill을 사용할 수 없다”면 현재 단계 `i`만으로는 다음 선택을 결정할 수 없다. 마지막에 사용한 Skill도 상태에 포함해야 한다.

```text
불충분: dp[i]
충분:   dp[i][lastSkill]
```

반대로 미래에 영향을 주지 않는 전체 선택 순서를 상태에 넣으면 동일한 상황이 서로 다른 상태로 분리되어 DP 이점이 사라진다.

두 경로가 앞으로 완전히 같은 선택지와 비용을 가진다면 같은 상태로 합칠 수 있다. 상태 설계는 “미래 관점에서 두 상황을 구분해야 하는가?”라는 질문으로 검증한다.

## 11. 계산 순서와 Dependency Graph

DP 상태를 Vertex, 의존 관계를 Edge로 보면 계산 순서는 의존 Graph의 위상 순서다. Cycle 없는 의존이어야 일반적인 단일 평가가 가능하다.

Grid에서 `dp[r][c]`가 위와 왼쪽만 참조하면 행·열 증가 순으로 채운다. 오른쪽과 아래를 참조하는데 같은 순서를 쓰면 아직 계산하지 않은 값을 읽는다.

```text
dp[r][c] ← dp[r-1][c], dp[r][c-1]

위 행 먼저, 같은 행의 왼쪽 Cell 먼저 계산
```

상태 전이에 Cycle이 있고 비용을 반복 Relax해야 한다면 단순 DP가 아니라 Graph 최단 경로나 고정점 계산 문제일 수 있다.

## 12. 정답 경로 복원

최적값만 저장하면 어떤 선택으로 그 값이 만들어졌는지 알 수 없다. 실제 Item 목록이나 Skill 순서가 필요하면 선택 정보를 저장한다.

```text
choice[i][w] = TAKE 또는 SKIP
```

마지막 상태부터 Choice를 따라가며 역추적한다. 공간 최적화로 이전 행을 버리면 복원 정보도 사라질 수 있다. 값만 필요한지 실제 경로도 필요한지에 따라 Memory 최적화 가능 범위가 달라진다.

전체 Choice Table 대신 최적값을 다시 계산하며 복원하거나 Divide-and-Conquer 기법을 쓸 수 있지만 구현 복잡도와 시간이 늘어난다.

## 13. DP와 다른 방식 비교

| 방식 | 핵심 | 적합한 조건 | 주요 위험 |
|---|---|---|---|
| Greedy | 현재 선택 확정 | 안전한 선택 증명 | 반례 시 오답 |
| DP | 상태별 결과 저장 | 겹치는 부분 문제 | 상태 폭발 |
| Backtracking | 선택·복구 탐색 | 입력 작음, 모든 해 | 지수 시간 |
| Divide and Conquer | 독립 부분 문제 결합 | 부분 문제가 거의 안 겹침 | 중복 시 비효율 |

DP로 풀 수 있다고 항상 DP가 최선은 아니다. Greedy 증명이 가능하면 더 단순하고 빠를 수 있고, 상태 공간이 너무 크지만 입력이 작으면 Pruning이 좋은 Backtracking이 나을 수 있다.

## 14. 게임 서버·백엔드 실무 예시

### 행동력으로 최대 보상 선택

하루 행동력 `W` 안에서 각 Dungeon을 한 번만 돌 수 있고 비용과 보상이 있다면 0/1 Knapsack으로 모델링할 수 있다. 하지만 선행 Quest, Party 조건, 시간대가 추가되면 상태 차원이 늘어나며 단순 Knapsack이 아니다.

```text
State: 고려한 Dungeon 수, 남은 행동력
Transition: Skip / Play
Goal: 총 보상 최대
```

Capacity가 작고 콘텐츠 설정이 고정이면 서버 요청마다 계산하지 않고 배포 시 사전 계산할 수 있다. 결과 Table에 설정 Version을 붙여 잘못된 버전의 Cache 사용을 막는다.

### Upgrade 비용 Table

Level별 Upgrade 경로가 여러 개이고 미래 비용이 현재 선택에만 의존한다면 최소 비용 DP를 사용할 수 있다. 실제 결제·확률 결과를 결정하는 Online Transaction에 거대한 DP를 실행하기보다 설정 검증과 추천 계산을 Offline Worker로 분리한다.

### 실시간 운영 고려

DP는 입력 크기 경계에서 Memory가 갑자기 커질 수 있다. `n`, Capacity, 상태 차원별 상한을 두고 요청이 넘으면 거절하거나 근사 Heuristic, 제한된 후보만 사용한다.

상태 수, 계산 상태 비율, Table Byte, 실행 시간, Cache Hit와 p99를 측정한다. 공용 Memo Cache는 Key에 모든 입력 조건과 콘텐츠 Version을 포함해야 한다. 누락하면 다른 문제의 결과를 재사용하는 정합성 Bug가 생긴다.

## 15. 장점과 단점

### 장점

- 중복 부분 문제를 한 번씩 계산해 지수 재귀를 크게 줄일 수 있다.
- 최적값, 경우의 수, 가능 여부 등 다양한 목적을 표현한다.
- 점화식과 상태가 명확하면 정당성과 복잡도를 체계적으로 분석할 수 있다.
- 의존 범위가 작으면 Rolling Array로 공간을 줄일 수 있다.

### 단점

- 상태 정의가 어렵고 정보 누락은 조용한 오답을 만든다.
- 차원이 늘면 상태 수의 곱으로 시간과 Memory가 폭증한다.
- Top-down은 Stack, Bottom-up은 불필요 상태 계산 위험이 있다.
- 공간 최적화가 경로 복원과 Debug를 어렵게 할 수 있다.
- 입력 값에 비례하는 Pseudo-polynomial Algorithm은 큰 값에 부적합하다.

## 16. 자주 하는 오해

- **재귀에 Cache를 붙이면 모두 DP다**: 겹치는 상태와 올바른 상태 정의·점화식이 필요하다.
- **DP는 항상 O(n)이다**: 상태 수와 상태당 전이 수에 따라 달라진다.
- **Top-down이 항상 상태를 적게 계산한다**: 모든 상태가 도달 가능하면 Bottom-up과 같다.
- **0으로 초기화하면 안전하다**: 도달 불가능, 실제 0, 미계산 상태가 구분되지 않을 수 있다.
- **1차원 Knapsack은 Loop 방향과 무관하다**: 방향이 같은 Item 재사용 여부를 바꾼다.
- **공간을 O(W)로 줄여도 항상 해를 복원할 수 있다**: Choice 정보가 사라질 수 있다.
- **O(nW)는 항상 다항 시간이다**: W의 숫자 값에 비례하는 Pseudo-polynomial이다.
- **상태에 정보를 많이 넣을수록 정확하다**: 불필요한 차원은 상태 폭발을 만든다.

## 17. 면접 질문

### Q1. 게임 서버 행동력 기반 콘텐츠 추천에서 상태, 점화식, 초기값을 어떻게 설계하는가?

하루 행동력 `W`와 Dungeon 목록이 있을 때 `dp[i][w]`를 "i번째까지 고려하고 남은 행동력 w일 때 최대 보상"으로 정의합니다. 점화식은 `dp[i][w] = max(dp[i-1][w], dp[i-1][w-cost[i]] + reward[i])`이고, 초기값은 `dp[0][w] = 0`(아무 Dungeon도 고려하지 않으면 보상 0)입니다. 콘텐츠 설정이 자주 바뀌지 않으면 배포 시 사전 계산 후 Cache Key에 설정 Version과 행동력 상한을 포함해 정합성을 보장합니다.

### Q2. Top-down Memoization 적용 중 Stack Overflow가 발생했을 때 Tabulation으로 전환하는 방법과 주의사항은?

재귀 깊이가 상태 수에 비례해 JVM Stack 한계를 초과할 때 Bottom-up Tabulation으로 전환합니다. 전환 절차는 ① 상태 의존 방향을 파악해 Loop 순서를 결정하고, ② Memo 배열을 Table로 교체하며, ③ 재귀 호출을 Loop 내 점화식으로 대체하는 것입니다. 주의사항은 Base Case와 INF 초기값이 그대로 유효한지 확인하는 것입니다. Top-down에서 필요한 상태만 계산하던 부분이 Bottom-up에서 전체 Table을 채우도록 바뀌므로 메모리 사용이 늘 수 있고, 도달 불가능 상태에 대한 오답 가능성도 재검증이 필요합니다.

### Q3. 행동력 W=5,000, Dungeon 수 n=100인 요청이 실시간으로 들어올 때 O(nW) DP를 요청 경로에서 실행하는 것이 타당한지 판단하는 기준과 사전 계산으로 분리하는 시점은?

O(nW) = 500,000 연산이므로 단일 요청에서 계산 자체는 빠르지만 동시 접속 규모에 따라 달라집니다. 판단 기준은 ① 콘텐츠 설정(비용·보상 테이블)이 얼마나 자주 바뀌는지, ② 요청당 W 값이 고정인지 사용자마다 다른지, ③ p99 목표 Latency 내 계산이 가능한지입니다. 설정이 배포 단위로만 바뀌고 W 상한이 고정이라면 배포 시 사전 계산 후 결과를 Cache에 저장하고 Key에 설정 Version과 W 값을 포함합니다. 반면 퀘스트 선행 조건이나 Party 상태처럼 사용자별로 상태 공간이 달라지면 사전 계산이 어려워 요청 경로에서 계산하되 상태 수와 실행 시간 상한을 두고 초과 시 근사 Heuristic으로 Fallback합니다.

### Q4. 행동력 소모형 Dungeon 추천을 1차원 배열로 구현했는데, 같은 Dungeon이 여러 번 선택되는 버그가 보고됐습니다. 코드를 보지 않고 Loop 방향만으로 원인을 어떻게 진단하고 수정하나요?

같은 Dungeon이 여러 번 선택된다면 Capacity를 오름차순(작은 쪽→큰 쪽)으로 순회하고 있을 가능성이 높습니다. 이 방향에서는 같은 Iteration 안에서 이미 현재 Dungeon으로 갱신된 작은 Capacity 값을 큰 Capacity 계산에 다시 사용하게 되어 Unbounded Knapsack처럼 동작합니다. 0/1 제약을 지키려면 Capacity를 내림차순(큰 쪽→작은 쪽)으로 순회해야 합니다. 역순에서는 `dp[w-cost]`가 현재 Dungeon 적용 이전 값이므로 이번 Iteration에서 같은 Dungeon을 두 번 선택하는 일이 없습니다. 수정 후 Capacity별 최적 Dungeon 목록을 역추적해 중복 선택 항목이 사라지는지 확인합니다.

### Q5. 연속으로 같은 Skill을 사용할 수 없다는 조건이 추가됐을 때 dp[i]만으로 오답이 나는 이유를 진단하고, 충분한 상태를 재정의하는 절차는?

`dp[i]`는 i번째 단계에서 얻은 보상만 표현하므로 다음 선택 가능 여부를 결정하는 "직전에 사용한 Skill" 정보가 없습니다. 결과적으로 연속 금지 조건을 위반한 경로와 합법 경로가 같은 칸에 합쳐져 오답이 납니다. 재정의 절차는 ① "미래 선택에 영향을 주는 정보가 무엇인가"를 묻고, ② 그 정보를 상태에 추가해 `dp[i][lastSkill]`로 확장하며, ③ 점화식에서 `lastSkill == currentSkill`이면 전이를 막는 조건을 추가하는 것입니다. 추가 차원이 Skill 종류 수 S라면 상태는 O(n × S)가 되므로 S가 크면 Memory 폭증 여부를 확인해야 합니다.

### Q6. Knapsack DP를 공간 O(W)로 최적화한 뒤 "어떤 Dungeon을 골랐는지" 목록이 필요하다는 요구사항이 추가됐습니다. 1차원 배열만으로 복원이 불가능한 이유와 서버 운영 중 요구사항을 충족하기 위한 트레이드오프 선택지는 무엇인가요?

1차원 배열은 이전 행(Item i-1 상태)을 덮어쓰기 때문에 특정 Capacity에서 Item i를 선택했는지 판단할 근거가 사라집니다. 복원 선택지는 세 가지입니다. 첫째, 2차원 `choice[i][w]` 테이블을 함께 유지하면 복원이 간단하지만 공간이 O(nW)로 되돌아갑니다. 둘째, 복원이 필요할 때만 2차원으로 다시 계산하면 요청 빈도가 낮을 때 평시 메모리를 아낄 수 있지만 복원 요청마다 O(nW) 재계산 비용이 발생합니다. 셋째, Hirschberg 분할 정복 기법을 사용하면 공간 O(W)를 유지하면서 경로를 복원할 수 있지만 구현 복잡도가 높아 버그 위험이 있습니다. 게임 서버에서는 복원이 필요한 경우가 콘텐츠 추천·디버깅 용도로 드물다면 두 번째 방법, 실시간 경로 표시가 매 요청마다 필요하다면 첫 번째 방법을 선택하고 Memory 상한을 별도로 관리합니다.

## 18. 예상 꼬리질문

- 행동력 DP에서 VIP 플레이어는 행동력 소모가 반감된다는 조건이 추가될 때 기존 `dp[i][w]` 상태만으로 정확한 결과를 보장할 수 없는 이유와 상태를 어떻게 확장해야 하는지 판단하는 기준은 무엇인가?
- 최솟값 DP에서 특정 Dungeon 도달 비용이 0이 정상 값인데 0으로 초기화하면 미계산 상태와 구분이 안 되는 버그가 생겼습니다. 실무에서 이 문제를 어떻게 처리하나요?
- `INF + cost` Overflow로 음수가 되면서 잘못된 최솟값이 선택되는 버그를 재현하는 최소 입력을 어떻게 설계하고 방어 코드는 어떻게 작성하나요?
- Top-down Memoization에서 재귀 깊이가 n=100,000 상태에 달해 Stack Overflow가 발생했을 때 Bottom-up 전환 이외에 JVM 스택 크기 조정과 Trampoline 방식 중 운영 환경에서 어떤 기준으로 선택하나요?
- Dungeon Capacity가 W=10⁹로 설정된 요청이 들어왔을 때 O(nW) DP를 그대로 실행하면 서버에 어떤 영향이 생기고, 입력 Capacity 상한을 강제하지 않는 구현의 위험을 어떻게 탐지하나요?
- 2차원 Knapsack 배열을 Rolling Array로 줄이면 메모리가 절반으로 줄지만 경로 복원이 불가능해지는 시나리오에서 콘텐츠 추천 로그 요구사항을 어떻게 충족하나요?
- 콘텐츠 설정 Version 없이 Memo Cache Key를 Capacity만으로 구성했다가 설정 핫픽스 배포 후 이전 결과가 캐시에서 반환되는 장애가 발생했습니다. Cache Key 구성 요소를 어떻게 설계해야 이 문제를 방지할 수 있나요?

## 19. 30초 모범답변

> DP는 겹치는 부분 문제의 답을 상태별로 저장하고 점화식으로 큰 문제를 구성합니다. 행동력 기반 Dungeon 추천을 예로 들면 `dp[i][w]`를 "i번째까지 고려하고 남은 행동력 w일 때 최대 보상"으로 정의하고, 점화식은 Skip/Play 선택 중 최대를 취합니다. 상태 차원이 커지면 시간과 Memory가 폭증하므로 콘텐츠 설정이 고정일 때는 배포 시 사전 계산하고 Cache Key에 설정 Version을 포함해 정합성을 보장합니다.

## 20. 1~2분 확장답변

> Dynamic Programming은 같은 부분 문제가 반복되고 큰 문제의 최적해가 부분 문제의 최적해로 구성될 때 사용합니다. 설계에서는 `dp[state]`의 의미를 문장으로 정의한 뒤 현재 상태가 어떤 이전 상태와 선택에서 오는지 점화식을 만들고 Base Case와 계산 순서를 정합니다. 복잡도는 계산 상태 수와 상태당 전이 수의 곱입니다.
>
> Top-down은 재귀와 Memoization으로 도달 상태만 계산하지만 Stack Overflow와 호출 비용이 있고, Bottom-up은 반복문으로 전체 Table을 채워 Memory Layout과 Rolling Array 최적화가 쉽습니다. 0/1 Knapsack은 O(nW)이며 1차원으로 줄일 때 같은 물건을 중복 사용하지 않도록 Capacity를 역순으로 순회합니다. 게임 서버에서는 행동력 기반 보상 추천 같은 문제에 적용할 수 있지만 큰 상태 공간을 요청 경로에서 계산하기보다 사전 계산하고 콘텐츠 Version과 Memory 상한, Timeout·Fallback을 관리하는 편이 안전합니다.

## 21. 핵심 요약

- DP는 겹치는 부분 문제의 결과를 저장해 반복 계산을 제거한다.
- 상태는 미래에 필요한 정보를 충분히 담되 불필요한 과거는 제거한다.
- 상태 정의, 점화식, 초기값, 계산 순서, 정답 위치를 순서대로 설계한다.
- Top-down은 필요한 상태, Bottom-up은 반복 실행과 공간 최적화에 강점이 있다.
- 시간은 상태 수×전이 수, 공간은 저장 상태와 Stack·보조 구조로 계산한다.
- 0/1 Knapsack의 1차원 최적화는 Capacity를 역순으로 순회한다.
- INF·경우의 수 Overflow, 미계산 Sentinel과 경로 복원을 주의한다.
- 상태 폭발과 Pseudo-polynomial 비용에는 상한·사전 계산·Fallback이 필요하다.

## 한 줄 정리

> DP의 핵심은 답을 저장하는 행위가 아니라 미래를 결정할 최소 상태와 올바른 전이를 설계하는 것이다.
