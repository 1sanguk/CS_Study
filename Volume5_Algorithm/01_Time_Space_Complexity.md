# 01. Time·Space Complexity

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 입력 크기에 따른 시간·공간 증가율을 설명할 수 있다.
- Big-O·Theta·Omega와 최악·평균·분할 상환 분석을 구분할 수 있다.
- 반복문, 재귀, 자료구조 연산의 복잡도를 계산할 수 있다.
- 게임 서버의 Tick·요청 Budget에서 복잡도와 실제 측정을 함께 적용할 수 있다.

## 1. 개요

시간 복잡도는 입력 크기 `n`이 증가할 때 알고리즘이 수행하는 기본 연산 수의 증가율이다. 공간 복잡도는 실행 중 필요한 메모리가 입력에 따라 얼마나 증가하는지를 나타낸다.

복잡도는 특정 CPU에서 몇 ms가 걸리는지를 직접 말하지 않는다. 하드웨어와 언어, 작은 상수의 영향을 줄이고 입력이 커졌을 때 어떤 알고리즘이 더 잘 확장되는지 비교하는 도구다.

```text
n이 2배가 될 때 대략적인 증가

O(1)      변화 없음
O(log n)  한 단계 정도 증가
O(n)      2배
O(n log n) 2배보다 조금 큼
O(n²)     4배
O(2ⁿ)     입력 1 증가마다 약 2배
```

게임 서버에서는 평균 처리량뿐 아니라 한 Tick을 넘기는 최악 입력이 중요한 경우가 많다. Big-O 분석과 실제 p95·p99 측정을 함께 사용해야 한다.

## 2. 왜 필요한가

작은 테스트에서는 모든 플레이어 쌍을 비교하는 코드도 빠르다. 하지만 플레이어 수가 10배가 되면 `O(n²)` 비교 횟수는 약 100배가 된다. 부하가 늘어난 뒤에야 구조를 바꾸면 장애와 큰 재작업이 생긴다.

복잡도 분석은 다음 질문에 답하는 데 도움을 준다.

- 입력 상한에서 시간 제한을 만족할 수 있는가?
- 데이터가 10배 증가하면 비용이 어느 정도 늘어나는가?
- 시간을 줄이기 위해 어느 정도의 추가 메모리를 사용할 것인가?
- 평균은 빠르지만 최악 입력에서 Tick을 막는가?
- 최적화할 부분이 Algorithm인지 I/O·Lock·Allocation인지?

복잡도는 정당성을 대신하지 않는다. 빠른 오답 Algorithm은 의미가 없다. 먼저 결과가 맞는 이유와 전제 조건을 확인하고, 그 다음 비용을 분석한다.

## 3. 입력 크기와 기본 연산

분석을 시작할 때 `n`이 무엇인지 정의한다. 배열 원소 수, Graph Vertex 수 `V`와 Edge 수 `E`, 문자열 길이 `L`, Grid의 행 `R`과 열 `C`처럼 입력이 여러 축일 수 있다.

```text
for each player:             n = player 수
for each graph neighbor:     V와 E를 함께 사용
for each cell in grid:       R × C
compare two strings:         문자열 길이 L의 영향
```

Hash Map 조회를 O(1)이라고 해도 긴 문자열 Key의 Hash를 처음 계산하는 데 O(L)이 들 수 있다. 비교 대상과 비용 Model을 명확히 해야 한다.

기본 연산은 비교, 덧셈, 배열 접근처럼 일정한 비용으로 가정하는 연산이다. 실제로는 Cache Miss와 I/O가 훨씬 비쌀 수 있지만 증가율 분석에서는 단순화한다.

## 4. Big-O, Theta, Omega

- **Big-O**: 충분히 큰 `n`에서 어떤 함수보다 빠르게 증가하지 않는다는 점근적 상한이다.
- **Big-Omega(Ω)**: 충분히 큰 `n`에서 어떤 함수보다 느리게 증가하지 않는다는 하한이다.
- **Big-Theta(Θ)**: 상한과 하한이 같은 증가율인 Tight Bound다.

선형으로 배열 전체를 반드시 한 번 순회하는 Algorithm은 `Θ(n)`이다. `Θ(n)`이면 `O(n²)`도 수학적으로 참이지만 너무 느슨해 유용하지 않다. 실무와 면접에서는 가능한 Tight한 상한을 말하는 관습이 있어 Big-O를 사실상 대표 증가율처럼 사용하는 경우가 많다.

Big-O와 최악 시간은 같은 개념이 아니다. Big-O는 함수 증가율의 상한 표기이고, 최악·평균·최선은 어떤 입력 집합의 비용을 분석하는지에 대한 구분이다. “평균 시간 O(n)”과 “최악 시간 O(n²)”처럼 함께 쓸 수 있다.

## 5. 상수와 낮은 차수 제거

`3n² + 10n + 20`은 `n`이 커질수록 `n²` 항이 지배하므로 `O(n²)`로 표현한다. 상수 계수와 낮은 차수 항을 제거한다.

```text
O(2n)          → O(n)
O(n² + n)      → O(n²)
O(500)         → O(1)
```

이것이 상수가 중요하지 않다는 뜻은 아니다. 동일한 `O(n)` Algorithm도 한 원소마다 Network I/O를 수행하는 것과 정수 덧셈 한 번은 실제 시간이 매우 다르다. Big-O는 큰 입력의 증가율 비교이고 실제 선택에는 상수와 Memory 접근을 다시 포함한다.

## 6. 반복문 분석

### 연속된 반복문은 더한다

```text
for i = 0 .. n-1: work()    // O(n)
for j = 0 .. n-1: work()    // O(n)

O(n + n) = O(n)
```

연속 실행은 비용을 합친 뒤 지배 항을 남긴다. 두 반복문이 있다고 무조건 `O(n²)`은 아니다.

### 중첩 반복문은 곱한다

```text
for i = 0 .. n-1:
    for j = 0 .. n-1:
        compare(i, j)

O(n × n) = O(n²)
```

두 입력 크기가 다르면 `O(nm)`으로 유지한다. 플레이어 `n`명과 Monster `m`마리를 모두 비교하는 비용을 성급히 `O(n²)`로 바꾸지 않는다.

### 반복 범위를 합으로 센다

```text
for i = 0 .. n-1:
    for j = i+1 .. n-1:
        compare(i, j)
```

반복 횟수는 `(n-1) + (n-2) + ... + 1 = n(n-1)/2`이므로 `Θ(n²)`이다. 삼각형 형태라고 차수가 줄지는 않는다.

### 입력을 나누면 Logarithm이다

```text
while n > 1:
    n = n / 2
```

`n`을 몇 번 2로 나누면 1이 되는지가 반복 횟수이므로 `O(log₂ n)`이다. Big-O에서는 Log 밑이 상수 배 차이이므로 보통 `O(log n)`이라고 쓴다. Binary Search와 균형 Tree 높이가 대표적이다.

## 7. 조건문과 Early Exit

조건문은 가능한 Branch 중 비용이 가장 큰 경로를 기준으로 최악 시간을 분석한다.

```text
if condition:
    linearWork(n)     // O(n)
else:
    sort(n)           // O(n log n)

최악: O(n log n)
```

선형 검색은 첫 원소에서 찾으면 최선 `O(1)`, 마지막이나 실패하면 최악 `O(n)`이다. 평균을 말하려면 찾는 위치와 성공 확률에 대한 입력 분포 가정이 필요하다. 근거 없이 “보통 중간에서 찾으니 O(n/2), 즉 O(n)”이라고만 말하면 평균 Case의 전제가 빠진다.

Early Exit은 실제 평균 시간을 크게 줄일 수 있지만 최악 상한이 바뀌지 않을 수 있다. 실시간 서버에서는 평균과 최악을 둘 다 기록한다.

## 8. 재귀 복잡도

재귀는 호출 횟수와 각 호출의 작업, 호출 Stack 깊이를 함께 본다.

### 선형 재귀

```text
f(n):
    if n == 0: return
    work O(1)
    f(n-1)
```

호출 `n`개이므로 시간 `O(n)`, 호출 Stack 공간 `O(n)`이다. 반복문으로 바꾸면 시간은 같고 추가 Stack 공간을 `O(1)`로 줄일 수 있다.

### 분할 정복

Merge Sort는 입력을 절반으로 나눈 두 재귀 호출과 합치는 O(n) 작업을 한다.

```text
T(n) = 2T(n/2) + O(n)

Level 수: log n
각 Level의 총 병합 작업: O(n)
전체: O(n log n)
```

Binary Search는 절반 중 한쪽만 재귀 호출하므로 `T(n)=T(n/2)+O(1)=O(log n)`이다.

### 중복 재귀

단순 Fibonacci `f(n)=f(n-1)+f(n-2)`는 같은 상태를 반복 계산해 호출 수가 지수적으로 증가한다. Memoization을 사용하면 상태 `n`개를 한 번씩 계산해 시간 O(n), 저장 공간 O(n)으로 바꿀 수 있다.

## 9. 평균·최악·분할 상환

### 최악 복잡도

허용 입력 중 가장 비용이 큰 경우다. SLA와 Tick Deadline처럼 상한이 중요한 시스템에서 중요하다. 단순 BST는 평균적으로 균형에 가까울 수 있어도 정렬 입력에서 최악 O(n)이다.

### 평균 복잡도

입력 분포에 대한 기대 비용이다. Hash Table의 평균 O(1)은 Hash가 Key를 Bucket에 고르게 분산한다는 전제가 있다. 실제 Traffic이 이 전제와 다르면 측정 결과도 달라진다.

### 분할 상환 복잡도

연속된 여러 연산 전체 비용을 연산 수로 나눈 상한이다. Dynamic Array Push는 대부분 O(1)이지만 Capacity 확장 시 O(n) 복사가 발생한다. Capacity를 배수로 늘리면 `m`번 Push의 총 복사가 O(m)이어서 한 번당 분할 상환 O(1)이다.

분할 상환은 확률적 평균이 아니다. 특정 입력 분포를 가정하지 않고 연산 Sequence 전체 비용을 분석한다. 또한 개별 연산의 지연 상한이 O(1)이라는 뜻도 아니다. 실시간 경로에서는 드문 재할당 O(n)도 문제가 될 수 있어 미리 Reserve할 수 있다.

## 10. 공간 복잡도

공간 복잡도는 입력 저장 공간을 포함하는지, Algorithm이 추가로 사용하는 보조 공간(Auxiliary Space)만 말하는지 구분한다.

- In-place 배열 역전: 보조 공간 O(1)
- Merge Sort: 병합 Buffer O(n), 재귀 Stack O(log n)
- BFS: 방문 배열과 Queue O(V)
- DFS: 방문 배열 O(V), 재귀 Stack 최악 O(V)
- Memoization: 상태 Cache O(n)

재귀 호출 Stack도 Memory다. 매우 깊은 Graph를 재귀 DFS하면 시간은 O(V+E)여도 Stack Overflow가 날 수 있다. 명시적 Stack도 O(V) 공간을 쓰지만 Heap에 두고 Capacity를 통제하기 쉽다.

Bitset, Streaming 처리, Rolling Array로 공간을 줄일 수 있지만 시간이나 구현 복잡도가 늘 수 있다. 시간-공간 Trade-off를 명시한다.

## 11. 대표 증가율과 현실적 크기

| 복잡도 | 예시 | 입력 증가 시 특징 |
|---|---|---|
| O(1) | 배열 Index, Heap Top | n과 무관한 단계 수 |
| O(log n) | Binary Search | 매우 완만하게 증가 |
| O(n) | 전체 순회 | 입력에 비례 |
| O(n log n) | 효율적 비교 정렬 | 큰 입력에서도 흔히 실용적 |
| O(n²) | 모든 쌍 비교 | n 증가에 빠르게 악화 |
| O(2ⁿ) | 부분집합 완전 탐색 | 작은 n만 가능 |
| O(n!) | 모든 순열 | 매우 작은 n만 가능 |

이 표만으로 시간 제한을 단정할 수는 없다. `n=10⁶`의 단순 정수 순회와 `n=10⁵`의 DB 호출은 전혀 다르다. Algorithm 내부가 CPU 연산인지 Allocation·Lock·Disk·Network인지 확인한다.

## 12. 게임 서버·백엔드 실무 예시

### 모든 플레이어 쌍 충돌 검사

플레이어 `n`명을 이중 반복해 거리 비교하면 O(n²)이다.

```text
n=100   → 약 4,950쌍
n=1,000 → 약 499,500쌍
```

Grid나 Spatial Hash로 공간을 나누고 같은 Cell과 인접 Cell만 검사하면 후보 수를 줄일 수 있다. 평균적으로 크게 개선되지만 한 Cell에 모두 몰리는 최악 Case는 여전히 O(n²)일 수 있다. Cell당 상한, 넓은 객체 처리, 밀집 지역 지표가 필요하다.

### Session 조회

매 Packet마다 Session List를 선형 검색하면 Packet 수 `p`, Session 수 `n`에 O(pn)이 된다. ID Hash Map으로 평균 O(p) 수준을 기대할 수 있지만 Hash Flooding, Rehash와 동시 Lock 경합을 측정해야 한다.

### Tick Budget과 Fallback

Pathfinding이 최악 입력에서 긴 시간을 쓰면 전체 Tick이 지연된다. 탐색 Node 수나 시간 Budget을 두고 넘으면 다음 Tick으로 이월하거나 근사 경로, 기존 경로 유지 같은 Fallback을 사용한다.

```text
요청 입력 상한
   ↓
예상 복잡도와 Memory 상한
   ↓
Tick당 작업 Budget
   ↓ 초과
Cancel / Defer / Approximate / Reject
```

평균 실행 시간만 보면 드문 Spike를 놓친다. 입력 크기별 실행 시간, 방문 Node 수, Allocation, p95·p99·최대 지연을 함께 기록한다.

## 13. 복잡도 분석 절차

1. 입력 크기 변수를 정의한다.
2. 가장 자주 반복되는 기본 연산을 고른다.
3. 반복문 범위와 재귀 호출 수를 센다.
4. 연속 비용은 더하고 중첩 비용은 곱한다.
5. 지배 항을 남기되 평균·최악·분할 상환을 구분한다.
6. 보조 Container와 호출 Stack의 공간을 계산한다.
7. 정당성, 입력 전제와 Overflow·경계를 확인한다.
8. 실제 입력 분포로 시간·Memory·Tail Latency를 측정한다.

최적화 전에는 느린 부분이 어디인지 Profile한다. O(n²)처럼 Algorithm 차수가 병목이면 구조 변경이 필요하지만, O(n) 코드의 DB Round Trip이 병목이면 Batch와 I/O 개선이 먼저다.

## 14. 자주 하는 오해

- **Big-O는 정확한 실행 시간이다**: 증가율의 상한 표현이며 실제 상수와 Hardware는 포함하지 않는다.
- **반복문이 두 개면 O(n²)이다**: 연속이면 O(n+n)=O(n), 중첩 관계를 봐야 한다.
- **O(2n)은 O(n)보다 다른 차수다**: 상수 계수는 제거한다.
- **평균 복잡도와 분할 상환은 같다**: 평균은 입력 분포, 분할 상환은 연산 Sequence 총비용을 다룬다.
- **재귀 시간만 계산하면 된다**: 호출 Stack 공간과 최대 깊이도 계산해야 한다.
- **Hash 조회는 문자열 길이와 무관한 O(1)이다**: Hash 계산과 Equality 비교에는 Key 길이가 영향을 줄 수 있다.
- **Big-O가 같으면 실제 성능도 같다**: Cache, Allocation, Branch, I/O 비용이 다르다.
- **평균이 빠르면 실시간 서버에 충분하다**: Tick Deadline에는 최악과 Tail Latency가 중요하다.

## 15. 면접 질문

### Q1. 시간 복잡도와 공간 복잡도를 설명해 주세요.

시간 복잡도는 입력 크기에 따라 기본 연산 수가 증가하는 비율이고, 공간 복잡도는 필요한 Memory 증가율입니다. 특정 실행 시간을 말하는 것이 아니라 큰 입력에서 Algorithm의 확장성을 비교합니다.

### Q2. Big-O, Theta, Omega의 차이는 무엇인가요?

Big-O는 점근적 상한, Omega는 하한, Theta는 상한과 하한이 일치하는 Tight Bound입니다. 실무에서는 Big-O를 대표 증가율처럼 말하는 경우가 많지만 가능한 Tight한 Bound와 분석 Case를 함께 밝히는 것이 정확합니다.

### Q3. 평균 복잡도와 분할 상환 복잡도를 비교해 주세요.

평균 복잡도는 입력 분포에 대한 기대 비용입니다. 분할 상환은 확률 가정 없이 연속된 여러 연산의 총비용을 나눕니다. Dynamic Array Push는 개별 재할당이 O(n)이지만 여러 Push는 분할 상환 O(1)입니다.

### Q4. Bottom-Up Heapify가 왜 O(n)인지 설명하는 방식과 유사하게 복잡도를 어떻게 세나요?

각 작업의 최악 비용을 단순히 모든 원소에 곱하지 않고, 실제로 그 비용을 수행하는 원소 수를 Level별로 합합니다. 비싼 상단 Node는 적고 대부분의 하단 Node는 거의 이동하지 않아 총합이 O(n)입니다.

### Q5. 재귀 Algorithm의 공간 복잡도는 어떻게 분석하나요?

동시에 살아 있는 호출 수인 최대 재귀 깊이와 각 Frame 크기를 봅니다. 선형 재귀는 Stack O(n), 균형 분할 재귀는 보통 Stack O(log n)입니다. 별도 배열이나 Memoization 공간도 더합니다.

### Q6. 게임 서버에서 Big-O 외에 무엇을 보나요?

Cache Miss, Allocation, Lock과 I/O, 입력 분포, p95·p99와 최대 지연을 봅니다. 실시간 경로에는 입력·작업 Budget과 Timeout, Defer·근사 같은 Fallback도 둡니다.

## 17. 30초 모범답변

> 시간·공간 복잡도는 입력 크기에 따른 연산 수와 Memory의 증가율입니다. Big-O는 점근적 상한이며 실제 시간과 같지 않습니다. 분석할 때 입력 변수를 정의하고 반복·재귀 횟수, 평균·최악·분할 상환, 보조 공간을 구분합니다. 게임 서버에서는 Cache와 I/O 같은 상수, p99 지연, 입력 상한과 Fallback까지 실제 부하로 검증해야 합니다.

## 18. 1~2분 확장답변

> 시간 복잡도는 입력이 커질 때 기본 연산 수가 어떻게 증가하는지, 공간 복잡도는 추가 Memory가 어떻게 증가하는지를 나타냅니다. Big-O는 상한, Theta는 Tight Bound, Omega는 하한입니다. 연속 반복문은 비용을 더하고 중첩 반복문은 곱하며, 입력을 절반씩 줄이면 O(log n)입니다. 재귀는 호출 수뿐 아니라 최대 Stack 깊이도 계산합니다.
>
> 평균 Case는 입력 분포가 필요하고, 분할 상환은 여러 연산 Sequence의 총비용을 나눕니다. 예를 들어 Dynamic Array Push는 재할당 한 번은 O(n)이지만 여러 Push는 분할 상환 O(1)입니다. 게임 서버에서는 모든 플레이어 쌍 비교 같은 O(n²) 작업이 인원 증가 시 Tick을 넘길 수 있어 공간 분할로 후보를 줄입니다. 그래도 밀집된 최악 Case가 남을 수 있으므로 입력 상한과 작업 Budget, Fallback을 두고 p95·p99·최대 지연과 Memory를 측정합니다.

## 19. 핵심 요약

- 시간 복잡도는 연산 수, 공간 복잡도는 Memory의 입력 대비 증가율이다.
- Big-O는 상한, Omega는 하한, Theta는 Tight Bound다.
- 입력 변수와 기본 연산을 먼저 정의하고 여러 입력 축을 구분한다.
- 연속 반복은 더하고 중첩 반복은 곱하며 절반씩 감소하면 O(log n)이다.
- 평균은 입력 분포, 분할 상환은 연산 Sequence 전체 비용을 다룬다.
- 재귀에서는 실행 시간과 최대 호출 Stack 공간을 함께 분석한다.
- Big-O는 실제 상수, Cache, Allocation, Lock, I/O를 대신하지 않는다.
- 실시간 서버에서는 최악 입력, Tail Latency, Budget과 Fallback까지 설계한다.

## 한 줄 정리

> 복잡도는 입력 증가에 따른 비용의 성장률을 예측하는 도구이며, 실제 시스템에서는 전제·최악 Case·Memory와 측정을 함께 봐야 한다.
