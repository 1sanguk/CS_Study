# 03. JOIN

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 한 줄 정의와 등장 이유를 설명할 수 있다.
- 핵심 동작과 비교 개념을 설명할 수 있다.
- 게임 백엔드의 정합성과 성능 설계에 적용할 수 있다.

## 1. 개요

JOIN은 공통 조건을 기준으로 여러 테이블의 행을 하나의 결과로 결합하는 연산이다.

조인은 정규화된 관계 사이를 조회 시점에 다시 연결한다. `Player.guild_id = Guild.guild_id`처럼 조인 조건을 만족하는 행 조합을 만들며, 어떤 행을 결과에 남길지는 INNER·OUTER 같은 논리 조인 종류가 정한다. DBMS가 그 결과를 계산하는 실제 방법은 Nested Loop·Hash·Merge 같은 물리 조인 알고리즘이다.

논리 조인과 물리 알고리즘을 구분해야 한다. `LEFT JOIN`이라고 해서 특정 알고리즘을 쓰는 것이 아니며 같은 SQL도 데이터 크기, 필터 선택도, 인덱스와 메모리에 따라 다른 실행 계획을 사용할 수 있다.

## 2. 왜 필요한가
정규화로 나눈 플레이어, 길드, 아이템 데이터를 필요한 조회에서 다시 연결해야 한다. 데이터베이스 선택은 편의가 아니라 불변식, 조회 패턴, 장애 복구 요구에서 출발한다.

플레이어 이름과 길드 이름을 길드원 행마다 중복 저장하면 이름 변경 때 여러 행을 갱신해야 한다. Player, Guild, Membership으로 분리하면 사실의 원본은 명확해지지만 랭킹 화면에서는 세 테이블 정보를 한 결과로 조합해야 한다. JOIN은 이 읽기 요구를 관계 조건으로 표현한다.

애플리케이션이 각 플레이어마다 별도 길드 조회를 반복할 수도 있지만 네트워크 왕복과 쿼리 파싱·실행이 늘어난다. 적절한 JOIN이나 일괄 조회는 DB가 전체 데이터 집합과 인덱스를 보고 한 번에 처리하도록 한다. 반대로 무조건 거대한 조인 하나로 모든 정보를 가져오면 중복 결과와 메모리·정렬 비용이 커질 수 있으므로 필요한 데이터 범위를 먼저 줄인다.

## 3. 핵심 동작 원리
```text
input tables→join condition→nested loop/hash/merge join→result
```
INNER는 일치 행, LEFT OUTER는 왼쪽 전체와 일치 오른쪽을 반환한다. WHERE 조건 위치가 OUTER JOIN 결과를 INNER처럼 바꿀 수 있다.

JOIN에서는 논리 모델과 물리 실행을 구분한다. 같은 SQL도 통계, 데이터 분포, 인덱스와 동시 부하에 따라 실행 비용이 달라진다.

### 예시 데이터

```text
Player                         Guild
┌────┬──────┬──────────┐      ┌──────────┬─────────┐
│ id │ name │ guild_id │      │ guild_id │ name    │
├────┼──────┼──────────┤      ├──────────┼─────────┤
│ 1  │ A    │ 10       │      │ 10       │ Knights │
│ 2  │ B    │ NULL     │      │ 20       │ Mages   │
│ 3  │ C    │ 30       │      └──────────┴─────────┘
└────┴──────┴──────────┘
```

Player 1은 Guild 10과 일치한다. Player 2는 길드가 없고 Player 3의 30은 참조 대상이 없다. 실제 스키마에 FK가 있다면 Player 3 같은 상태는 일반적으로 저장되지 않도록 막을 수 있다.

### INNER JOIN

양쪽에서 조인 조건이 참인 행만 반환한다.

```sql
SELECT p.id, p.name, g.name AS guild_name
FROM player AS p
JOIN guild AS g ON g.guild_id = p.guild_id;
```

예시에서는 Player 1만 반환된다. 동일한 키가 오른쪽에 여러 행 있으면 왼쪽 한 행이 여러 결과 행으로 늘어난다. “JOIN하면 원본 행 수가 유지된다”는 보장은 조인 열의 유일성에 달려 있다.

### LEFT·RIGHT·FULL OUTER JOIN

LEFT JOIN은 왼쪽 행을 모두 유지하고 오른쪽에 일치가 없으면 오른쪽 열을 NULL로 채운다. 예시에서는 Player 1, 2, 3이 모두 나오고 2와 3의 guild_name이 NULL이다.

RIGHT JOIN은 오른쪽을 모두 유지한다. 테이블 순서를 바꾼 LEFT JOIN으로 표현할 수 있어 팀에서 LEFT 중심으로 통일하기도 한다. FULL OUTER JOIN은 양쪽의 일치하지 않는 행도 모두 유지하지만 지원 여부와 대체 표현은 DBMS별로 확인한다.

```text
INNER: 교집합
LEFT : 왼쪽 전체 + 일치 오른쪽
RIGHT: 오른쪽 전체 + 일치 왼쪽
FULL : 양쪽 전체
```

### ON과 WHERE 조건

OUTER JOIN에서 조건 위치는 결과 의미를 바꿀 수 있다.

```sql
-- 길드 레벨 10 이상이면 붙이되 모든 Player 유지
SELECT p.id, g.name
FROM player p
LEFT JOIN guild g
  ON g.guild_id = p.guild_id
 AND g.level >= 10;

-- JOIN 후 g.level 조건을 통과한 행만 유지
SELECT p.id, g.name
FROM player p
LEFT JOIN guild g ON g.guild_id = p.guild_id
WHERE g.level >= 10;
```

두 번째 쿼리에서 일치하지 않은 행의 `g.level`은 NULL이고 WHERE 조건은 참이 아니므로 제거된다. 결과가 INNER JOIN처럼 보일 수 있다. 모든 플레이어를 유지하려는 요구라면 오른쪽 필터를 ON에 두거나 NULL 처리 의미를 명시한다.

### CROSS JOIN과 SELF JOIN

CROSS JOIN은 양쪽 모든 행의 조합인 카티션 곱을 만든다. A가 1,000행, B가 1,000행이면 필터 전 최대 100만 조합이다. 의도적인 날짜×상품 조합 등에 쓰지만 조인 조건 누락으로 우연히 발생하면 결과와 비용이 폭증한다.

SELF JOIN은 같은 테이블을 서로 다른 별칭으로 조인한다. 추천인, 조직 상하 관계처럼 한 행이 같은 테이블의 다른 행을 참조할 때 사용한다.

```sql
SELECT child.name, parent.name AS referrer_name
FROM player child
LEFT JOIN player parent ON parent.id = child.referrer_id;
```

SELF JOIN은 논리 용법이고 별도 물리 알고리즘 이름이 아니다.

### Semi Join과 Anti Join 관점

왼쪽 행에 대응하는 오른쪽 행의 존재만 확인하려면 `EXISTS`, 존재하지 않음을 확인하려면 `NOT EXISTS`를 사용할 수 있다. 결과에 오른쪽 열을 붙이지 않고 왼쪽 행을 중복시키지 않는 Semi·Anti Join 의미다.

```sql
SELECT p.id
FROM player p
WHERE EXISTS (
  SELECT 1 FROM inventory_item i WHERE i.player_id = p.id
);
```

`JOIN` 후 `DISTINCT`로 중복을 제거하는 것보다 의도를 정확히 표현하고 불필요한 행 생성을 피할 수 있다. `NOT IN`은 하위 결과에 NULL이 있을 때 3값 논리 때문에 예상과 다를 수 있어 NULL 가능성을 확인한다.

### Nested Loop Join

한 입력의 각 행마다 다른 입력에서 일치 행을 찾는다.

```text
for each row in outer:
    find matching rows in inner
```

바깥 입력이 작고 안쪽 조인 키에 효율적인 인덱스가 있으면 좋다. 예를 들어 20명의 랭킹 플레이어 각각을 PK로 조회하면 인덱스 탐색 비용이 작다. 반대로 바깥쪽이 수백만 행인데 안쪽을 매번 전체 스캔하면 비용이 매우 커진다.

DBMS에 따라 Block Nested Loop, Batched Key Access 등 변형이 있다. 핵심은 바깥 행 수와 안쪽 접근 비용의 곱을 본다는 점이다.

### Hash Join

일반적으로 작은 입력의 조인 키로 해시 테이블을 만들고 다른 입력을 스캔하며 일치 버킷을 찾는다. 정렬되지 않은 대량 동등 조인에 유리할 수 있다.

```text
Build: Guild rows → Hash(guild_id)
Probe: Player rows → Hash(player.guild_id)로 Match
```

해시 테이블이 메모리에 맞지 않으면 파티션과 디스크 임시 공간을 사용할 수 있어 느려진다. 범위 조건 조인에는 일반적인 Hash Join을 직접 적용하기 어렵다. 어느 입력을 Build로 선택했는지와 실제 크기를 확인한다.

### Merge Join

두 입력이 조인 키로 정렬되어 있으면 앞에서부터 비교하며 일치 구간을 병합한다. 대량 입력과 범위 성격에 유리할 수 있고 이미 인덱스 순서를 활용하면 별도 정렬을 피할 수 있다. 정렬이 필요하면 그 CPU·메모리·임시 디스크 비용을 포함해야 한다.

### Optimizer와 Join 순서

INNER JOIN은 결과 의미를 유지하는 범위에서 옵티마이저가 조인 순서를 바꿀 수 있다. 가장 선택적인 필터로 행 수를 먼저 줄이면 이후 비용이 작아질 수 있다. OUTER JOIN은 보존할 행 방향 때문에 재배치 제약이 더 크다.

옵티마이저는 통계로 각 조건의 행 수를 추정한다. 길드 하나에 플레이어가 몰리는 데이터 편향이나 두 열의 상관관계를 제대로 추정하지 못하면 작은 입력으로 예상한 쪽이 실제로 매우 커질 수 있다. 실행 계획에서 추정 행과 실제 행의 차이를 찾는다.

## 4. 쉬운 예시
JOIN에서는 플레이어가 아이템을 구매하면 재화 확인, 차감, 아이템 생성이 연결된다. 일부만 반영되거나 동시에 두 번 처리되지 않도록 제약 조건과 트랜잭션 경계를 설계한다.

랭킹 상위 100명의 플레이어와 길드 표시 이름을 조회한다고 하자. 먼저 전체 Player와 Ranking을 조인한 뒤 정렬·LIMIT하면 많은 행을 처리할 수 있다. 랭킹 인덱스로 상위 100개를 먼저 구하고 그 작은 결과를 Player와 Guild에 조인하면 처리량을 줄일 수 있다. 옵티마이저가 자동으로 좋은 계획을 선택할 수도 있지만 실행 계획으로 확인한다.

```text
Ranking Index → Top 100
       │
       ├─ Join Player by PK
       └─ Join Guild by PK
              ↓
          100 Result Rows
```

목록의 각 플레이어에 대해 애플리케이션이 Player 조회 1번, Guild 조회 1번을 반복하면 N+1 문제가 된다. JOIN, 필요한 ID의 일괄 `IN` 조회, DataLoader 성격의 배치 중 결과 중복과 데이터 크기에 맞는 방식을 선택한다.

## 5. 비슷한 개념과 비교
| 관점 | 질문 | 점검 항목 |
|---|---|---|
| 논리 모델 | 어떤 불변식인가 | Key·Constraint |
| 물리 실행 | 몇 Page를 읽는가 | Index·Plan |
| 동시성 | 무엇을 함께 허용하는가 | Transaction·Lock |

| 물리 방식 | 유리한 상황 | 주요 조건·비용 |
|---|---|---|
| Nested Loop | 작은 Outer + Indexed Inner | Outer 행 수 × Inner 접근 비용 |
| Hash Join | 대량 동등 조건 | Build Memory, Spill 가능성 |
| Merge Join | 정렬된 대량 입력·범위 | 정렬 비용 또는 정렬 Index |

JOIN과 UNION도 구분한다. JOIN은 열 방향으로 관련 행을 결합하고 UNION은 호환되는 열 구조의 결과를 행 방향으로 이어 붙인다. `UNION`은 중복 제거 비용이 있고 `UNION ALL`은 중복을 유지한다.

## 6. 장점과 단점
JOIN에서는 RDBMS는 제약과 트랜잭션, 유연한 조회가 강점이다. 인덱스 유지, Lock 경쟁, Schema 변경과 수평 확장 비용이 있다. 읽기 최적화가 쓰기 비용을 만들 수 있음을 고려한다.

JOIN은 중복 저장 없이 필요한 관점을 유연하게 만들고 DB가 집합 단위 최적화를 수행하게 한다. 반면 많은 테이블, 낮은 선택도, 큰 중간 결과와 정렬·해시 Spill은 CPU·메모리·I/O를 크게 사용한다. 서로 다른 샤드나 서비스 DB 사이의 조인은 네트워크와 분산 정합성을 추가하므로 데이터 배치 경계를 고려한다.

## 7. 게임 서버·백엔드 실무 예시
랭킹에 플레이어 표시 이름을 붙일 때 JOIN한다. N+1 쿼리를 피하고 조인 키 인덱스, 선택도, 예상·실제 행 수와 실행 계획을 확인한다.

JOIN에서는 운영에서는 처리량만 보지 않고 쿼리 p95·p99, 실행 계획, 읽은 행·Page, Lock 대기, Deadlock과 Connection Pool을 함께 관찰한다.

일대다 관계를 여러 개 동시에 조인하면 결과 행이 곱으로 늘 수 있다. Player 1명에 Item 100개와 Quest 50개를 동시에 단순 조인하면 최대 5,000개 조합이 생겨 같은 Item과 Quest 정보가 반복된다. 각각 집계하거나 별도 일괄 조회하고 애플리케이션에서 조립하는 편이 나을 수 있다.

ORM의 Eager Loading이 자동으로 좋은 JOIN을 만든다고 가정하지 않는다. 생성 SQL, 선택 열, 결과 행 수와 객체 Materialization 비용을 확인한다. Lazy Loading은 루프 안에서 N+1을 만들기 쉬우므로 요청당 Query 수와 SQL Trace를 관찰한다.

조인 성능을 볼 때는 조인 키 양쪽의 타입·Collation이 호환되는지 확인한다. 열에 함수나 암시적 형 변환이 적용되면 인덱스 탐색을 방해할 수 있다. 외래키는 무결성을 제공하지만 참조하는 열에 필요한 인덱스가 자동 생성되는지는 DBMS별로 다르므로 실행 계획을 확인한다.

## 8. 자주 하는 오해
- 제약 조건을 애플리케이션 검사만으로 대체한다.
- 인덱스가 많을수록 모든 쿼리가 빨라진다고 본다.
- 트랜잭션이 외부 API까지 자동 원자화한다고 생각한다.
- 격리 수준 이름만으로 구현 동작을 단정한다.
- 평균 쿼리 시간만 보고 꼬리 지연을 무시한다.
- LEFT JOIN이면 WHERE 조건과 무관하게 왼쪽 Row가 모두 남는다고 생각한다.
- JOIN 결과의 Row 수는 항상 입력 중 큰 Table과 같다고 본다.
- Foreign Key가 있으면 모든 Join이 자동으로 빨라진다고 생각한다.
- Hash Join은 모든 조건에서 Nested Loop보다 빠르다고 본다.
- N+1은 JOIN 하나로 바꾸기만 하면 항상 해결된다고 생각한다.

랭킹에 플레이어 표시 이름을 붙일 때 JOIN한다. N+1 쿼리를 피하고 조인 키 인덱스, 선택도, 예상·실제 행 수와 실행 계획을 확인한다.
### Q4. 성능 문제는 무엇을 확인하나요?
실행 계획과 실제 행 수, Index 사용, Lock 대기와 꼬리 지연을 확인한다.

### Q5. INNER JOIN과 LEFT JOIN의 차이는 무엇인가요?

INNER JOIN은 조건이 일치하는 양쪽 행만 반환한다. LEFT JOIN은 왼쪽 행을 모두 유지하고 오른쪽 일치가 없으면 오른쪽 열을 NULL로 채운다. 오른쪽 열 필터를 WHERE에 두면 불일치 행이 제거될 수 있다.

### Q6. Nested Loop, Hash, Merge Join을 비교해 주세요.

Nested Loop는 작은 바깥 입력과 인덱스가 있는 안쪽 탐색에 유리하다. Hash Join은 정렬되지 않은 대량 동등 조인에 적합하지만 Build 메모리와 Spill을 고려한다. Merge Join은 정렬된 대량 입력이나 범위에 유리하며 정렬이 없다면 정렬 비용이 든다.

### Q7. JOIN 후 행이 예상보다 늘어나는 이유는 무엇인가요?

조인 키가 한쪽 또는 양쪽에서 유일하지 않으면 일치 조합마다 결과 행이 생긴다. 여러 일대다 관계를 함께 조인하면 곱으로 늘 수 있다. 키 제약과 관계의 Cardinality, 실제 중간 행 수를 확인해야 한다.
