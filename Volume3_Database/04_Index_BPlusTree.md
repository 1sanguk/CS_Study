# 04. Index와 B+Tree

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- B+Tree의 Fan-out이 낮은 트리 높이를 만드는 원리와 범위 조회에 유리한 이유를 설명할 수 있다.
- 인덱스 사용 여부를 선택도와 Sargable 조건 기준으로 설명할 수 있다.
- Covering Index의 동작과 Table Lookup의 비용을 설명할 수 있다.
- 게임 서버에서 랭킹 범위 조회에 적합한 인덱스를 설계하고 쓰기 비용 트레이드오프를 설명할 수 있다.

## 1. 개요

인덱스는 검색 키와 행 위치를 별도 구조로 유지해 전체 스캔을 줄이며 RDBMS의 대표 인덱스 구조가 B+Tree다.

인덱스(Index)는 테이블의 모든 행을 직접 훑지 않고 조건에 맞는 행의 위치를 찾기 위한 보조 자료구조다. 검색 대상 열이 정렬된 B+Tree 계열 인덱스는 동등 조건, 범위와 정렬에 널리 쓰인다.

인덱스는 공짜 복사본이 아니다. 별도 페이지와 메모리를 차지하고 INSERT·UPDATE·DELETE마다 일관되게 갱신해야 한다. 조회 패턴에서 절약하는 페이지 접근이 쓰기와 저장 비용보다 큰지 판단한다.

## 2. 왜 필요한가

디스크·메모리 페이지 접근을 줄여 WHERE, JOIN, ORDER BY 조회를 빠르게 해야 한다.

플레이어 1억 명 중 `player_id = 123` 한 명을 찾기 위해 모든 행을 읽으면 데이터가 커질수록 비용이 선형으로 증가한다. 균형 잡힌 B+Tree는 높은 Fan-out으로 소수의 페이지 경로만 따라가 후보 행을 찾는다.

저장장치는 바이트 하나가 아니라 페이지 단위로 읽고 DB도 버퍼 풀에서 페이지를 관리한다. 결과가 테이블의 대부분이면 인덱스로 수많은 행 위치를 따라가는 것보다 순차 테이블 스캔이 더 저렴할 수 있다.

## 3. 핵심 동작 원리

```text
B+Tree 구조
                     [ 30 | 70 ]               Root
                    /     |      \
          [10|20]        [40|60]       [80|90] Internal
             |               |              |
Leaf: [1..9] ↔ [10..19] ↔ [20..29] ↔ ... ↔ [90..] 
      (Key, Row Locator 또는 Row Data)
```

루트와 내부 노드는 분리 키와 자식 페이지 포인터를 저장한다. 실제 검색 키와 행 위치는 주로 리프에 있다. 리프 페이지는 키 순으로 연결되어 시작 키를 찾은 뒤 옆 페이지를 따라 범위를 순회하기 쉽다.

노드 하나가 페이지 크기 안에 많은 키와 포인터를 담으므로 Fan-out이 크고 트리 높이가 낮다. 수백만 행이어도 루트에서 리프까지 적은 페이지 접근으로 도달할 수 있다. 상위 페이지는 자주 접근되어 버퍼 풀에 남을 가능성이 높다.

### 단건 탐색과 Lookup

보조 인덱스가 필요한 열을 모두 포함하지 않으면 인덱스 탐색 후 테이블 페이지를 추가로 읽는 Lookup이 필요하다. 결과 행이 많고 위치가 흩어져 있으면 이 무작위 접근 비용이 커진다.

### 선택도와 인덱스 사용 결정

선택도는 조건이 전체 중 얼마나 적은 행을 고르는지 나타낸다. `player_id`는 매우 선택적이지만 `status`가 두 가지 값뿐이면 낮다. 옵티마이저는 통계로 인덱스 탐색과 전체 스캔 비용을 비교해 선택한다.

### Sargable 조건

인덱스 검색 범위를 만들 수 있는 조건을 Sargable하다고 한다. 인덱스 열에 함수를 적용하거나 타입이 맞지 않아 암시적 변환이 생기면 정렬된 값을 바로 탐색하기 어렵다.

### Covering Index

쿼리의 필터·조인·출력에 필요한 열이 모두 인덱스에 있으면 테이블 행을 추가로 읽지 않고 인덱스만으로 결과를 만들 수 있다.

### 삽입과 Page Split

INSERT는 정렬 위치의 리프 페이지에 키를 넣는다. 페이지에 여유가 없으면 두 페이지로 나누고 부모에 분리 키를 추가한다. 무작위 키 삽입은 분할과 캐시 미스를 만들 수 있다. 단조 증가 키는 마지막 페이지에 집중되어 지역성은 좋지만 매우 높은 동시 쓰기에서 Hot Spot이 될 수 있다.

## 4. 쉬운 예시

```sql
-- 인덱스 없이 범위 조회: Full Table Scan
EXPLAIN SELECT * FROM player WHERE score BETWEEN 1000 AND 2000;
-- type=ALL, rows=1000000 (전체 스캔)

-- score 인덱스 추가 후
CREATE INDEX idx_player_score ON player (score);
EXPLAIN SELECT * FROM player WHERE score BETWEEN 1000 AND 2000;
-- type=range, key=idx_player_score, rows=5000 (범위 스캔)
```

```sql
-- Non-Sargable: created_at에 함수 적용 → 인덱스 활용 어려움
WHERE DATE(created_at) = '2026-07-14'

-- Sargable: 범위 조건으로 변환
WHERE created_at >= '2026-07-14'
  AND created_at <  '2026-07-15'

-- Non-Sargable: 선두 와일드카드 → B+Tree 시작 범위 없음
WHERE nickname LIKE '%dragon'

-- Sargable: Prefix 범위 사용 가능
WHERE nickname LIKE 'dragon%'
```

```sql
-- Covering Index: Table Lookup 없이 인덱스만으로 결과 반환
CREATE INDEX idx_ranking_cover ON ranking (season_id, score, player_id);

SELECT player_id, score
FROM ranking
WHERE season_id = 7
ORDER BY score DESC
LIMIT 100;
-- idx_ranking_cover가 season_id 필터, score 정렬, player_id 출력을 모두 커버
-- EXPLAIN에서 Extra=Using index 확인

-- Covering 안 됨: guild_name이 인덱스에 없음 → Table Lookup 발생
SELECT player_id, score, guild_name
FROM ranking
WHERE season_id = 7
ORDER BY score DESC
LIMIT 100;
```

```sql
-- 낮은 선택도 예시: 인덱스가 있어도 Full Scan 선택 가능
-- status = 'active'가 전체 90%라면 Lookup보다 스캔이 더 저렴
SELECT * FROM player WHERE status = 'active';
-- 반면 status = 'banned'이 0.01%라면 인덱스 탐색이 유리
SELECT * FROM player WHERE status = 'banned';
```

## 5. 비슷한 개념과 비교

| 구조 | 강점 | 약점·용도 |
|---|---|---|
| B+Tree | 동등·범위·정렬, 안정적 높이 | 쓰기 시 Page 유지 비용 |
| Hash Index | 동등 Key 탐색 | 범위·순서 탐색에 부적합, 제품별 지원 |
| Full-text Index | Token·자연어 검색 | 일반 B+Tree와 갱신·검색 의미 다름 |
| Bitmap 성격 Index | 낮은 Cardinality 분석 | 빈번한 OLTP 쓰기에 부적합할 수 있음 |

| 상황 | 결정 |
|---|---|
| 결과가 전체 일부, 인덱스 열에 조건 | 인덱스 Scan 유리 |
| 결과가 전체 대부분, Lookup 많음 | Full Table Scan 유리 |
| 출력 열이 모두 인덱스에 포함 | Index-only Scan (Covering) |
| 열에 함수 적용, 암시적 변환 | 인덱스 활용 어려움 |

테이블 스캔은 인덱스가 없을 때만 쓰는 실패 계획이 아니다. 결과 비율이 크거나 연속 페이지 읽기가 유리한 분석 쿼리에서는 합리적일 수 있다.

## 6. 장점과 단점

**인덱스의 장점**

- WHERE, JOIN, ORDER BY에서 읽는 페이지 수를 줄인다.
- UNIQUE 인덱스로 DB 레벨에서 중복을 방지한다.
- Covering Index는 Table Lookup 없이 결과를 반환한다.
- 리프 연결을 따라 범위와 정렬을 효율적으로 처리한다.

**인덱스의 단점**

- INSERT/UPDATE/DELETE마다 인덱스를 함께 갱신해야 한다.
- 별도 페이지와 버퍼 풀을 차지한다.
- Page Split이 쓰기 비용을 늘리고 조각화를 만들 수 있다.
- 사용하지 않는 인덱스도 쓰기 비용을 지불한다.

**인덱스 설계 시 확인 사항**

- 추가 전 쿼리 빈도와 읽기 열을 수집한다.
- 추가 후 INSERT/UPDATE 지연, 저장 공간, 캐시 적중을 비교한다.
- 사용되지 않는 것처럼 보여도 UNIQUE·FK 검증이나 드문 운영 쿼리에 필요할 수 있다.

## 7. 게임 서버·백엔드 실무 예시

player_id 단건 조회와 score 범위 랭킹에 맞는 인덱스를 둔다. 함수 적용, 암시적 형 변환, 선두 와일드카드는 인덱스 활용을 방해할 수 있다.

슬로우 쿼리는 "인덱스 미사용" 한 항목으로 진단하지 않는다. 실행 계획의 접근 방식, 추정·실제 행 수, 필터율, Lookup 횟수, Sort·Temporary Spill, 버퍼 적중과 Lock 대기를 본다. 같은 쿼리가 특정 플레이어에서만 느리면 데이터 편향과 매개변수별 계획을 확인한다.

모든 플레이어의 점수가 매 전투마다 갱신되면 랭킹 인덱스도 계속 수정된다. 읽기 빈도와 점수 갱신량, 실시간 요구를 비교해 별도 랭킹 저장 구조나 주기 집계도 고려한다.

Online Index 생성이라는 이름도 리소스와 락이 0이라는 뜻이 아니다. 대형 테이블 스캔, 정렬, 임시 공간, 복제 지연과 Metadata Lock이 발생할 수 있다. 트래픽이 낮은 시간대와 취소·재시도 계획을 준비한다.

## 8. 자주 하는 오해

- **"인덱스가 있으면 DB가 반드시 사용한다"**: 결과 비율이 크면 Table Lookup 비용이 Full Scan보다 클 수 있다. 옵티마이저는 통계로 비용을 비교해 선택한다. 실행 계획의 추정 행 수와 접근 방식을 확인한다.
- **"B+Tree 탐색은 항상 디스크를 매 Level 한 번씩 읽는다"**: 상위 노드는 자주 접근되어 버퍼 풀에 남을 가능성이 높다. 실제 디스크 I/O는 캐시 히트율에 따라 다르므로 Cold Cache와 Warm Cache의 차이를 구분한다.
- **"낮은 Cardinality 열의 인덱스는 절대 쓸모없다"**: 다른 조건과 복합 인덱스를 이루거나 일부 값(예: 금지 사용자)이 매우 희귀하면 유용할 수 있다. 단독 조건에서의 선택도와 복합 인덱스에서의 역할을 구분한다.
- **"Covering Index에 열을 많이 넣을수록 좋다"**: 인덱스 크기가 커져 버퍼 풀 효율이 떨어지고 쓰기 비용이 늘어난다. 실제 쿼리에 필요한 열만 포함하고 INCLUDE 열 기능도 과용을 피한다.
- **"LIKE '%dragon'은 인덱스가 없어서 느린 것이다"**: B+Tree는 시작값을 알아야 탐색 범위를 정할 수 있다. 선두 와일드카드는 인덱스가 있어도 활용하기 어렵다. 전문 검색이 필요하면 Full-text Index를 사용한다.
- **"인덱스 재구성(Rebuild)은 항상 안전하다"**: 대형 테이블에서는 큰 I/O, 로그, 락을 만든다. 조각화 수치만 보고 무조건 Rebuild하면 트래픽 영향이 생길 수 있다. 실제 성능 영향을 측정하고 트래픽이 낮은 시간대에 계획한다.
- **"인덱스 추가는 쓰기에 영향이 없다"**: INSERT/UPDATE/DELETE마다 인덱스를 함께 갱신해야 하므로 쓰기 지연이 늘어난다. 쓰기가 많은 열에 인덱스가 많으면 쓰기 병목이 될 수 있다.

## 9. 면접 질문

### Q1. B+Tree가 DB 인덱스에 적합한 이유는 무엇인가요?

한 페이지에 많은 키와 포인터를 담아 Fan-out이 크고 트리 높이가 낮다. 수백만 행이어도 루트에서 리프까지 적은 페이지 접근으로 도달할 수 있다. 모든 레코드 로케이터가 리프에 있고 리프가 연결되어 범위 조회와 ORDER BY를 순차 스캔으로 처리할 수 있다.

### Q2. 인덱스가 있어도 사용하지 않는 이유는 무엇인가요?

결과 비율이 크면 Table Lookup 비용이 Full Scan보다 클 수 있다. 열에 함수를 적용하거나 암시적 형 변환이 생기면 정렬된 값을 바로 탐색하기 어렵다. 통계가 실제 분포를 잘못 추정하면 비효율적인 계획을 선택할 수 있다. 실행 계획의 추정·실제 행 수와 접근 방식을 확인한다.

### Q3. Covering Index란 무엇인가요?

쿼리의 필터·조인·출력에 필요한 열이 모두 인덱스에 있어 테이블 행을 추가로 읽지 않고 인덱스만으로 결과를 만들 수 있는 인덱스다. EXPLAIN에서 `Using index`로 확인할 수 있다. 인덱스 크기와 쓰기 비용이 증가하므로 실제 쿼리 패턴에 맞게 설계한다.

### Q4. Sargable 조건이란 무엇인가요?

인덱스의 검색 범위를 정할 수 있는 조건이다. `WHERE created_at >= '2026-07-14' AND created_at < '2026-07-15'`처럼 시작과 끝 범위를 지정할 수 있으면 Sargable하다. `DATE(created_at) = '2026-07-14'`처럼 열에 함수를 적용하면 인덱스 탐색을 방해한다. 조건을 상수 쪽에 적용하는 방식으로 재작성한다.

### Q5. 인덱스 쓰기 비용은 어떻게 발생하나요?

INSERT는 정렬 위치 리프 페이지에 키를 넣고 가득 차면 Page Split이 발생한다. UPDATE는 이전 키를 제거하고 새 키를 삽입한다. DELETE는 페이지에서 키를 표시하지만 즉시 공간이 회수되지 않을 수 있다. 인덱스가 많을수록 쓰기마다 갱신해야 할 인덱스 수가 늘어난다.

### Q6. 게임 랭킹 범위 조회 인덱스를 어떻게 설계하나요?

시즌별 상위 N명을 자주 조회한다면 `(season_id, score DESC, player_id)` 성격의 인덱스를 검토한다. `season_id` 필터로 범위를 좁히고, `score` 순서로 정렬 Sort를 피하며, `player_id`를 포함해 Covering 효과를 얻는다. 단 점수가 매 전투마다 갱신되면 이 인덱스도 계속 수정되므로 갱신 빈도와 읽기 요구를 비교해 별도 랭킹 구조나 주기 집계도 고려한다.

> 인덱스는 검색 키를 정렬 구조로 유지해 읽는 페이지 수를 줄입니다. B+Tree는 높은 Fan-out으로 트리 높이를 낮게 유지하고 리프가 연결되어 범위·정렬 조회를 효율적으로 처리합니다. 쓰기마다 인덱스를 함께 갱신해야 하므로 인덱스 수는 실제 쿼리 패턴에 맞게 선택하고 EXPLAIN으로 효과를 검증합니다.

## 12. 1~2분 확장답변

> 인덱스는 검색 키를 정렬 구조로 유지해 읽는 페이지 수를 줄이고 B+Tree는 높은 Fan-out으로 트리 높이를 낮게 유지하며 리프가 연결되어 범위 조회에 유리합니다. 옵티마이저는 통계로 인덱스 탐색과 Full Scan 비용을 비교해 선택하므로 결과 비율이 크면 인덱스가 있어도 Full Scan을 선택할 수 있습니다. 열에 함수를 적용하거나 암시적 형 변환이 생기면 Sargable 조건이 깨져 인덱스 범위를 탐색하기 어렵습니다. Covering Index는 Table Lookup 없이 인덱스만으로 결과를 반환하지만 인덱스 크기와 쓰기 비용이 늘어납니다. 게임 랭킹에서는 시즌·점수·플레이어 ID를 함께 인덱스에 두어 Covering 효과를 얻을 수 있지만 점수 갱신이 잦으면 인덱스 갱신 비용도 함께 커지므로 읽기·쓰기 비율을 측정해 결정합니다.

## 13. 핵심 요약

- 인덱스는 검색 키와 행 위치를 별도 구조로 유지해 전체 스캔을 줄인다. 쓰기와 저장 비용이 수반된다.
- B+Tree는 한 페이지에 많은 키를 담아 Fan-out이 크고 트리 높이가 낮다. 리프가 연결되어 범위 조회와 ORDER BY 정렬에 유리하다.
- 옵티마이저는 통계로 인덱스 탐색과 Full Scan 비용을 비교해 선택한다. 결과 비율이 크면 Table Lookup 수가 많아 Full Scan을 선택할 수 있다.
- Sargable 조건은 인덱스 검색 범위를 정할 수 있는 조건이다. 열에 함수를 적용하거나 암시적 형 변환이 생기면 인덱스 탐색을 방해한다.
- Covering Index는 쿼리에 필요한 모든 열이 인덱스에 있어 Table Lookup 없이 결과를 만든다. 인덱스 크기와 쓰기 비용이 증가한다.
- 단조 증가 키는 B+Tree 삽입 지역성이 좋고, 무작위 키는 분할과 캐시 미스를 만들 수 있다.
- 인덱스 열에 함수, 선두 와일드카드, 암시적 형 변환은 인덱스 범위 탐색을 방해한다. 조건을 Sargable하게 재작성한다.
- 인덱스 추가 전 쿼리 빈도와 읽기 열을 확인하고, 추가 후 INSERT/UPDATE 지연, 저장 공간, 캐시 적중 변화를 비교한다.

## 한 줄 정리

> 인덱스는 검색 키를 정렬 구조로 유지해 읽기 페이지 수를 줄이고 B+Tree는 낮은 높이와 연결된 리프로 단건·범위 조회를 지원합니다. 쓰기마다 갱신 비용이 발생하므로 실제 접근 패턴에 맞게 설계합니다.
