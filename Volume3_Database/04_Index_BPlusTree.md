# 04. Index와 B+Tree

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 한 줄 정의와 등장 이유를 설명할 수 있다.
- 핵심 동작과 비교 개념을 설명할 수 있다.
- 게임 백엔드의 정합성과 성능 설계에 적용할 수 있다.

## 1. 개요

인덱스는 검색 키와 행 위치를 별도 구조로 유지해 전체 스캔을 줄이며 RDBMS의 대표 인덱스 구조가 B+Tree다.

인덱스(Index)는 테이블의 모든 행을 직접 훑지 않고 조건에 맞는 행의 위치를 찾기 위한 보조 자료구조다. 책의 색인이 단어와 페이지를 연결하듯 인덱스는 키와 행을 찾을 수 있는 로케이터를 저장한다. 검색 대상 열이 정렬된 B+Tree 계열 인덱스는 동등 조건, 범위와 정렬에 널리 쓰인다.

인덱스는 테이블 데이터의 공짜 복사본이 아니다. 별도 페이지와 메모리를 차지하고 INSERT·UPDATE·DELETE마다 일관되게 갱신해야 한다. 조회 패턴에서 절약하는 페이지 접근이 쓰기와 저장 비용보다 큰지 판단한다.

## 2. 왜 필요한가
디스크·메모리 페이지 접근을 줄여 WHERE, JOIN, ORDER BY 조회를 빠르게 해야 한다. 데이터베이스 선택은 편의가 아니라 불변식, 조회 패턴, 장애 복구 요구에서 출발한다.

플레이어 1억 명 중 `player_id = 123` 한 명을 찾기 위해 모든 행을 읽으면 데이터가 커질수록 비용이 선형으로 증가한다. 균형 잡힌 B+Tree는 높은 Fan-out으로 소수의 페이지 경로만 따라가 후보 행을 찾는다. 자주 조회하는 단건 키, 외래키 조인과 랭킹 범위를 효율적으로 지원한다.

저장장치는 바이트 하나가 아니라 페이지 단위로 읽고 DB도 버퍼 풀에서 페이지를 관리한다. 성능 목표는 단순 비교 횟수뿐 아니라 필요한 인덱스·테이블 페이지 수와 무작위 I/O를 줄이는 것이다. 결과가 테이블의 대부분이면 인덱스로 수많은 행 위치를 따라가는 것보다 순차 테이블 스캔이 더 저렴할 수 있다.

## 3. 핵심 동작 원리
```text
root→internal nodes→leaf pages↔leaf pages→row locator
```
B+Tree는 높은 fan-out으로 높이를 낮추고 리프에 정렬된 키를 두어 범위 조회에 유리하다. 인덱스는 쓰기·저장 비용과 선택도 문제를 만든다.

Index와 B+Tree에서는 논리 모델과 물리 실행을 구분한다. 같은 SQL도 통계, 데이터 분포, 인덱스와 동시 부하에 따라 실행 비용이 달라진다.

### B+Tree 구조

```text
                         [ 30 | 70 ]               Root
                        /     |      \
              [10|20]        [40|60]       [80|90] Internal
                 |               |              |
Leaf: [1..9] ↔ [10..19] ↔ [20..29] ↔ ... ↔ [90..] 
        (Key, Row Locator 또는 Row Data)
```

루트와 내부 노드는 탐색 방향을 정하는 분리 키와 자식 페이지 포인터를 저장한다. 실제 검색 키와 행 위치는 주로 리프에 있다. 리프 페이지는 키 순으로 연결되어 시작 키를 찾은 뒤 옆 페이지를 따라 범위를 순회하기 쉽다.

노드 하나가 페이지 크기 안에 많은 키와 포인터를 담으므로 Fan-out이 크고 트리 높이가 낮다. 수백만 행이어도 루트에서 리프까지 적은 페이지 접근으로 도달할 수 있다. 상위 페이지는 자주 접근되어 버퍼 풀에 남을 가능성이 높다.

B-Tree와 B+Tree의 교과서 차이는 B+Tree가 실제 레코드 로케이터를 리프에 두고 내부 노드는 탐색 키 중심이며 리프가 연결된다는 점이다. 제품 문서가 내부 구조를 B-tree라는 이름으로 부르기도 하므로 용어보다 실제 보장을 확인한다.

### 단건 탐색

`WHERE player_id = 123`을 찾을 때 루트 키와 비교해 자식 페이지를 선택하고 같은 과정을 리프까지 반복한다. 리프에서 키를 찾으면 로케이터로 테이블 행을 읽거나, 클러스터드 구조라면 리프 자체에서 행을 얻는다.

```text
Root → Internal → Leaf → Table Row
                     └─ Covering이면 여기서 종료 가능
```

보조 인덱스가 행의 모든 필요한 열을 포함하지 않으면 인덱스 탐색 후 테이블 페이지를 추가로 읽는 Lookup이 필요하다. 결과 행이 많고 행 위치가 흩어져 있으면 이 무작위 접근 비용이 커진다.

### 범위 탐색과 정렬

`score BETWEEN 1000 AND 2000`은 시작 키 1000을 트리로 찾고 연결된 리프를 2000까지 순서대로 읽을 수 있다. 인덱스 순서가 `ORDER BY`와 맞으면 별도 Sort를 피할 수 있다.

```sql
SELECT player_id, score
FROM ranking
WHERE score >= 1000
ORDER BY score
LIMIT 100;
```

`score` 인덱스가 있으면 조건·정렬·LIMIT를 함께 활용할 가능성이 있다. 동일 점수의 안정적 페이지네이션에는 `(score, player_id)`처럼 Tie-breaker를 포함한다. 정렬 방향 혼합 지원과 역방향 스캔 능력은 DBMS별로 확인한다.

### 삽입, Page Split과 삭제

INSERT는 정렬 위치의 리프 페이지에 키를 넣는다. 페이지에 여유가 없으면 두 페이지로 나누고 부모에 분리 키를 추가한다. 부모도 가득 차면 분할이 위로 전파되고 루트가 분할되면 트리 높이가 증가한다.

```text
Before: Leaf [10 20 30 40] (Full)
Insert 25
After : [10 20 25] ↔ [30 40]
                 Parent에 새 경계 Key 반영
```

무작위 키 삽입은 여러 페이지에 분산되어 분할과 캐시 미스를 만들 수 있다. 단조 증가 키는 마지막 페이지에 집중되어 지역성은 좋지만 매우 높은 동시 쓰기에서 마지막 페이지가 Hot Spot이 될 수 있다. 어느 패턴이 좋은지는 엔진과 부하에 따라 측정한다.

DELETE 후 공간은 즉시 파일 크기 감소로 이어지지 않을 수 있다. 페이지 내부에서 재사용하거나 백그라운드 정리와 재구성이 필요할 수 있다. 조각화 수치만 보고 무조건 Rebuild하면 큰 I/O·로그와 락을 만들 수 있으므로 실제 성능과 제품 동작을 확인한다.

### 선택도와 Cardinality

선택도(Selectivity)는 조건이 전체 중 얼마나 적은 행을 고르는지 나타내는 관점이다. `player_id`는 매우 선택적이지만 값이 `active/inactive` 두 개인 열은 단독 조건으로 많은 행을 반환할 수 있다. 낮은 선택도 인덱스도 다른 조건과 복합 인덱스를 이루거나 일부 값이 매우 희귀하면 유용할 수 있다.

옵티마이저는 통계의 Cardinality와 분포로 인덱스 탐색과 전체 스캔 비용을 비교한다. `status='active'`가 전체 95%라면 인덱스 Lookup 수백만 번보다 테이블 스캔을 고를 수 있다. “인덱스가 있는데 왜 안 쓰나요?”에는 결과 비율, Lookup 비용, 통계와 조건 표현을 확인한다고 답한다.

### Covering Index

쿼리의 필터·조인·출력에 필요한 열이 모두 인덱스에 있으면 테이블 행을 추가로 읽지 않고 인덱스만으로 결과를 만들 수 있다. 이를 Covering Index 또는 Index-only Scan 관점으로 부른다.

```sql
SELECT player_id, score
FROM ranking
WHERE season_id = 7
ORDER BY score DESC
LIMIT 100;
```

`(season_id, score, player_id)` 성격의 인덱스가 조회를 Cover할 수 있다. DBMS의 INCLUDE 열 기능은 검색 순서에는 쓰지 않고 리프에 출력 열을 포함할 수 있다. 포함 열이 많으면 인덱스가 커지고 쓰기와 캐시 효율이 나빠진다.

### Sargable 조건

인덱스 검색 범위를 만들 수 있는 조건을 Sargable하다고 표현한다. 인덱스 열에 함수를 적용하거나 타입이 맞지 않아 열 쪽에 암시적 변환이 생기면 정렬된 원래 값을 바로 탐색하기 어려울 수 있다.

```sql
-- 일반 Index(created_at)를 활용하기 어려울 수 있음
WHERE DATE(created_at) = '2026-07-14'

-- 범위로 표현
WHERE created_at >= '2026-07-14'
  AND created_at <  '2026-07-15'
```

`LIKE '%dragon'`은 시작 위치를 알 수 없어 일반 B+Tree 선두 탐색에 불리하다. `LIKE 'dragon%'`은 Prefix 범위를 사용할 가능성이 있다. 함수 기반 인덱스, 전문 검색 인덱스 같은 대안은 제품과 요구에 맞춘다.

### Unique Index와 Constraint

UNIQUE 제약은 업무 유일성을 표현하고 DBMS가 Unique Index로 구현할 수 있다. 인덱스는 빠른 조회를 위한 물리 구조이고 제약은 데이터가 반드시 지켜야 할 논리 규칙이라는 목적 차이가 있다. 애플리케이션의 사전 중복 조회만으로는 동시 INSERT 경쟁을 막지 못하므로 최종 DB 제약을 둔다.

## 4. 쉬운 예시
Index와 B+Tree에서는 플레이어가 아이템을 구매하면 재화 확인, 차감, 아이템 생성이 연결된다. 일부만 반영되거나 동시에 두 번 처리되지 않도록 제약 조건과 트랜잭션 경계를 설계한다.

전화번호부에서 이름순 색인이 없으면 첫 페이지부터 모두 읽어야 한다. 색인이 있으면 이름의 첫 글자와 범위를 따라가 해당 페이지를 찾는다. B+Tree도 루트와 내부 페이지를 따라 리프 위치를 찾는다. 비유와 달리 DB 인덱스는 데이터 변경 때마다 함께 수정되고 버퍼 풀·락·로그 비용이 든다.

게임 랭킹에서 시즌 7의 상위 100명을 자주 읽는다면 `(season_id, score DESC, player_id)` 성격의 인덱스를 검토한다. 하지만 모든 플레이어의 점수가 매 전투마다 갱신되면 이 인덱스도 계속 수정된다. 읽기 빈도와 점수 갱신량, 실시간 요구를 비교해 별도 랭킹 저장 구조나 주기 집계도 고려한다.

## 5. 비슷한 개념과 비교
| 관점 | 질문 | 점검 항목 |
|---|---|---|
| 논리 모델 | 어떤 불변식인가 | Key·Constraint |
| 물리 실행 | 몇 Page를 읽는가 | Index·Plan |
| 동시성 | 무엇을 함께 허용하는가 | Transaction·Lock |

| 구조 | 강점 | 약점·용도 |
|---|---|---|
| B+Tree | 동등·범위·정렬, 안정적 높이 | 쓰기 시 Page 유지 비용 |
| Hash Index | 동등 Key 탐색 | 범위·순서 탐색에 부적합, 제품별 지원 |
| Full-text Index | Token·자연어 검색 | 일반 B+Tree와 갱신·검색 의미 다름 |
| Bitmap 성격 Index | 낮은 Cardinality 분석 | 빈번한 OLTP 쓰기에 부적합할 수 있음 |

테이블 스캔은 인덱스가 없을 때만 쓰는 실패 계획이 아니다. 결과 비율이 크거나 작은 테이블, 연속 페이지 읽기가 유리한 분석 쿼리에서는 합리적일 수 있다. 핵심은 실제 읽은 페이지와 전체 비용이다.

## 6. 장점과 단점
Index와 B+Tree에서는 RDBMS는 제약과 트랜잭션, 유연한 조회가 강점이다. 인덱스 유지, Lock 경쟁, Schema 변경과 수평 확장 비용이 있다. 읽기 최적화가 쓰기 비용을 만들 수 있음을 고려한다.

인덱스는 검색·조인·정렬의 페이지 접근을 줄이고 UNIQUE로 중복을 방지할 수 있다. 단점은 저장 공간, 버퍼 풀 점유, 쓰기 증폭, 페이지 분할과 통계·유지보수 비용이다. 비슷한 인덱스가 중복되면 쓰기 비용만 늘 수 있으므로 사용량과 Query 패턴을 점검한다.

## 7. 게임 서버·백엔드 실무 예시
player_id 단건 조회와 score 범위 랭킹에 맞는 인덱스를 둔다. 함수 적용, 암시적 형 변환, 선행 와일드카드는 인덱스 활용을 방해할 수 있다.

Index와 B+Tree에서는 운영에서는 처리량만 보지 않고 쿼리 p95·p99, 실행 계획, 읽은 행·Page, Lock 대기, Deadlock과 Connection Pool을 함께 관찰한다.

슬로우 쿼리는 “인덱스 미사용” 한 항목으로 진단하지 않는다. 실행 계획의 접근 방식, 추정·실제 행 수, 조건별 필터율, 인덱스 Lookup 횟수, Sort·Temporary Spill, 버퍼 적중과 Lock 대기를 본다. 같은 쿼리가 특정 플레이어에서만 느리면 데이터 편향과 매개변수별 계획을 확인한다.

인덱스를 추가하기 전에 실제 쿼리 빈도와 읽기 열을 수집한다. 배포 후에는 p99와 페이지 읽기 감소뿐 아니라 INSERT·UPDATE 지연, 로그량, 저장 공간과 캐시 적중 변화를 비교한다. 사용되지 않는 것처럼 보이는 인덱스도 UNIQUE·FK 검증이나 드문 운영 쿼리에 필요할 수 있어 목적을 확인한 뒤 제거한다.

Online Index 생성이라는 이름도 리소스와 락이 0이라는 뜻은 아니다. 대형 테이블 스캔, 정렬, 임시 공간, 복제 지연과 짧은 Metadata Lock이 발생할 수 있다. 트래픽 창과 Replica 상태를 관찰하고 취소·재시도 계획을 둔다.

## 8. 자주 하는 오해
- 제약 조건을 애플리케이션 검사만으로 대체한다.
- 인덱스가 많을수록 모든 쿼리가 빨라진다고 본다.
- 트랜잭션이 외부 API까지 자동 원자화한다고 생각한다.
- 격리 수준 이름만으로 구현 동작을 단정한다.
- 평균 쿼리 시간만 보고 꼬리 지연을 무시한다.
- 인덱스가 있으면 DB가 반드시 사용한다고 생각한다.
- B+Tree 탐색은 항상 Disk를 매 Level 한 번씩 읽는다고 본다.
- 낮은 Cardinality 열의 Index는 절대 쓸모없다고 단정한다.
- Covering Index에 열을 많이 넣을수록 항상 좋다고 생각한다.
- Page Split과 조각화만 없애면 쓰기가 항상 빨라진다고 본다.

## 9. 면접 질문
### Q1. 핵심 개념을 설명해 주세요.
인덱스는 검색 키와 행 위치를 별도 구조로 유지해 전체 스캔을 줄이며 RDBMS의 대표 인덱스 구조가 B+Tree다.
### Q2. 왜 필요한가요?
디스크·메모리 페이지 접근을 줄여 WHERE, JOIN, ORDER BY 조회를 빠르게 해야 한다.
### Q3. 게임 백엔드에서는 어떻게 적용하나요?
player_id 단건 조회와 score 범위 랭킹에 맞는 인덱스를 둔다. 함수 적용, 암시적 형 변환, 선행 와일드카드는 인덱스 활용을 방해할 수 있다.
### Q4. 성능 문제는 무엇을 확인하나요?
실행 계획과 실제 행 수, Index 사용, Lock 대기와 꼬리 지연을 확인한다.

### Q5. B+Tree가 DB 인덱스에 적합한 이유는 무엇인가요?

한 페이지에 많은 키와 포인터를 담아 Fan-out이 크고 트리 높이가 낮다. 모든 리프가 비슷한 깊이에 있어 단건 탐색이 안정적이며 정렬된 리프 연결을 따라 범위와 ORDER BY를 효율적으로 처리할 수 있다.

### Q6. 인덱스가 있어도 사용하지 않는 이유는 무엇인가요?

조건이 많은 행을 반환해 Lookup보다 전체 스캔이 싸거나, 함수·암시적 변환으로 검색 범위를 만들기 어렵거나, 통계가 실제 분포를 잘못 추정할 수 있다. 실행 계획의 추정·실제 행과 페이지 비용을 확인한다.

### Q7. Covering Index는 무엇인가요?

쿼리에 필요한 필터·조인·출력 열이 모두 인덱스에 있어 테이블 행 추가 조회 없이 결과를 만들 수 있는 인덱스다. Lookup을 줄이지만 인덱스 크기와 쓰기 비용이 증가한다.
