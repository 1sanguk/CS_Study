# 02. Key와 정규화

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 한 줄 정의와 등장 이유를 설명할 수 있다.
- 핵심 동작과 비교 개념을 설명할 수 있다.
- 게임 백엔드의 정합성과 성능 설계에 적용할 수 있다.

## 1. 개요

키는 행을 식별하거나 관계를 연결하는 속성이고 정규화는 함수 종속성을 기준으로 중복과 갱신 이상을 줄이는 설계 과정이다.

키(Key)는 단순히 인덱스를 만드는 열이 아니라 데이터의 정체성과 관계를 표현하는 논리 제약이다. 정규화(Normalization)는 한 테이블에 섞인 서로 다른 사실을 함수 종속성에 따라 분리해 같은 사실을 여러 곳에서 수정해야 하는 문제를 줄인다.

정규화의 목표는 테이블을 가능한 많이 쪼개는 것이 아니다. 각 테이블이 무엇에 관한 사실을 저장하는지 명확히 하고 삽입·수정·삭제 이상을 줄이는 것이다. 실제 조회 요구 때문에 중복을 도입하는 반정규화는 가능하지만 원본과 동기화 책임을 함께 설계해야 한다.

## 2. 왜 필요한가
중복 저장은 삽입·수정·삭제 시 서로 다른 값이 남는 이상을 만든다. 데이터베이스 선택은 편의가 아니라 불변식, 조회 패턴, 장애 복구 요구에서 출발한다.

길드원 행마다 길드 이름과 길드 마스터 정보를 반복 저장한다고 하자. 길드 이름을 바꿀 때 일부 행만 갱신되면 같은 길드가 여러 이름을 가진다. 길드원이 아직 없으면 길드 정보를 저장할 행이 없고, 마지막 길드원을 삭제하면서 길드 자체 정보까지 잃을 수도 있다. 이를 각각 수정·삽입·삭제 이상 관점으로 설명할 수 있다.

키가 명확하지 않으면 중복 행을 구분하기 어렵고 다른 테이블이 안정적으로 참조할 수도 없다. 애플리케이션에서 UUID를 발급했다고 업무상 중복 닉네임이나 동일 주문 중복 처리가 자동으로 막히지는 않는다. 식별용 키와 업무상 유일성 제약을 구분한다.

## 3. 핵심 동작 원리
```text
candidate key→primary key / foreign key→referenced key / 1NF→2NF→3NF
```
슈퍼키 중 최소 집합이 후보키이고 그중 선택한 것이 기본키다. 대체키는 식별을 단순화하지만 업무상 유일성에는 별도 UNIQUE가 필요하다.

Key와 정규화에서는 논리 모델과 물리 실행을 구분한다. 같은 SQL도 통계, 데이터 분포, 인덱스와 동시 부하에 따라 실행 비용이 달라진다.

### 키의 종류

- 슈퍼키(Super Key): 행을 유일하게 식별할 수 있는 속성 집합이다. 불필요한 속성이 포함될 수 있다.
- 후보키(Candidate Key): 슈퍼키 중 어떤 속성을 빼도 유일성을 잃는 최소 집합이다.
- 기본키(Primary Key): 여러 후보키 중 테이블의 대표 식별자로 선택한 키다.
- 대체키(Alternate Key): 후보키였지만 기본키로 선택되지 않은 키다. 보통 UNIQUE 제약으로 보존한다.
- 복합키(Composite Key): 둘 이상의 속성으로 구성된 키다.
- 외래키(Foreign Key): 다른 테이블의 후보키·고유키를 참조해 관계와 참조 무결성을 표현한다.

```text
Player(player_id PK, email UNIQUE, nickname UNIQUE)

Candidate Keys: {player_id}, {email}, {nickname}
Primary Key:    {player_id}
Alternate Keys:{email}, {nickname}
```

`{player_id, email}`도 행을 유일하게 찾을 수 있어 슈퍼키지만 `email`을 빼도 유일하므로 최소 후보키는 아니다.

### 자연키와 대리키

자연키(Natural Key)는 이메일, 국가 코드처럼 업무 의미가 있는 값이다. 대리키(Surrogate Key)는 DB 식별을 위해 만든 순번이나 UUID처럼 업무 의미가 약한 값이다.

자연키는 별도 식별자가 없어도 업무 유일성을 직접 표현하지만 값이 바뀌거나 길고 복합적이면 모든 참조와 인덱스에 부담이 된다. 이메일은 사용자 식별처럼 보여도 변경 가능하고 재사용 정책도 필요하다. 대리키는 짧고 안정적인 참조를 만들기 쉽지만 업무 중복을 막지 않는다.

```sql
CREATE TABLE player (
    player_id BIGINT PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    CONSTRAINT uq_player_email UNIQUE (email)
);
```

대리키 `player_id`와 업무상 유일한 `email`을 함께 제약한다. 단, 이메일의 대소문자·정규화 규칙과 NULL 허용 여부는 서비스 정책과 DB Collation에 맞춰야 한다.

순차 증가 키는 비교와 인덱스 지역성이 좋을 수 있지만 여러 노드에서 생성 조정이 필요하고 외부 노출 시 사용자 수나 생성 순서를 추측하게 할 수 있다. 무작위 UUID는 분산 생성이 쉽지만 크기가 크고 B+Tree 삽입 위치가 흩어질 수 있다. 시간 순서 성격의 식별자도 같은 시각 충돌, 시계와 정보 노출을 고려한다. “UUID가 항상 확장에 좋다”가 아니라 생성·인덱스·노출 요구를 비교한다.

### 함수 종속성

함수 종속 `X → Y`는 같은 X 값을 가진 모든 행이 같은 Y 값을 가져야 한다는 의미다. 예를 들어 `player_id → email`이면 player_id가 정해질 때 email이 하나로 정해진다. 실제 현재 데이터가 우연히 중복되지 않았다는 사실만으로 종속성을 판단하지 않고 업무 규칙을 기준으로 한다.

```text
Enrollment(player_id, course_id, player_name, course_name, score)

(player_id, course_id) → score
player_id              → player_name
course_id              → course_name
```

성적은 플레이어와 과정의 조합에 종속되지만 이름은 복합키 전체가 아닌 일부에 종속된다. 이 차이가 2NF 분해의 근거가 된다.

### 제1정규형(1NF)

각 속성 값이 해당 관계가 다루는 도메인에서 원자적인 값이 되도록 한다. 한 열에 `sword,potion,shield`를 쉼표로 넣으면 특정 아이템 검색, FK, 수량 제약과 부분 갱신이 어려워진다. 인벤토리 아이템은 별도 행으로 표현한다.

원자성은 문자열을 더 이상 나눌 수 없다는 절대적 의미가 아니라 관계 연산에서 하나의 값으로 다루는 단위다. 주소를 한 열로 둘지 시·구·도로로 나눌지는 조회와 제약 요구에 달려 있다. JSON 열이 존재한다고 무조건 1NF 위반이라고 단정하기보다 그 내부 요소를 관계적으로 검색·제약해야 하는지 본다.

### 제2정규형(2NF)

1NF를 만족하고 기본키가 아닌 속성이 후보키의 일부에만 종속되는 부분 함수 종속을 제거한다. 주로 복합 후보키에서 의미가 있다.

```text
Before: Enrollment(player_id, course_id, player_name, course_name, score)

After:
Player(player_id, player_name)
Course(course_id, course_name)
Enrollment(player_id, course_id, score)
```

`player_name`은 player_id에, `course_name`은 course_id에만 종속되므로 각 테이블로 분리한다. Enrollment에는 조합 전체에 관한 score를 남긴다.

### 제3정규형(3NF)

2NF를 만족하고 비키 속성이 다른 비키 속성을 통해 후보키에 이행적으로 종속되는 문제를 줄인다.

```text
Character(character_id, guild_id, guild_name)

character_id → guild_id
guild_id     → guild_name

After:
Character(character_id, guild_id)
Guild(guild_id, guild_name)
```

길드 이름은 캐릭터 ID가 아니라 길드 ID에 관한 사실이다. 분리하면 길드 이름을 한 곳에서 바꿀 수 있다. BCNF는 모든 결정자가 후보키가 되도록 하는 더 강한 형태로 소개할 수 있지만 기본 면접에서는 1NF~3NF의 문제와 예를 정확히 설명하는 것이 우선이다.

### 무손실 분해와 종속성 보존

테이블을 분해한 뒤 조인했을 때 원래의 유효한 정보를 잃거나 가짜 조합이 생기지 않아야 한다. 이를 무손실 분해 관점으로 본다. 또한 중요한 제약을 여러 테이블 조인 없이 각 테이블의 키·제약으로 검사할 수 있으면 종속성 보존에 유리하다.

무조건 열을 각자 테이블로 분리하면 관계를 재구성할 정보가 부족하거나 모든 검증에 복잡한 조인이 필요해질 수 있다. 정규화는 함수 종속성과 키를 근거로 수행한다.

## 4. 쉬운 예시
Key와 정규화에서는 플레이어가 아이템을 구매하면 재화 확인, 차감, 아이템 생성이 연결된다. 일부만 반영되거나 동시에 두 번 처리되지 않도록 제약 조건과 트랜잭션 경계를 설계한다.

```text
Before
Membership(player_id, player_name, guild_id, guild_name, guild_level)

After
Player(player_id, player_name)
Guild(guild_id, guild_name, guild_level)
Membership(player_id, guild_id)
```

Before 구조에서는 길드원 수만큼 길드 이름과 레벨이 반복된다. After 구조에서는 길드 사실을 Guild 한 행에서 변경한다. Membership의 `player_id`에 UNIQUE를 두면 한 플레이어가 최대 한 길드에 속한다는 규칙을 표현할 수 있고, 여러 길드 가입을 허용한다면 `(player_id, guild_id)` 복합키를 선택할 수 있다.

## 5. 비슷한 개념과 비교
| 관점 | 질문 | 점검 항목 |
|---|---|---|
| 논리 모델 | 어떤 불변식인가 | Key·Constraint |
| 물리 실행 | 몇 Page를 읽는가 | Index·Plan |
| 동시성 | 무엇을 함께 허용하는가 | Transaction·Lock |

| 구분 | 정규화 | 반정규화 |
|---|---|---|
| 목표 | 중복·갱신 이상 감소 | 읽기 단순화·Join 비용 감소 |
| 쓰기 | 한 사실의 변경 지점 명확 | 여러 복사본 갱신 필요 |
| 읽기 | Join 필요 가능 | 미리 결합된 값 조회 가능 |
| 위험 | 과도한 분해와 복잡한 Query | Stale Data·복구 복잡성 |

인덱스와 키도 구분한다. 키는 유일성과 관계라는 논리 규칙이고 인덱스는 접근을 빠르게 하는 물리 구조다. DBMS는 PRIMARY KEY와 UNIQUE를 구현하기 위해 인덱스를 만들 수 있지만 모든 인덱스가 키는 아니고 FK에 자동 인덱스가 생기는지도 제품별로 다르다.

## 6. 장점과 단점
Key와 정규화에서는 RDBMS는 제약과 트랜잭션, 유연한 조회가 강점이다. 인덱스 유지, Lock 경쟁, Schema 변경과 수평 확장 비용이 있다. 읽기 최적화가 쓰기 비용을 만들 수 있음을 고려한다.

정규화는 중복을 줄여 저장 공간과 갱신 오류를 줄이고 테이블의 책임을 명확히 한다. 대신 조회 시 조인이 늘고 서비스가 여러 데이터 소유 경계를 오갈 수 있다. 반정규화는 자주 읽는 데이터를 미리 저장해 조회를 줄이지만 동기·비동기 갱신, 실패 복구와 재구축 절차가 필요하다.

## 7. 게임 서버·백엔드 실무 예시
길드 이름을 길드원 행마다 반복하지 않고 Guild와 Membership으로 분리한다. 조회 성능 때문에 반정규화할 때는 원본, 갱신 경로, 복구 방법을 명시한다.

Key와 정규화에서는 운영에서는 처리량만 보지 않고 쿼리 p95·p99, 실행 계획, 읽은 행·Page, Lock 대기, Deadlock과 Connection Pool을 함께 관찰한다.

랭킹 화면에서 플레이어 닉네임과 길드 이름을 매번 여러 테이블과 조인하는 것이 실제 병목이라면 읽기 전용 랭킹 테이블이나 캐시에 표시용 이름을 복제할 수 있다. 원본은 Player와 Guild이며 변경 이벤트로 읽기 모델을 갱신한다. 이벤트 누락을 대비해 원본에서 재구축하는 작업과 최대 허용 지연을 정한다.

인벤토리는 `InventoryItem(player_id, slot, item_instance_id, quantity)`처럼 설계할 수 있다. `(player_id, slot)` UNIQUE로 한 슬롯에 한 아이템만, `item_instance_id` UNIQUE로 고유 아이템 중복 배치를 막는다. 스택 가능한 아이템과 고유 장비의 불변식이 다르면 타입과 제약 또는 테이블 경계를 명확히 한다.

Schema 변경 시 새 NOT NULL 열을 한 번에 추가하고 모든 행을 갱신하면 큰 락과 로그를 만들 수 있다. Nullable 또는 Default 단계, 점진적 Backfill, 애플리케이션 이중 호환, 최종 제약 적용 순으로 배포하는 방법을 고려한다. 구체적인 Online DDL 능력은 DBMS와 버전을 확인한다.

## 8. 자주 하는 오해
- 제약 조건을 애플리케이션 검사만으로 대체한다.
- 인덱스가 많을수록 모든 쿼리가 빨라진다고 본다.
- 트랜잭션이 외부 API까지 자동 원자화한다고 생각한다.
- 격리 수준 이름만으로 구현 동작을 단정한다.
- 평균 쿼리 시간만 보고 꼬리 지연을 무시한다.
- 기본키만 있으면 업무 중복도 모두 방지된다고 생각한다.
- 대리키를 쓰면 자연키의 UNIQUE 제약이 필요 없다고 본다.
- 정규화는 무조건 테이블 수를 최대화하는 과정이라고 생각한다.
- 반정규화하면 Join 비용만 줄고 정합성 비용은 없다고 본다.
- 외래키와 인덱스를 같은 개념으로 본다.

중복 저장은 삽입·수정·삭제 시 서로 다른 값이 남는 이상을 만든다.
### Q3. 게임 백엔드에서는 어떻게 적용하나요?
길드 이름을 길드원 행마다 반복하지 않고 Guild와 Membership으로 분리한다. 조회 성능 때문에 반정규화할 때는 원본, 갱신 경로, 복구 방법을 명시한다.
### Q4. 성능 문제는 무엇을 확인하나요?
실행 계획과 실제 행 수, Index 사용, Lock 대기와 꼬리 지연을 확인한다.

### Q5. 슈퍼키와 후보키의 차이는 무엇인가요?

슈퍼키는 행을 유일하게 식별하는 모든 속성 집합이고 불필요한 속성을 포함할 수 있다. 후보키는 그중 어떤 속성을 제거해도 유일성을 잃는 최소 슈퍼키다. 후보키 중 하나를 기본키로 선택한다.

### Q6. 자연키와 대리키를 어떻게 선택하나요?

자연키가 짧고 불변이며 업무상 안정적이면 직접 사용할 수 있다. 변경 가능하거나 복합·대형이면 대리키로 참조를 단순화하되 자연키의 업무 유일성은 UNIQUE로 유지한다. 생성 분산, 인덱스 지역성과 외부 노출도 고려한다.

### Q7. 2NF와 3NF의 차이는 무엇인가요?

2NF는 복합 후보키의 일부에만 종속되는 비키 속성을 분리한다. 3NF는 비키 속성이 다른 비키 속성을 거쳐 후보키에 종속되는 이행 종속을 줄인다. 둘 다 현재 데이터 모양이 아니라 업무 함수 종속성을 기준으로 판단한다.
