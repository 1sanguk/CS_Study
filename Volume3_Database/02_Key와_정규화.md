# 02. Key와 정규화


## 학습 목표

- 슈퍼키·후보키·기본키의 관계와 대리키·자연키의 선택 기준을 설명할 수 있다.
- 함수 종속성을 근거로 1NF·2NF·3NF의 분해 이유와 방법을 설명할 수 있다.
- 삽입·수정·삭제 이상이 발생하는 원인을 예시로 설명할 수 있다.
- 정규화와 반정규화의 트레이드오프와 반정규화 시 동기화 책임을 설명할 수 있다.

## 1. 개요

키는 행을 식별하거나 관계를 연결하는 속성이고 정규화는 함수 종속성을 기준으로 중복과 갱신 이상을 줄이는 설계 과정이다.

키(Key)는 단순히 인덱스를 만드는 열이 아니라 데이터의 정체성과 관계를 표현하는 논리 제약이다. 정규화(Normalization)는 한 테이블에 섞인 서로 다른 사실을 함수 종속성에 따라 분리해 같은 사실을 여러 곳에서 수정해야 하는 문제를 줄인다.

정규화의 목표는 테이블을 가능한 많이 쪼개는 것이 아니다. 각 테이블이 무엇에 관한 사실을 저장하는지 명확히 하고 삽입·수정·삭제 이상을 줄이는 것이다. 실제 조회 요구 때문에 중복을 도입하는 반정규화는 가능하지만 원본과 동기화 책임을 함께 설계해야 한다.

## 2. 왜 필요한가

중복 저장은 삽입·수정·삭제 시 서로 다른 값이 남는 이상을 만든다. 키가 명확하지 않으면 중복 행을 구분하기 어렵고 다른 테이블이 안정적으로 참조할 수도 없다.

길드원 행마다 길드 이름과 길드 마스터 정보를 반복 저장한다고 하자. 길드 이름을 바꿀 때 일부 행만 갱신되면 같은 길드가 여러 이름을 가진다(수정 이상). 길드원이 아직 없으면 길드 정보를 저장할 행이 없고(삽입 이상), 마지막 길드원을 삭제하면서 길드 자체 정보까지 잃을 수 있다(삭제 이상).

애플리케이션에서 UUID를 발급했다고 닉네임 중복이나 동일 주문 중복 처리가 자동으로 막히지는 않는다. 식별용 키와 업무상 유일성 제약을 구분한다.

## 3. 핵심 동작 원리

```text
후보키 집합 중 하나 → 기본키 선택, 나머지 → 대체키(UNIQUE)
함수 종속 X→Y → 같은 X 값이면 항상 같은 Y 값 (업무 규칙)
1NF: 원자값 → 2NF: 부분 종속 제거 → 3NF: 이행 종속 제거
```

### 키의 종류

- **슈퍼키(Super Key)**: 행을 유일하게 식별하는 속성 집합. 불필요한 속성을 포함할 수 있다.
- **후보키(Candidate Key)**: 슈퍼키 중 어떤 속성을 빼도 유일성을 잃는 최소 집합.
- **기본키(Primary Key)**: 후보키 중 대표 식별자로 선택한 키.
- **대체키(Alternate Key)**: 후보키였지만 기본키로 선택되지 않은 키. UNIQUE 제약으로 보존한다.
- **복합키(Composite Key)**: 둘 이상의 속성으로 구성된 키.
- **외래키(Foreign Key)**: 다른 테이블의 후보키·고유키를 참조해 참조 무결성을 표현한다.

```text
Player(player_id PK, email UNIQUE, nickname UNIQUE)

Candidate Keys: {player_id}, {email}, {nickname}
Primary Key:    {player_id}
Alternate Keys: {email}, {nickname}

{player_id, email}은 슈퍼키지만 email을 빼도 유일 → 최소 후보키 아님
```

### 자연키와 대리키

자연키(Natural Key)는 이메일, 국가 코드처럼 업무 의미가 있는 값이다. 대리키(Surrogate Key)는 순번이나 UUID처럼 DB 식별을 위해 만든 값이다.

자연키는 업무 유일성을 직접 표현하지만 값이 바뀌거나 복합적이면 모든 참조와 인덱스에 부담이 된다. 대리키는 짧고 안정적인 참조를 만들기 쉽지만 업무 중복을 자동으로 막지 않는다. 대리키를 기본키로 쓰면 이메일·닉네임의 업무 유일성을 별도 UNIQUE로 보호해야 한다.

순차 증가 키는 B+Tree 삽입 지역성이 좋지만 외부 노출 시 생성 순서를 추측하게 할 수 있다. 무작위 UUID는 분산 생성이 쉽지만 삽입 위치가 흩어진다. 요구에 맞게 선택하고 성능은 측정으로 검증한다.

### 함수 종속성

함수 종속 `X → Y`는 같은 X 값을 가진 모든 행이 같은 Y 값을 가져야 한다는 업무 규칙이다. 현재 데이터가 우연히 중복되지 않았다고 종속성이 없다고 판단하지 않는다.

```text
Enrollment(player_id, course_id, player_name, course_name, score)

(player_id, course_id) → score      (복합키 전체에 종속)
player_id              → player_name (부분 종속: 2NF 위반)
course_id              → course_name (부분 종속: 2NF 위반)
```

### 제1정규형(1NF)

각 속성 값이 관계 연산에서 하나의 값으로 다루는 단위가 되도록 한다. 한 열에 `sword,potion,shield`를 쉼표로 넣으면 특정 아이템 검색, FK, 수량 제약과 부분 갱신이 어려워진다. 인벤토리 아이템은 별도 행으로 표현한다.

JSON 열이 있다고 무조건 1NF 위반이라고 단정하기보다 그 내부 요소를 관계적으로 검색·제약해야 하는지 본다.

### 제2정규형(2NF)

1NF를 만족하고 비키 속성이 후보키의 일부에만 종속되는 부분 함수 종속을 제거한다.

```text
Before: Enrollment(player_id, course_id, player_name, course_name, score)

After:
Player(player_id, player_name)        ← player_id에만 종속
Course(course_id, course_name)        ← course_id에만 종속
Enrollment(player_id, course_id, score) ← 복합키 전체에 종속
```

### 제3정규형(3NF)

2NF를 만족하고 비키 속성이 다른 비키 속성을 거쳐 후보키에 이행적으로 종속되는 문제를 줄인다.

```text
Before: Character(character_id, guild_id, guild_name)
character_id → guild_id → guild_name (이행 종속)

After:
Character(character_id, guild_id)
Guild(guild_id, guild_name)
```

길드 이름은 캐릭터 ID가 아니라 길드 ID에 관한 사실이다. 분리하면 길드 이름을 한 행에서만 변경할 수 있다.

## 4. 쉬운 예시

```sql
-- Before: 길드원 행마다 길드 정보 반복 (갱신 이상 발생 가능)
-- membership(player_id, player_name, guild_id, guild_name, guild_level)
-- guild_name을 바꿀 때 길드원 수만큼 UPDATE 필요 → 일부만 갱신되면 불일치

-- After: 정규화
CREATE TABLE guild (
    guild_id   BIGINT PRIMARY KEY,
    guild_name VARCHAR(64) NOT NULL,
    guild_level INT NOT NULL DEFAULT 1
);

CREATE TABLE membership (
    player_id BIGINT NOT NULL,
    guild_id  BIGINT NOT NULL REFERENCES guild(guild_id),
    joined_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (player_id)          -- 한 플레이어가 한 길드만 가입 가능
    -- 다중 길드 허용 시: PRIMARY KEY (player_id, guild_id)
);

-- 길드 이름 변경: guild 한 행만 UPDATE
UPDATE guild SET guild_name = '최강길드' WHERE guild_id = 42;
-- membership 행은 건드리지 않음
```

```sql
-- 반정규화: 랭킹 표시용 비정규화 (원본은 player 테이블)
CREATE TABLE ranking_display (
    rank_position INT PRIMARY KEY,
    player_id     BIGINT NOT NULL,
    player_name   VARCHAR(32),  -- player 테이블에서 복제
    score         BIGINT NOT NULL
);
-- 닉네임 변경 시 ranking_display도 갱신해야 함
-- 이벤트 기반 동기화 + 원본에서 주기적 재구축 절차 필요
```

```sql
-- 대리키 + 자연키 UNIQUE 함께 사용
CREATE TABLE player (
    player_id BIGINT PRIMARY KEY,         -- 대리키: 안정적 참조
    email     VARCHAR(255) NOT NULL,
    nickname  VARCHAR(32) NOT NULL,
    CONSTRAINT uq_player_email    UNIQUE (email),    -- 업무 유일성
    CONSTRAINT uq_player_nickname UNIQUE (nickname)  -- 업무 유일성
);
```

## 5. 비슷한 개념과 비교

| 구분 | 정규화 | 반정규화 |
|---|---|---|
| 목표 | 중복·갱신 이상 감소 | 읽기 단순화·Join 비용 감소 |
| 쓰기 | 한 사실의 변경 지점 명확 | 여러 복사본 갱신 필요 |
| 읽기 | Join 필요 가능 | 미리 결합된 값 조회 가능 |
| 위험 | 과도한 분해·복잡한 Query | Stale Data·복구 복잡성 |

| 구분 | 자연키 | 대리키 |
|---|---|---|
| 업무 의미 | 직접 표현 | 없거나 약함 |
| 안정성 | 변경 가능 (이메일 등) | 불변 |
| 크기 | 다양 (복합·대형 가능) | 짧음 (BIGINT/UUID) |
| 업무 유일성 | 키 자체로 표현 | 별도 UNIQUE 제약 필요 |

외래키(FK)는 참조 무결성이라는 논리 규칙이고 인덱스는 접근을 빠르게 하는 물리 구조다. FK 구현을 위해 인덱스가 자동 생성되는지는 제품별로 다르다.

## 6. 장점과 단점

**정규화의 장점**

- 같은 사실의 변경 지점이 하나이므로 수정·삭제 이상을 줄인다.
- 각 테이블의 책임이 명확해 제약 조건을 간단하게 표현할 수 있다.
- 저장 중복을 줄여 공간을 절약하고 쓰기 시 갱신해야 할 열 수가 적다.

**정규화의 단점**

- 관련 데이터를 조회할 때 여러 테이블을 조인해야 할 수 있다.
- 과도한 분해는 복잡한 쿼리와 실행 계획을 만들 수 있다.

**반정규화의 장점**

- 자주 읽는 데이터를 미리 결합해 조인 비용과 쿼리 복잡성을 줄인다.

**반정규화의 단점**

- 원본이 바뀔 때 복제본도 갱신해야 한다. 갱신 누락 시 불일치가 생긴다.
- 갱신 실패 복구와 원본에서 재구축하는 절차를 함께 설계해야 한다.
- 허용 가능한 지연과 일관성 수준을 명시해야 한다.

## 7. 게임 서버·백엔드 실무 예시

길드 이름을 길드원 행마다 반복하지 않고 Guild와 Membership으로 분리한다. 조회 성능 때문에 반정규화할 때는 원본, 갱신 경로, 복구 방법을 명시한다.

랭킹 화면에서 닉네임과 길드 이름을 매번 여러 테이블과 조인하는 것이 실제 병목이라면 읽기 전용 랭킹 테이블이나 캐시에 표시용 이름을 복제할 수 있다. 변경 이벤트로 읽기 모델을 갱신하고 이벤트 누락을 대비해 원본에서 재구축하는 작업과 최대 허용 지연을 정한다.

인벤토리는 `(player_id, slot)` UNIQUE로 한 슬롯에 한 아이템만, `item_instance_id` UNIQUE로 고유 아이템 중복 배치를 막는다. 스택 가능한 아이템과 고유 장비의 불변식이 다르면 타입과 제약 또는 테이블 경계를 명확히 한다.

대형 테이블에 NOT NULL 열을 추가할 때는 Nullable 또는 Default 단계, 점진적 Backfill, 최종 제약 적용 순으로 배포해 큰 락을 피한다.

## 8. 자주 하는 오해

- **"기본키만 있으면 업무 중복도 모두 방지된다"**: 대리키 player_id는 행을 식별하지만 닉네임·이메일 중복을 막지 않는다. 업무상 유일성은 별도 UNIQUE 제약이 필요하다.
- **"대리키를 쓰면 자연키의 UNIQUE 제약이 필요 없다"**: 대리키는 DB 내 식별을 위한 것이다. 이메일이 업무상 유일해야 한다면 UNIQUE를 따로 두어야 동시 삽입도 막을 수 있다.
- **"정규화는 테이블 수를 최대화하는 과정이다"**: 목표는 함수 종속성을 기준으로 중복과 갱신 이상을 줄이는 것이다. 과도한 분해는 복잡한 조인을 만들 수 있다.
- **"반정규화하면 Join 비용만 줄고 정합성 비용은 없다"**: 원본이 바뀔 때 복제본도 갱신해야 한다. 갱신 누락 시 불일치가 생기고 재구축 절차와 허용 지연을 설계해야 한다.
- **"외래키는 인덱스와 같다"**: 외래키는 참조 무결성이라는 논리 규칙이고 인덱스는 접근을 빠르게 하는 물리 구조다. FK 구현을 위한 인덱스가 자동 생성되는지는 제품별로 다르다.
- **"현재 데이터에 중복이 없으면 함수 종속성이 없다"**: 함수 종속성은 현재 데이터 모양이 아니라 업무 규칙으로 판단한다. 우연히 지금은 중복이 없어도 업무상 종속성이 있을 수 있다.
- **"1NF는 JSON 열을 쓰면 무조건 위반이다"**: 핵심은 관계 연산에서 하나의 값으로 다루는 단위다. JSON 내부 요소를 관계적으로 검색·제약해야 하면 문제가 되지만 단순 저장이라면 다를 수 있다.

## 9. 면접 질문

### Q1. 후보키와 기본키의 차이를 설명해 주세요.

후보키는 슈퍼키 중 어떤 속성을 빼도 유일성을 잃는 최소 집합이다. 기본키는 여러 후보키 중 대표 식별자로 선택한 키로 NULL을 허용하지 않는다. 선택되지 않은 후보키는 대체키로 UNIQUE 제약으로 보존한다.

### Q2. 자연키와 대리키를 어떻게 선택하나요?

자연키가 짧고 불변이며 업무상 안정적이면 직접 사용할 수 있다. 변경 가능하거나 복합·대형이면 대리키로 참조를 단순화하되 자연키의 업무 유일성은 UNIQUE로 따로 보호한다. 대리키를 쓴다고 업무 유일성 제약이 자동으로 생기지 않는다.

### Q3. 갱신 이상이란 무엇이고 어떻게 발생하나요?

한 사실이 여러 행에 반복 저장될 때 발생한다. 수정 이상은 일부 행만 갱신되어 같은 사실이 서로 다른 값을 가지는 것이고, 삽입 이상은 저장하고 싶은 사실이 다른 데이터와 묶여 있어 별도로 저장하기 어려운 것이며, 삭제 이상은 행을 삭제할 때 원치 않는 다른 사실도 함께 잃는 것이다. 정규화로 각 사실을 한 곳에 저장하면 이상을 줄인다.

### Q4. 2NF와 3NF의 차이를 설명해 주세요.

2NF는 복합 후보키의 일부에만 종속되는 비키 속성(부분 함수 종속)을 분리한다. 3NF는 비키 속성이 다른 비키 속성을 거쳐 후보키에 종속되는 이행 종속을 줄인다. 둘 다 현재 데이터 모양이 아니라 업무 함수 종속성을 기준으로 판단한다.

### Q5. 반정규화는 언제 사용하고 무엇을 주의해야 하나요?

자주 읽는 데이터를 조인 없이 빠르게 조회해야 하고 읽기가 쓰기보다 훨씬 많을 때 검토한다. 단 원본이 바뀔 때 복제본도 갱신해야 하며 갱신 누락 시 불일치가 생긴다. 갱신 경로, 허용 지연, 실패 복구, 원본에서 재구축하는 절차를 함께 설계한다.

### Q6. 인벤토리 테이블을 어떻게 설계하나요?

아이템을 열로 저장하지 않고 행으로 표현한다. `(player_id, slot)` UNIQUE로 한 슬롯에 한 아이템만, 고유 아이템이라면 `item_instance_id` UNIQUE로 중복 배치를 막는다. 스택 가능한 아이템과 고유 장비의 불변식이 다르면 타입과 제약을 명확히 분리한다.

## 10. 예상 꼬리질문

- 슈퍼키에서 후보키를 구분하는 기준은 무엇인가요?
  > 슈퍼키는 행을 유일하게 식별하는 속성 집합이며 불필요한 속성을 포함할 수 있다. 후보키는 슈퍼키 중 어떤 속성을 하나라도 제거하면 유일성을 잃는 최소 집합이다. 즉 최소성이 후보키를 슈퍼키와 구분하는 기준이다.
- UUID와 자동증가 키의 인덱스 성능 차이는 무엇인가요?
  > 자동증가 키는 항상 B+Tree의 마지막 리프 페이지에 순차 삽입되어 Page Split이 드물고 버퍼 풀 지역성이 좋다. UUID는 삽입 위치가 트리 전체에 무작위로 분산되어 기존 페이지를 매번 메모리로 불러와야 하고 Page Split 빈도가 높아 쓰기 성능이 저하된다. 분산 생성 편의와 외부 노출 보안이 필요하다면 시간 순 정렬이 가능한 UUIDv7 같은 방식을 검토한다.
- 무손실 분해란 무엇인가요?
  > 테이블을 분해했을 때 분해된 테이블을 다시 조인하면 원본 테이블을 완전히 복원할 수 있는 성질이다. 무손실 분해가 보장되지 않으면 조인 결과에 원본에 없던 행(Spurious Tuple)이 생기거나 원본 행이 누락될 수 있다. 함수 종속성을 기준으로 올바르게 분해하면 무손실성이 보장된다.
- BCNF는 3NF와 어떻게 다른가요?
  > 3NF는 비키 속성이 후보키에 이행적으로 종속되지 않아야 한다는 조건이다. BCNF는 더 엄격하게 모든 함수 종속의 결정자가 후보키여야 한다고 요구한다. 실제로 3NF를 만족하면서도 BCNF를 위반하는 경우는 드물지만, BCNF 분해는 무손실성을 보장하면서도 일부 함수 종속성을 보존하지 못할 수 있어 실용성과 정합성을 함께 고려한다.
- 반정규화한 읽기 모델을 어떻게 재구축하나요?
  > 원본 테이블을 소스로 삼아 전체 데이터를 읽기 모델에 다시 써넣는 배치 Job을 준비한다. 이벤트 기반 동기화가 실패하거나 지연된 경우 이 Job으로 일관성을 복원한다. 재구축 중에도 서비스가 이전 데이터를 읽을 수 있도록 Blue-Green 방식이나 버전 열로 전환 시점을 제어하고, 허용 가능한 최대 지연을 SLA로 명시한다.
- 외래키 없이 참조 무결성을 어떻게 보장하나요?
  > 애플리케이션 레이어에서 삽입·수정·삭제 전 참조 대상 존재 여부를 확인하고, 주기적인 정합성 검사 배치 Job으로 고아 행을 탐지한다. 메시지 큐 기반 아키텍처에서는 이벤트 소비 시 참조 무결성 위반을 감지해 보상 처리한다. DB 레벨 FK가 없으면 동시성 환경에서 Check-then-Act 사이 레이스 컨디션이 발생할 수 있으므로 주의한다.
- 복합키와 대리키 중 무엇을 선택하나요?
  > 복합키는 업무 의미를 직접 표현하고 별도 JOIN 없이 유일성을 확인할 수 있지만, 여러 열이 외래키로 전파되면 참조 테이블의 인덱스 크기와 쓰기 비용이 커진다. 대리키는 짧고 불변인 식별자로 참조를 단순화하지만 업무 유일성은 별도 UNIQUE 제약으로 보호해야 한다. 참조가 많고 복합키가 변경 가능성이 있다면 대리키가 유리하다.

## 12. 1~2분 확장답변

> 키는 행과 관계의 정체성을 보장하고 정규화는 함수 종속성에 따라 사실을 분리해 삽입·수정·삭제 이상을 줄입니다. 대리키는 안정적 참조를 제공하지만 이메일·닉네임처럼 업무상 유일해야 하는 값은 별도 UNIQUE로 보호해야 합니다. 2NF는 복합 후보키의 일부에만 종속된 비키 속성을 분리하고, 3NF는 비키 속성이 다른 비키 속성을 거쳐 종속되는 이행 종속을 줄입니다. 랭킹 화면에서 닉네임을 매번 조인하는 것이 병목이라면 반정규화를 검토할 수 있지만 닉네임이 변경될 때 읽기 모델도 갱신해야 하고 이벤트 누락을 대비한 재구축 절차가 필요합니다.

## 13. 핵심 요약

- 슈퍼키는 행을 유일하게 식별하는 속성 집합이고, 후보키는 그중 최소 집합이며, 기본키는 대표 식별자로 선택한 후보키다.
- 대리키는 안정적 식별을 제공하지만 업무상 유일성(닉네임, 이메일)은 별도 UNIQUE 제약으로 보호해야 한다.
- 함수 종속 X→Y는 현재 데이터 모양이 아닌 업무 규칙으로 판단한다. 우연히 중복이 없어도 종속성이 있을 수 있다.
- 2NF는 복합 후보키의 일부에만 종속되는 부분 종속을 분리하고, 3NF는 비키 속성이 다른 비키 속성을 통해 종속되는 이행 종속을 줄인다.
- 정규화는 삽입·수정·삭제 이상을 줄이고 각 테이블의 책임을 명확히 한다. 과도한 분해는 복잡한 조인을 만들 수 있다.
- 반정규화는 읽기를 단순화하지만 원본과 복제본 동기화, 갱신 실패 복구, 재구축 절차를 함께 설계해야 한다.
- 외래키는 참조 무결성이라는 논리 규칙이고 인덱스는 접근을 빠르게 하는 물리 구조다. FK에 자동 인덱스가 생기는지는 제품별로 다르다.
- 대형 테이블에 NOT NULL 열을 추가할 때는 Nullable→점진적 Backfill→최종 제약 적용 순으로 배포해 큰 락을 피한다.
