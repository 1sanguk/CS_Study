# 01. RDBMS와 SQL 기초

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 한 줄 정의와 등장 이유를 설명할 수 있다.
- 핵심 동작과 비교 개념을 설명할 수 있다.
- 게임 백엔드의 정합성과 성능 설계에 적용할 수 있다.

## 1. 개요

RDBMS는 행과 열의 테이블, 관계, 제약 조건으로 데이터를 관리하고 SQL은 이를 정의·조회·변경하는 선언적 언어다.

관계형 데이터베이스 관리 시스템(RDBMS)은 데이터를 릴레이션(Relation)이라는 논리 구조로 표현한다. 실무에서는 릴레이션을 테이블, 튜플(Tuple)을 행, 속성(Attribute)을 열로 대응해 설명한다. 각 열은 허용되는 타입과 제약을 가지고 행은 하나의 사실을 나타낸다.

SQL(Structured Query Language)은 “어떤 반복문으로 데이터를 찾을지”보다 “어떤 결과가 필요한지”를 선언한다. DBMS의 옵티마이저가 인덱스와 통계, 조인 순서를 이용해 물리 실행 계획을 선택한다. SQL이 짧다고 실행 비용도 작은 것은 아니다.

## 2. 왜 필요한가
정형 데이터의 일관성을 제약 조건과 트랜잭션으로 보장하고 다양한 조건의 조회를 지원한다. 데이터베이스 선택은 편의가 아니라 불변식, 조회 패턴, 장애 복구 요구에서 출발한다.

게임 백엔드의 플레이어, 캐릭터, 재화와 아이템은 서로 관계를 가진다. 캐릭터는 존재하는 플레이어에 속해야 하고 닉네임은 중복되면 안 되며 재화는 허용 범위 안에 있어야 한다. 이런 규칙을 애플리케이션 코드에만 흩어 놓으면 여러 서비스와 배치 작업이 서로 다르게 적용할 수 있다. 스키마와 제약 조건은 데이터가 저장되는 마지막 경계에서 공통 불변식을 지킨다.

RDBMS는 임의 조건 필터, 정렬, 집계와 조인을 제공해 접근 패턴이 다양하거나 변하는 업무에 유리하다. 트랜잭션과 복구 로그는 일부 변경만 남는 문제를 줄인다. 반면 모든 데이터가 고정 스키마와 강한 관계를 필요로 하는 것은 아니므로 문서형 저장소, 키-값 저장소와 캐시를 요구에 따라 함께 사용할 수 있다.

## 3. 핵심 동작 원리
```text
SQL parse→optimize plan→execute operators→storage pages→result
```
DDL은 구조, DML은 데이터, DCL은 권한, TCL은 트랜잭션을 다룬다. 논리 SQL 순서와 실제 실행 계획은 다를 수 있다.

RDBMS와 SQL 기초에서는 논리 모델과 물리 실행을 구분한다. 같은 SQL도 통계, 데이터 분포, 인덱스와 동시 부하에 따라 실행 비용이 달라진다.

### 관계형 모델의 기본 요소

```text
Player Table
┌───────────┬──────────────┬─────────┐
│ player_id │ nickname     │ balance │  ← Attribute(Column)
├───────────┼──────────────┼─────────┤
│ 101       │ KnightA      │ 1200    │  ← Tuple(Row)
│ 102       │ MageB        │ 800     │
└───────────┴──────────────┴─────────┘
      ↑
 Primary Key로 Row 식별
```

릴레이션은 논리적으로 행 순서를 보장하지 않는다. `ORDER BY`가 없으면 현재 저장 순서나 실행 계획에 따라 결과 순서가 달라질 수 있다. 열 순서도 관계형 모델의 핵심 의미라기보다 스키마 표현과 결과 형식의 일부다.

NULL은 값이 없거나 알 수 없음을 표현하며 0이나 빈 문자열과 다르다. SQL 비교에는 참, 거짓, 알 수 없음의 3값 논리가 적용된다. `column = NULL`이 아니라 `IS NULL`을 사용하고, `NOT IN` 목록에 NULL이 있을 때처럼 예상 밖 결과가 생길 수 있는 표현을 주의한다. 비즈니스상 반드시 필요한 값에는 `NOT NULL`을 적용해 불확실성을 줄인다.

### 주요 무결성 제약

- `PRIMARY KEY`: 행을 고유하게 식별하고 일반적으로 NULL을 허용하지 않는다.
- `UNIQUE`: 지정 열 조합의 중복을 제한한다. NULL 처리 세부는 DBMS별로 확인한다.
- `FOREIGN KEY`: 자식 값이 참조 대상에 존재하도록 참조 무결성을 지킨다.
- `NOT NULL`: 값 부재를 허용하지 않는다.
- `CHECK`: 잔액이 0 이상 같은 행 수준 조건을 검증한다.
- `DEFAULT`: 값을 생략했을 때 기본값을 제공한다. 기존 행 변경과 같은 의미는 아니다.

외래키는 부모 삭제 시 거부, 연쇄 삭제, NULL 설정 같은 동작을 선택할 수 있다. 편리한 연쇄 삭제는 예상보다 넓은 데이터와 많은 행을 잠글 수 있으므로 도메인 수명주기에 맞춘다. 모든 복잡한 비즈니스 규칙을 단일 CHECK나 FK로 표현할 수는 없지만 DB에서 표현 가능한 핵심 무결성은 제약으로 이중 방어한다.

### SQL 분류

```sql
CREATE TABLE player (...);                 -- DDL
INSERT INTO player (...) VALUES (...);     -- DML
SELECT player_id FROM player WHERE ...;    -- Query/DML 분류 관례 차이
GRANT SELECT ON player TO analyst;         -- DCL
COMMIT;                                    -- TCL
```

DDL(Data Definition Language)은 스키마 객체를 정의·변경한다. DML(Data Manipulation Language)은 데이터를 조회·변경한다. DCL은 권한, TCL은 트랜잭션 제어에 관한 분류다. 명령 분류와 트랜잭션 처리 방식은 제품별 차이가 있으므로 DDL이 언제나 자동 커밋된다고 일반화하지 않는다.

### SELECT의 논리 처리와 실제 실행

SELECT 문을 작성하는 순서와 논리적으로 결과를 구성하는 순서는 다르게 설명할 수 있다.

```text
FROM·JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

이 순서는 별칭 사용 가능 위치나 집계 필터 차이를 이해하는 데 도움을 주는 논리 모델이다. 실제 DB 엔진은 결과 의미를 유지하면서 조건을 아래로 밀고 조인 순서를 바꾸며 인덱스를 선택한다. 실행 계획의 연산 순서를 논리 순서와 동일하다고 보면 안 된다.

`WHERE`는 그룹화 전 행을 필터하고 `HAVING`은 그룹화 결과를 필터한다. 불필요한 행을 일찍 줄일 수 있는 조건은 보통 `WHERE`에 두는 것이 유리하지만 옵티마이저가 변환할 수도 있다.

### SQL 실행 과정

1. Parser가 문법과 객체 이름을 확인하고 내부 표현을 만든다.
2. Optimizer가 가능한 접근 경로와 Join 순서의 비용을 추정한다.
3. Executor가 Scan, Filter, Join, Sort, Aggregate 같은 연산자를 실행한다.
4. Buffer Pool과 Storage Engine이 필요한 Page와 Row를 읽고 Lock·MVCC 규칙을 적용한다.
5. 결과가 Network를 통해 Client로 반환된다.

옵티마이저의 비용은 통계와 추정치에 기반한다. 오래된 통계, 열 사이 상관관계, 매개변수에 따른 데이터 편향으로 예상 행 수가 실제와 크게 다르면 비효율적인 조인이나 스캔을 선택할 수 있다. `EXPLAIN` 계열 실행 계획에서 추정 행 수와 실제 행 수, 읽은 페이지, 정렬과 임시 공간을 확인한다.

### 논리 스키마와 물리 저장

SQL 사용자는 테이블과 행을 보지만 저장 엔진은 고정 크기 페이지에 레코드와 인덱스 노드를 저장한다. 한 행을 조회해도 디스크와 버퍼 풀은 페이지 단위로 접근할 수 있다. 인덱스는 필요한 행의 위치를 빠르게 찾는 별도 구조지만 쓰기 때 함께 갱신해야 한다.

페이지가 버퍼 풀에 있으면 저장장치 I/O 없이 읽을 수 있고 없으면 디스크나 SSD에서 가져와야 한다. 같은 쿼리도 Cold Cache와 Warm Cache에서 지연이 다른 이유다. 논리 행 수뿐 아니라 실제 페이지 읽기와 캐시 적중을 보는 이유다.

## 4. 쉬운 예시
RDBMS와 SQL 기초에서는 플레이어가 아이템을 구매하면 재화 확인, 차감, 아이템 생성이 연결된다. 일부만 반영되거나 동시에 두 번 처리되지 않도록 제약 조건과 트랜잭션 경계를 설계한다.

```sql
UPDATE player
SET balance = balance - 100
WHERE player_id = 101
  AND balance >= 100;
```

이 조건부 갱신은 잔액 확인과 차감을 DB의 한 변경 문장으로 표현한다. 영향받은 행이 1개면 차감 성공, 0개면 플레이어가 없거나 잔액이 부족한 것이다. 이어지는 아이템 생성과 하나의 트랜잭션으로 묶어야 둘 중 하나만 반영되는 문제를 막을 수 있다.

`SELECT balance`로 먼저 확인하고 별도 `UPDATE`를 실행하면 그 사이 다른 요청이 잔액을 변경할 수 있다. SQL 문장을 썼다는 사실만으로 동시성이 안전한 것이 아니라 조건부 변경, 락 또는 격리 수준과 트랜잭션 경계가 필요하다.

## 5. 비슷한 개념과 비교
| 관점 | 질문 | 점검 항목 |
|---|---|---|
| 논리 모델 | 어떤 불변식인가 | Key·Constraint |
| 물리 실행 | 몇 Page를 읽는가 | Index·Plan |
| 동시성 | 무엇을 함께 허용하는가 | Transaction·Lock |

| 구분 | RDBMS | Key-Value Store | Document DB |
|---|---|---|---|
| 기본 모델 | Table·Relation | Key→Value | Document |
| 강점 | Constraint·Join·Transaction·SQL | 단순 Key 접근·확장 | 유연한 중첩 구조 |
| 적합 예 | 재화·결제·인벤토리 원장 | Session·단순 Cache | 구조가 다양한 Content |
| 주의점 | Schema·Join·Write 비용 | 보조 Query 직접 설계 | 중복 Data 정합성 |

NoSQL은 SQL을 절대 지원하지 않거나 정합성이 없다는 뜻이 아니다. 제품마다 Query, Transaction과 일관성 수준이 다르다. 저장소 범주보다 실제 보장과 접근 패턴을 확인한다.

## 6. 장점과 단점
RDBMS와 SQL 기초에서는 RDBMS는 제약과 트랜잭션, 유연한 조회가 강점이다. 인덱스 유지, Lock 경쟁, Schema 변경과 수평 확장 비용이 있다. 읽기 최적화가 쓰기 비용을 만들 수 있음을 고려한다.

정규화된 관계 구조는 중복을 줄이고 한 사실의 변경 지점을 명확히 한다. 조인을 통해 여러 관점의 결과를 만들 수 있다. 반면 대규모 조인과 집계는 CPU·메모리·I/O를 사용하고, 엄격한 단일 노드 트랜잭션 경계를 여러 샤드로 확장하면 복잡성이 커진다. 읽기 모델을 별도로 비정규화할 때는 갱신 경로와 허용 가능한 지연을 정의한다.

## 7. 게임 서버·백엔드 실무 예시
플레이어, 캐릭터, 아이템을 테이블과 FK로 표현하고 잔액·수량은 CHECK와 트랜잭션으로 보호한다. SELECT *를 피하고 실행 계획과 실제 행 수를 확인한다.

RDBMS와 SQL 기초에서는 운영에서는 처리량만 보지 않고 쿼리 p95·p99, 실행 계획, 읽은 행·Page, Lock 대기, Deadlock과 Connection Pool을 함께 관찰한다.

플레이어 닉네임 중복은 조회 후 애플리케이션에서만 검사하지 않고 DB에 UNIQUE 제약을 둔다. 동시 요청 둘이 모두 사전 조회에서 “없음”을 보더라도 삽입 시 하나만 성공하게 한다. 애플리케이션은 중복 키 오류를 예상 가능한 비즈니스 결과로 변환한다.

외래키를 사용할지 여부는 쓰기량과 서비스 경계를 고려하지만, 사용하지 않는다면 존재하지 않는 부모를 참조하는 행을 어떻게 막고 정리할지 명시해야 한다. “성능 때문에 FK를 제거한다”에서 끝내지 않고 측정된 비용과 대체 무결성 절차가 필요하다.

`SELECT *`는 사용하지 않는 대형 열까지 읽고 네트워크로 보내며 스키마 변경에 클라이언트를 민감하게 만들 수 있다. 필요한 열만 선택한다. 페이지네이션은 큰 `OFFSET`이 앞 행을 계속 건너뛰는 비용을 만들 수 있어 정렬 키 기반 Keyset 방식도 고려한다.

## 8. 자주 하는 오해
- 제약 조건을 애플리케이션 검사만으로 대체한다.
- 인덱스가 많을수록 모든 쿼리가 빨라진다고 본다.
- 트랜잭션이 외부 API까지 자동 원자화한다고 생각한다.
- 격리 수준 이름만으로 구현 동작을 단정한다.
- 평균 쿼리 시간만 보고 꼬리 지연을 무시한다.
- Table의 Row는 저장 순서대로 항상 반환된다고 생각한다.
- NULL을 0이나 빈 문자열과 같다고 본다.
- SQL 한 문장이면 모든 비즈니스 연산이 자동으로 원자적이라고 생각한다.
- 선언형 SQL은 실행 방법을 전혀 고려하지 않아도 된다고 본다.

## 9. 면접 질문
### Q1. 핵심 개념을 설명해 주세요.
RDBMS는 행과 열의 테이블, 관계, 제약 조건으로 데이터를 관리하고 SQL은 이를 정의·조회·변경하는 선언적 언어다.
### Q2. 왜 필요한가요?
정형 데이터의 일관성을 제약 조건과 트랜잭션으로 보장하고 다양한 조건의 조회를 지원한다.
### Q3. 게임 백엔드에서는 어떻게 적용하나요?
플레이어, 캐릭터, 아이템을 테이블과 FK로 표현하고 잔액·수량은 CHECK와 트랜잭션으로 보호한다. SELECT *를 피하고 실행 계획과 실제 행 수를 확인한다.
### Q4. 성능 문제는 무엇을 확인하나요?
실행 계획과 실제 행 수, Index 사용, Lock 대기와 꼬리 지연을 확인한다.

### Q5. SQL이 선언적이라는 뜻은 무엇인가요?

개발자가 원하는 결과와 조건을 표현하고 DBMS가 통계와 인덱스를 바탕으로 Scan·Join 순서 같은 물리 실행 방법을 선택한다는 뜻이다. 같은 SQL도 데이터 분포와 통계에 따라 실행 계획과 비용이 달라질 수 있다.

### Q6. DB 제약 조건이 필요한 이유는 무엇인가요?

여러 애플리케이션과 동시 요청이 데이터를 변경해도 저장 경계에서 공통 불변식을 지키기 위해서다. UNIQUE로 닉네임 중복을 막고 FK로 참조 존재를 확인하며 CHECK로 값 범위를 제한할 수 있다.

### Q7. NULL을 다룰 때 무엇을 주의해야 하나요?

NULL은 0이나 빈 문자열이 아니라 알 수 없거나 없는 값이다. 일반 비교 대신 `IS NULL`을 사용하고 SQL의 3값 논리 때문에 `NOT IN`, 조건식과 집계 결과가 예상과 달라질 수 있음을 고려한다.
