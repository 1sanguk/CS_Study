# 05. Race Condition과 Critical Section


## 학습 목표

- 경쟁 상태와 임계 구역의 정확한 의미를 읽기-수정-쓰기 원자성 관점에서 설명할 수 있다.
- 보호할 불변식을 정의하고 락의 범위를 결정하는 기준을 설명할 수 있다.
- 경쟁 상태와 데이터 레이스, TOCTOU의 차이를 설명할 수 있다.
- 게임 서버에서 동시 아이템·재화 처리에 메모리 락과 DB 트랜잭션·멱등성을 함께 적용하는 이유를 설명할 수 있다.

## 1. 개요

경쟁 상태는 실행 순서에 따라 결과가 달라지는 오류이고 임계 구역은 공유 상태를 변경해 동시 접근을 제어할 코드 영역이다.

좀 더 정확히 말하면 여러 실행 흐름이 공유 자원에 접근하고, 그중 하나 이상이 값을 변경하며, 접근 순서가 적절히 동기화되지 않을 때 경쟁 상태가 발생할 수 있다. 결과가 매번 틀리는 것은 아니다. 특정 실행 순서에서만 갱신 손실, 중복 처리, 손상된 자료구조가 나타나기 때문에 테스트에서는 통과하고 운영 부하에서 드물게 발생하기 쉽다.

임계 구역(Critical Section)은 "락을 거는 코드" 자체가 아니라 동시에 실행되면 안 되는 공유 상태 접근 구간이다. 어떤 데이터의 어떤 불변식을 보호하는지가 먼저이고, 락이나 메시지 큐는 그 구간을 안전하게 만드는 수단이다.

## 2. 왜 필요한가

count 증가도 읽기·계산·쓰기로 나뉘므로 두 스레드가 겹치면 갱신을 잃는다. 동시성 버그는 실행 순서와 부하에 따라 간헐적으로 나타나므로 불변식과 소유권을 설계 단계에서 명시해야 한다.

고수준 코드 한 줄이 CPU(Central Processing Unit) 관점에서도 하나의 원자 연산이라는 보장은 없다. `count++`는 현재 값을 읽고 증가시킨 뒤 저장하는 여러 단계가 될 수 있다. 컬렉션에서 "없으면 추가"도 조회와 삽입이라는 복합 연산이다. 각 메서드가 개별적으로 스레드 안전하더라도 둘 사이에 다른 스레드가 끼어들 수 있다.

동기화하지 않은 코드는 단순히 오래된 값을 읽는 데서 끝나지 않는다. 언어와 메모리 모델이 허용하는 범위에서 컴파일러와 CPU가 접근 순서를 바꾸거나 코어별 캐시에 값이 머물 수 있다. 따라서 소스 코드에서 우연히 원하는 순서로 보인다는 사실은 스레드 간 관찰 순서를 보장하지 않는다.

## 3. 핵심 동작 원리

```text
A read 10 → B read 10 → A write 11 → B write 11
```

두 번 증가했지만 최종 값은 11이다. 각 스레드의 계산은 독립적으로 맞았으나 읽기-수정-쓰기 전체가 원자적이지 않아 한 갱신이 사라졌다.

락, 원자 연산, 불변 데이터, 메시지 전달로 공유를 줄인다. 동기화의 목적은 모든 실행을 막는 것이 아니라 필요한 원자성과 관찰 순서를 최소 범위에 제공하는 것이다.

### 임계 구역의 요구사항

고전적으로 임계 구역 해결은 다음 성질을 고려한다.

- 상호 배제(Mutual Exclusion): 한 실행 흐름이 임계 구역에 있으면 충돌하는 다른 흐름은 동시에 들어가지 않는다.
- 진행(Progress): 아무도 임계 구역에 없고 진입하려는 작업이 있다면 무관한 작업 때문에 결정이 무한히 미뤄지지 않는다.
- 한정 대기(Bounded Waiting): 진입을 요청한 작업이 다른 작업에게 무한히 추월당하지 않아야 한다.

실제 라이브러리 락이 모든 상황에서 엄격한 공정성을 보장한다는 뜻은 아니다. 면접에서는 정확성뿐 아니라 교착 상태와 기아 가능성도 함께 설명하면 된다.

### 불변식 단위로 보호하기

플레이어 인벤토리의 `currentWeight`가 모든 아이템 무게 합과 같아야 한다면 아이템 목록 수정과 무게 갱신은 하나의 불변식이다. 서로 다른 락으로 독립 보호하면 중간 상태를 다른 스레드가 볼 수 있다.

```text
Lock(inventory)
  1. 보유 여부 확인
  2. Item 추가
  3. currentWeight 갱신
  4. 최대 무게 불변식 확인
Unlock(inventory)
```

락 범위는 이 불변식을 깨지 않도록 충분히 넓어야 하지만, 네트워크 호출이나 DB 응답처럼 오래 걸리고 제어하기 어려운 작업까지 포함해서는 안 된다. 외부 호출 중 락을 잡으면 다른 요청이 모두 기다리고 상대 서비스 장애가 로컬 락 정체로 확대된다.

### 원자성, 가시성, 순서

- 원자성(Atomicity): 연산이 다른 스레드 관점에서 중간 상태 없이 하나의 단위처럼 수행되는 성질이다.
- 가시성(Visibility): 한 스레드의 쓰기가 다른 스레드에 관찰되는 조건이다.
- 순서(Ordering): 메모리 연산이 다른 스레드에 어떤 순서로 관찰되는지에 관한 규칙이다.

원자 카운터 증가는 해당 값의 갱신 손실을 막지만 여러 값의 복합 불변식을 자동으로 보호하지 않는다. `volatile` 성격의 기능은 가시성과 순서에 도움을 주지만 일반적인 읽기-수정-쓰기 전체를 원자적으로 만들지는 않는다. 구체적인 보장은 C++, C#, Java 등 언어 메모리 모델에 따라 확인해야 한다.

### 공유를 줄이는 설계

가장 단순한 경쟁 상태 해결은 공유하지 않는 것이다. 불변 객체를 전달하거나 데이터 복사본을 사용하고, 한 상태를 하나의 스레드나 액터가 소유하게 할 수 있다. 다른 스레드는 상태를 직접 수정하지 않고 명령을 큐에 보낸다.

```text
Network Threads ── Commands ──> Room Queue
                                  |
                              Owner Thread
                                  |
                           World State 변경
```

이 구조도 자동으로 안전한 것은 아니다. 큐가 무한히 커질 수 있고, 명령 간 순서와 실패 처리, 여러 소유자에 걸친 거래를 설계해야 한다. 그러나 공유 메모리의 임의 접근을 소유자 하나로 제한해 추론 범위를 크게 줄인다.

## 4. 쉬운 예시

```java
// BAD: 읽기-수정-쓰기가 비원자적 → 경쟁 상태 발생
public class PlayerWallet {
    private int balance = 100;

    public boolean spend(int amount) {
        if (balance >= amount) {   // 읽기
            balance -= amount;     // 수정 + 쓰기 (두 스레드가 동시에 통과 가능)
            return true;
        }
        return false;
    }
}
// T1: balance(100) >= 80 → true
// T2: balance(100) >= 80 → true  ← T1이 아직 쓰기 전이라 여전히 100
// T1: balance = 20
// T2: balance = 20   ← 두 번 차감했는데 결과는 20 (40이어야 함)
```

```java
// GOOD 방법 1: synchronized로 불변식 보호 (검사 + 차감 원자화)
public synchronized boolean spend(int amount) {
    if (balance >= amount) {
        balance -= amount;
        return true;
    }
    return false;
}
```

```java
// GOOD 방법 2: Room Owner 패턴 — 소유권을 단일 스레드에 집중
public class GameRoom {
    private final Map<String, Integer> balances = new HashMap<>();
    private final ExecutorService roomExecutor = Executors.newSingleThreadExecutor();

    // 외부 스레드는 명령만 전달 → 실제 수정은 roomExecutor 단일 스레드에서만
    public CompletableFuture<Boolean> spend(String playerId, int amount) {
        return CompletableFuture.supplyAsync(() -> {
            int balance = balances.getOrDefault(playerId, 0);
            if (balance >= amount) {
                balances.put(playerId, balance - amount);
                return true;
            }
            return false;
        }, roomExecutor); // HashMap이어도 안전 — 단일 스레드만 접근
    }
}
```

```java
// 복합 비즈니스 연산의 함정: 스레드 안전 컬렉션도 두 호출 사이는 안전하지 않음
ConcurrentHashMap<String, Item> inventory = new ConcurrentHashMap<>();

// BAD: 조회 후 삽입 사이에 다른 스레드가 같은 키를 추가할 수 있음
if (!inventory.containsKey(itemId)) {        // 호출 1
    inventory.put(itemId, new Item(itemId)); // 호출 2 — 사이에 다른 스레드가 끼어들 수 있음
}

// GOOD: 원자적 복합 API 사용
inventory.putIfAbsent(itemId, new Item(itemId));
```

## 5. 비슷한 개념과 비교

| 방식 | 적합한 대상 | 비용·주의점 |
|---|---|---|
| Lock | 복합 불변식 | 대기와 Deadlock |
| Atomic | 단일 값 갱신 | 복합 상태 한계 |
| 메시지 전달 | 소유권 분리 | 큐 지연과 역압력 |

| 문제 | 핵심 의미 | 예시 |
|---|---|---|
| Race Condition | 실행 순서에 따라 결과가 달라짐 | 갱신 손실, 중복 차감 |
| Data Race | 동기화 없는 충돌 메모리 접근 | C++에서는 정의되지 않은 동작 가능 |
| TOCTOU | 확인과 사용 사이에 상태가 바뀜 | 파일 존재 확인 후 열기 |
| Deadlock | 서로 가진 자원을 기다려 진행 불가 | A→B, B→A 락 순서 |
| Starvation | 특정 작업이 계속 기회를 얻지 못함 | 불공정한 락 경쟁 |

데이터 레이스와 경쟁 상태는 흔히 섞어 쓰지만 완전히 같은 범위는 아니다. TOCTOU처럼 메모리 데이터 레이스 없이도 검사와 사용 사이의 경쟁 상태가 생길 수 있다.

## 6. 장점과 단점

**동기화(락)의 장점**

- 복합 불변식을 원자적으로 보호해 경쟁 상태를 막는다.
- 정확성 추론이 단순해진다.

**동기화(락)의 단점**

- 대기·문맥 교환·캐시 무효화 비용이 발생한다.
- 잘게 나누면 락 순서 관리와 복합 불변식 검증이 복잡해진다.
- 락 범위 내 외부 I/O(Input/Output)가 포함되면 장애 전파 경로가 된다.

**소유권 분리(Room Owner 패턴)의 장점**

- 상태를 단일 스레드에 집중해 임계 구역 추론이 단순해진다.
- 락 없이도 HashMap 등 비스레드 안전 자료구조를 사용할 수 있다.

**소유권 분리의 단점**

- 큐가 무한히 커지는 역압력 문제를 별도로 설계해야 한다.
- 여러 소유자에 걸친 거래(아이템 이동)는 여전히 순서와 실패 처리를 명시해야 한다.

## 7. 게임 서버·백엔드 실무 예시

동시 아이템 획득과 재화 차감은 메모리 락뿐 아니라 DB 트랜잭션과 멱등성까지 경계를 맞춘다. 락 대기 시간, 큐 길이, 타임아웃과 p99 지연을 함께 관찰한다.

패킷 재전송이나 사용자의 빠른 연속 클릭으로 같은 구매 명령이 두 번 도착할 수 있다. 이것은 스레드 경쟁과 별도로 중복 요청 문제다. 요청 ID를 저장해 같은 명령의 효과를 한 번만 반영하고, 재화 차감과 아이템 지급을 하나의 트랜잭션 경계로 묶는다. 메모리 락 하나만으로 프로세스 장애 뒤의 재시도까지 해결할 수는 없다.

경쟁 상태를 추적할 때는 오류 결과에 영향을 준 명령 ID, 플레이어 ID, 상태 버전과 처리 스레드를 기록한다. 전체 로그 순서만 믿기보다 상태 변경에 단조 증가 버전을 붙이면 뒤늦은 쓰기와 중복 반영을 찾기 쉽다. 부하 테스트에서 의도적으로 스레드 양보와 지연을 삽입하거나 Thread Sanitizer 같은 도구를 활용할 수 있지만, 도구가 비즈니스 불변식 오류까지 자동으로 찾지는 못한다.

## 8. 자주 하는 오해

- **"스레드 안전 컬렉션이면 복합 비즈니스 연산도 안전하다"**: 각 메서드가 개별로 안전해도 두 호출 사이에 다른 스레드가 끼어들 수 있다. containsKey 후 put 사이가 대표 사례다.
- **"Atomic 연산이면 모든 경쟁 상태가 해결된다"**: 단일 값의 갱신 손실은 막지만 여러 값의 복합 불변식을 자동으로 보호하지 않는다. 잔액·인벤토리가 함께 변해야 하는 경우에는 락이 필요하다.
- **"volatile이면 경쟁 상태 걱정이 없다"**: 가시성과 순서를 제공하지만 읽기-수정-쓰기 전체를 원자적으로 만들지 않는다. `volatile int count; count++`는 여전히 경쟁 상태다.
- **"메모리 락 하나로 분산 환경의 경쟁 상태도 막을 수 있다"**: 여러 서버 인스턴스가 같은 DB 행을 수정한다면 로컬 락은 다른 프로세스를 막지 못한다. DB 트랜잭션·행 잠금·멱등성 키가 필요하다.
- **"동시성 버그는 테스트에서 재현된다"**: 실행 순서와 부하에 따라 달라져 테스트에서는 통과하고 운영 트래픽 아래에서만 드물게 나타나기 쉽다.
- **"경쟁 상태 = 데이터 레이스"**: 데이터 레이스는 동기화 없는 충돌 메모리 접근이다. TOCTOU처럼 메모리 레이스 없이도 확인과 사용 사이에 경쟁 상태가 발생할 수 있다.
- **"락 범위를 잘게 나눌수록 항상 성능이 좋다"**: 잘게 나누면 병렬성은 높아지지만 락 순서 관리와 복합 불변식 검증이 복잡해져 교착 상태나 새로운 경쟁 상태가 더 생길 수 있다.

## 9. 면접 질문

### Q1. 경쟁 상태란 무엇이며 왜 발생하나요?

경쟁 상태는 여러 실행 흐름이 공유 자원에 동기화 없이 접근할 때 실행 순서에 따라 결과가 달라지는 오류다. `count++` 한 줄도 읽기·계산·쓰기로 나뉘므로 두 스레드가 겹치면 갱신을 잃는다. 항상 틀리는 것이 아니라 특정 타이밍에만 발생해 테스트에서 잘 잡히지 않는다.

### Q2. 임계 구역의 범위는 어떻게 결정하나요?

먼저 반드시 함께 성립해야 하는 데이터 불변식을 정의한다. 그 불변식을 읽고 변경하는 전체 연산을 하나의 보호 단위로 묶되, 네트워크·DB 같은 긴 외부 대기는 가능하면 락 밖으로 분리하고 상태 버전으로 변경을 다시 검증한다.

### Q3. 경쟁 상태와 데이터 레이스는 같은 개념인가요?

아니다. 데이터 레이스는 동기화 없이 같은 메모리를 두 스레드가 접근하고 그중 하나가 쓰기인 경우다. C++에서는 정의되지 않은 동작이 될 수 있다. 경쟁 상태는 더 넓은 개념으로, 파일 존재 확인 후 생성하는 TOCTOU처럼 메모리 레이스 없이도 발생한다.

### Q4. TOCTOU란 무엇인가요?

Time-of-check to time-of-use의 약자다. 조건을 확인한 시점과 그 결과를 사용하는 시점 사이에 상태가 바뀌어 생기는 경쟁 상태다. 파일 존재 여부를 확인한 뒤 열면 사이에 다른 프로세스가 파일을 삭제할 수 있다. 스레드 안전 컬렉션의 containsKey → put 패턴도 같은 구조다.

### Q5. 스레드 안전 컬렉션으로 '없으면 추가'가 안전한가요?

안전하지 않다. 조회(`containsKey`)와 추가(`put`)가 각각 스레드 안전해도 두 호출 사이에 다른 스레드가 같은 키를 추가할 수 있다. 컬렉션이 제공하는 원자적 `putIfAbsent`나 `computeIfAbsent` 같은 복합 API를 사용하거나 전체 비즈니스 불변식을 별도 동기화로 보호해야 한다.

### Q6. 게임 아이템 구매 시 중복 처리를 어떻게 막나요?

네트워크 재전송이나 연속 클릭으로 같은 구매 요청이 두 번 도착할 수 있다. 요청 ID(멱등성 키)를 저장해 같은 명령의 효과를 한 번만 반영하고, 재화 차감과 아이템 지급을 하나의 DB 트랜잭션으로 묶는다. 메모리 락만으로는 서버 재시작 후 재시도나 다중 인스턴스 환경을 막을 수 없다.

## 10. 예상 꼬리질문

- 원자성과 가시성은 어떻게 다른가요?
  > 원자성은 연산이 다른 스레드에 중간 상태 없이 하나의 단위로 관찰되는 성질이다. 가시성은 한 스레드가 쓴 값이 다른 스레드에 언제 관찰되는지를 다루는 성질이다. 원자성이 보장돼도 가시성이 없으면 다른 스레드가 오래된 캐시 값을 읽을 수 있다.
- 락 범위가 길면 어떤 문제가 생기나요?
  > 락을 오래 잡을수록 다른 스레드의 대기 시간이 늘어 처리량이 낮아진다. 네트워크·DB 같은 외부 호출을 락 범위 안에 두면 외부 장애가 로컬 락 정체로 전파되고 교착 상태 위험도 높아진다.
- 메시지 전달 방식의 단점은 무엇인가요?
  > 생산자가 소비자보다 빠르면 큐가 무한히 커질 수 있어 역압력 처리를 별도로 설계해야 한다. 여러 소유자에 걸친 거래(예: 플레이어 간 아이템 이동)는 메시지 순서와 실패 처리를 명시적으로 정의해야 한다.
- 운영에서 경쟁 상태의 원인을 어떻게 찾나요?
  > 상태 변경 시 단조 증가 버전 번호, 명령 ID, 처리 스레드를 로그에 기록한다. 버전이 역전되거나 같은 명령이 두 번 반영된 흔적을 추적해 원인 구간을 좁힌다. Thread Sanitizer와 부하 테스트에서 의도적 지연 삽입도 병행한다.
- Thread Sanitizer는 어떤 경쟁 상태를 찾지 못하나요?
  > Thread Sanitizer는 동기화 없는 충돌 메모리 접근(데이터 레이스)을 탐지한다. 개별 메서드가 스레드 안전하지만 두 호출 사이에 상태가 바뀌는 TOCTOU나 비즈니스 불변식 수준의 경쟁 상태는 자동으로 탐지하지 못한다.
- 경쟁 상태와 데이터 레이스는 항상 같은가요?
  > 같지 않다. 데이터 레이스는 동기화 없는 충돌 메모리 접근이 전제다. 경쟁 상태는 더 넓은 개념으로 파일 존재 확인 후 열기와 같이 메모리 레이스 없이도 확인 시점과 사용 시점 사이에 상태가 바뀌면 발생한다.
- TOCTOU는 무엇인가요?
  > Time-of-check to time-of-use의 줄임말로, 조건을 확인한 시점과 그 결과를 사용하는 시점 사이에 다른 스레드나 프로세스가 상태를 바꿔 발생하는 경쟁 상태다. containsKey 후 put, 파일 존재 확인 후 열기가 대표 예시다.

## 11. 30초 모범답변

> 경쟁 상태는 실행 순서에 따라 공유 상태 결과가 달라지는 문제입니다. `count++` 한 줄도 읽기·수정·쓰기로 나뉘어 원자적이지 않습니다. 먼저 보호할 불변식을 정의하고 그 전체 구간을 하나의 임계 구역으로 묶어야 합니다. 게임 서버에서는 메모리 락뿐 아니라 DB 트랜잭션과 멱등성 키까지 함께 적용합니다.

## 12. 1~2분 확장답변

> 경쟁 상태는 실행 순서에 따라 공유 상태 결과가 달라지는 오류이며 임계 구역의 불변식을 동기화해야 합니다. 핵심은 공유 데이터의 불변식과 소유권을 정하는 것입니다. 스레드 안전 컬렉션의 개별 메서드가 안전해도 두 호출 사이에 다른 스레드가 끼어드는 TOCTOU 문제가 생길 수 있습니다. Atomic은 단일 값, volatile은 가시성만 보장하므로 복합 불변식에는 락이나 소유권 분리가 필요합니다. 게임 서버에서는 룸 단위 소유권으로 락 복잡도를 줄이고, 재화·아이템 거래는 DB 트랜잭션과 멱등성 키까지 경계를 맞춥니다.

## 13. 핵심 요약

- 경쟁 상태는 실행 순서에 따라 결과가 달라지는 오류다. 항상 틀리는 것이 아니라 특정 타이밍에만 나타나 재현이 어렵다.
- 임계 구역은 함께 성립해야 하는 불변식을 읽고 변경하는 전체 구간이다. 락을 거는 코드 자체가 아니다.
- `count++` 한 줄도 읽기·계산·쓰기로 나뉘어 원자적이지 않다.
- 스레드 안전 컬렉션의 개별 메서드가 안전해도 두 호출 사이에 다른 스레드가 끼어드는 TOCTOU 문제가 생길 수 있다.
- 데이터 레이스는 동기화 없는 충돌 메모리 접근이고, 경쟁 상태는 TOCTOU처럼 메모리 레이스 없이도 발생할 수 있다.
- 락 범위는 불변식을 깨지 않을 만큼 넓어야 하지만 DB·네트워크 같은 긴 외부 대기는 밖으로 분리한다.
- Room Owner 패턴은 상태를 단일 스레드에 맡겨 락 없이 임계 구역 문제를 단순화한다.
- 메모리 락만으로 분산 환경의 경쟁 상태를 막을 수 없다. DB 트랜잭션·행 잠금·멱등성까지 경계를 함께 맞춰야 한다.
