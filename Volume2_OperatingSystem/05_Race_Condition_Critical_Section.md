# 05. Race Condition과 Critical Section

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 정의와 발생 원인을 설명할 수 있다.
- 대표 해결 도구와 차이를 설명할 수 있다.
- 게임 서버의 안전한 설계에 적용할 수 있다.

## 1. 개요

경쟁 상태는 실행 순서에 따라 결과가 달라지는 오류이고 임계 구역은 공유 상태를 변경해 동시 접근을 제어할 코드 영역이다.

좀 더 정확히 말하면 여러 실행 흐름이 공유 자원에 접근하고, 그중 하나 이상이 값을 변경하며, 접근 순서가 적절히 동기화되지 않을 때 경쟁 상태가 발생할 수 있다. 결과가 매번 틀리는 것은 아니다. 특정 실행 순서에서만 갱신 손실, 중복 처리, 손상된 자료구조가 나타나기 때문에 테스트에서는 통과하고 운영 부하에서 드물게 발생하기 쉽다.

임계 구역(Critical Section)은 “락을 거는 코드” 자체가 아니라 동시에 실행되면 안 되는 공유 상태 접근 구간이다. 어떤 데이터의 어떤 불변식을 보호하는지가 먼저이고, 락이나 메시지 큐는 그 구간을 안전하게 만드는 수단이다.

## 2. 왜 필요한가

count 증가도 읽기·계산·쓰기로 나뉘므로 두 스레드가 겹치면 갱신을 잃는다. 동시성 버그는 실행 순서와 부하에 따라 간헐적으로 나타나므로 불변식과 소유권을 설계 단계에서 명시해야 한다.

고수준 코드 한 줄이 CPU 관점에서도 하나의 원자 연산이라는 보장은 없다. `count++`는 현재 값을 읽고 증가시킨 뒤 저장하는 여러 단계가 될 수 있다. 컬렉션에서 “없으면 추가”도 조회와 삽입이라는 복합 연산이다. 각 메서드가 개별적으로 스레드 안전하더라도 둘 사이에 다른 스레드가 끼어들 수 있다.

동기화하지 않은 코드는 단순히 오래된 값을 읽는 데서 끝나지 않는다. 언어와 메모리 모델이 허용하는 범위에서 컴파일러와 CPU가 접근 순서를 바꾸거나 코어별 캐시에 값이 머물 수 있다. 따라서 소스 코드에서 우연히 원하는 순서로 보인다는 사실은 스레드 간 관찰 순서를 보장하지 않는다.

## 3. 핵심 동작 원리

```text
A read 10 → B read 10 → A write 11 → B write 11
```

두 번 증가했지만 최종 값은 11이다. 각 스레드의 계산은 독립적으로 맞았으나 읽기-수정-쓰기 전체가 원자적이지 않아 한 갱신이 사라졌다.

락, 원자 연산, 불변 데이터, 메시지 전달로 공유를 줄인다. 동기화의 목적은 모든 실행을 막는 것이 아니라 필요한 원자성과 관찰 순서를 최소 범위에 제공하는 것이다.

### 임계 구역의 요구사항

고전적으로 임계 구역 해결은 다음 성질을 고려한다.

- 상호 배제(Mutual Exclusion): 한 실행 흐름이 임계 구역에 있으면 충돌하는 다른 흐름은 동시에 들어가지 않는다.
- 진행(Progress): 아무도 임계 구역에 없고 진입하려는 작업이 있다면 무관한 작업 때문에 결정이 무한히 미뤄지지 않는다.
- 한정 대기(Bounded Waiting): 진입을 요청한 작업이 다른 작업에게 무한히 추월당하지 않아야 한다.

실제 라이브러리 락이 모든 상황에서 엄격한 공정성을 보장한다는 뜻은 아니다. 면접에서는 정확성뿐 아니라 교착 상태와 기아 가능성도 함께 설명하면 된다.

### 불변식 단위로 보호하기

플레이어 인벤토리의 `currentWeight`가 모든 아이템 무게 합과 같아야 한다면 아이템 목록 수정과 무게 갱신은 하나의 불변식이다. 서로 다른 락으로 독립 보호하면 중간 상태를 다른 스레드가 볼 수 있다.

```text
Lock(inventory)
  1. 보유 여부 확인
  2. Item 추가
  3. currentWeight 갱신
  4. 최대 무게 불변식 확인
Unlock(inventory)
```

락 범위는 이 불변식을 깨지 않도록 충분히 넓어야 하지만, 네트워크 호출이나 DB 응답처럼 오래 걸리고 제어하기 어려운 작업까지 포함해서는 안 된다. 외부 호출 중 락을 잡으면 다른 요청이 모두 기다리고 상대 서비스 장애가 로컬 락 정체로 확대된다.

### 원자성, 가시성, 순서

- 원자성(Atomicity): 연산이 다른 스레드 관점에서 중간 상태 없이 하나의 단위처럼 수행되는 성질이다.
- 가시성(Visibility): 한 스레드의 쓰기가 다른 스레드에 관찰되는 조건이다.
- 순서(Ordering): 메모리 연산이 다른 스레드에 어떤 순서로 관찰되는지에 관한 규칙이다.

원자 카운터 증가는 해당 값의 갱신 손실을 막지만 여러 값의 복합 불변식을 자동으로 보호하지 않는다. `volatile` 성격의 기능은 가시성과 순서에 도움을 주지만 일반적인 읽기-수정-쓰기 전체를 원자적으로 만들지는 않는다. 구체적인 보장은 C++, C#, Java 등 언어 메모리 모델에 따라 확인해야 한다.

### 공유를 줄이는 설계

가장 단순한 경쟁 상태 해결은 공유하지 않는 것이다. 불변 객체를 전달하거나 데이터 복사본을 사용하고, 한 상태를 하나의 스레드나 액터가 소유하게 할 수 있다. 다른 스레드는 상태를 직접 수정하지 않고 명령을 큐에 보낸다.

```text
Network Threads ── Commands ──> Room Queue
                                  |
                              Owner Thread
                                  |
                           World State 변경
```

이 구조도 자동으로 안전한 것은 아니다. 큐가 무한히 커질 수 있고, 명령 간 순서와 실패 처리, 여러 소유자에 걸친 거래를 설계해야 한다. 그러나 공유 메모리의 임의 접근을 소유자 하나로 제한해 추론 범위를 크게 줄인다.

## 4. 쉬운 예시

두 요청이 같은 잔액을 읽고 각각 차감하면 둘 다 성공할 수 있다. 읽기, 조건 검사, 쓰기를 하나의 보호 단위로 만들거나 상태 소유 스레드에 명령을 직렬화한다.

잔액이 100이고 두 요청이 각각 80을 차감한다고 하자. 둘 다 100을 읽어 충분하다고 판단한 뒤 각각 20을 쓰면 두 요청이 성공했는데 잔액은 20으로 남는 잘못된 결과가 나온다. 단일 프로세스에서는 잔액별 락으로 검사와 차감을 묶을 수 있다. 여러 서버가 같은 DB 행을 수정한다면 로컬 락만으로 부족하며 DB 트랜잭션의 조건부 갱신이나 행 잠금이 필요하다.

## 5. 비슷한 개념과 비교

| 방식 | 적합한 대상 | 비용·주의점 |
|---|---|---|
| Lock | 복합 불변식 | 대기와 Deadlock |
| Atomic | 단일 값 갱신 | 복합 상태 한계 |
| 메시지 전달 | 소유권 분리 | 큐 지연과 역압력 |

| 문제 | 핵심 의미 | 예시 |
|---|---|---|
| Race Condition | 실행 순서에 따라 결과가 달라짐 | 갱신 손실 |
| Data Race | 동기화 없는 충돌 메모리 접근 | C++에서는 정의되지 않은 동작 가능 |
| Deadlock | 서로 가진 자원을 기다려 진행 불가 | A→B, B→A 락 순서 |
| Starvation | 특정 작업이 계속 기회를 얻지 못함 | 불공정한 락 경쟁 |

데이터 레이스와 경쟁 상태는 흔히 섞어 쓰지만 완전히 같은 범위는 아니다. 파일 생성 전 존재 여부를 확인하는 TOCTOU(Time-of-check to time-of-use) 문제처럼 메모리 데이터 레이스 없이도 검사와 사용 사이의 경쟁 상태가 생길 수 있다.

## 6. 장점과 단점

동기화는 정합성을 지키지만 경쟁, 문맥 전환, 캐시 무효화 비용을 만든다. 공유를 줄인 뒤 단순한 도구를 적용하고 측정 결과로 세분화한다.

하나의 큰 락은 정확성을 검토하기 쉽지만 관련 없는 작업까지 직렬화해 처리량과 꼬리 지연을 악화시킬 수 있다. 락을 잘게 나누면 병렬성은 높아지지만 획득 순서와 여러 락에 걸친 불변식이 복잡해진다. 처음부터 락 없는 구조를 선택하기보다 올바른 단순 구현을 만든 뒤 측정된 경쟁 구간을 개선하는 편이 안전하다.

## 7. 게임 서버·백엔드 실무 예시

동시 아이템 획득과 재화 차감은 메모리 락뿐 아니라 DB 트랜잭션과 멱등성까지 경계를 맞춘다. 락 대기 시간, 큐 길이, 타임아웃과 p99 지연을 함께 관찰한다.

패킷 재전송이나 사용자의 빠른 연속 클릭으로 같은 구매 명령이 두 번 도착할 수 있다. 이것은 스레드 경쟁과 별도로 중복 요청 문제다. 요청 ID를 저장해 같은 명령의 효과를 한 번만 반영하고, 재화 차감과 아이템 지급을 하나의 트랜잭션 경계로 묶는다. 메모리 락 하나만으로 프로세스 장애 뒤의 재시도까지 해결할 수는 없다.

경쟁 상태를 추적할 때는 오류 결과에 영향을 준 명령 ID, 플레이어 ID, 상태 버전과 처리 스레드를 기록한다. 전체 로그 순서만 믿기보다 상태 변경에 단조 증가 버전을 붙이면 뒤늦은 쓰기와 중복 반영을 찾기 쉽다. 부하 테스트에서 의도적으로 스레드 양보와 지연을 삽입하거나 Thread Sanitizer 같은 도구를 활용할 수 있지만, 도구가 비즈니스 불변식 오류까지 자동으로 찾지는 못한다.

## 8. 자주 하는 오해

- 스레드 안전 컬렉션이면 복합 비즈니스 연산도 안전하다고 본다.
- Atomic이나 volatile이 모든 경쟁을 해결한다고 본다.
- 락 범위를 크게 만들수록 좋다고 생각한다.
- 재시도를 무제한 적용한다.
- Deadlock만 없으면 안전하다고 본다.

### 최종 실무 판단 기준

- **요구 확인**: 경쟁 상태는 실행 순서에 따라 결과가 달라지는 오류이고 임계 구역은 공유 상태를 변경해 동시 접근을 제어할 코드 영역이다. 이 내용을 적용하기 전에 데이터 규모, 호출 빈도와 허용 지연을 수치로 확인한다. 같은 기술도 요청량과 정확성 요구가 달라지면 적합한 선택이 달라질 수 있다.
- **정확성 경계**: 불변식과 소유권이 출발점이다. 정상 흐름만 설명하지 않고 중복, 역순, 동시 실행과 부분 실패에서 어떤 불변식을 지켜야 하는지 함께 명시한다.
- **비용 비교**: 동기화는 정확성과 대기 비용을 함께 만든다. 평균 복잡도나 처리량 하나만 보지 않고 Memory, CPU, I/O, Lock 대기와 구현 복잡도까지 비교한다.
- **장애 대응**: Race Condition과 Critical Section 관련 구성 요소가 느려지거나 중단됐을 때 Timeout, Retry 상한, Backpressure와 복구 순서를 정한다. Retry가 중복 부작용이나 연쇄 부하를 만들지 검증한다.
- **운영 검증**: Race Condition과 Critical Section에서는 기능 Test와 함께 경계값, Peak 부하와 장애 주입 Test를 수행한다. 처리 시간 p95·p99, 오류율, Queue와 Resource 사용량을 관찰하고 변경 전후 결과를 비교한다.

Race Condition과 Critical Section 답변에서는 이 기준으로 답하면 개념 정의에 그치지 않고 선택 조건, Trade-off와 실무 검증 방법까지 논리적으로 연결할 수 있다.

## 9. 면접 질문

### Q1. 핵심 개념을 설명해 주세요.

경쟁 상태는 실행 순서에 따라 결과가 달라지는 오류이고 임계 구역은 공유 상태를 변경해 동시 접근을 제어할 코드 영역이다.

### Q2. 대표 해결 원칙은 무엇인가요?

보호할 불변식과 소유권을 정하고 Lock, Atomic 또는 메시지 전달을 선택한다.

### Q3. 실무에서는 어떻게 적용하나요?

동시 아이템 획득과 재화 차감은 메모리 락뿐 아니라 DB 트랜잭션과 멱등성까지 경계를 맞춘다.

### Q4. 성능과 정확성을 어떻게 균형 잡나요?

공유 범위를 줄이고 단순한 동기화를 적용한 뒤 경쟁과 꼬리 지연을 측정한다.

### Q5. 스레드 안전 컬렉션으로 `없으면 추가`가 안전한가요?

조회와 추가를 별도 호출하면 그 사이에 다른 스레드가 같은 키를 추가할 수 있다. 컬렉션이 제공하는 원자적 `GetOrAdd` 같은 복합 API를 사용하거나 전체 비즈니스 불변식을 별도 동기화로 보호해야 한다.

### Q6. 임계 구역을 어떻게 정하나요?

먼저 반드시 함께 성립해야 하는 데이터 불변식을 정의한다. 그 불변식을 읽고 변경하는 전체 연산을 하나의 보호 단위로 묶되, 네트워크나 DB 같은 긴 외부 대기는 가능하면 락 밖으로 분리하고 상태 버전으로 변경을 다시 검증한다.
