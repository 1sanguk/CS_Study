# 07. Atomic과 Memory Visibility

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 정의와 발생 원인을 설명할 수 있다.
- 대표 해결 도구와 차이를 설명할 수 있다.
- 게임 서버의 안전한 설계에 적용할 수 있다.

## 1. 개요

Atomic은 중간 상태가 관찰되지 않는 연산이고 메모리 가시성은 한 스레드의 쓰기를 다른 스레드가 언제 보는지에 관한 성질이다.

원자 연산(Atomic Operation)은 지정된 연산 단위가 다른 실행 흐름에 쪼개진 중간 상태로 관찰되지 않도록 한다. 메모리 가시성(Memory Visibility)은 한 스레드가 쓴 값이 다른 스레드에 언제, 어떤 동기화 관계를 통해 보이는지를 다룬다. 여기에 연산의 관찰 순서(Ordering)까지 구분해야 한다. 한 값의 읽기와 쓰기가 원자적이어도 여러 값 사이의 순서와 비즈니스 불변식은 별도 보장이 필요할 수 있다.

## 2. 왜 필요한가

CPU 캐시와 명령 재배치 때문에 소스 코드 순서만으로 스레드 간 관찰 순서를 보장할 수 없다. 동시성 버그는 실행 순서와 부하에 따라 간헐적으로 나타나므로 불변식과 소유권을 설계 단계에서 명시해야 한다.

컴파일러는 단일 스레드 결과가 같다면 명령을 재배치하거나 값을 레지스터에 유지할 수 있다. CPU도 성능을 위해 메모리 접근을 파이프라인과 캐시에서 처리한다. 다른 코어가 어느 시점에 어떤 순서로 쓰기를 관찰하는지는 언어 메모리 모델과 동기화 연산이 정의한다. “코드는 위에서 아래로 실행되므로 다른 스레드도 같은 순서로 본다”는 가정은 안전하지 않다.

동기화가 없는 데이터 레이스는 언어별로 결과가 다르다. 특히 C++의 일반 메모리 데이터 레이스는 정의되지 않은 동작이므로 단순히 오래된 값 중 하나를 읽는다고만 설명하면 부정확하다. C#과 Java에서도 `volatile`이나 락 없이 공유 상태를 읽고 쓰면 기대한 가시성과 순서를 보장받지 못한다. 구체적인 API 보장은 해당 언어 사양을 기준으로 판단한다.

## 3. 핵심 동작 원리

```text
Producer data write→release flag / Consumer acquire flag→data read
```

volatile은 복합 연산 원자성을 제공하지 않는다. acquire와 release는 관찰 순서를 만든다. 동기화의 목적은 모든 실행을 막는 것이 아니라 필요한 원자성과 관찰 순서를 최소 범위에 제공하는 것이다.

### 읽기-수정-쓰기와 CAS

원자 카운터 증가는 일반적인 읽기-증가-쓰기를 하나의 원자적 갱신으로 제공한다. 많은 락 없는 알고리즘은 비교 후 교환(Compare-And-Swap, CAS)을 사용한다. CAS는 메모리 값이 예상값과 같을 때만 새 값으로 바꾸고 성공 여부를 반환한다.

```text
do {
    old = counter.load()
    next = old + 1
} while (!counter.compare_exchange(old, next))
```

다른 스레드가 먼저 값을 바꾸면 CAS가 실패하고 최신 값을 읽어 다시 계산한다. 이 반복은 스레드를 블로킹하지 않지만 경쟁이 심하면 여러 코어가 계속 실패하며 CPU와 캐시 일관성 트래픽을 소비한다. 락이 없다는 사실이 대기나 성능 문제가 없다는 뜻은 아니다.

### Acquire와 Release

생산자가 데이터 객체를 완성한 뒤 `ready` 플래그를 release 저장하고 소비자가 같은 플래그를 acquire 읽기로 확인했다고 하자. 이 동기화가 성공하면 생산자의 release 이전 쓰기들이 소비자의 acquire 이후 읽기에 관찰되도록 관계를 만든다.

```text
Producer                         Consumer
data.x = 10
data.y = 20
ready.store(true, release)  -->  ready.load(acquire) == true
                                  read data.x, data.y
```

핵심은 플래그 자체의 최신 값만 보는 것이 아니라 그 플래그를 통해 앞선 데이터 쓰기를 안전하게 게시(Publication)하는 것이다. release 이후 연산이 앞쪽으로, acquire 이전 연산이 뒤쪽으로 마음대로 넘어가지 못하도록 필요한 순서를 제한한다.

순차 일관성(Sequential Consistency)은 원자 연산들이 모든 스레드에 하나의 전역 순서처럼 보이는 강한 모델을 제공한다. 이해하기 쉽지만 모든 알고리즘에 가장 약한 순서를 직접 고르는 것보다 성능이 다를 수 있다. 반대로 Relaxed 원자 연산은 해당 원자 변수 자체의 원자성은 제공하지만 다른 데이터와의 게시 순서를 만들지 않는다. 단순 통계 카운터처럼 다른 상태와 결합되지 않을 때 사용할 수 있으나 근거 없이 약한 순서를 선택하면 버그가 생긴다.

### Happens-before

Happens-before는 단순한 실제 시간 선후가 아니라 한 작업의 메모리 효과가 다른 작업에 관찰되도록 언어 메모리 모델이 보장하는 관계다. 같은 스레드의 프로그램 순서, 뮤텍스 해제와 이후 획득, 스레드 시작·합류, 대응하는 release/acquire 등이 관계를 만들 수 있다. 이 관계가 없는 충돌 접근을 “현실에서 먼저 실행됐으니 보인다”고 가정할 수 없다.

### ABA 문제

CAS가 값이 A인지 검사하는 동안 다른 스레드가 A를 B로 바꿨다가 다시 A로 돌려놓으면 CAS는 중간 변경을 알아채지 못할 수 있다. 이를 ABA 문제라고 한다. 락 없는 스택에서 노드를 제거하고 재사용하는 경우 포인터 값은 같아도 객체의 생명주기가 달라졌을 수 있다. 버전 태그를 함께 비교하거나 안전한 메모리 회수 기법을 사용한다. 단순 정수 카운터 CAS마다 ABA가 문제인 것은 아니며 알고리즘 의미가 중간 변화를 구분해야 할 때 중요하다.

### 안전한 게시와 객체 수명

객체 참조를 다른 스레드에 전달하기 전에 객체 초기화를 끝내고 적절한 동기화로 게시해야 한다. 참조만 원자적으로 저장해도 다른 필드의 초기화 순서가 자동으로 전달되는지는 사용한 메모리 순서에 달려 있다. 또한 락 없는 자료구조에서는 어떤 스레드도 이전 객체를 읽지 않는다는 사실을 확인하기 전까지 메모리를 재사용하면 안 된다. 원자 포인터 교체와 객체 수명 관리는 별도 문제다.

## 4. 쉬운 예시

두 요청이 같은 잔액을 읽고 각각 차감하면 둘 다 성공할 수 있다. 읽기, 조건 검사, 쓰기를 하나의 보호 단위로 만들거나 상태 소유 스레드에 명령을 직렬화한다.

서버 종료 플래그를 일반 `bool`로 두고 작업 스레드가 반복해서 읽는다고 하자. 동기화가 없다면 컴파일러가 값을 반복해서 메모리에서 읽어야 한다고 보장할 수 없다. 언어가 제공하는 원자·volatile 플래그나 취소 토큰을 사용하면 가시성을 표현할 수 있다. 하지만 `if (!stopped) activeWorkers++` 같은 두 상태의 복합 조건은 플래그와 카운터를 각각 원자적으로 만드는 것만으로 전체 원자성을 얻지 못한다.

## 5. 비슷한 개념과 비교

| 방식 | 적합한 대상 | 비용·주의점 |
|---|---|---|
| Lock | 복합 불변식 | 대기와 Deadlock |
| Atomic | 단일 값 갱신 | 복합 상태 한계 |
| 메시지 전달 | 소유권 분리 | 큐 지연과 역압력 |

| 개념 | 보장하려는 것 | 해결하지 못하는 것 |
|---|---|---|
| Atomic 연산 | 지정 값의 분할 없는 갱신 | 여러 값의 복합 불변식 |
| volatile 성격 접근 | 언어가 정의한 가시성·순서 | `count++` 같은 복합 원자성 |
| Mutex | 임계 구역 상호 배제와 순서 관계 | 분산 프로세스 간 정합성 |
| Concurrent Queue | 정해진 Queue 연산의 안전성 | 소비된 명령의 비즈니스 성공 |

C++ `std::atomic`, C# `Interlocked`와 `Volatile`, Java `Atomic*`와 `volatile`은 세부 API와 메모리 모델이 다르다. “volatile이면 스레드 안전하다” 같은 언어 독립적인 단정 대신 어떤 읽기·쓰기·복합 연산을 보호하는지 말한다.

## 6. 장점과 단점

동기화는 정합성을 지키지만 경쟁, 문맥 전환, 캐시 무효화 비용을 만든다. 공유를 줄인 뒤 단순한 도구를 적용하고 측정 결과로 세분화한다.

원자 연산은 간단한 플래그와 카운터에서 락과 커널 대기를 피할 수 있다. 그러나 복잡한 CAS 반복은 검증하기 어렵고 경쟁 시 성능이 급격히 나빠질 수 있다. 강한 메모리 순서는 추론하기 쉽고, 약한 순서는 일부 하드웨어에서 최적화 여지를 주지만 정확성 증명 부담을 키운다. 면접 수준에서는 먼저 표준 동시성 컬렉션과 뮤텍스로 올바르게 만들고 실제 병목에서만 락 없는 설계를 고려한다고 답하는 것이 합리적이다.

## 7. 게임 서버·백엔드 실무 예시

네트워크 스레드가 게임 스레드로 작업을 넘길 때 검증된 동시성 큐를 사용한다. 락 대기 시간, 큐 길이, 타임아웃과 p99 지연을 함께 관찰한다.

큐 내부가 스레드 안전해도 명령의 의미까지 안전해지는 것은 아니다. 네트워크 스레드가 동일 플레이어의 명령을 여러 생산자로 넣으면 큐가 보장하는 전체 또는 생산자별 순서를 확인해야 한다. 게임 스레드는 세션 세대 번호와 명령 시퀀스를 검증해 재접속 이전 명령이나 중복 명령을 버린다.

접속자 수 같은 관측용 카운터는 원자 증가로 충분할 수 있다. 반면 “접속자 수가 정원보다 작으면 증가하고 세션을 등록한다”는 카운터와 세션 맵의 복합 불변식이다. 하나의 락이나 소유 스레드 명령으로 함께 처리한다. 정확한 용량 제어와 대략적인 메트릭 집계를 구분하면 불필요하게 강한 동기화를 피할 수 있다.

## 8. 자주 하는 오해

- 스레드 안전 컬렉션이면 복합 비즈니스 연산도 안전하다고 본다.
- Atomic이나 volatile이 모든 경쟁을 해결한다고 본다.
- 락 범위를 크게 만들수록 좋다고 생각한다.
- 재시도를 무제한 적용한다.
- Deadlock만 없으면 안전하다고 본다.

## 9. 면접 질문

### Q1. 핵심 개념을 설명해 주세요.

Atomic은 중간 상태가 관찰되지 않는 연산이고 메모리 가시성은 한 스레드의 쓰기를 다른 스레드가 언제 보는지에 관한 성질이다.

### Q2. 대표 해결 원칙은 무엇인가요?

보호할 불변식과 소유권을 정하고 Lock, Atomic 또는 메시지 전달을 선택한다.

### Q3. 실무에서는 어떻게 적용하나요?

네트워크 스레드가 게임 스레드로 작업을 넘길 때 검증된 동시성 큐를 사용한다.

### Q4. 성능과 정확성을 어떻게 균형 잡나요?

공유 범위를 줄이고 단순한 동기화를 적용한 뒤 경쟁과 꼬리 지연을 측정한다.

### Q5. Atomic 카운터를 쓰면 경쟁 상태가 모두 해결되나요?

해당 카운터의 개별 갱신 손실은 막을 수 있지만 다른 값과의 조건 검사·수정 전체는 보호하지 않는다. 예를 들어 정원 검사, 카운터 증가, 세션 맵 등록은 하나의 복합 불변식이므로 락이나 단일 소유자 처리가 필요하다.

### Q6. Acquire와 Release는 왜 필요한가요?

생산자가 데이터를 초기화한 뒤 release로 게시하고 소비자가 대응하는 acquire를 관찰하면 앞선 데이터 쓰기들이 소비자에게 보이는 순서 관계를 만든다. 플래그만 최신으로 읽고 초기화되지 않은 데이터를 보는 문제를 막기 위한 것이다.

### Q7. CAS 기반 알고리즘도 느려질 수 있나요?

그렇다. 경쟁이 심하면 여러 스레드가 같은 캐시 라인을 갱신하며 CAS 실패와 재시도를 반복한다. 블로킹은 없어도 CPU를 소비하고 공정성이 낮아질 수 있으므로 실제 경쟁 패턴을 측정해야 한다.

> Atomic은 단일 연산의 원자성을, 메모리 가시성은 스레드 간 쓰기의 관찰 순서를 다룹니다. 핵심은 공유 데이터의 불변식과 소유권을 정하는 것입니다. 도구마다 보호 범위와 비용이 다르므로 게임 서버에서는 룸 단위 소유권과 짧은 임계 구역을 사용하고 외부 DB에는 트랜잭션과 멱등성도 적용합니다.

## 13. 핵심 요약

- Atomic은 중간 상태가 관찰되지 않는 연산이고 메모리 가시성은 한 스레드의 쓰기를 다른 스레드가 언제 보는지에 관한 성질이다.
- 불변식과 소유권이 출발점이다.
- 동기화는 정확성과 대기 비용을 함께 만든다.
- 락 순서와 범위를 명시한다.
- 운영에서는 대기와 꼬리 지연을 본다.
- Atomicity, Visibility, Ordering과 객체 수명은 각각 필요한 보장을 확인해야 한다.
