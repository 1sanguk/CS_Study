# 07. Atomic과 Memory Visibility


## 학습 목표

- 원자 연산이 보장하는 것과 보장하지 못하는 것(복합 불변식, 가시성)을 구분할 수 있다.
- volatile과 Atomic의 차이와 각각 적합한 사용 시점을 설명할 수 있다.
- Acquire/Release 메모리 순서가 게시 패턴에서 왜 필요한지 설명할 수 있다.
- CAS(Compare-And-Swap)의 동작 원리와 경쟁 시 성능 특성을 설명할 수 있다.

## 1. 개요

Atomic은 중간 상태가 관찰되지 않는 연산이고 메모리 가시성은 한 스레드의 쓰기를 다른 스레드가 언제 보는지에 관한 성질이다.

원자 연산은 지정된 연산 단위가 다른 실행 흐름에 쪼개진 중간 상태로 관찰되지 않도록 한다. 메모리 가시성은 한 스레드가 쓴 값이 다른 스레드에 언제, 어떤 동기화 관계를 통해 보이는지를 다룬다. 한 값의 읽기와 쓰기가 원자적이어도 여러 값 사이의 순서와 비즈니스 불변식은 별도 보장이 필요할 수 있다.

## 2. 왜 필요한가

CPU 캐시와 명령 재배치 때문에 소스 코드 순서만으로 스레드 간 관찰 순서를 보장할 수 없다.

컴파일러는 단일 스레드 결과가 같다면 명령을 재배치하거나 값을 레지스터에 유지할 수 있다. CPU(Central Processing Unit)도 성능을 위해 메모리 접근을 파이프라인과 캐시에서 처리한다. 다른 코어가 어느 시점에 어떤 순서로 쓰기를 관찰하는지는 언어 메모리 모델과 동기화 연산이 정의한다. "코드는 위에서 아래로 실행되므로 다른 스레드도 같은 순서로 본다"는 가정은 안전하지 않다.

## 3. 핵심 동작 원리

```text
Producer data write→release flag / Consumer acquire flag→data read
```

volatile은 복합 연산 원자성을 제공하지 않는다. acquire와 release는 관찰 순서를 만든다.

### 읽기-수정-쓰기와 CAS

원자 카운터 증가는 일반적인 읽기-증가-쓰기를 하나의 원자적 갱신으로 제공한다. 많은 락 없는 알고리즘은 비교 후 교환(Compare-And-Swap, CAS)을 사용한다. CAS는 메모리 값이 예상값과 같을 때만 새 값으로 바꾸고 성공 여부를 반환한다.

```text
do {
    old = counter.load()
    next = old + 1
} while (!counter.compare_exchange(old, next))
```

다른 스레드가 먼저 값을 바꾸면 CAS가 실패하고 최신 값을 읽어 다시 계산한다. 이 반복은 스레드를 블로킹하지 않지만 경쟁이 심하면 여러 코어가 계속 실패하며 CPU와 캐시 일관성 트래픽을 소비한다. 락이 없다는 사실이 대기나 성능 문제가 없다는 뜻은 아니다.

### Acquire와 Release

생산자가 데이터 객체를 완성한 뒤 `ready` 플래그를 release 저장하고 소비자가 같은 플래그를 acquire 읽기로 확인했다고 하자. 이 동기화가 성공하면 생산자의 release 이전 쓰기들이 소비자의 acquire 이후 읽기에 관찰되도록 관계를 만든다.

```text
Producer                         Consumer
data.x = 10
data.y = 20
ready.store(true, release)  -->  ready.load(acquire) == true
                                  read data.x, data.y
```

핵심은 플래그 자체의 최신 값만 보는 것이 아니라 그 플래그를 통해 앞선 데이터 쓰기를 안전하게 게시하는 것이다.

### Happens-before

Happens-before는 단순한 실제 시간 선후가 아니라 한 작업의 메모리 효과가 다른 작업에 관찰되도록 언어 메모리 모델이 보장하는 관계다. 같은 스레드의 프로그램 순서, 뮤텍스 해제와 이후 획득, 스레드 시작·합류, 대응하는 release/acquire 등이 관계를 만들 수 있다. 이 관계가 없는 충돌 접근을 "현실에서 먼저 실행됐으니 보인다"고 가정할 수 없다.

### ABA 문제

CAS가 값이 A인지 검사하는 동안 다른 스레드가 A를 B로 바꿨다가 다시 A로 돌려놓으면 CAS는 중간 변경을 알아채지 못할 수 있다. 버전 태그를 함께 비교하거나 안전한 메모리 회수 기법을 사용한다. 단순 정수 카운터 증감마다 ABA(ABA problem)가 문제인 것은 아니며 알고리즘 의미가 중간 변화를 구분해야 할 때 중요하다.

## 4. 쉬운 예시

```java
// AtomicInteger: 접속자 수 카운터 (단일 값 원자적 증가)
AtomicInteger connectedPlayers = new AtomicInteger(0);
connectedPlayers.incrementAndGet();  // 읽기-증가-쓰기가 원자적

// BAD: 정원 검사 + 증가 + 세션 등록은 복합 불변식 — Atomic만으로 부족
if (connectedPlayers.get() < MAX_PLAYERS) {   // 읽기
    connectedPlayers.incrementAndGet();        // 증가 — 사이에 다른 스레드가 끼어들 수 있음
    sessionMap.put(playerId, session);         // 세션 등록
}

// GOOD: CAS로 정원 제한과 증가를 원자적으로 처리
int current;
do {
    current = connectedPlayers.get();
    if (current >= MAX_PLAYERS) throw new RoomFullException();
} while (!connectedPlayers.compareAndSet(current, current + 1));
// 주의: 위에서 increment 이후 sessionMap 등록도 원자적으로 묶으려면 락 필요
```

```java
// volatile: 종료 플래그 가시성 보장
volatile boolean serverRunning = true;

// 다른 스레드에서 serverRunning = false 설정 시 이 스레드가 반드시 관찰
while (serverRunning) {
    processNextTick();
}

// volatile만으로는 count++ 안전하지 않음 — 복합 원자성 미보장
volatile int count = 0;
count++;  // 읽기-증가-쓰기 → 여전히 경쟁 상태. AtomicInteger 사용 필요
```

```java
// Acquire/Release: 게임 스냅샷 게시 패턴
AtomicBoolean snapshotReady = new AtomicBoolean(false);

// 생산자 스레드 (게임 틱)
snapshot.x = 100;
snapshot.y = 200;
snapshot.tick = tickCount;
snapshotReady.set(true);   // release: 위 쓰기들이 이 시점 이후에 관찰됨을 보장

// 소비자 스레드 (렌더러)
if (snapshotReady.get()) { // acquire: 이후 읽기에서 위 시점 이전 쓰기가 보임
    render(snapshot.x, snapshot.y); // 초기화 완료된 값 안전하게 읽기
}
// snapshotReady 없이 snapshot을 직접 읽으면 초기화 전 값(0)을 볼 수 있음
```

## 5. 비슷한 개념과 비교

| 개념 | 보장하는 것 | 보장하지 못하는 것 |
|---|---|---|
| Atomic 연산 | 단일 값의 분할 없는 갱신 | 여러 값의 복합 불변식 |
| volatile (Java) | 가시성과 읽기·쓰기 순서 | count++ 같은 복합 원자성 |
| Acquire/Release | 게시 이전 쓰기들의 가시성 | 임계 구역 상호 배제 |
| Mutex | 임계 구역 상호 배제와 happens-before | 분산 프로세스 간 정합성 |

| 순서 모델 | 강도 | 적합 사용처 |
|---|---|---|
| Sequentially Consistent | 가장 강함 | 정확성이 중요한 기본 선택 |
| Acquire/Release | 중간 | 생산자-소비자 게시 패턴 |
| Relaxed | 가장 약함 | 다른 상태와 무관한 통계 카운터 |

C++ `std::atomic`, C# `Interlocked`와 `Volatile`, Java `Atomic*`와 `volatile`은 세부 API와 메모리 모델이 다르다. 어떤 읽기·쓰기·복합 연산을 보호하는지를 언어 사양 기준으로 판단한다.

## 6. 장점과 단점

**Atomic 연산의 장점**

- 간단한 카운터와 플래그에서 락과 커널 대기를 피할 수 있다.
- CAS 기반 알고리즘은 스레드를 블로킹하지 않는다.

**Atomic 연산의 단점**

- 복합 불변식 보호에는 부족하다. 여러 원자 변수를 조합해도 전체가 원자적이지 않다.
- 경쟁이 심하면 CAS 반복 실패로 CPU와 캐시 트래픽이 낭비된다.
- 복잡한 CAS 알고리즘은 정확성 증명이 어렵다.

**volatile의 장점**

- 종료 플래그처럼 단순한 단방향 가시성 전달에 간결하다.

**volatile의 단점**

- count++ 같은 복합 원자성을 제공하지 않는다.
- 언어마다 보장 범위가 달라 C++ volatile과 Java volatile을 혼동하기 쉽다.

## 7. 게임 서버·백엔드 실무 예시

네트워크 스레드가 게임 스레드로 작업을 넘길 때 검증된 동시성 큐를 사용한다. 락 대기 시간, 큐 길이, 타임아웃과 p99 지연을 함께 관찰한다.

큐 내부가 스레드 안전해도 명령의 의미까지 안전해지는 것은 아니다. 네트워크 스레드가 동일 플레이어의 명령을 여러 생산자로 넣으면 큐가 보장하는 전체 또는 생산자별 순서를 확인해야 한다. 게임 스레드는 세션 세대 번호와 명령 시퀀스를 검증해 재접속 이전 명령이나 중복 명령을 버린다.

접속자 수 같은 관측용 카운터는 원자 증가로 충분할 수 있다. 반면 "접속자 수가 정원보다 작으면 증가하고 세션을 등록한다"는 카운터와 세션 맵의 복합 불변식이다. 하나의 락이나 소유 스레드 명령으로 함께 처리한다.

## 8. 자주 하는 오해

- **"volatile이면 스레드 안전하다"**: volatile(Java)은 가시성과 일부 순서를 제공하지만 count++ 같은 복합 연산을 원자적으로 만들지 않는다. C++ volatile은 메모리 가시성 보장이 더 제한적이다.
- **"Atomic 카운터 하나로 복합 불변식을 보호할 수 있다"**: 카운터 증가는 원자적이어도 조건 검사 + 증가 + 다른 자료구조 수정 전체는 별도 락이나 단일 소유자가 필요하다.
- **"코드가 위에서 아래로 실행되므로 다른 스레드도 같은 순서로 본다"**: 컴파일러와 CPU가 단일 스레드 결과가 같으면 재배치를 허용한다. Happens-before 관계가 없이는 관찰 순서가 보장되지 않는다.
- **"CAS는 블로킹이 없으니 항상 빠르다"**: 경쟁이 심하면 여러 스레드가 같은 캐시 라인을 갱신하며 CAS 실패와 재시도를 반복해 CPU를 낭비한다. 락 없다고 성능 문제가 없는 것이 아니다.
- **"Relaxed 원자 연산은 성능이 좋으니 기본으로 써도 된다"**: 해당 값의 원자성만 보장하고 다른 데이터와의 게시 순서를 만들지 않는다. 근거 없이 사용하면 버그가 생기고 추론이 어려워진다.
- **"데이터 레이스에서는 오래된 값 중 하나를 읽는다"**: C++에서는 정의되지 않은 동작으로 엉뚱한 값이나 충돌이 날 수 있다. Java에서도 보장이 줄어든다.
- **"원자 참조만 교체하면 새 객체의 필드도 안전하게 보인다"**: 참조 자체는 원자적이지만 새 객체의 필드 초기화가 다른 스레드에 보이는지는 사용한 메모리 순서에 달려 있다. 게시 패턴에서 Acquire/Release를 함께 써야 한다.

## 9. 면접 질문

### Q1. Atomic 연산이 보장하는 것과 보장하지 못하는 것은 무엇인가요?

단일 값의 읽기-수정-쓰기가 중간 상태 없이 원자적으로 보인다는 것을 보장한다. 여러 값의 복합 불변식은 자동으로 보호하지 않는다. 카운터 증가는 원자적이어도 카운터 + 세션 맵 같은 두 자료구조의 복합 조건은 별도 동기화가 필요하다.

### Q2. volatile과 Atomic은 어떻게 다른가요?

Java volatile은 가시성과 읽기·쓰기 순서를 제공하지만 count++ 같은 읽기-수정-쓰기 전체를 원자적으로 만들지 않는다. AtomicInteger는 이 복합 연산을 원자적으로 제공한다. 단순 플래그처럼 단방향 가시성 전달에는 volatile이 간결하고, 카운터 증감에는 Atomic을 써야 한다.

### Q3. Acquire/Release 메모리 순서는 왜 필요한가요?

생산자가 데이터를 초기화한 뒤 release로 플래그를 게시하고, 소비자가 acquire로 같은 플래그를 읽으면 생산자의 데이터 쓰기들이 소비자에게 보이는 순서 관계를 만든다. 이 관계 없이 플래그만 최신으로 읽으면 데이터 필드는 초기화 전 값을 볼 수 있다.

### Q4. Happens-before 관계란 무엇인가요?

한 작업의 메모리 효과가 다른 작업에 관찰되도록 언어 메모리 모델이 보장하는 관계다. 실제 시간 선후가 아니라 동기화 연산(뮤텍스 해제·획득, release/acquire, 스레드 시작·합류 등)이 이 관계를 만든다. 이 관계가 없는 충돌 접근을 "먼저 실행됐으니 보인다"고 가정할 수 없다.

### Q5. Atomic 카운터를 쓰면 경쟁 상태가 모두 해결되나요?

해당 카운터의 개별 갱신 손실은 막을 수 있지만 다른 값과의 조건 검사·수정 전체는 보호하지 않는다. 정원 검사, 카운터 증가, 세션 맵 등록은 하나의 복합 불변식이므로 락이나 단일 소유자 처리가 필요하다.

### Q6. CAS 기반 알고리즘도 느려질 수 있나요?

그렇다. 경쟁이 심하면 여러 스레드가 같은 캐시 라인을 갱신하며 CAS 실패와 재시도를 반복한다. 블로킹은 없어도 CPU를 소비하고 공정성이 낮아질 수 있으므로 실제 경쟁 패턴을 측정해야 한다. 락 없다는 것이 성능이 좋다는 보장이 아니다.

## 11. 30초 모범답변

> Atomic은 단일 연산의 원자성을, 메모리 가시성은 스레드 간 쓰기의 관찰 순서를 다룹니다. volatile은 가시성을 제공하지만 count++ 같은 복합 원자성은 보장하지 않습니다. 생산자-소비자 패턴에서는 Acquire/Release로 데이터 초기화가 완료된 뒤에야 소비자가 읽도록 게시 관계를 만들어야 합니다.

## 12. 1~2분 확장답변

> Atomic은 단일 값의 읽기-수정-쓰기를 원자적으로 보장하지만 여러 값의 복합 불변식은 별도 락이나 단일 소유자가 필요합니다. volatile은 가시성과 순서를 제공하지만 count++ 전체는 원자적으로 만들지 않습니다. CAS는 스레드를 블로킹하지 않지만 경쟁이 심하면 반복 실패로 CPU를 낭비합니다. Acquire/Release는 생산자의 데이터 쓰기가 소비자에게 순서대로 보이는 게시 관계를 만듭니다. 게임 서버에서 관측용 카운터는 Atomic으로 충분하지만 정원 제어처럼 복합 조건이 있는 경우에는 락으로 전체를 함께 보호해야 합니다.

## 13. 핵심 요약

- Atomic 연산은 단일 값의 읽기-수정-쓰기를 원자적으로 보장한다. 여러 값의 복합 불변식은 별도 락이나 단일 소유자가 필요하다.
- volatile(Java)은 가시성과 순서를 제공하지만 count++ 같은 복합 원자성을 보장하지 않는다.
- CAS는 예상값과 같을 때만 새 값으로 바꾼다. 경쟁 시 여러 스레드가 반복 실패하며 CPU를 낭비할 수 있다.
- Acquire/Release 순서는 생산자의 데이터 쓰기가 소비자에게 보이는 게시 관계를 만든다.
- Happens-before는 실제 시간 선후가 아니라 동기화 연산이 만드는 메모리 관찰 관계다.
- ABA 문제: CAS가 A를 확인하는 사이에 B로 바뀌었다가 다시 A가 되면 중간 변경을 알아채지 못한다. 버전 태그로 완화한다.
- 코드 실행 순서와 다른 스레드 관찰 순서는 다르다. 컴파일러와 CPU가 단일 스레드 결과가 같으면 재배치를 허용한다.
- 관측용 카운터는 Atomic으로 충분하지만 카운터 + 세션 맵 복합 불변식은 락이나 단일 소유자로 함께 처리해야 한다.
