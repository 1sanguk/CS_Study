# 13. OS 종합면접


## 학습 목표

- 프로세스와 스레드의 격리·공유 경계를 설명하고 게임 서버 장애에서 CPU·락 병목을 구분할 수 있다.
- 동기화 도구(Mutex, Semaphore, Atomic)를 보호할 불변식에 따라 선택할 수 있다.
- 가상 메모리, TLB, CPU Cache 계층의 역할을 설명하고 Minor/Major Fault를 구분할 수 있다.
- p99 틱 지연의 원인을 CPU, 락, 메모리, I/O 증거를 기준으로 진단 순서에 맞게 설명할 수 있다.

## 1. 개요

OS 종합면접은 격리·실행·동기화·메모리·I/O를 하나의 요청 흐름과 장애 증거로 연결하는 것이다.

운영체제는 제한된 CPU(Central Processing Unit), 메모리와 장치를 여러 프로그램이 안전하게 공유하도록 추상화하고 중재한다. 프로세스는 주소 공간과 자원의 격리 단위이고 스레드는 프로세스 안의 CPU 실행 흐름이다. 스케줄러가 실행 순서를 결정하고 가상 메모리가 주소와 권한을 관리하며 시스템 콜이 보호된 커널 기능의 진입점을 제공한다.

면접에서는 개념을 따로 암기하기보다 요청 하나가 네트워크에서 도착해 스레드에서 처리되고 메모리를 읽으며 다시 응답하는 흐름에 연결한다. 성능 문제도 CPU 사용률 하나가 아니라 실행, 대기, 주소 변환과 I/O 중 어디에서 시간이 쓰이는지 나눠 설명한다.

## 2. 왜 필요한가

게임 서버 지연은 CPU, 락, 메모리와 I/O를 함께 봐야 한다. 추상화의 편리함에도 실제 전환과 메모리 비용은 남는다.

프로세스 격리가 없으면 한 서버 모듈의 잘못된 포인터가 다른 서비스 메모리를 직접 손상시킬 수 있다. 스케줄링이 없으면 CPU를 오래 쓰는 작업이 입력 처리를 독점할 수 있다. 동기화가 없으면 여러 스레드가 공유 상태를 손상시키고, 가상 메모리와 권한 경계가 없으면 프로그램이 임의의 장치와 메모리에 접근할 수 있다.

이 보호와 추상화에는 문맥 교환, 락 대기, 페이지 테이블 탐색, 캐시 미스와 시스템 콜 같은 비용이 따른다. 비용을 없애는 것이 목표가 아니라 서비스 요구에 맞게 격리와 공유 범위를 선택하고 실제 병목을 측정하는 것이 목표다.

## 3. 핵심 동작 원리

```text
Network Card
    │ Interrupt·Polling, Kernel Network Stack
    v
Socket Receive Queue
    │ I/O Completion·Readiness
    v
Application Work Queue
    │ Scheduler가 Thread에 CPU 배정
    v
Game Logic ── Lock·Atomic·Owner Thread ──> Shared State
    │                                      │
    └──── Virtual Address → TLB → Cache → Physical Memory
    │
    └──── System Call → Socket Send Buffer → Network
```

프로세스는 자원을 격리하고 스레드는 실행되며 가상 메모리와 System Call이 보호 경계를 만든다. 보호, 변환, Cache 계층 중 어디서 대기하는지 구분한다.

### 실행과 스케줄링

프로그램이 실행되면 운영체제는 프로세스 주소 공간과 자원을 만들고 초기 스레드를 준비한다. 실행 가능한 스레드는 준비 큐에서 CPU를 기다리고 스케줄러가 코어에 배정한다. I/O나 락을 기다리면 대기 상태가 되고 조건이 충족되면 다시 준비 상태로 간다.

문맥 교환은 레지스터와 실행 위치를 저장·복원하는 비용뿐 아니라 캐시와 TLB(Translation Lookaside Buffer) 지역성 손실을 만들 수 있다. 스레드를 늘리면 I/O 대기를 겹칠 수 있지만 CPU 작업 스레드가 코어보다 지나치게 많으면 실행 큐와 전환만 늘 수 있다. 동시성은 여러 작업이 진행되는 구조이고 병렬성은 여러 코어에서 실제 동시 실행되는 상태라는 차이를 함께 설명한다.

### 공유 상태와 동기화

경쟁 상태는 공유 자원에 대한 실행 순서에 따라 결과가 달라지는 문제다. 보호할 임계 구역은 코드 줄 수가 아니라 함께 유지해야 하는 불변식으로 정한다. Mutex는 한 소유자의 상호 배제, Semaphore는 N개의 허가, SpinLock은 매우 짧은 CPU 반복 대기를 표현한다.

Atomic은 지정된 단일 연산의 원자성을 제공하지만 여러 값의 복합 불변식을 자동으로 지키지 않는다. 메모리 가시성과 관찰 순서도 필요하다. 가능하면 룸 상태를 단일 스레드가 소유하고 다른 스레드는 명령 큐로 전달해 임의 공유를 줄인다.

```text
동기화 선택 흐름
공유가 필요한가?
  ├─ 아니오 → 불변 Data·복사·Thread Local
  └─ 예
      ├─ 단일 값 갱신 → Atomic 검토
      ├─ 복합 불변식 → Mutex·Owner Thread
      └─ N개 Resource → Semaphore
```

### 메모리와 주소 변환

프로세스의 Code·Data·BSS(Block Started by Symbol)·Heap·Stack은 실행 명령과 데이터 수명·권한을 이해하는 대표 영역이다. 각 스레드는 Stack을 가지고 Heap과 전역 상태는 프로세스 안에서 공유한다. 가상 메모리는 페이지를 물리 프레임에 매핑해 격리, 요구 할당과 파일 공유를 제공한다.

TLB는 가상→물리 주소 변환을, CPU Cache는 명령과 데이터를 캐시한다. TLB Miss는 유효한 Page Table Mapping이 있으면 Page Fault 없이 해결할 수 있다. Page Fault도 새 0 Page나 Copy-on-Write를 처리하는 Minor Fault와 저장장치 I/O가 필요한 Major Fault, 불법 접근을 구분한다.

### 권한 경계와 I/O

System Call은 사용자 코드가 커널 서비스를 의도적으로 요청하는 진입이다. 장치 인터럽트는 현재 명령과 비동기적으로 발생할 수 있다. System Call은 Mode Switch를 동반하지만 같은 스레드로 바로 복귀할 수 있으므로 반드시 Context Switch인 것은 아니다. Blocking I/O로 스레드가 대기할 때 다른 스레드로 전환될 수 있다.

비동기 I/O는 I/O가 끝날 때까지 호출 스레드를 붙잡지 않고 여러 작업을 겹쳐 처리한다. CPU 계산을 자동으로 병렬화한다는 뜻은 아니다.

## 4. 쉬운 예시

```java
// 틱 지연 원인 탐색: 락 대기 중인 스레드 추출
Thread.getAllStackTraces().forEach((thread, stack) -> {
    if (thread.getState() == Thread.State.BLOCKED) {
        System.out.println("BLOCKED: " + thread.getName());
        for (StackTraceElement e : stack) System.out.println("  " + e);
    }
});
// → BLOCKED 스레드가 많으면 Lock Contention 의심
// → CPU는 낮지만 틱이 느린 경우 이 패턴이 원인일 수 있음
```

```bash
# Tick 지연 진단 순서

# 1. CPU & Context Switch
vmstat 1 5         # cs 열 = 초당 Context Switch, us=사용자 CPU, sy=시스템 CPU

# 2. Memory & Fault
cat /proc/<pid>/status | grep -E "VmRSS|VmSwap"
cat /proc/<pid>/stat | awk '{print "minor:", $10, "major:", $12}'
# → major가 늘면 Working Set이 RAM에 맞지 않을 수 있음

# 3. System Call 통계
strace -c -p <pid>      # System Call별 호출 수·시간
# → send/write가 많으면 배치 최적화 검토

# 4. Thread Dump (JVM)
jstack <pid>            # 스레드 상태와 Lock 소유자 확인
```

## 5. 비슷한 개념과 비교

| 혼동하기 쉬운 쌍 | 차이 |
|---|---|
| Process / Thread | 자원·주소 공간 격리 / Process 내 실행 흐름 |
| Concurrency / Parallelism | 겹친 시간에 진행 / 같은 순간 실제 실행 |
| Mutex / Semaphore | 한 소유자의 상호 배제 / N개 Permit 제어 |
| Atomicity / Visibility | 연산의 분할 없는 효과 / 다른 Thread가 쓰기를 보는 조건 |
| Deadlock / Starvation / Livelock | 순환 대기 / 특정 작업 기회 없음 / 반응하지만 완료 없음 |
| TLB / CPU Cache | 주소 변환 Cache / 명령·Data Cache |
| Mode Switch / Context Switch | 권한 수준 전환 / 실행 주체 전환 |
| Minor / Major Fault | Disk 없는 처리 / 저장장치 I/O 필요 |

| 진단 증거 | 의심 원인 | 확인 방법 |
|---|---|---|
| CPU 높음, 실행 큐 김 | CPU 경쟁, Hot Path | CPU Profile, 코어별 분산 |
| CPU 낮음, BLOCKED 스레드 많음 | Lock Contention | Thread Dump, Lock Owner |
| Major Fault 증가, Swap I/O | Working Set > RAM | RSS, Heap, Buffer 분리 |
| System CPU 높음, 시스템 콜 많음 | I/O 배치 부족 | strace -c, 호출당 Byte |

## 6. 장점과 단점

**OS 추상화(격리·스케줄링·가상 메모리·시스템 콜)의 장점**

- 프로세스별 주소 공간 격리로 한 모듈의 오류가 다른 서비스를 직접 손상시키지 않는다.
- 스케줄러가 CPU 독점 없이 여러 작업을 공정하게 실행한다.
- 가상 메모리가 연속 주소, 요구 할당, 파일 공유를 제공한다.
- 시스템 콜이 검증된 진입점으로 하드웨어를 보호하면서 접근하게 한다.

**OS 추상화의 단점**

- 문맥 교환이 캐시·TLB 지역성 손실을 만들 수 있다.
- 락 대기는 처리를 직렬화해 처리량을 제한한다.
- Major Fault는 저장장치 I/O 지연을 직접 유발한다.
- 시스템 콜은 권한 전환, 검증, 복사 비용을 포함한다.

**측정 없는 최적화의 위험**

- 프로파일 없이 구조를 바꾸면 실제 병목이 아닌 곳을 최적화한다.
- Lock-free로 교체해도 CAS(Compare-And-Swap) 재시도와 메모리 배리어 비용이 남을 수 있다.
- 스레드를 줄이면 CPU 경쟁이 해결될 수 있지만 I/O 대기 겹침이 줄 수 있다.

## 7. 게임 서버·백엔드 실무 예시

p99 틱 지연과 실행 큐, Context Switch, Fault, Lock 대기를 같은 시간축에서 본다. 평균 CPU뿐 아니라 할당률, RSS, Fault, 호출 수와 p99를 본다.

### 진단 순서

1. 영향 범위와 시작 시각, 배포·트래픽 변화를 확인한다.
2. CPU 사용률을 코어별로 보고 실행 큐와 Context Switch를 연결한다.
3. CPU Profile에서 계산 Hot Path를, Thread Dump에서 대기 원인을 본다.
4. Lock 대기·보유 시간과 큐 길이로 공유 병목을 찾는다.
5. RSS, Heap, Native Buffer, Minor·Major Fault와 Swap을 분리한다.
6. System CPU, I/O 호출 수, 호출당 Byte와 Network Drop을 확인한다.
7. 변경 후 처리량뿐 아니라 p99 Tick, 오류율과 자원 사용을 비교한다.

연결마다 스레드를 만드는 대신 비동기 I/O와 제한된 작업 풀을 사용하고, CPU 작업과 Blocking I/O Pool을 분리한다. 룸 단위 상태 소유권으로 Lock 범위를 줄인다. 캐시와 작업 큐에는 상한을 두어 메모리 압박이 Major Fault와 OOM으로 번지기 전에 과부하를 거절한다.

## 8. 자주 하는 오해

- **"CPU 사용률이 낮으면 서버에 병목이 없다"**: 락 대기, Blocking I/O, Major Fault로 CPU를 거의 쓰지 않아도 처리가 느릴 수 있다. 실행 큐, BLOCKED 스레드, Fault 수와 I/O 대기를 함께 봐야 한다.
- **"Thread를 늘리면 CPU 처리량이 비례한다"**: CPU 바운드 작업에서 스레드가 코어 수를 초과하면 Context Switch만 늘고 처리량이 정체한다. Lock 경쟁이 많으면 스레드를 늘릴수록 직렬화가 심해질 수 있다.
- **"Lock-free 구조는 대기와 성능 문제가 없다"**: CAS 재시도 루프, 메모리 배리어 비용, ABA 문제, 메모리 수명 관리와 검증 어려움이 있다. 특정 Hot Path에서 프로파일로 검증된 경우에만 적용한다.
- **"프로세스 격리는 항상 안전하다"**: 공유 메모리 IPC(Inter-Process Communication)를 쓰면 격리 보호가 줄어들고, 락 없는 공유 메모리 접근은 일반 스레드 경쟁과 동일한 문제를 일으킨다.
- **"평균 지연이 SLA를 만족하면 성능 문제가 없다"**: 평균은 드문 긴 Pause를 숨긴다. p99·p99.9와 최대값, 발생 시점의 요청·Tick ID를 남겨야 간헐적 장애 원인을 찾을 수 있다.
- **"진단 시 가장 먼저 코드를 바꿔야 한다"**: 배포·트래픽 변화 확인, 지표 수집, 증거 기반 원인 좁히기가 먼저다. 추정만으로 바꾸면 실제 병목이 아닌 곳을 최적화하게 된다.
- **"Thread-safe 컬렉션이면 복합 비즈니스 연산도 안전하다"**: ConcurrentHashMap의 containsKey + put은 두 연산 사이에 다른 스레드가 끼어들 수 있다. 복합 불변식은 Mutex나 Owner Thread로 보호해야 한다.

## 9. 면접 질문

### Q1. Process와 Thread의 차이를 설명해 주세요.

프로세스는 독립 주소 공간과 열린 파일 같은 자원의 격리 단위이고, 스레드는 프로세스 자원을 공유하는 CPU 실행 흐름이다. 프로세스는 장애 격리가 강하지만 IPC가 필요하고, 스레드는 데이터 교환이 빠르지만 공유 상태를 동기화해야 한다.

### Q2. Context Switch가 많으면 왜 성능이 저하될 수 있나요?

레지스터 저장·복원뿐 아니라 새 실행 흐름의 Cache·TLB 지역성이 약해져 Miss가 늘 수 있다. 다만 Context Switch 수만으로 병목을 단정하지 않고 실행 큐, CPU 사용과 자발적·비자발적 전환을 함께 본다. I/O 대기가 원인이라면 스레드 수를 줄이기보다 비동기 I/O를 검토한다.

### Q3. 동기화 도구를 어떻게 선택하나요?

보호할 불변식에서 출발한다. 단일 카운터 증감처럼 원자성만 필요하면 Atomic을 검토한다. 잔액 차감과 인벤토리 갱신처럼 여러 값을 함께 유지해야 하면 Mutex나 Owner Thread로 임계 구역 전체를 보호한다. DB 연결처럼 N개 자원을 제한하면 Semaphore를 사용한다.

### Q4. Virtual Memory와 Page Fault를 설명해 주세요.

가상 메모리는 프로세스별 독립 주소 공간과 Page 단위 보호를 제공하고, Page Table로 가상 Page를 물리 Frame에 매핑한다. Page Fault는 접근한 Page의 매핑이 없거나 물리 메모리에 없을 때 발생한다. Disk I/O가 없는 Minor Fault와 필요한 Major Fault를 구분해야 한다. Major Fault가 늘면 Working Set이 RAM에 맞지 않을 수 있다.

### Q5. 게임 서버의 간헐적 Tick 지연을 어떻게 진단하나요?

문제 시각을 기준으로 코어별 CPU와 실행 큐, Lock Wait, GC·할당, Minor·Major Fault, Swap과 I/O 지연을 맞춘다. CPU Profile과 Thread Dump로 실행과 대기를 구분하고 평균보다 p99와 긴 Pause 구간을 분석한다. 배포·트래픽 변화를 먼저 확인해 원인 범위를 좁힌 뒤 코드 수정을 검토한다.

### Q6. CPU 사용률이 낮은데도 서버가 느릴 수 있는 이유는 무엇인가요?

락 대기(BLOCKED 스레드), Blocking I/O 대기, Major Fault로 인한 Disk I/O, 또는 작업 큐가 처리보다 빠르게 쌓여 큐 대기로 처리가 미뤄질 수 있다. CPU는 유휴 상태이지만 스레드가 실행 가능 상태가 아닌 대기 상태에 있는 경우다. Thread Dump와 BLOCKED 스레드, Fault 수와 I/O 대기를 함께 확인한다.

## 11. 30초 모범답변

> 운영체제는 프로세스를 격리하고 스레드를 스케줄링하며 가상 메모리와 시스템 콜로 CPU, 메모리와 장치를 안전하게 공유하게 합니다. 동시 접근에는 보호할 불변식에 맞게 Mutex·Atomic·소유권 구조를 선택하고, 실제 성능에는 문맥 교환, Cache·TLB Miss, Page Fault와 I/O 대기가 영향을 줍니다. 게임 서버 장애에서는 CPU, 실행 큐, Lock, Memory와 I/O 지표를 같은 시간축에서 확인합니다.

## 12. 1~2분 확장답변

> 운영체제는 프로세스라는 자원·주소 공간 단위로 프로그램을 격리하고 스레드를 CPU 실행 단위로 스케줄링합니다. 여러 스레드가 Heap과 전역 상태를 공유하므로 복합 불변식은 Mutex나 단일 소유자 구조로 보호하고, 단순 카운터는 필요한 경우 Atomic을 사용합니다. 가상 메모리는 Page Table로 가상 Page를 물리 Frame에 연결하고 TLB가 변환을, CPU Cache가 명령과 데이터를 가속합니다. Mapping을 바로 처리할 수 없으면 Page Fault가 발생하며 Disk I/O가 없는 Minor와 필요한 Major를 구분해야 합니다. System Call은 Mode Switch이지 반드시 Context Switch가 아니고, 비동기 I/O도 System Call을 사용하되 스레드를 블로킹하지 않고 여러 요청을 겹쳐 처리합니다. 게임 서버의 p99 Tick 지연은 배포·트래픽 변화를 먼저 확인하고 CPU Hot Path, 실행 큐와 Context Switch, Lock 대기, Fault·Swap, System CPU와 I/O 큐를 동일 시간축에서 분석합니다. CPU가 낮아도 락 대기와 Major Fault로 처리가 느릴 수 있으므로 지표를 분리해서 봐야 합니다.

## 13. 핵심 요약

- 프로세스는 주소 공간과 자원의 격리 단위이고 스레드는 프로세스 안의 CPU 실행 흐름이다. 스레드는 Heap과 전역 상태를 공유하므로 불변식을 동기화로 보호해야 한다.
- 동기화 도구 선택은 보호할 불변식에서 출발한다. 단순 카운터는 Atomic, 복합 불변식은 Mutex, 자원 수 제한은 Semaphore를 검토한다.
- 동시성은 여러 작업이 겹쳐 진행되는 구조이고 병렬성은 여러 코어에서 실제 동시 실행이다. 비동기 I/O는 동시성이지 자동으로 병렬 CPU 계산이 아니다.
- 가상 메모리는 프로세스별 독립 주소 공간과 요구 Paging을 제공한다. TLB는 주소 변환을, CPU Cache는 명령과 데이터를 가속한다.
- Page Fault는 Disk I/O가 없는 Minor Fault와 필요한 Major Fault를 구분해야 한다. Major Fault가 늘면 Working Set이 RAM에 맞지 않을 수 있다.
- System Call은 Mode Switch이지 반드시 Context Switch가 아니다. Blocking I/O 대기 시 스케줄러가 다른 스레드를 선택하면 추가될 수 있다.
- CPU 사용률이 낮아도 락 대기, I/O 대기, Major Fault로 처리가 느릴 수 있다. 실행, 대기, 주소 변환, I/O 중 어디서 시간이 쓰이는지 나눠 본다.
- p99 틱 지연은 CPU Hot Path, 실행 큐와 Context Switch, Lock Wait, Minor·Major Fault, 시스템 CPU와 I/O 지연을 같은 시간축에서 분석한다. 평균보다 p99와 긴 Pause가 장애를 드러낸다.
- 배포·트래픽 변화 확인이 먼저이고 코드 수정은 증거로 원인을 좁힌 뒤에 한다.
