# 13. OS 종합면접

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 프로그램·프로세스·스레드와 운영체제의 역할을 연결해 설명할 수 있다.
- 스케줄링, 동기화, 가상 메모리와 I/O 경계를 비교할 수 있다.
- 게임 서버의 CPU·락·메모리·I/O 지연을 증거로 분류할 수 있다.

## 1. 개요

OS 핵심은 자원 소유, 실행, 스케줄링, 동기화, 주소 변환과 보호를 연결해 설명하는 것이다.

운영체제는 제한된 CPU, 메모리와 장치를 여러 프로그램이 안전하게 공유하도록 추상화하고 중재한다. 프로세스는 주소 공간과 자원의 격리 단위이고 스레드는 프로세스 안의 CPU 실행 흐름이다. 스케줄러가 실행 순서를 결정하고 가상 메모리가 주소와 권한을 관리하며 시스템 콜이 보호된 커널 기능의 진입점을 제공한다.

면접에서는 개념을 따로 암기하기보다 요청 하나가 네트워크에서 도착해 스레드에서 처리되고 메모리를 읽으며 다시 응답하는 흐름에 연결한다. 성능 문제도 CPU 사용률 하나가 아니라 실행, 대기, 주소 변환과 I/O 중 어디에서 시간이 쓰이는지 나눠 설명한다.

## 2. 왜 필요한가

게임 서버 지연은 CPU, 락, 메모리와 I/O를 함께 봐야 한다. 추상화의 편리함에도 실제 전환과 메모리 비용은 남는다.

프로세스 격리가 없으면 한 서버 모듈의 잘못된 포인터가 다른 서비스 메모리를 직접 손상시킬 수 있다. 스케줄링이 없으면 CPU를 오래 쓰는 작업이 입력 처리를 독점할 수 있다. 동기화가 없으면 여러 스레드가 공유 상태를 손상시키고, 가상 메모리와 권한 경계가 없으면 프로그램이 임의의 장치와 메모리에 접근할 수 있다.

이 보호와 추상화에는 문맥 교환, 락 대기, 페이지 테이블 탐색, 캐시 미스와 시스템 콜 같은 비용이 따른다. 비용을 없애는 것이 목표가 아니라 서비스 요구에 맞게 격리와 공유 범위를 선택하고 실제 병목을 측정하는 것이 목표다.

## 3. 핵심 동작 원리

```text
Network Card
    │ Interrupt·Polling, Kernel Network Stack
    v
Socket Receive Queue
    │ I/O Completion·Readiness
    v
Application Work Queue
    │ Scheduler가 Thread에 CPU 배정
    v
Game Logic ── Lock·Atomic·Owner Thread ──> Shared State
    │                                      │
    └──── Virtual Address → TLB → Cache → Physical Memory
    │
    └──── System Call → Socket Send Buffer → Network
```
프로세스는 자원을 격리하고 스레드는 실행되며 가상 메모리와 System Call이 보호 경계를 만든다. 보호, 변환, Cache 계층 중 어디서 대기하는지 구분한다.

### 실행과 스케줄링

프로그램이 실행되면 운영체제는 프로세스 주소 공간과 자원을 만들고 초기 스레드를 준비한다. 실행 가능한 스레드는 준비 큐에서 CPU를 기다리고 스케줄러가 코어에 배정한다. I/O나 락을 기다리면 대기 상태가 되고 조건이 충족되면 다시 준비 상태로 간다.

문맥 교환은 레지스터와 실행 위치를 저장·복원하는 비용뿐 아니라 캐시와 TLB 지역성 손실을 만들 수 있다. 스레드를 늘리면 I/O 대기를 겹칠 수 있지만 CPU 작업 스레드가 코어보다 지나치게 많으면 실행 큐와 전환만 늘 수 있다. 동시성은 여러 작업이 진행되는 구조이고 병렬성은 여러 코어에서 실제 동시 실행되는 상태라는 차이를 함께 설명한다.

### 공유 상태와 동기화

경쟁 상태는 공유 자원에 대한 실행 순서에 따라 결과가 달라지는 문제다. 보호할 임계 구역은 코드 줄 수가 아니라 함께 유지해야 하는 불변식으로 정한다. Mutex는 한 소유자의 상호 배제, Semaphore는 N개의 허가, SpinLock은 매우 짧은 CPU 반복 대기를 표현한다.

Atomic은 지정된 단일 연산의 원자성을 제공하지만 여러 값의 복합 불변식을 자동으로 지키지 않는다. 메모리 가시성과 관찰 순서도 필요하다. 가능하면 룸 상태를 단일 스레드가 소유하고 다른 스레드는 명령 큐로 전달해 임의 공유를 줄인다. 큐에도 상한과 역압력이 필요하다.

```text
안전한 동기화 선택
공유가 필요한가?
  ├─ 아니오 → 불변 Data·복사·Thread Local
  └─ 예
      ├─ 단일 값 갱신 → Atomic 검토
      ├─ 복합 불변식 → Mutex·Owner Thread
      └─ N개 Resource → Semaphore
```

교착 상태는 상호 배제, 점유 대기, 비선점, 순환 대기가 함께 성립할 때 가능하다. 락 획득 순서를 고정해 순환을 막고 외부 I/O 중 락을 보유하지 않는다. 타임아웃은 영구 대기를 끊지만 중간 상태 롤백과 제한된 재시도가 없으면 완전한 해결이 아니다.

### 메모리와 주소 변환

프로세스의 Code·Data·BSS·Heap·Stack은 실행 명령과 데이터 수명·권한을 이해하는 대표 영역이다. 각 스레드는 Stack을 가지고 Heap과 전역 상태는 프로세스 안에서 공유한다. 가상 메모리는 페이지를 물리 프레임에 매핑해 격리, 요구 할당과 파일 공유를 제공한다.

TLB는 가상→물리 주소 변환을, CPU Cache는 명령과 데이터를 캐시한다. TLB 미스는 유효한 Page Table Mapping이 있으면 Page Fault 없이 해결할 수 있다. Page Fault도 새 0 Page나 Copy-on-Write를 처리하는 Minor Fault와 저장장치 I/O가 필요한 Major Fault, 불법 접근을 구분한다.

데이터가 연속적이고 반복 접근되면 공간·시간 지역성을 활용하기 쉽다. 서로 다른 코어의 독립 카운터가 같은 Cache Line에 놓이면 False Sharing으로 Line 소유권이 반복 이동할 수 있다. 자료구조의 이론 복잡도가 같아도 실제 배치가 Tick 성능을 바꿀 수 있다.

### 권한 경계와 I/O

시스템 콜은 사용자 코드가 커널 서비스를 의도적으로 요청하는 진입이다. 장치 인터럽트는 현재 명령과 비동기적으로 발생할 수 있다. 시스템 콜은 Mode Switch를 동반하지만 같은 스레드로 바로 복귀할 수 있으므로 반드시 Context Switch인 것은 아니다. Blocking I/O로 스레드가 대기할 때 다른 스레드로 전환될 수 있다.

비동기 I/O는 I/O가 끝날 때까지 호출 스레드를 붙잡지 않고 여러 작업을 겹쳐 처리한다. CPU 계산을 자동으로 병렬화한다는 뜻은 아니다. 작은 `send`를 제한된 시간과 크기로 배치하면 System Call 횟수를 줄일 수 있지만 과한 배치는 메시지 지연을 늘린다.

## 4. 쉬운 예시

OS 종합면접에서는 같은 결과의 코드라도 연속 메모리 순회와 흩어진 객체 접근은 실제 시간이 다르다. 데이터 수명과 호출 횟수를 함께 본다.

50ms 주기의 게임 틱이 가끔 200ms 걸린다고 하자. 먼저 같은 시간대의 코어별 CPU와 실행 큐를 본다. CPU와 비자발적 Context Switch가 높다면 CPU 경쟁을 의심한다. CPU는 낮지만 Lock Wait이 길면 공유 상태 정체를 확인한다. Major Fault와 Swap I/O가 늘었다면 Working Set이 RAM에 맞지 않을 수 있다. 시스템 CPU와 네트워크 큐가 높다면 System Call·Packet 처리와 작은 I/O 폭증을 본다.

원인을 추정한 뒤 프로파일과 덤프로 검증한다. CPU Hot Path, Thread Wait Stack, Lock Owner, Fault 종류와 I/O 지연을 동일 시간축에 놓는다. 평균값만 보면 드문 긴 Pause를 놓치므로 p95·p99와 최대값, 발생 시점의 요청·Tick ID를 남긴다.

## 6. 장점과 단점

OS 종합면접에서는 보호와 추상화는 안정성을 높이지만 Fault, Miss, System Call과 할당 지연을 만든다. 측정된 병목만 최적화한다.

강한 프로세스 격리와 단순한 큰 락은 정확성과 장애 범위를 이해하기 쉽지만 통신·직렬화와 경쟁 비용이 커질 수 있다. 공유 메모리와 Lock-free 구조는 특정 Hot Path에서 처리량을 높일 수 있지만 검증과 메모리 수명 관리가 어렵다. 기본은 올바르고 관찰 가능한 구조이며, 프로파일로 확인된 구간만 세분화한다.

## 7. 게임 서버·백엔드 실무 예시

p99 틱 지연과 실행 큐, Context Switch, Fault, Lock 대기를 같은 시간축에서 본다. 평균 CPU뿐 아니라 할당률, RSS, Fault, 호출 수와 p99를 본다.

### 진단 순서

1. 영향 범위와 시작 시각, 배포·트래픽 변화를 확인한다.
2. CPU 사용률을 코어별로 보고 실행 큐와 Context Switch를 연결한다.
3. CPU 프로파일에서 계산 Hot Path를, Thread Dump에서 대기 원인을 본다.
4. Lock 대기·보유 시간과 Queue 길이로 공유 병목을 찾는다.
5. RSS, Heap, Native Buffer, Minor·Major Fault와 Swap을 분리한다.
6. System CPU, I/O 호출 수, 호출당 Byte와 Network Drop을 확인한다.
7. 변경 후 처리량뿐 아니라 p99 Tick, 오류율과 자원 사용을 비교한다.

연결마다 스레드를 만드는 대신 비동기 I/O와 제한된 작업 풀을 사용하고, CPU 작업과 Blocking I/O Pool을 분리한다. 룸 단위 상태 소유권으로 Lock 범위를 줄인다. Cache와 작업 Queue에는 상한을 두어 메모리 압박이 Major Fault와 OOM으로 번지기 전에 과부하를 거절한다.

## 8. 자주 하는 오해
- 가상 주소와 물리 사용량을 같다고 본다.
- Heap은 언제나 느리다고 단정한다.
- Page Fault는 모두 디스크 I/O라고 본다.
- TLB와 CPU Cache를 혼동한다.
- System Call과 Context Switch를 같다고 본다.
- Thread를 늘리면 CPU 처리량도 비례한다고 생각한다.
- Thread-safe Collection이면 복합 비즈니스 연산도 안전하다고 본다.
- Atomic이나 volatile이 모든 공유 상태를 보호한다고 생각한다.
- CPU 사용률이 낮으면 서버에 병목이 없다고 단정한다.
- Lock-free는 대기와 성능 문제가 없다고 생각한다.

## 9. 면접 질문

### Q1. 핵심 개념은 무엇인가요?
OS 핵심은 자원 소유, 실행, 스케줄링, 동기화, 주소 변환과 보호를 연결해 설명하는 것이다.

### Q2. 왜 필요한가요?
게임 서버 지연은 CPU, 락, 메모리와 I/O를 함께 봐야 한다.

### Q3. 실무 적용은 무엇인가요?
p99 틱 지연과 실행 큐, Context Switch, Fault, Lock 대기를 같은 시간축에서 본다.

### Q4. Process와 Thread를 비교해 주세요.

프로세스는 독립 주소 공간과 열린 파일 같은 자원의 격리 단위이고, 스레드는 프로세스 자원을 공유하는 CPU 실행 흐름이다. 프로세스는 장애 격리가 강하지만 IPC가 필요하고, 스레드는 데이터 교환이 빠르지만 경쟁 상태를 동기화해야 한다.

### Q5. Context Switch가 많으면 왜 느려질 수 있나요?

레지스터 저장·복원뿐 아니라 새 실행 흐름의 Cache·TLB 지역성이 약해져 Miss가 늘 수 있다. 다만 전환 수만으로 병목을 단정하지 않고 실행 큐, CPU 사용과 자발적·비자발적 전환을 함께 본다.

### Q6. 게임 서버의 간헐적 Tick 지연을 어떻게 진단하나요?

문제 시각을 기준으로 코어별 CPU와 실행 큐, Lock Wait, GC·할당, Minor·Major Fault, Swap과 I/O 지연을 맞춘다. CPU Profile과 Thread Dump로 실행과 대기를 구분하고 평균보다 p99와 긴 Pause 구간을 분석한다.

### Q7. Virtual Memory의 장점은 무엇인가요?

프로세스별 독립 주소 공간과 Page별 보호를 제공하고, 물리 메모리와 무관한 연속 주소 추상화, 요구 Paging, File Mapping과 Copy-on-Write를 가능하게 한다. Page Table·TLB와 Fault 처리 비용은 남는다.

## 11. 30초 모범답변

> 운영체제는 프로세스를 격리하고 스레드를 스케줄링하며 가상 메모리와 시스템 콜로 CPU, 메모리와 장치를 안전하게 공유하게 합니다. 동시 접근에는 Mutex·Atomic·소유권 같은 동기화가 필요하고, 실제 성능에는 문맥 교환, Cache·TLB Miss, Page Fault와 I/O 대기가 영향을 줍니다. 게임 서버 장애에서는 CPU, 실행 큐, Lock, Memory와 I/O 지표를 같은 시간축에서 확인합니다.

## 12. 1~2분 확장답변

> 운영체제는 프로세스라는 자원·주소 공간 단위로 프로그램을 격리하고 스레드를 CPU 실행 단위로 스케줄링합니다. 여러 스레드가 Heap과 전역 상태를 공유하므로 복합 불변식은 Mutex나 단일 소유자 구조로 보호하고, 단순 카운터는 필요한 경우 Atomic을 사용합니다. 가상 메모리는 Page Table로 가상 Page를 물리 Frame에 연결하고 TLB가 변환을, CPU Cache가 명령과 Data를 가속합니다. Mapping을 바로 처리할 수 없으면 Page Fault가 발생하며 Disk I/O가 없는 Minor와 필요한 Major를 구분해야 합니다. 파일과 Network는 System Call로 Kernel에 요청하고 비동기 I/O로 대기를 겹칠 수 있습니다. 게임 서버의 p99 Tick 지연은 CPU Hot Path, 실행 Queue와 Context Switch, Lock 대기, GC·Fault·Swap, System CPU와 Network Queue를 동일 시간축에서 분석합니다.

## 13. 핵심 요약
- OS 핵심은 자원 소유, 실행, 스케줄링, 동기화, 주소 변환과 보호를 연결해 설명하는 것이다.
- 보호와 추상화에는 비용이 있다.
- 데이터 수명과 지역성이 중요하다.
- 평균과 꼬리 지연을 함께 본다.
- Process는 자원 격리, Thread는 실행과 공유의 단위다.
- 동기화는 보호할 불변식과 소유권에서 출발한다.
- Virtual Memory, TLB와 CPU Cache는 서로 다른 주소·Data 계층이다.
- System Call의 Mode Switch와 실행 주체의 Context Switch를 구분한다.
- 장애는 CPU·대기·Memory·I/O 증거를 같은 시간축에서 좁힌다.

## 한 줄 정리

> 운영체제 면접의 핵심은 격리·실행·동기화·메모리·I/O를 하나의 요청 흐름과 장애 증거로 연결하는 것이다.
