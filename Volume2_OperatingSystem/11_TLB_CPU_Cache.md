# 11. TLB와 CPU Cache


## 학습 목표

- TLB와 CPU 캐시의 역할 차이와 각각 Miss 시 발생하는 일을 설명할 수 있다.
- 시간 지역성과 공간 지역성이 캐시 성능에 미치는 영향을 설명할 수 있다.
- False Sharing의 발생 원인과 해결 방법을 설명할 수 있다.
- 게임 서버에서 AoS와 SoA 중 접근 패턴에 맞는 데이터 배치를 선택할 수 있다.

## 1. 개요

TLB는 최근 주소 변환을, CPU Cache는 최근 명령과 데이터를 저장한다.

TLB(Translation Lookaside Buffer)는 가상 페이지 번호에서 물리 프레임 번호로의 변환 결과를 캐시한다. CPU 캐시는 메모리에서 읽은 명령과 실제 데이터의 복사본을 캐시 라인 단위로 보관한다. 둘 다 느린 하위 계층 접근을 줄이는 하드웨어 캐시지만 무엇을 저장하는지가 다르다.

TLB 미스는 주소 변환을 찾기 위한 페이지 테이블 탐색을 만들고, CPU 캐시 미스는 필요한 데이터나 명령을 하위 캐시 또는 DRAM에서 가져오게 한다. TLB 미스가 곧 페이지 폴트는 아니며 CPU 캐시 미스가 디스크 접근을 뜻하지도 않는다.

## 2. 왜 필요한가

Page Table 탐색과 DRAM 접근 지연을 줄인다.

CPU는 한 명령을 처리하는 동안 여러 메모리 접근이 필요할 수 있는데 DRAM은 CPU 연산보다 훨씬 느리다. 가상 주소를 사용할 때마다 다단계 페이지 테이블을 메모리에서 읽고, 이어서 실제 데이터까지 DRAM에서 읽는다면 지연이 누적된다. TLB가 변환을, L1·L2·L3 캐시가 명령과 데이터를 가까이 보관해 이 간격을 줄인다.

캐시는 용량이 작을수록 빠르고 코어 가까이에 둘 수 있다. 그래서 하나의 거대한 캐시보다 작고 빠른 L1, 더 크지만 느린 L2와 L3 같은 계층을 사용한다.

## 3. 핵심 동작 원리

```text
Virtual Address
      |
      v
     TLB ── miss ──> Page Table Walk
      |
Physical Address
      |
      v
 L1 Cache → L2 Cache → L3 Cache → DRAM
   빠름·작음                      느림·큼
```

TLB는 주소 변환이고 Cache는 데이터다. 지역성이 높을수록 효과적이며 False Sharing은 Cache Line 경쟁을 만든다.

### TLB Hit와 Miss

TLB에 가상 페이지 변환이 있으면 물리 주소를 빠르게 구성한다. 없으면 페이지 테이블을 탐색한다. 페이지 테이블에 유효한 매핑이 있다면 TLB를 채우고 접근을 계속하므로 페이지 폴트는 발생하지 않는다. 매핑이 없거나 권한 처리가 필요할 때 페이지 폴트가 발생한다.

큰 페이지는 한 TLB 항목이 더 넓은 메모리 범위를 표현하게 해 TLB 도달 범위를 늘린다. 대형 연속 데이터에서 미스를 줄일 수 있지만 내부 단편화와 메모리 관리 부담이 늘 수 있다.

### Cache Line과 계층

CPU 캐시는 보통 바이트 하나가 아니라 고정 크기 캐시 라인 단위로 데이터를 가져온다. 배열의 한 원소를 읽으면 인접 원소도 같은 라인에 들어올 수 있어 순차 접근이 유리하다. 캐시 라인의 정확한 크기와 정책은 하드웨어마다 다르지만 64바이트가 흔한 예다.

```text
Array: [0][1][2][3][4][5][6][7]...
        └──── 한 Cache Line ────┘

순차 접근: 이미 가져온 Line의 이웃 Data 사용
무작위 Pointer 추적: 다른 Line을 반복해서 가져올 가능성
```

### False Sharing

서로 다른 스레드가 논리적으로 독립된 변수에 쓰더라도 두 변수가 같은 캐시 라인에 있으면 라인 전체의 소유권이 코어 사이를 오갈 수 있다.

```text
한 Cache Line (64바이트)
┌───────────────────────────────────┐
│ Counter A (Core 0 수정) | Counter B (Core 1 수정) │
└───────────────────────────────────┘
          Line 소유권 Ping-Pong
```

### Cache Coherence

여러 코어가 각자 캐시를 가지면 한 코어가 쓴 값을 다른 코어의 오래된 캐시 복사본과 일관되게 만들어야 한다. 그러나 캐시 일관성이 프로그램의 복합 연산 원자성과 관찰 순서를 자동으로 보장하는 것은 아니다. 언어의 락과 원자 연산이 여전히 필요하다.

## 4. 쉬운 예시

```java
// AoS (Array of Structures): 한 Player의 모든 필드가 하나의 객체
public class PlayerAoS {
    public float x, y, z;  // 12바이트
    public int hp;          // 4바이트
    public long lastActive; // 8바이트
    // 총 ~24바이트 이상. 위치만 갱신해도 hp, lastActive가 같은 캐시 라인에 올라옴
}
PlayerAoS[] players = new PlayerAoS[100_000];

// 매 틱 위치만 갱신: players[i].x, y, z만 읽지만 객체 전체가 힙에 흩어짐
// → 각 Player 접근 시 새 캐시 라인 필요 가능성
```

```java
// SoA (Structure of Arrays): 필드별로 배열 분리
public class PlayerSoA {
    public final float[] x = new float[100_000]; // 위치 X: 연속 400KB
    public final float[] y = new float[100_000]; // 위치 Y: 연속 400KB
    public final float[] z = new float[100_000]; // 위치 Z: 연속 400KB
    public final int[] hp  = new int[100_000];   // 체력: 연속 400KB
}

// 매 틱 위치만 갱신: x[], y[], z[] 순회 → 높은 공간 지역성 → 캐시 효율 ↑
// 단, 한 플레이어의 여러 필드를 동시 접근이 많다면 AoS가 더 단순하고 유리할 수 있음
```

```java
// False Sharing: 독립 카운터가 같은 캐시 라인에 배치되는 경우
// BAD: 두 AtomicLong이 인접해 같은 64바이트 캐시 라인에 들어갈 수 있음
AtomicLong networkPackets = new AtomicLong(0); // Core 0에서 매 패킷 증가
AtomicLong gameEvents    = new AtomicLong(0); // Core 1에서 매 틱 증가
// → 서로 다른 변수지만 같은 라인 → 쓰기마다 라인 소유권 핑퐁

// GOOD 방법 1: ThreadLocal로 분리 후 합산
ThreadLocal<Long> packetCount = ThreadLocal.withInitial(() -> 0L);
// 각 스레드가 로컬에 누적, 모니터링 시 스레드별 합산 → 캐시 경쟁 없음
// 단: 정확한 용량 제한(정원 초과 차단)에는 적합하지 않음

// GOOD 방법 2: @Contended (JVM 내부 API, JVM 옵션 필요)
// @sun.misc.Contended  // 해당 필드를 별도 캐시 라인으로 패딩
```

## 5. 비슷한 개념과 비교

| 구분 | TLB | CPU Cache | Page Cache(OS) |
|---|---|---|---|
| 저장 대상 | 주소 변환 결과 | 명령·메모리 데이터 | 파일 내용 페이지 |
| 관리 중심 | CPU·MMU | CPU 하드웨어 | OS 커널 |
| Miss 결과 | Page Table Walk | 하위 Cache·DRAM 접근 | 저장장치 Read 가능 |
| 관련 최적화 | Huge Page·Working Set | 지역성·데이터 배치 | I/O 패턴·메모리 압력 |

| 데이터 배치 | AoS | SoA |
|---|---|---|
| 한 엔티티 전체 필드 접근 | 유리 | 비효율 (각 배열 접근) |
| 특정 필드만 일괄 처리 | 비효율 (불필요 필드 로드) | 유리 (연속 접근) |
| 코드 단순성 | 높음 | 낮음 (필드마다 배열) |
| 대표 사용처 | 객체 중심 일반 코드 | ECS·물리 시뮬레이션 |

## 6. 장점과 단점

**TLB와 CPU 캐시의 장점**

- 프로그램 수정 없이 평균 메모리 접근 시간을 크게 줄인다.
- 공간 지역성이 좋은 접근 패턴은 자동으로 이점을 받는다.

**TLB와 CPU 캐시의 단점**

- 용량이 제한되어 Working Set이 크면 Miss가 늘어난다.
- 멀티코어에서 캐시 일관성 트래픽과 False Sharing 비용이 발생한다.
- 데이터 배치 최적화가 자료구조 복잡도와 유지보수 비용을 늘릴 수 있다.

## 7. 게임 서버·백엔드 실무 예시

연속 배열 순회로 지역성을 높이고 스레드별 카운터의 False Sharing을 피한다. CPU가 100%인데 함수별 명령 수 대비 진행이 적다면 하드웨어 성능 카운터로 캐시 미스, TLB 미스, 메모리 대역폭과 코어별 사용률을 확인한다.

ECS(Entity Component System) 형태의 게임 데이터 배치는 같은 컴포넌트를 연속 처리해 지역성을 높일 수 있다. 하지만 엔티티 이동에 따른 배열 재배치와 복잡성이 있다. 데이터 지향 설계라는 이름만으로 도입하지 않고 실제 틱의 Hot Path와 접근 필드를 측정한다.

공유 통계 카운터를 모든 네트워크 스레드가 매 패킷 증가시키면 원자 연산 자체가 짧아도 캐시 라인이 코어 사이를 이동한다. 스레드별 카운터에 누적하고 모니터링 시 합치면 경쟁을 줄일 수 있다. 이 값이 정확한 용량 제한에 쓰인다면 지연된 집계가 허용되는지 별도로 판단한다.

## 8. 자주 하는 오해

- **"TLB Miss는 항상 Page Fault다"**: TLB Miss는 페이지 테이블에 유효한 매핑이 있으면 OS 개입 없이 해결된다. Page Fault는 유효한 매핑 자체가 없거나 권한 문제로 OS에 제어를 넘기는 것이다.
- **"CPU Cache Miss는 디스크 I/O를 만든다"**: L1 Miss → L2/L3 → DRAM 순서로 하위 캐시를 찾는다. 디스크 I/O는 Page Fault 중 Major Fault에서 발생한다.
- **"Cache Coherence가 Data Race까지 해결한다"**: 캐시 일관성은 같은 메모리 위치의 최신 값을 코어 간에 전파하지만 복합 연산의 원자성과 관찰 순서는 보장하지 않는다. 락과 원자 연산이 여전히 필요하다.
- **"False Sharing은 같은 변수를 공유할 때만 생긴다"**: 서로 다른 변수여도 같은 캐시 라인(64바이트)에 있으면 한 코어의 쓰기가 다른 코어의 캐시를 무효화한다. 인접한 카운터가 대표 사례다.
- **"연속 배열은 모든 접근 패턴에서 항상 빠르다"**: 필요한 필드 외 다른 큰 필드가 같은 캐시 라인에 올라오거나(AoS), 무작위 인덱스로 접근한다면 효과가 줄어든다. 접근 패턴을 먼저 측정한다.
- **"Huge Page(큰 페이지)는 항상 좋다"**: TLB 도달 범위는 늘지만 내부 단편화와 할당·회수 유연성이 낮아질 수 있다. 대형 연속 Working Set에서만 이점이 있다.
- **"AoS보다 SoA가 항상 빠르다"**: 한 엔티티의 여러 필드를 동시에 접근하는 패턴이라면 AoS가 더 단순하고 효율적일 수 있다. 어느 것이 유리한지는 실제 접근 패턴을 측정해야 알 수 있다.

## 9. 면접 질문

### Q1. TLB와 CPU 캐시의 차이는 무엇인가요?

TLB는 가상 주소 → 물리 주소 변환 결과를 캐시한다. CPU 캐시는 DRAM에서 읽은 명령과 데이터를 캐시 라인 단위로 보관한다. 둘 다 하드웨어 캐시이지만 무엇을 저장하는지가 다르다. TLB Miss는 페이지 테이블 탐색을, CPU 캐시 Miss는 하위 캐시·DRAM 접근을 만든다.

### Q2. 캐시 계층(L1/L2/L3)을 사용하는 이유는 무엇인가요?

용량이 작을수록 빠르고 코어에 가까이 둘 수 있다. 하나의 거대한 캐시보다 작고 빠른 L1, 더 크지만 느린 L2와 L3 계층으로 평균 접근 시간을 줄인다. 자주 사용하는 데이터는 L1에 머물고, Working Set이 크면 L2·L3·DRAM 순서로 접근한다.

### Q3. Cache Coherence와 Data Race는 어떻게 다른가요?

Cache Coherence는 하드웨어가 같은 메모리 위치의 최신 값을 모든 코어의 캐시에 일관되게 전파하는 메커니즘이다. Data Race는 동기화 없이 여러 스레드가 같은 메모리를 접근하고 그중 하나가 쓰기인 경우다. Cache Coherence가 최신 값을 전파해도 복합 연산의 원자성과 관찰 순서를 보장하지 않으므로 Data Race와 동시성 버그는 여전히 발생한다.

### Q4. TLB Miss와 Page Fault의 차이는 무엇인가요?

TLB Miss는 변환 캐시에 항목이 없어 페이지 테이블을 탐색하는 사건이다. 페이지 테이블에 유효한 매핑이 있으면 OS 없이 끝난다. Page Fault는 현재 매핑이나 권한으로 메모리 접근을 완료할 수 없어 커널 처리가 필요한 사건이다.

### Q5. False Sharing은 무엇인가요?

여러 코어가 서로 다른 변수에 쓰지만 그 변수들이 같은 캐시 라인에 있어 라인 소유권이 계속 이동하는 현상이다. 데이터상 공유가 없어도 캐시 단위가 더 크기 때문에 성능 저하가 생긴다. 스레드별 로컬 누적 후 합산하거나 패딩으로 캐시 라인을 분리해 완화한다.

### Q6. 시간 지역성과 공간 지역성의 차이는 무엇인가요?

시간 지역성은 최근 사용한 데이터를 곧 다시 사용하는 성질이고, 공간 지역성은 접근한 주소 주변 데이터를 곧 사용하는 성질이다. 반복 룩업 테이블 접근과 연속 배열 순회가 각각 대표 예다. CPU 캐시는 두 지역성이 모두 높을 때 최고의 효과를 낸다.

> TLB는 가상→물리 주소 변환을, CPU 캐시는 명령·데이터를 코어 가까이 캐시합니다. TLB Miss는 페이지 테이블 탐색, 캐시 Miss는 하위 캐시·DRAM 접근이 발생합니다. 게임 서버에서는 연속 배열 순회로 공간 지역성을 높이고, 스레드별 독립 카운터가 같은 캐시 라인에 배치되는 False Sharing을 피합니다.

## 12. 1~2분 확장답변

> TLB는 주소 변환을, CPU 캐시는 명령·데이터를 빠르게 하며 배치와 접근 패턴이 실제 성능을 좌우합니다. 순차 배열은 공간 지역성 덕분에 캐시 라인 하나로 여러 원소를 처리하지만, 각 엔티티를 따로 힙에 할당하면 포인터 추적마다 다른 라인을 가져옵니다. False Sharing은 서로 다른 변수가 같은 라인에 있을 때 쓰기마다 라인 소유권이 이동해 성능을 저하시킵니다. Cache Coherence는 최신 값을 전파하지만 복합 연산 원자성은 보장하지 않으므로 락이 여전히 필요합니다. 데이터 배치 최적화는 하드웨어 성능 카운터로 Miss를 확인한 뒤 적용합니다.

## 13. 핵심 요약

- TLB는 최근 주소 변환을 캐시하고 CPU 캐시는 명령과 데이터를 캐시한다. 무엇을 저장하는지가 다르다.
- TLB Miss는 페이지 테이블에 유효한 매핑이 있으면 OS 없이 해결된다. CPU 캐시 Miss는 하위 캐시나 DRAM에서 가져온다.
- CPU 캐시는 캐시 라인 단위로 데이터를 가져온다. 순차 접근은 같은 라인의 인접 데이터를 재사용해 효율이 높다.
- 시간 지역성은 최근 사용한 데이터를 곧 다시 사용하는 성질, 공간 지역성은 접근한 주소 근처를 곧 사용하는 성질이다.
- Cache Coherence는 최신 값을 코어 간에 전파하지만 복합 연산 원자성과 관찰 순서는 보장하지 않는다. 락과 원자 연산이 여전히 필요하다.
- False Sharing: 서로 다른 변수여도 같은 캐시 라인에 있으면 쓰기 시 라인 소유권이 코어 사이를 이동한다. 스레드 로컬 누적 또는 패딩으로 완화한다.
- AoS와 SoA 중 어느 것이 유리한지는 접근 패턴에 달려 있다. Hot Path와 접근 필드를 측정한 뒤 선택한다.
- 하드웨어 성능 카운터(캐시 미스, TLB 미스, 메모리 대역폭)로 병목을 확인한 뒤 데이터 배치를 최적화한다.

## 한 줄 정리

> TLB는 주소 변환을, CPU Cache는 데이터 접근을 빠르게 하며 배치와 접근 패턴이 실제 성능을 좌우합니다.
