# 04. 동시성과 병렬성


## 학습 목표

- 동시성과 병렬성의 차이를 코어·타임슬라이싱 관점에서 설명할 수 있다.
- 비동기·멀티스레딩·병렬성의 관계를 구분하고 각각 적합한 상황을 설명할 수 있다.
- Amdahl의 법칙이 병렬 확장의 상한을 만드는 원리를 설명할 수 있다.
- 게임 서버에서 I/O 동시성과 CPU 병렬성을 구분해 설계할 수 있다.

## 1. 개요

동시성(Concurrency)은 여러 작업이 겹친 시간에 진행되는 구조이고, 병렬성(Parallelism)은 여러 작업이 실제로 동시에 실행되는 상태이다.

동시성은 작업을 분리하고 진행 상태를 관리하는 소프트웨어 구조에 가깝다. 단일 코어가 A와 B를 짧게 번갈아 실행해도 두 작업은 같은 시간 구간에 진행된다. 병렬성은 하드웨어 실행 관점이다. 둘 이상의 코어가 A와 B를 같은 순간에 실행해야 한다. 병렬 프로그램은 여러 작업을 동시에 다루므로 동시성 문제도 함께 가지지만, 동시 프로그램이 반드시 병렬로 실행되는 것은 아니다.

## 2. 왜 필요한가

I/O 대기 중 다른 일을 진행해 자원을 활용하고, 다중 코어로 계산 처리량을 높이기 위해 필요하다.

## 3. 핵심 동작 원리

```text
단일 코어 동시성: 작업 A와 B를 번갈아 실행 / 다중 코어 병렬성: 코어마다 A와 B를 동시에 실행
```

비동기는 완료를 기다리는 동안 호출 흐름을 막지 않는 프로그래밍 방식이고 동시성과 관련되지만 동일하지 않다. 멀티스레딩도 단일 코어에서는 병렬이 아닐 수 있다.

### 세 개념의 실행 모습

```text
동시성, 단일 코어
시간 ─────────────────────────>
Core 0: [ A ][ B ][ A ][ B ][ A ]

병렬성, 다중 코어
시간 ─────────────────────────>
Core 0: [       A       ][  A  ]
Core 1: [       B       ][  B  ]

비동기 I/O
Task A: [요청] ............ [완료 처리]
Thread: [Task B][Task C]... [Task A 계속]
```

비동기 예시의 점 구간에서는 외부 장치나 DB가 작업을 수행하고 호출 스레드는 다른 일을 할 수 있다. 비동기 API를 호출했다고 CPU 계산이 자동으로 다른 코어에서 병렬 실행되는 것은 아니다. 반대로 스레드 풀에 CPU 계산을 맡기면 호출자는 비동기적으로 기다릴 수 있고 작업은 다른 코어에서 병렬 실행될 수도 있다.

### 작업 분해와 합류

병렬화하려면 큰 작업을 서로 독립적인 작은 작업으로 나누고 결과를 합쳐야 한다. 분할 자체, 작업 큐 등록, 동기화, 결과 병합에도 비용이 든다. 매우 작은 계산을 수천 개 작업으로 나누면 실제 계산보다 스케줄링 비용이 커질 수 있다.

```text
입력 World Snapshot
   ├─ Region A 계산 ─┐
   ├─ Region B 계산 ─┼─ Barrier ─> 결과 반영
   └─ Region C 계산 ─┘
```

Barrier는 모든 병렬 작업이 끝날 때까지 다음 단계가 기다리는 지점이다. 가장 느린 작업이 전체 완료 시간을 결정할 수 있으므로 작업량을 균등하게 나누는 것이 중요하다. 한 지역에 플레이어가 몰리면 정적 분할의 부하가 불균형해질 수 있다.

### 병렬화 한계

전체 작업 중 순차적으로 실행해야 하는 부분은 코어를 늘려도 줄지 않는다. 예를 들어 한 틱의 40%가 반드시 단일 스레드에서 상태를 반영해야 한다면 나머지 60%를 빠르게 만들어도 전체 속도 향상에는 한계가 있다. 이를 정량화하는 Amdahl의 법칙을 면접에서 증명할 필요는 없지만, 순차 구간과 동기화가 병렬 확장의 상한을 만든다는 원리는 설명할 수 있어야 한다.

공유 데이터에 락을 많이 걸면 코어들은 계산보다 락을 기다린다. 같은 캐시 라인의 서로 다른 값을 여러 코어가 자주 쓰는 False Sharing도 캐시 일관성 트래픽을 만들 수 있다. 병렬화를 위해서는 단순히 스레드를 추가하기보다 데이터 소유권과 작업 경계를 함께 바꿔야 한다.

## 4. 쉬운 예시

식당 비유: 한 직원이 주문 후 조리 대기 중 다음 주문을 받는 것은 동시성이다. 여러 요리사가 서로 다른 음식을 같은 순간 만드는 것은 병렬성이다.

```java
// 동시성: 비동기 I/O로 여러 DB 조회를 겹쳐 처리
// 순차 시: 총 지연 = 200ms + 150ms = 350ms
// 동시 시: 총 지연 = max(200ms, 150ms) = 200ms
ExecutorService ioPool = Executors.newCachedThreadPool();

CompletableFuture<PlayerData> playerFuture =
    CompletableFuture.supplyAsync(() -> db.getPlayer(playerId), ioPool);
CompletableFuture<RankData> rankFuture =
    CompletableFuture.supplyAsync(() -> db.getRank(playerId), ioPool);

CompletableFuture.allOf(playerFuture, rankFuture).join();
// 두 I/O를 동시에 시작 → 대기 시간 겹침. CPU 병렬화 아님 (I/O는 장치가 처리)
```

```java
// 병렬성: 여러 룸의 AI 경로탐색을 실제로 여러 코어에서 동시 계산
ExecutorService pathfindPool = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors()); // 코어 수 = 실제 병렬 실행 수

List<Future<List<Path>>> futures = rooms.stream()
    .map(room -> pathfindPool.submit(() -> room.computeAIPaths()))
    .toList();

// Barrier: 모든 룸 완료 대기
List<Path> allPaths = new ArrayList<>();
for (Future<List<Path>> f : futures) {
    allPaths.addAll(f.get()); // 가장 느린 룸이 전체 완료 시간 결정
}
// 주의: 완료 순서가 달라질 수 있으므로 결과 순서 의존 로직 금지
```

```text
Amdahl의 법칙 예시:
- 틱 작업 중 60%만 병렬화 가능, 40%는 순차(상태 반영, 브로드캐스트)
- 코어 4개: 속도 향상 = 1 / (0.4 + 0.6/4) ≈ 2.05배
- 코어 무한대: 속도 향상 = 1 / 0.4 = 2.5배 (상한)
→ 순차 구간 40%가 최대 2.5배 이상의 확장을 막음
```

## 5. 비슷한 개념과 비교

| 구분 | 목적 | 코어 추가 필요 | 대표 위험 |
|---|---|---|---|
| 동시성 | 여러 작업의 진행과 응답성 | 필수 아님 | 순서·경쟁 상태 |
| 병렬성 | 계산 시간 단축·처리량 증가 | 일반적으로 필요 | 분할·동기화 비용 |
| 비동기 | 기다리는 스레드 낭비 감소 | 필수 아님 | 취소·오류·흐름 복잡성 |
| 멀티스레딩 | 여러 실행 흐름 사용 | 필수 아님 | 공유 메모리 동기화 |

| 게임 서버 작업 | 권장 방식 | 이유 |
|---|---|---|
| 소켓 I/O, DB 조회 | 비동기·동시성 | 대기 시간을 겹쳐 처리 |
| AI 경로탐색, 물리 계산 | 병렬성 (멀티코어) | CPU 계산 분산 |
| 게임 룸 상태 관리 | Room Owner 단일 스레드 | 순서 보장·동기화 단순화 |
| 전체 월드 틱 집계 | Barrier 병렬화 후 순차 반영 | 결정성 유지 |

## 6. 장점과 단점

**동시성의 장점**

- I/O 대기 중 다른 요청을 처리해 응답성과 자원 활용률을 높인다.
- 단일 코어에서도 여러 작업을 겹쳐 진행할 수 있다.

**동시성의 단점**

- 실행 순서가 다양해지고 취소·오류 전달, 공유 상태 정합성이 복잡해진다.

**병렬성의 장점**

- CPU 계산 처리량을 실제로 높일 수 있다.
- 독립적인 작업은 코어 수에 비례해 빨라진다.

**병렬성의 단점**

- 순차 실행 구간, 동기화 비용, False Sharing이 확장의 상한을 만든다.
- 결과 결정성(재현 가능성)이 깨질 수 있다.
- 분할·합류 비용이 작은 작업에서는 역효과가 날 수 있다.

## 7. 게임 서버·백엔드 실무 예시

게임 서버는 소켓 I/O는 비동기로 겹쳐 처리하고, 독립적인 룸이나 경로 탐색은 여러 코어에 병렬 배치할 수 있다. 공유 월드 상태를 병렬화하면 락과 결정성 비용을 함께 고려한다.

룸 단위로 한 스레드만 상태를 변경하게 하면 룸 내부의 실행 순서를 단순하게 유지하면서 여러 룸을 코어에 나눠 병렬 실행할 수 있다. 플레이어가 룸을 이동할 때는 두 소유자 사이의 메시지 순서와 인계 시점을 정의한다.

재현 가능한 전투 결과가 중요하면 병렬 작업 완료 순서가 결과에 영향을 주지 않게 해야 한다. 부동소수점 누적 순서, 동일 우선순위 이벤트의 처리 순서, 난수 스트림을 고정한다. 성능 향상을 얻었더라도 결과가 실행마다 달라지면 리플레이와 버그 분석이 어려워진다.

## 8. 자주 하는 오해

- **"비동기 = 병렬 = 멀티스레딩"**: 셋은 서로 다른 개념이다. 비동기는 대기 중 흐름을 막지 않는 실행 모델, 병렬성은 물리적 동시 실행, 멀티스레딩은 여러 실행 흐름 구성 방법이다.
- **"코어를 늘리면 성능이 비례해 증가한다"**: Amdahl의 법칙에 따라 순차 실행 구간이 확장 상한을 만든다. 순차 40%가 남으면 코어를 무한정 늘려도 2.5배 이상 빨라지지 않는다.
- **"단일 스레드는 동시성이 없다"**: 이벤트 루프(Netty, Node.js)는 단일 스레드로 수천 개의 I/O 작업을 동시에 진행한다. 동시성은 스레드 수가 아니라 작업 구조의 개념이다.
- **"비동기 I/O를 사용하면 CPU 계산도 병렬화된다"**: 비동기 I/O는 대기 시간을 겹칠 뿐이다. CPU 연산을 여러 코어에서 병렬로 실행하려면 별도의 CPU 바운드 스레드 풀이 필요하다.
- **"False Sharing은 같은 변수를 공유할 때만 발생한다"**: 서로 다른 변수여도 같은 캐시 라인(일반적으로 64바이트)에 있으면 한 코어의 쓰기가 다른 코어의 캐시를 무효화한다. 인접한 카운터 변수가 대표 사례다.
- **"병렬 실행의 결과는 항상 결정적이다"**: 병렬 작업의 완료 순서는 스케줄링에 따라 달라질 수 있다. 누적 연산 순서가 바뀌거나 동일 우선순위 이벤트 처리 순서가 달라지면 결과가 달라진다.
- **"병렬화하면 항상 성능이 좋아진다"**: 작업 분할·큐 등록·결과 병합 비용이 실제 계산보다 크면 단일 스레드보다 느릴 수 있다. 충분히 큰 작업 단위에서만 병렬화 효과가 있다.

## 9. 면접 질문

### Q1. 동시성과 병렬성의 차이는 무엇인가요?

동시성은 여러 작업이 겹친 시간 구간에 진행되는 소프트웨어 구조이고, 단일 코어에서도 가능하다. 병렬성은 여러 작업이 여러 코어에서 실제로 같은 순간에 실행되는 상태다. 병렬 프로그램은 동시성 문제도 함께 가지지만, 동시성이 반드시 병렬성을 의미하지는 않는다.

### Q2. 비동기는 동시성인가요, 병렬성인가요?

비동기는 완료를 기다리는 동안 호출 흐름을 막지 않는 실행 방식이다. 동시성과 관련되지만 같은 개념은 아니다. 단일 스레드 이벤트 루프도 비동기로 동시성을 구현한다. 비동기 I/O 자체는 CPU 계산을 병렬화하지 않는다.

### Q3. Amdahl의 법칙이란 무엇인가요?

전체 작업 중 순차 실행 구간은 코어를 늘려도 줄지 않아 병렬 확장의 상한을 만든다는 원리다. 순차 구간이 40%라면 코어를 무한정 늘려도 2.5배 이상 빨라지지 않는다. 병렬화 전에 순차 구간과 동기화 비용부터 줄이는 것이 더 효과적이다.

### Q4. False Sharing이란 무엇인가요?

서로 다른 변수여도 같은 CPU 캐시 라인(64바이트)에 있으면, 한 코어의 쓰기가 다른 코어의 캐시를 무효화해 캐시 일관성 트래픽이 생기는 현상이다. 서로 관련 없는 카운터를 같은 구조체에 인접 배치하면 발생한다. 패딩이나 `@Contended` 어노테이션으로 완화한다.

### Q5. 비동기와 병렬성은 어떻게 다른가요?

비동기는 작업 완료를 기다리는 동안 호출 흐름을 막지 않는 방식이고 단일 스레드에서도 가능하다. 병렬성은 여러 작업이 여러 실행 자원에서 같은 순간 실제로 수행되는 것이다. 비동기 I/O가 CPU 계산을 자동으로 병렬화하지는 않는다.

### Q6. 게임 월드 병렬화 시 결정성을 어떻게 유지하나요?

병렬 작업의 완료 순서가 결과에 영향을 주지 않도록 작업을 설계한다. 동일 우선순위 이벤트의 처리 순서를 ID 등으로 고정하고, 부동소수점 누적 순서를 보장하며, 스레드별 난수 스트림을 분리한다. Barrier 후 순차적으로 상태를 반영하면 읽기 단계는 병렬화하면서 쓰기 단계의 결정성을 유지할 수 있다.

- 동시성 버그를 재현하기 어려운 이유는 무엇인가요?

## 11. 30초 모범답변

> 동시성은 여러 작업이 겹친 시간에 진행되는 구조로 단일 코어에서도 가능하고, 병렬성은 여러 코어에서 실제로 동시에 실행되는 상태입니다. 비동기 I/O는 대기 시간을 겹쳐 응답성을 높이지만 CPU 계산은 별도 코어가 필요합니다. 게임 서버에서는 소켓 I/O는 비동기로, AI 경로탐색 같은 CPU 계산은 병렬로 분리해 설계합니다.

## 12. 1~2분 확장답변

> 동시성은 여러 작업을 독립적으로 진행할 수 있게 구성하는 것이고 병렬성은 여러 코어에서 실제로 동시에 실행하는 것입니다. 비동기 I/O는 대기 시간을 활용하며 CPU 작업 병렬화와 목적이 다릅니다. 병렬화할 때는 Amdahl의 법칙에 따라 순차 구간이 확장 상한을 만든다는 점을 이해해야 합니다. 게임 서버에서 룸 단위 단일 스레드 소유권 패턴은 동시성 복잡도를 줄이면서 룸 간 병렬성을 얻습니다. 병렬 작업의 완료 순서가 결과에 영향을 주면 결정성이 깨져 리플레이 버그를 분석하기 어려워지므로, 쓰기 단계는 Barrier 후 순차로 반영합니다.

## 13. 핵심 요약

- 동시성은 여러 작업이 겹친 시간에 진행되는 구조다. 단일 코어에서도 가능하다.
- 병렬성은 여러 작업이 여러 코어에서 실제로 같은 순간에 실행되는 상태다.
- 비동기는 대기 중 흐름을 막지 않는 실행 방식이다. I/O 대기는 겹치지만 CPU는 병렬화 안 된다.
- Amdahl의 법칙: 순차 구간이 병렬 확장의 상한을 만든다. 순차 40% → 최대 2.5배.
- False Sharing: 다른 변수도 같은 캐시 라인이면 한 코어의 쓰기가 다른 코어 캐시를 무효화한다.
- 병렬 작업의 완료 순서가 달라지면 결과 결정성이 깨진다. Barrier + 순차 반영으로 보완한다.
- 게임 서버: I/O → 비동기/동시성, AI 계산 → 병렬성, 룸 상태 → Room Owner 단일 스레드.
- 작업 분할·병합 비용이 계산보다 크면 병렬화가 역효과를 낸다. 충분한 작업 크기에서만 적용한다.

## 한 줄 정리

> 동시성은 여러 작업을 겹쳐 진행하는 구조, 병렬성은 여러 코어에서 실제로 동시에 실행하는 것이다. 비동기 I/O는 동시성이지 병렬성이 아니다.
