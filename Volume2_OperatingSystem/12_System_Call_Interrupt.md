# 12. System Call과 Interrupt

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 정의와 필요성을 설명할 수 있다.
- 핵심 동작과 비교 개념을 설명할 수 있다.
- 게임 서버 성능 진단에 적용할 수 있다.

## 1. 개요

System Call은 사용자 코드가 커널 서비스를 요청하는 진입이고 Interrupt는 장치·예외 사건을 커널에 알린다.

시스템 콜(System Call)은 사용자 프로그램이 파일, 소켓, 프로세스, 메모리처럼 권한이 필요한 운영체제 서비스를 요청하는 공식 인터페이스다. 인터럽트(Interrupt)는 CPU의 정상 명령 흐름을 잠시 중단하고 정해진 처리 루틴으로 제어를 넘기는 사건이다. 장치가 발생시키는 하드웨어 인터럽트뿐 아니라 현재 명령에서 발생하는 예외와 의도적인 커널 진입도 넓은 예외 처리 체계와 관련된다.

둘은 모두 커널 코드 실행으로 이어질 수 있지만 시작 주체와 목적이 다르다. 시스템 콜은 현재 사용자 코드가 의도적으로 요청한다. 네트워크 카드 완료 같은 하드웨어 인터럽트는 현재 실행 중인 명령과 비동기적으로 발생한다.

## 2. 왜 필요한가

권한을 보호하면서 파일, 네트워크와 장치를 사용하게 한다. 추상화의 편리함에도 실제 전환과 메모리 비용은 남는다.

사용자 프로그램이 장치 레지스터와 페이지 테이블을 직접 바꾸거나 다른 프로세스의 파일 자원을 조작할 수 있다면 격리와 안정성을 유지하기 어렵다. CPU는 사용자 모드와 커널 모드 같은 권한 수준을 제공하고, 제한된 진입점에서 인자를 검증한 뒤 커널이 작업을 대신 수행한다.

장치는 CPU보다 느리고 완료 시점을 예측하기 어렵다. CPU가 디스크나 네트워크 완료를 계속 반복 확인하면 계산 시간을 낭비한다. 장치가 완료나 입력 도착을 인터럽트로 알리면 CPU는 그동안 다른 작업을 할 수 있다. 다만 매우 높은 이벤트율에서는 인터럽트 자체가 과부하가 될 수 있어 폴링과 배치 처리를 섞기도 한다.

## 3. 핵심 동작 원리

```text
User Code
   │ system call instruction
   v
CPU가 Kernel 진입점으로 전환
   │ 인자·권한 검증
   │ Kernel 작업 수행 또는 I/O 등록
   v
결과 반환 / Thread 대기

Device ── interrupt ──> Interrupt Handler ──> 완료 Queue·대기 Thread 깨움
```
일반 함수 호출과 달리 권한 경계를 넘는다. Interrupt가 항상 Context Switch를 뜻하지는 않는다. 보호, 변환, Cache 계층 중 어디서 대기하는지 구분한다.

### System Call 흐름

애플리케이션은 보통 C 라이브러리나 런타임 API를 호출한다. 모든 라이브러리 함수가 시스템 콜인 것은 아니다. 문자열 길이 계산은 사용자 모드에서 끝날 수 있고, `read`, `write`, `send`, 메모리 매핑 같은 작업은 필요할 때 커널 인터페이스로 진입한다.

1. 래퍼가 시스템 콜 번호와 인자를 정해진 레지스터나 메모리에 놓는다.
2. 전용 명령을 실행하면 CPU가 사용자 상태를 보존하고 검증된 커널 진입점으로 이동한다.
3. 커널은 포인터, 길이, 파일 디스크립터와 권한을 검사한다.
4. 즉시 처리하거나 I/O를 등록한다. 완료를 기다려야 하는 동기 호출이면 현재 스레드를 대기 상태로 둘 수 있다.
5. 결과나 오류 코드를 설정하고 사용자 모드로 돌아간다.

구체적인 호출 규약과 명령은 운영체제와 CPU 아키텍처에 따라 다르다. 면접에서는 권한 전환, 검증, 커널 작업, 반환이라는 흐름을 설명하면 충분하다.

### Mode Switch와 Context Switch

시스템 콜은 사용자 모드에서 커널 모드로 권한을 전환하지만 같은 스레드의 요청을 처리하고 바로 복귀할 수 있다. 이 경우 실행 주체가 바뀌는 문맥 교환과는 구분한다. 반대로 시스템 콜이 I/O를 기다려 현재 스레드를 재우면 스케줄러가 다른 스레드를 선택해 문맥 교환이 뒤따를 수 있다.

```text
send() 즉시 Buffer에 기록 가능
User → Kernel → 같은 Thread로 Return
          Mode Switch, 반드시 Context Switch는 아님

read() Data 없음, Blocking Mode
User → Kernel → Thread Waiting → 다른 Thread 실행
          Mode Switch + Context Switch 가능
```

### Interrupt와 Exception

하드웨어 인터럽트는 네트워크 패킷 수신, 타이머, 장치 I/O 완료처럼 현재 명령과 비동기적으로 도착할 수 있다. 예외(Exception)는 0으로 나누기, 페이지 폴트, 잘못된 명령처럼 현재 명령 실행과 동기적으로 발생한다. 시스템 콜도 소프트웨어가 의도적으로 커널로 진입시키는 동기 사건이다. 용어 분류는 아키텍처와 문헌에 따라 조금 다를 수 있으므로 “모든 인터럽트가 하드웨어” 또는 “모든 Trap이 오류”라고 단정하지 않는다.

CPU는 사건 종류에 맞는 처리기 주소를 찾아 커널 코드로 이동한다. 처리기는 필요한 최소 상태를 저장하고 원인을 확인한다. Page Fault라면 매핑을 보완할 수 있고, Timer Interrupt라면 스케줄링 시점을 만들 수 있다. 처리 후 원래 실행을 이어가거나 스케줄러가 다른 작업을 실행할 수 있다.

### Interrupt 처리 분리

인터럽트 처리 중에는 다른 중요한 사건이 지연될 수 있으므로 가능한 한 짧게 처리한다. 장치 상태 확인과 최소한의 데이터 수거만 빠른 경로에서 하고, 시간이 걸리는 프로토콜 처리와 콜백은 지연 처리 메커니즘이나 일반 스레드 문맥으로 넘긴다. Linux의 구체적인 용어와 구조는 구현 세부이므로 면접 기본 답변에서는 “긴 작업을 뒤로 미룬다”는 원리를 설명하면 된다.

### 네트워크 I/O 예시

네트워크 카드가 패킷을 DMA(Direct Memory Access)로 메모리 버퍼에 옮기면 CPU가 바이트마다 직접 복사하지 않아도 된다. 장치는 인터럽트로 수신을 알리고 커널 네트워크 스택이 패킷을 처리해 소켓 수신 큐에 놓는다. 대기 중인 스레드나 이벤트 루프가 준비 상태를 통지받는다.

패킷이 매우 많을 때 패킷마다 인터럽트를 발생시키면 CPU가 인터럽트 처리에 묶일 수 있다. 장치는 여러 완료를 묶어 알리는 Interrupt Coalescing을 사용하거나 커널이 일정량을 Polling으로 처리할 수 있다. 묶으면 처리량은 좋아질 수 있지만 알림 지연이 조금 늘어나는 트레이드오프가 있다.

### 비동기 I/O와 System Call

비동기 API도 커널 작업 등록과 완료 수집을 위해 시스템 콜을 전혀 사용하지 않는다는 뜻은 아니다. 호출 스레드가 각 I/O 완료까지 블로킹되지 않고 여러 요청을 등록한 뒤 완료 이벤트를 묶어 처리한다는 의미다. `epoll`, `kqueue`, IOCP, `io_uring` 등은 인터페이스와 완료 모델이 다르지만 많은 연결을 제한된 스레드로 처리하도록 돕는다.

준비 통지 모델에서는 “읽을 수 있다”는 알림 뒤 실제로 `read`나 `recv`를 호출해 데이터를 가져온다. 완료 통지 모델에서는 제출한 작업의 완료 결과를 받는다. 사용 중인 플랫폼의 레벨·에지 트리거, 취소와 오류 의미를 확인해야 한다.

### 비용은 어디서 생기는가

시스템 콜 비용에는 권한 전환 자체뿐 아니라 인자 검증, 사용자·커널 메모리 사이 복사, 락, 장치 큐와 스케줄링 대기가 포함될 수 있다. 호출 종류에 따라 비용 차이가 크다. 현재 시간처럼 일부 조회는 공유된 사용자 매핑을 이용해 실제 커널 진입을 피할 수도 있다.

따라서 “시스템 콜은 느리다”에서 끝내지 않고 호출 빈도와 전달 바이트, 블로킹 시간, 복사량을 측정한다. 여러 작은 메시지를 한 번에 보내는 `writev` 계열 Scatter/Gather I/O나 애플리케이션 버퍼링은 호출 횟수를 줄일 수 있다. 지나친 배치는 각 메시지의 지연을 늘릴 수 있으므로 시간과 크기 상한을 둔다.

## 4. 쉬운 예시

System Call과 Interrupt에서는 같은 결과의 코드라도 연속 메모리 순회와 흩어진 객체 접근은 실제 시간이 다르다. 데이터 수명과 호출 횟수를 함께 본다.

채팅 메시지 100개를 각각 즉시 작은 `send`로 호출하면 사용자·커널 경계를 100번 넘고 작은 패킷과 잠금 비용이 늘 수 있다. 짧은 시간 동안 같은 연결의 메시지를 버퍼에 모아 한 번에 보내면 호출 수를 줄일 수 있다. 그러나 1초씩 기다려 모으면 채팅 지연이 나빠진다. 예를 들어 최대 1ms 또는 일정 바이트가 모일 때 전송하는 식으로 처리량과 지연을 조절한다.

키보드나 네트워크 카드가 새 데이터를 만들 때마다 애플리케이션이 장치를 직접 계속 확인하는 대신 운영체제가 인터럽트와 이벤트 통지로 준비된 작업을 알려 준다. 실제 고성능 네트워킹은 인터럽트와 폴링을 상황에 맞게 혼합할 수 있다.

## 5. 비슷한 개념과 비교

| 관점 | 역할 | 비용 |
|---|---|---|
| OS 추상화 | 보호·자원 관리 | 전환 |
| 메모리 | 주소·수명 관리 | Fault·할당 |
| 하드웨어 | 접근 가속 | Cache Miss |

| 구분 | 발생 주체 | 현재 명령과 관계 | 대표 예 |
|---|---|---|---|

## 6. 장점과 단점

System Call과 Interrupt에서는 보호와 추상화는 안정성을 높이지만 Fault, Miss, System Call과 할당 지연을 만든다. 측정된 병목만 최적화한다.

시스템 콜은 안정적인 권한 경계와 장치 추상화를 제공하지만 호출과 검증·복사·대기 비용이 있다. 인터럽트는 CPU가 장치 완료를 계속 확인하지 않게 하지만 이벤트율이 높으면 처리 오버헤드와 캐시 교란이 커진다. 배치와 폴링은 처리량을 높일 수 있지만 지연과 CPU 사용을 바꾼다.

## 7. 게임 서버·백엔드 실무 예시

작은 send를 반복하기보다 버퍼링·배치하고 비동기 I/O로 대기를 겹친다. 평균 CPU뿐 아니라 할당률, RSS, Fault, 호출 수와 p99를 본다.

성능 분석에서는 초당 `send`·`recv` 호출 수, 호출당 바이트, 짧은 쓰기와 `EAGAIN` 성격의 재시도, 소켓 버퍼 정체를 본다. 시스템 CPU 사용률이 높다면 네트워크 스택, 시스템 콜, 락과 인터럽트 처리 비중을 사용자 코드 CPU와 구분한다.

이벤트 루프가 읽기 준비 알림을 받았지만 한 연결만 끝까지 처리하면 다른 연결이 굶을 수 있다. 한 번에 처리할 패킷이나 바이트 예산을 두고 다시 큐에 넣어 공정성을 유지한다. 반대로 알림을 충분히 소비하지 않으면 에지 트리거 방식에서 추가 통지를 놓친 것처럼 보일 수 있으므로 API 계약을 따른다.

서버 틱 지연이 특정 NIC 인터럽트 코어와 겹친다면 코어별 CPU, Soft IRQ 성격의 처리량, 패킷 드롭과 Receive Queue를 확인한다. 무조건 CPU Affinity를 고정하기 전에 네트워크 처리와 게임 스레드의 코어 경쟁, NUMA 메모리 위치를 함께 측정한다.

## 8. 자주 하는 오해
- 가상 주소와 물리 사용량을 같다고 본다.
- Heap은 언제나 느리다고 단정한다.
- Page Fault는 모두 디스크 I/O라고 본다.
- TLB와 CPU Cache를 혼동한다.
- System Call과 Context Switch를 같다고 본다.
- 모든 Library 함수가 System Call이라고 생각한다.
- Interrupt가 발생하면 반드시 다른 Process로 전환된다고 본다.
- 비동기 I/O는 Kernel 진입이 전혀 없다고 생각한다.
- 호출 횟수를 줄이면 지연도 항상 줄어든다고 단정한다.

## 9. 면접 질문
### Q1. 핵심 개념은 무엇인가요?
System Call은 사용자 코드가 커널 서비스를 요청하는 진입이고 Interrupt는 장치·예외 사건을 커널에 알린다.
### Q2. 왜 필요한가요?
권한을 보호하면서 파일, 네트워크와 장치를 사용하게 한다.
### Q3. 실무 적용은 무엇인가요?
작은 send를 반복하기보다 버퍼링·배치하고 비동기 I/O로 대기를 겹친다.

### Q4. System Call과 일반 함수 호출의 차이는 무엇인가요?

일반 함수 호출은 보통 같은 권한과 주소 공간 안에서 호출 규약에 따라 이동한다. 시스템 콜은 검증된 진입점을 통해 커널 권한으로 전환해 보호된 자원을 요청하며 인자와 권한 검증이 필요하다.

### Q5. System Call은 항상 Context Switch를 일으키나요?

아니다. 커널이 요청을 처리한 뒤 같은 스레드로 바로 돌아올 수 있다. 블로킹 I/O처럼 현재 스레드가 대기 상태가 되면 스케줄러가 다른 스레드를 선택해 문맥 교환이 추가될 수 있다.

### Q6. Interrupt와 Exception은 어떻게 다른가요?

장치 인터럽트는 현재 명령과 비동기적으로 발생하는 것이 일반적이다. 페이지 폴트나 0 나누기 같은 예외는 현재 명령 실행과 동기적으로 발생한다. 둘 다 커널 처리기로 제어를 넘길 수 있다.

### Q7. System Call 횟수를 줄이는 방법은 무엇인가요?

작은 I/O를 제한된 시간·크기 안에서 배치하고 Scatter/Gather I/O나 비동기 완료 묶음을 활용할 수 있다. 다만 큰 배치는 개별 메시지 지연을 늘리므로 처리량과 p99 지연을 함께 측정한다.

## 11. 30초 모범답변
> System Call은 커널 서비스를 안전하게 요청하고 Interrupt는 하드웨어와 예외 사건을 커널에 알립니다. System Call과 Interrupt을 선택하거나 적용할 때는 정확성, 성능과 구현 복잡도의 균형을 함께 봐야 합니다. 작은 send를 반복하기보다 버퍼링·배치하고 비동기 I/O로 대기를 겹친다.

## 12. 1~2분 확장답변
> System Call은 커널 서비스를 안전하게 요청하고 Interrupt는 하드웨어와 예외 사건을 커널에 알립니다. 보호와 추상화에는 Fault, Miss와 전환 비용이 있으므로 게임 서버에서는 데이터 수명과 배치를 설계하고 p99 지연과 OS 지표를 함께 확인합니다.

## 13. 핵심 요약
- System Call은 사용자 코드가 커널 서비스를 요청하는 진입이고 Interrupt는 장치·예외 사건을 커널에 알린다.
- 보호와 추상화에는 비용이 있다.
- 데이터 수명과 지역성이 중요하다.
- 평균과 꼬리 지연을 함께 본다.
- 권한 전환, 실행 주체 전환, 장치 알림은 서로 관련되지만 다른 사건이다.
