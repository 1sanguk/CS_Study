# 02. Process Memory와 PCB


## 학습 목표

- 가상 주소 공간의 영역(코드·데이터·BSS·힙·스택)과 각 역할을 설명할 수 있다.
- PCB가 담는 정보와 프로세스 상태 전이(Ready·Running·Waiting)를 설명할 수 있다.
- 가상 메모리 크기·RSS·힙 사용량의 차이를 게임 서버 메모리 분석에 적용할 수 있다.
- 메모리 누수 증상(RSS 지속 증가, 힙 외 누수)을 진단하는 지표와 도구를 설명할 수 있다.

## 1. 개요

프로세스 주소 공간의 코드·데이터·힙·스택과 운영체제가 프로세스를 관리하는 PCB의 역할이다.

프로세스 메모리는 실행 중인 코드가 사용하는 가상 주소 공간이다. PCB(Process Control Block)는 운영체제 커널이 프로세스의 신원, 상태와 자원을 추적하기 위해 유지하는 관리 정보다. 주소 공간은 애플리케이션이 사용하는 내용이고 PCB는 커널이 프로세스를 관리하기 위한 장부라는 차이가 있다.

## 2. 왜 필요한가

각 프로세스에 독립적인 가상 주소 공간을 제공하고 실행 상태, 권한, 열린 파일, 스케줄링 정보를 일관되게 관리해야 한다.

운영체제는 제한된 CPU와 메모리를 여러 작업에 안전하고 효율적으로 나누어야 한다. 개발자는 추상화가 감추는 비용과 공유 범위를 알아야 성능 저하와 동시성 버그를 진단할 수 있다.

## 3. 핵심 동작 원리

```text
실행 파일 매핑 → 코드·데이터 영역 구성 → 힙과 스택 준비 → PCB에 PID·상태·레지스터·자원 참조 저장
```

운영체제는 사용자 프로그램이 직접 하드웨어와 다른 프로세스의 자원을 침범하지 않도록 권한과 상태를 관리한다. 실행 단위가 대기하면 다른 준비 작업을 실행하고, 다시 실행할 때 필요한 문맥을 복원한다.

주소 공간은 사용자 코드가 보는 메모리 배치이고 PCB(Process Control Block)는 커널이 프로세스를 추적하는 관리 정보다. 문맥 교환 때 PCB와 스레드 관리 구조에 실행 문맥이 보존된다.

### 가상 주소 공간의 대표 영역

```text
높은 주소
┌────────────────────┐
│ Thread Stack       │ 아래 방향으로 성장하는 구현이 흔함
├────────────────────┤
│ Memory Mapping     │ 공유 Library, 파일, 익명 Mapping
├────────────────────┤
│ Heap               │ 동적 할당, 위 방향 성장이 흔함
├────────────────────┤
│ BSS                │ 0으로 초기화되는 전역·정적 데이터
│ Data               │ 초기값이 있는 전역·정적 데이터
│ Code / Text        │ 실행 명령, 주로 읽기·실행 권한
└────────────────────┘
낮은 주소
```

이 배치는 이해를 위한 전형적인 모습이며 운영체제, 실행 파일 형식, 보안 설정에 따라 실제 위치와 성장 방향은 달라질 수 있다. 주소 공간 배치 난수화(ASLR)는 영역 위치를 매 실행마다 바꿔 특정 주소를 전제로 한 공격을 어렵게 한다.

코드 영역은 실행 명령을 담고 읽기 전용으로 매핑되는 경우가 많다. 데이터와 BSS는 전역·정적 변수에 사용된다. 힙은 동적 객체와 버퍼를 할당하는 영역이며 런타임 할당자가 운영체제에서 받은 큰 영역을 다시 나눠 관리할 수 있다. 스택은 함수 호출 프레임, 반환 주소, 일부 지역 변수를 담고 스레드마다 존재한다. 메모리 매핑 영역에는 공유 라이브러리, 파일 매핑, 익명 메모리가 놓일 수 있다.

가상 주소를 예약했다고 같은 크기의 물리 메모리를 즉시 점유하는 것은 아니다. 페이지가 실제로 접근될 때 물리 페이지가 연결될 수 있고, 파일의 읽기 전용 코드 페이지는 여러 프로세스가 물리적으로 공유할 수 있다. 프로세스가 보는 주소는 같아 보여도 페이지 테이블을 통해 서로 다른 물리 페이지로 변환될 수 있다.

### PCB에 들어가는 정보

구현마다 이름과 분리는 다르지만 PCB 성격의 커널 구조에는 다음 정보가 연결된다.

- PID와 부모·자식 관계, 사용자와 권한 정보
- 준비·실행·대기·종료 같은 프로세스 상태
- 스케줄링 우선순위와 CPU 사용 통계
- 주소 공간을 설명하는 페이지 테이블 관련 정보
- 열린 파일, 소켓, 신호와 IPC 자원에 대한 참조
- 실행을 재개하는 데 필요한 문맥 또는 스레드 관리 구조의 참조

현대 운영체제는 CPU 실행 문맥을 스레드별 구조에 더 직접적으로 저장한다. 따라서 "PCB 하나가 모든 스레드의 레지스터 한 세트를 가진다"라고 단순화하기보다, 프로세스 공통 자원과 스레드별 실행 문맥이 나뉜다고 설명하는 편이 정확하다.

### 상태 전이

```text
       dispatch
Ready ----------> Running
  ^                  |
  | preempt          | I/O wait / lock wait
  |                  v
  +--------------- Waiting
       event complete
```

준비 상태는 CPU만 배정되면 실행할 수 있는 상태다. 실행 상태에서 시간 할당량이 끝나거나 더 높은 우선순위 작업이 오면 다시 준비 상태가 될 수 있다. I/O나 락을 기다리면 대기 상태로 이동하고, 조건이 충족되면 바로 실행되는 것이 아니라 보통 준비 큐로 돌아간다.

## 4. 쉬운 예시

게임 서버가 8GB의 가상 주소를 예약했지만 실제로 접근한 페이지가 2GB라면 가상 크기와 물리 상주 크기는 다르게 보일 수 있다. 반대로 관리형 힙은 2GB여도 네이티브 네트워크 버퍼, 스레드 스택, 메모리 매핑이 추가되어 프로세스 RSS는 더 클 수 있다. "힙 크기만 정상인데 왜 메모리가 부족한가"라는 질문에는 전체 주소 공간 구성과 운영체제 지표가 필요하다.

```bash
# Linux: 프로세스 메모리 지표 확인
cat /proc/<pid>/status | grep -E "VmRSS|VmSize|Threads"
# VmSize: 가상 주소 공간 예약 크기 (실제 RAM 사용량 ≠)
# VmRSS:  현재 물리 메모리에 상주한 페이지 크기

pmap -x <pid>       # 영역별 상세 매핑 확인 (스택·힙·공유 라이브러리 분리)
ls -l /proc/<pid>/fd | wc -l  # 열린 파일 디스크립터 수 확인
```

```java
// Java: JVM 힙 사용량 확인 (힙 외 영역은 포함 안 됨!)
Runtime runtime = Runtime.getRuntime();
long heapUsed = runtime.totalMemory() - runtime.freeMemory();
long heapMax  = runtime.maxMemory();
System.out.printf("JVM Heap: %d MB / %d MB max%n",
    heapUsed >> 20, heapMax >> 20);

// 주의: 이 값은 JVM 힙만. 아래는 포함되지 않음:
//   - 스레드 스택 (기본 512KB~1MB × 스레드 수)
//   - 네이티브 버퍼 (DirectByteBuffer, Netty off-heap)
//   - JVM 코드 캐시 (JIT 컴파일 결과)
//   - 공유 라이브러리
// → 프로세스 RSS는 힙 사용량보다 훨씬 클 수 있음
```

```text
메모리 증가 원인별 진단 방향:
힙 증가     → heap dump (jmap, JVisualVM) → 참조 사이클·캐시 누수 확인
스레드 증가 → jstack → 스레드 수, 상태, 생성 위치 확인
FD 누수     → /proc/<pid>/fd 개수 → 소켓·파일 close() 누락 확인
네이티브    → pmap + Native Memory Tracking → DirectByteBuffer 등 확인
```

## 5. 비슷한 개념과 비교

| 구분 | 의미 | 주의점 |
|---|---|---|
| Virtual Size (VmSize) | 가상 주소 공간에 예약·매핑된 범위 | 실제 RAM 사용량과 다름 |
| RSS (VmRSS) | 현재 물리 메모리에 상주하는 페이지 규모 | 공유 페이지 계산 방식 차이 |
| Heap 사용량 | 런타임·할당자가 관리하는 동적 메모리 | 스택·매핑·네이티브 버퍼 제외 |
| Page Fault | 주소 변환 중 물리 페이지 처리가 필요한 사건 | 디스크 I/O를 항상 의미하지 않음 |

| 영역 | 내용 | 특징 |
|---|---|---|
| Code / Text | 실행 명령 | 읽기·실행 권한, 여러 프로세스 공유 가능 |
| Data | 초기값 있는 전역·정적 변수 | 쓰기 가능 |
| BSS | 0으로 초기화되는 전역·정적 변수 | 실행 파일에 값 저장 불필요 |
| Heap | 동적 할당 객체·버퍼 | 위 방향 성장, GC 관리 |
| Stack | 함수 프레임, 반환 주소, 지역 변수 | 스레드마다 독립, 아래 방향 성장 |

## 6. 장점과 단점

**가상 주소 공간의 장점**

- 프로세스마다 독립적인 주소 공간을 제공해 한 프로세스의 메모리 오류가 다른 프로세스에 전파되지 않는다.
- 물리 메모리보다 큰 주소 공간을 사용할 수 있다(페이징·스와핑).
- 코드 영역 공유로 같은 실행 파일·라이브러리를 여러 프로세스가 물리 메모리 하나로 사용한다.

**가상 주소 공간의 단점**

- 페이지 테이블 관리와 TLB 미스 비용이 있다.
- 가상 크기가 커도 실제 물리 메모리가 부족하면 스와핑·OOM 킬이 발생한다.

**PCB의 역할**

- 문맥 교환 시 레지스터·PC·스택 포인터를 보존해 실행을 재개할 수 있다.
- 프로세스 상태·자원 사용량·권한을 커널이 중앙 관리한다.

## 7. 게임 서버·백엔드 실무 예시

게임 서버 메모리가 증가하면 힙 객체, 스레드 스택, 메모리 매핑, 네이티브 버퍼를 구분한다. RSS와 가상 메모리 크기가 다르며 단순 주소 공간 예약이 실제 물리 메모리 사용과 같지는 않다.

관찰할 때는 평균 CPU만 보지 않고 스레드 수, 실행 큐, 문맥 교환, 메모리, 락 대기와 꼬리 지연을 같은 시간축에서 확인한다.

메모리 증가를 분석할 때는 시간에 따른 RSS, 가상 크기, 관리형 힙, 네이티브 할당, 스레드 수를 비교한다. 힙 덤프는 관리 객체를 찾는 데 유용하지만 소켓 버퍼나 네이티브 라이브러리 할당은 별도 도구가 필요할 수 있다. 컨테이너의 메모리 제한도 확인한다. 호스트에 여유가 있어도 해당 프로세스의 cgroup 제한을 넘으면 종료될 수 있다.

프로세스가 파일이나 소켓을 계속 열고 닫지 않으면 PCB에 직접 모든 내용이 들어간다기보다 커널의 파일 테이블 등에 대한 참조와 관련 자원이 누적된다. 메모리만 보지 말고 열린 파일 수, 핸들 수, 연결 상태도 함께 본다.

## 8. 자주 하는 오해

- **"JVM 힙 사용량이 정상이면 메모리 누수가 없다"**: 스레드 스택, DirectByteBuffer(네이티브), JIT 코드 캐시, 공유 라이브러리는 힙 지표에 포함되지 않는다. RSS가 계속 증가하면 힙 외 영역도 확인해야 한다.
- **"가상 메모리 크기 = RSS = 실제 RAM 사용량"**: 가상 크기는 예약 범위, RSS는 물리 상주 페이지, 실제 RAM 기여는 공유 페이지를 제외한 값이다. 셋 모두 다르다.
- **"가상 주소를 예약하면 RAM이 그만큼 감소한다"**: 물리 페이지는 실제 접근 시 연결된다. 예약만으로 물리 메모리가 즉시 할당되지 않는다.
- **"대기 상태의 프로세스는 이벤트 완료 후 바로 실행된다"**: 이벤트 완료 후 준비 큐로 이동하고, 스케줄러가 선택할 때 실행된다. 즉시 실행이 보장되지 않는다.
- **"BSS와 Data 영역은 같다"**: Data는 초기값이 있는 전역·정적 변수를 실행 파일에 저장한다. BSS는 0으로 초기화하는 변수로 실행 파일에 실제 값을 저장할 필요 없이 크기 정보만 기록한다.
- **"페이지 폴트는 항상 디스크 I/O를 의미한다"**: Minor Fault(물리 페이지 미연결)는 디스크 접근 없이 물리 페이지만 연결한다. Major Fault가 스와핑·파일 읽기 등 실제 I/O를 동반한다.
- **"프로세스 종료 시 모든 자원이 자동 정리되니 실행 중 누수는 무시해도 된다"**: 종료 시 운영체제가 정리하지만 실행 중 파일 디스크립터 고갈, 소켓 고갈은 장애로 이어진다. 실행 중 close() 누락은 별도로 추적해야 한다.

## 9. 면접 질문

### Q1. 프로세스 가상 주소 공간의 구성 영역을 설명해 주세요.

코드 영역은 실행 명령을 담고 읽기 전용이다. Data는 초기값 있는 전역·정적 변수, BSS는 0으로 초기화되는 전역·정적 변수다. 힙은 동적 할당 영역으로 위 방향으로 성장하고 스택은 함수 호출 프레임을 담으며 스레드마다 독립적으로 존재한다. 메모리 매핑 영역에는 공유 라이브러리와 파일 매핑이 들어간다.

### Q2. PCB에는 어떤 정보가 들어가나요?

PID와 부모·자식 관계, 프로세스 상태(Ready/Running/Waiting/Terminated), 스케줄링 우선순위와 CPU 통계, 페이지 테이블 정보, 열린 파일·소켓 참조, 스레드별 실행 문맥(레지스터·PC·스택 포인터) 참조가 포함된다.

### Q3. 프로세스 상태 전이를 설명해 주세요.

Ready → Running은 스케줄러가 CPU를 배정할 때 일어난다. Running → Waiting은 I/O·락 대기 시 이동하고, 이벤트가 완료되면 바로 Running이 아니라 Ready로 복귀한다. Running에서 시간 할당량 초과나 선점 시 Ready로 돌아온다.

### Q4. 가상 메모리 크기와 RSS는 왜 다른가요?

가상 메모리 크기는 예약하거나 매핑한 주소 범위를 포함하지만 RSS는 현재 물리 메모리에 상주한 페이지를 나타낸다. 아직 접근하지 않은 페이지, 파일 매핑과 공유 페이지 때문에 두 값은 같지 않다.

### Q5. 게임 서버 메모리가 지속 증가할 때 어떻게 진단하나요?

먼저 RSS 증가가 힙인지 스레드 스택인지 네이티브 버퍼인지 pmap과 JVM NMT로 구분한다. 힙이면 힙 덤프로 참조 사이클·캐시 누수를 찾는다. 스레드 수가 증가하면 스레드 생성 코드를 추적한다. 파일 디스크립터가 증가하면 소켓·파일의 close() 누락을 확인한다. 컨테이너 cgroup 메모리 제한도 별도로 확인한다.

### Q6. PCB와 프로세스 주소 공간은 어떻게 다른가요?

주소 공간은 프로세스 코드가 사용하는 코드·데이터·힙·스택 등의 가상 메모리다. PCB는 커널이 PID, 상태, 스케줄링 정보와 자원 참조를 관리하는 구조다. 여러 스레드의 레지스터와 스택은 스레드별 실행 문맥으로 구분된다.

- Minor Page Fault와 Major Page Fault의 차이는 무엇인가요?

- 파일 디스크립터 고갈은 어떻게 진단하나요?

## 11. 30초 모범답변

> 프로세스 주소 공간은 코드·데이터·BSS·힙·스택으로 나뉩니다. PCB는 PID·상태·스케줄링 정보·열린 파일 참조 등 커널이 프로세스를 관리하는 장부입니다. 게임 서버 메모리가 증가할 때는 JVM 힙만 보지 않고 RSS, 스레드 수, 네이티브 버퍼, 파일 디스크립터를 함께 확인해야 합니다.

## 12. 1~2분 확장답변

> 프로세스 메모리는 코드·데이터·힙·스택 등 실행에 필요한 주소 공간이고 PCB는 PID, 상태, 레지스터, 열린 파일 같은 관리 정보를 담는 커널 구조입니다. 가상 주소 예약과 물리 메모리 상주는 다릅니다. 페이지는 실제로 접근될 때 물리 페이지가 연결되며 코드 페이지는 여러 프로세스가 공유할 수 있습니다. 게임 서버에서 메모리 누수를 진단할 때는 JVM 힙 덤프로 관리 객체를 보고, pmap으로 네이티브 버퍼와 스레드 스택을 확인하며, FD 수로 소켓·파일 누수를 감지합니다. 컨테이너 환경에서는 cgroup 제한도 별도로 확인해야 합니다.

## 13. 핵심 요약

- 프로세스 가상 주소 공간은 코드·Data·BSS·힙·스택·메모리 매핑으로 구성된다.
- PCB는 PID·상태·스케줄링 정보·페이지 테이블·열린 파일 참조를 담는 커널 관리 구조다.
- 가상 주소를 예약해도 물리 페이지는 실제 접근 시 연결된다.
- Virtual Size(예약) ≠ RSS(물리 상주) ≠ JVM 힙 사용량. 셋 모두 다르다.
- 이벤트 완료 후 대기 상태는 Running이 아니라 Ready로 돌아간다. 즉시 실행 아님.
- BSS는 실행 파일에 값을 저장하지 않고 크기만 기록해 0으로 초기화한다.
- 메모리 누수 진단: RSS 추이 → 힙 덤프(관리) / pmap(네이티브) / FD 수(소켓·파일) 순으로 분리.
- 컨테이너 OOM Kill은 호스트 여유와 무관하게 cgroup 제한 초과 시 발생한다.

## 한 줄 정리

> 프로세스 메모리는 코드·힙·스택 등 실행 주소 공간이고, PCB는 커널이 상태·자원을 추적하는 장부다. 가상 크기·RSS·힙은 모두 다른 지표다.
