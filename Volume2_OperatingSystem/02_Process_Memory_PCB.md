# 02. Process Memory와 PCB

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 핵심 정의와 등장 이유를 설명할 수 있다.
- 대표 동작 과정과 유사 개념의 차이를 설명할 수 있다.
- 게임 서버 장애와 설계에 적용할 수 있다.

## 1. 개요

프로세스 주소 공간의 코드·데이터·힙·스택과 운영체제가 프로세스를 관리하는 PCB의 역할이다.

프로세스 메모리는 실행 중인 코드가 사용하는 가상 주소 공간이다. PCB(Process Control Block)는 운영체제 커널이 프로세스의 신원, 상태와 자원을 추적하기 위해 유지하는 관리 정보다. 주소 공간은 애플리케이션이 사용하는 내용이고 PCB는 커널이 프로세스를 관리하기 위한 장부라는 차이가 있다.

## 2. 왜 필요한가

각 프로세스에 독립적인 가상 주소 공간을 제공하고 실행 상태, 권한, 열린 파일, 스케줄링 정보를 일관되게 관리해야 한다.

운영체제는 제한된 CPU와 메모리를 여러 작업에 안전하고 효율적으로 나누어야 한다. 개발자는 추상화가 감추는 비용과 공유 범위를 알아야 성능 저하와 동시성 버그를 진단할 수 있다.

## 3. 핵심 동작 원리

```text
실행 파일 매핑 → 코드·데이터 영역 구성 → 힙과 스택 준비 → PCB에 PID·상태·레지스터·자원 참조 저장
```

운영체제는 사용자 프로그램이 직접 하드웨어와 다른 프로세스의 자원을 침범하지 않도록 권한과 상태를 관리한다. 실행 단위가 대기하면 다른 준비 작업을 실행하고, 다시 실행할 때 필요한 문맥을 복원한다.

주소 공간은 사용자 코드가 보는 메모리 배치이고 PCB(Process Control Block)는 커널이 프로세스를 추적하는 관리 정보다. 문맥 교환 때 PCB와 스레드 관리 구조에 실행 문맥이 보존된다.

### 가상 주소 공간의 대표 영역

```text
높은 주소
┌────────────────────┐
│ Thread Stack       │ 아래 방향으로 성장하는 구현이 흔함
├────────────────────┤
│ Memory Mapping     │ 공유 Library, 파일, 익명 Mapping
├────────────────────┤
│ Heap               │ 동적 할당, 위 방향 성장이 흔함
├────────────────────┤
│ BSS                │ 0으로 초기화되는 전역·정적 데이터
│ Data               │ 초기값이 있는 전역·정적 데이터
│ Code / Text        │ 실행 명령, 주로 읽기·실행 권한
└────────────────────┘
낮은 주소
```

이 배치는 이해를 위한 전형적인 모습이며 운영체제, 실행 파일 형식, 보안 설정에 따라 실제 위치와 성장 방향은 달라질 수 있다. 주소 공간 배치 난수화(ASLR)는 영역 위치를 매 실행마다 바꿔 특정 주소를 전제로 한 공격을 어렵게 한다.

코드 영역은 실행 명령을 담고 읽기 전용으로 매핑되는 경우가 많다. 데이터와 BSS는 전역·정적 변수에 사용된다. 힙은 동적 객체와 버퍼를 할당하는 영역이며 런타임 할당자가 운영체제에서 받은 큰 영역을 다시 나눠 관리할 수 있다. 스택은 함수 호출 프레임, 반환 주소, 일부 지역 변수를 담고 스레드마다 존재한다. 메모리 매핑 영역에는 공유 라이브러리, 파일 매핑, 익명 메모리가 놓일 수 있다.

가상 주소를 예약했다고 같은 크기의 물리 메모리를 즉시 점유하는 것은 아니다. 페이지가 실제로 접근될 때 물리 페이지가 연결될 수 있고, 파일의 읽기 전용 코드 페이지는 여러 프로세스가 물리적으로 공유할 수 있다. 프로세스가 보는 주소는 같아 보여도 페이지 테이블을 통해 서로 다른 물리 페이지로 변환될 수 있다.

### PCB에 들어가는 정보

구현마다 이름과 분리는 다르지만 PCB 성격의 커널 구조에는 다음 정보가 연결된다.

- PID와 부모·자식 관계, 사용자와 권한 정보
- 준비·실행·대기·종료 같은 프로세스 상태
- 스케줄링 우선순위와 CPU 사용 통계
- 주소 공간을 설명하는 페이지 테이블 관련 정보
- 열린 파일, 소켓, 신호와 IPC 자원에 대한 참조
- 실행을 재개하는 데 필요한 문맥 또는 스레드 관리 구조의 참조

현대 운영체제는 CPU 실행 문맥을 스레드별 구조에 더 직접적으로 저장한다. 따라서 “PCB 하나가 모든 스레드의 레지스터 한 세트를 가진다”라고 단순화하기보다, 프로세스 공통 자원과 스레드별 실행 문맥이 나뉜다고 설명하는 편이 정확하다.

### 상태 전이

```text
       dispatch
Ready ----------> Running
  ^                  |
  | preempt          | I/O wait / lock wait
  |                  v
  +--------------- Waiting
       event complete
```

준비 상태는 CPU만 배정되면 실행할 수 있는 상태다. 실행 상태에서 시간 할당량이 끝나거나 더 높은 우선순위 작업이 오면 다시 준비 상태가 될 수 있다. I/O나 락을 기다리면 대기 상태로 이동하고, 조건이 충족되면 바로 실행되는 것이 아니라 보통 준비 큐로 돌아간다.

## 4. 쉬운 예시

게임 서버가 네트워크 입력을 기다리는 동안 랭킹 요청을 처리하면 여러 작업이 진전된다. CPU 계산을 여러 코어에 분배하면 실제 동시 실행도 가능하다. 다만 같은 플레이어 상태를 함께 변경한다면 순서와 동기화를 정의해야 한다.

게임 서버가 8GB의 가상 주소를 예약했지만 실제로 접근한 페이지가 2GB라면 가상 크기와 물리 상주 크기는 다르게 보일 수 있다. 반대로 관리형 힙은 2GB여도 네이티브 네트워크 버퍼, 스레드 스택, 메모리 매핑이 추가되어 프로세스 RSS는 더 클 수 있다. “힙 크기만 정상인데 왜 메모리가 부족한가”라는 질문에는 전체 주소 공간 구성과 운영체제 지표가 필요하다.

## 5. 비슷한 개념과 비교

| 구분 | 핵심 | 주의점 |
|---|---|---|
| 프로세스 수준 | 주소 공간과 자원 격리 | 생성·통신 비용 |
| 스레드 수준 | 자원 공유와 실행 흐름 | 경쟁 상태·동기화 |
| 운영체제 관리 | 보호와 스케줄링 | 전환·캐시 비용 |

개념 이름보다 무엇을 공유하고 누가 실행 순서를 결정하는지 설명하는 것이 중요하다.

| 지표 | 의미 | 주의점 |
|---|---|---|
| Virtual Size | 프로세스에 매핑·예약된 가상 주소 범위 | 실제 RAM 사용량과 다름 |
| RSS | 현재 물리 메모리에 상주하는 페이지 규모 | 공유 페이지 계산 방식 차이 |
| Heap 사용량 | 런타임·할당자가 관리하는 동적 메모리 | Stack·Mapping·Native Buffer 제외 가능 |
| Page Fault | 주소 변환 중 페이지 처리가 필요한 사건 | 모두 디스크 I/O를 뜻하지 않음 |

## 6. 장점과 단점

운영체제 추상화는 격리, 자원 공유, 응답성과 처리량을 제공한다. 반면 관리 구조, 스케줄링, 문맥 교환, 동기화에는 비용이 있다. 작업 수를 늘리는 것만으로 성능이 비례해 증가하지 않는다.

## 7. 게임 서버·백엔드 실무 예시

게임 서버 메모리가 증가하면 힙 객체, 스레드 스택, 메모리 매핑, 네이티브 버퍼를 구분한다. RSS와 가상 메모리 크기가 다르며 단순 주소 공간 예약이 실제 물리 메모리 사용과 같지는 않다.

관찰할 때는 평균 CPU만 보지 않고 스레드 수, 실행 큐, 문맥 교환, 메모리, 락 대기와 꼬리 지연을 같은 시간축에서 확인한다.

메모리 증가를 분석할 때는 시간에 따른 RSS, 가상 크기, 관리형 힙, 네이티브 할당, 스레드 수를 비교한다. 힙 덤프는 관리 객체를 찾는 데 유용하지만 소켓 버퍼나 네이티브 라이브러리 할당은 별도 도구가 필요할 수 있다. 컨테이너의 메모리 제한도 확인한다. 호스트에 여유가 있어도 해당 프로세스의 cgroup 제한을 넘으면 종료될 수 있다.

프로세스가 파일이나 소켓을 계속 열고 닫지 않으면 PCB에 직접 모든 내용이 들어간다기보다 커널의 파일 테이블 등에 대한 참조와 관련 자원이 누적된다. 메모리만 보지 말고 열린 파일 수, 핸들 수, 연결 상태도 함께 본다.

## 8. 자주 하는 오해

- 실행 단위와 자원 소유 단위를 같은 개념으로 본다.
- 스레드를 늘리면 처리량이 항상 증가한다고 생각한다.
- 비동기와 병렬 실행을 같은 의미로 사용한다.
- CPU 사용률이 낮으면 서버에 병목이 없다고 단정한다.
- 운영체제 추상화의 비용은 무시해도 된다고 생각한다.

### 최종 실무 판단 기준

- **요구 확인**: 프로세스 주소 공간의 코드·데이터·힙·스택과 운영체제가 프로세스를 관리하는 PCB의 역할이다. 이 내용을 적용하기 전에 데이터 규모, 호출 빈도와 허용 지연을 수치로 확인한다. 같은 기술도 요청량과 정확성 요구가 달라지면 적합한 선택이 달라질 수 있다.
- **정확성 경계**: 필요한 이유는 제한된 자원의 보호와 효율적 사용이다. 정상 흐름만 설명하지 않고 중복, 역순, 동시 실행과 부분 실패에서 어떤 불변식을 지켜야 하는지 함께 명시한다.
- **비용 비교**: 공유 범위와 실행 단위를 구분해야 한다. 평균 복잡도나 처리량 하나만 보지 않고 Memory, CPU, I/O, Lock 대기와 구현 복잡도까지 비교한다.
- **장애 대응**: Process Memory와 PCB 관련 구성 요소가 느려지거나 중단됐을 때 Timeout, Retry 상한, Backpressure와 복구 순서를 정한다. Retry가 중복 부작용이나 연쇄 부하를 만들지 검증한다.
- **운영 검증**: Process Memory와 PCB에서는 기능 Test와 함께 경계값, Peak 부하와 장애 주입 Test를 수행한다. 처리 시간 p95·p99, 오류율, Queue와 Resource 사용량을 관찰하고 변경 전후 결과를 비교한다.

Process Memory와 PCB 답변에서는 이 기준으로 답하면 개념 정의에 그치지 않고 선택 조건, Trade-off와 실무 검증 방법까지 논리적으로 연결할 수 있다.

## 9. 면접 질문

### Q1. 핵심 개념을 한 문장으로 설명해 주세요.

프로세스 주소 공간의 코드·데이터·힙·스택과 운영체제가 프로세스를 관리하는 PCB의 역할이다.

### Q2. 왜 필요한가요?

각 프로세스에 독립적인 가상 주소 공간을 제공하고 실행 상태, 권한, 열린 파일, 스케줄링 정보를 일관되게 관리해야 한다.

### Q3. 게임 서버에서는 어떻게 적용하나요?

게임 서버 메모리가 증가하면 힙 객체, 스레드 스택, 메모리 매핑, 네이티브 버퍼를 구분한다. RSS와 가상 메모리 크기가 다르며 단순 주소 공간 예약이 실제 물리 메모리 사용과 같지는 않다.

### Q4. 성능 문제는 무엇을 확인하나요?

CPU 사용률과 함께 실행 큐, 전환 횟수, 대기 원인, 메모리와 p95·p99 지연을 확인한다.

### Q5. 가상 메모리 크기와 RSS는 왜 다른가요?

가상 메모리 크기는 예약하거나 매핑한 주소 범위를 포함하지만 RSS는 현재 물리 메모리에 상주한 페이지를 나타낸다. 아직 접근하지 않은 페이지, 파일 매핑과 공유 페이지 때문에 두 값은 같지 않다.

### Q6. PCB와 프로세스 주소 공간은 어떻게 다른가요?

주소 공간은 프로세스 코드가 사용하는 코드·데이터·힙·스택 등의 가상 메모리다. PCB는 커널이 PID, 상태, 스케줄링 정보와 자원 참조를 관리하는 구조다. 여러 스레드의 레지스터와 스택은 스레드별 실행 문맥으로 구분된다.

## 12. 1~2분 확장답변

> 프로세스 메모리는 코드·데이터·힙·스택 등 실행에 필요한 주소 공간이고 PCB는 PID, 상태, 레지스터, 열린 파일 같은 관리 정보를 담는 커널 구조입니다. 운영체제는 제한된 자원을 보호하면서 여러 작업을 진행시키고, 대기와 실행 상태를 전환합니다. 이 과정에는 스케줄링과 캐시 지역성 손실 같은 비용이 있습니다. 게임 서버에서는 I/O 대기와 CPU 계산을 구분하고, 공유 상태 범위를 줄이며, 평균값뿐 아니라 락 대기와 꼬리 지연을 함께 관찰해야 합니다.

## 13. 핵심 요약

- 프로세스 주소 공간의 코드·데이터·힙·스택과 운영체제가 프로세스를 관리하는 PCB의 역할이다.
- 필요한 이유는 제한된 자원의 보호와 효율적 사용이다.
- 공유 범위와 실행 단위를 구분해야 한다.
- 동시 실행에는 전환과 동기화 비용이 따른다.
- 게임 서버에서는 지표와 꼬리 지연으로 실제 병목을 확인한다.
- 가상 주소 예약, 물리 상주 메모리, 런타임 힙은 서로 다른 지표다.
