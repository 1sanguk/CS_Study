# 01. Program, Process, Thread


## 학습 목표

- 프로그램·프로세스·스레드의 차이와 각각 공유하는 것과 독립적인 것을 설명할 수 있다.
- 프로세스 격리와 스레드 공유의 장단점을 게임 서버 설계(로그인·게임·DB 분리)에 적용할 수 있다.
- 스레드 풀 크기 결정 원칙과 작업 큐 상한 설계를 설명할 수 있다.
- 멀티스레드 환경에서 경쟁 상태가 발생하는 조건과 동기화 필요성을 설명할 수 있다.

## 1. 개요

실행 파일인 프로그램, 자원 컨테이너인 프로세스(Process), CPU(Central Processing Unit) 실행 단위인 스레드(Thread)의 차이이다.

- 프로그램(Program): 디스크에 저장된 명령어와 정적 데이터의 집합이다.
- 프로세스: 프로그램이 실행되어 주소 공간, 열린 파일, 권한 같은 운영체제 자원을 할당받은 상태다.
- 스레드: 프로세스 안에서 스케줄링되어 명령어를 실행하는 흐름이다.

같은 프로그램을 두 번 실행하면 일반적으로 서로 다른 프로세스가 된다. 두 프로세스는 같은 실행 파일의 코드를 이용하더라도 각자 독립된 가상 주소 공간과 운영체제 상태를 가진다. 반대로 한 프로세스의 여러 스레드는 대부분의 프로세스 자원을 공유한다.

## 2. 왜 필요한가

프로그램은 디스크의 정적 코드이고 프로세스는 이를 실행하며 독립 주소 공간과 운영체제 자원을 가진다. 스레드는 프로세스 안에서 코드·힙·파일을 공유하되 각자 스택과 레지스터 실행 문맥을 가진다.

운영체제는 제한된 CPU와 메모리를 여러 작업에 안전하고 효율적으로 나누어야 한다. 개발자는 추상화가 감추는 비용과 공유 범위를 알아야 성능 저하와 동시성 버그를 진단할 수 있다.

## 3. 핵심 동작 원리

```text
프로그램 로드 → 프로세스 주소 공간·PCB 생성 → 기본 스레드 생성 → 스케줄러가 스레드 실행
```

운영체제는 사용자 프로그램이 직접 하드웨어와 다른 프로세스의 자원을 침범하지 않도록 권한과 상태를 관리한다. 실행 단위가 대기하면 다른 준비 작업을 실행하고, 다시 실행할 때 필요한 문맥을 복원한다.

프로세스 격리는 한 프로세스 오류가 다른 프로세스 메모리를 직접 손상시키기 어렵게 한다. 스레드 공유는 통신이 빠르지만 동기화가 필요하다.

### 프로세스가 만들어질 때

운영체제는 실행 파일을 바탕으로 가상 주소 공간을 구성하고 코드와 데이터 영역을 연결한다. 스택과 힙을 준비하고 열린 파일, 작업 디렉터리, 사용자 권한 같은 실행 환경을 설정한다. 이어서 첫 스레드의 레지스터와 스택을 만들고 실행 가능한 상태로 둔다. 실제 물리 메모리는 요구될 때 페이지 단위로 할당될 수 있으므로 실행 파일 전체가 즉시 메모리에 복사된다고 단정하면 안 된다.

Unix 계열의 `fork()`는 부모 프로세스의 실행 문맥을 논리적으로 복제하고, `exec()`는 현재 프로세스의 프로그램 이미지를 새 실행 파일로 교체한다. 복제 직후 모든 메모리를 실제로 복사하기보다 쓰기 시 복사(Copy-on-Write)를 활용할 수 있다. Windows의 프로세스 생성 API는 인터페이스가 다르지만 결과적으로 새 프로세스 자원과 초기 스레드를 구성한다.

프로세스가 종료되면 운영체제는 주소 공간과 열린 핸들 같은 자원을 회수한다. 다만 부모가 자식의 종료 상태를 아직 수거하지 않은 Unix 프로세스는 좀비 상태로 남을 수 있다. 이는 실행 중인 프로세스가 아니라 종료 정보가 프로세스 테이블에 남은 상태다.

### 스레드가 공유하는 것과 독립적인 것

```text
Process
├─ 공유: Code, Heap, 전역 데이터, 열린 파일·Socket
├─ Thread A: Stack, Register, 실행 위치, Thread-local storage
├─ Thread B: Stack, Register, 실행 위치, Thread-local storage
└─ Thread C: Stack, Register, 실행 위치, Thread-local storage
```

힙 객체를 공유하기 때문에 한 스레드가 객체를 변경하면 다른 스레드도 그 결과를 볼 수 있다. 하지만 "공유한다"가 곧 "즉시 안전하게 같은 값을 본다"는 뜻은 아니다. 경쟁 상태와 메모리 가시성 문제를 막으려면 락, 원자 연산, 메시지 전달 같은 동기화 규칙이 필요하다.

각 스레드는 독립된 스택을 가지므로 지역 변수는 기본적으로 해당 호출 흐름에 속한다. 그러나 지역 변수가 가리키는 힙 객체는 여러 스레드가 공유할 수 있다. 스택 크기도 메모리 자원이므로 연결마다 스레드를 무제한 생성하면 실제 작업이 적어도 메모리와 스케줄링 비용이 증가한다.

### 프로세스 간 통신

격리된 프로세스는 상대 주소 공간의 일반 포인터를 직접 사용할 수 없다. 파이프, 소켓, 공유 메모리, 메시지 큐 같은 프로세스 간 통신(IPC)을 이용한다. 소켓과 메시지 큐는 경계와 소유권이 분명하지만 직렬화와 데이터 복사 비용이 생길 수 있다. 공유 메모리는 대용량 교환에 유리할 수 있으나 접근 동기화와 장애 복구를 직접 설계해야 한다.

## 4. 쉬운 예시

게임 서버가 네트워크 입력을 기다리는 동안 랭킹 요청을 처리하면 여러 작업이 진전된다. CPU 계산을 여러 코어에 분배하면 실제 동시 실행도 가능하다. 다만 같은 플레이어 상태를 함께 변경한다면 순서와 동기화를 정의해야 한다.

```java
// BAD: 연결마다 스레드 생성 → 10000 클라이언트 = 10000 스레드
ServerSocket server = new ServerSocket(7777);
while (true) {
    Socket client = server.accept();
    new Thread(() -> handleClient(client)).start(); // 스택 메모리 × 연결 수
}

// GOOD: 스레드 풀로 자원 제한 (CPU-bound 작업 기준)
int cores = Runtime.getRuntime().availableProcessors();
ExecutorService pool = new ThreadPoolExecutor(
    cores, cores * 2,
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),          // 큐 상한: 과부하 시 빠른 거절
    new ThreadPoolExecutor.CallerRunsPolicy() // 큐 초과 시 호출 스레드에서 직접 처리
);
```

```java
// GameRoom: Room Owner 패턴 — 룸 상태는 단일 스레드만 수정
public class GameRoom {
    // 비동기화 HashMap: roomExecutor 스레드만 접근하므로 안전
    private final Map<String, Player> players = new HashMap<>();
    private final ExecutorService roomExecutor = Executors.newSingleThreadExecutor();

    // 네트워크 I/O 스레드가 호출 → roomExecutor 큐에 직렬화
    public void submitInput(String playerId, Input input) {
        roomExecutor.submit(() -> processInput(playerId, input));
    }

    private void processInput(String playerId, Input input) {
        // 이 메서드는 항상 roomExecutor에서 실행 → 락 없이 상태 변경 가능
        Player player = players.get(playerId);
        if (player != null) player.apply(input);
    }
}
// 핵심: 공유 객체를 락으로 보호하는 대신 단일 스레드에 소유권을 집중
```

## 5. 비슷한 개념과 비교

| 구분 | 핵심 | 주의점 |
|---|---|---|
| 프로세스 수준 | 주소 공간과 자원 격리 | 생성·통신(IPC) 비용 |
| 스레드 수준 | 자원 공유와 실행 흐름 | 경쟁 상태·동기화 |
| 운영체제 관리 | 보호와 스케줄링 | 문맥 전환·캐시 비용 |

| 선택 | 격리 | 데이터 교환 | 대표 사용 |
|---|---|---|---|
| 여러 프로세스 | 강함 | IPC 필요 | 서비스·장애 영역 분리 |
| 여러 스레드 | 약함 | 공유 메모리로 빠름 | 프로세스 내부 병렬 작업 |
| 비동기 작업 | 실행 모델에 따라 다름 | 콜백·Task·Coroutine | 많은 I/O(Input/Output) 대기 처리 |

비동기는 작업이 대기하는 동안 스레드를 붙잡지 않는 실행 구성 방식이다. 단일 스레드에서도 여러 I/O 작업을 번갈아 진행할 수 있으므로 스레드 자체와 같은 개념이 아니다. 병렬성은 둘 이상의 작업이 여러 코어에서 같은 시점에 실제 실행되는 성질이다.

## 6. 장점과 단점

**프로세스의 장점**

- 가상 주소 공간 격리로 한 프로세스의 메모리 오류가 다른 프로세스에 직접 전파되지 않는다.
- 개별 재시작·자원 제한(CPU·메모리 cgroup)을 독립적으로 적용할 수 있다.

**프로세스의 단점**

- 생성 비용(주소 공간·PCB(Process Control Block) 설정)이 스레드보다 높다.
- IPC(소켓·파이프)를 거치면 직렬화·복사 비용과 부분 실패 처리가 필요하다.

**스레드의 장점**

- 같은 프로세스 안에서 힙·파일 디스크립터를 공유하므로 통신이 빠르다.
- 생성·전환 비용이 프로세스보다 낮다.

**스레드의 단점**

- 공유 상태를 동기화하지 않으면 경쟁 상태·메모리 가시성 버그가 발생한다.
- 한 스레드의 비정상 메모리 접근이 전체 프로세스에 영향을 줄 수 있다.
- 스레드 수를 무제한 늘리면 스택 메모리 소비와 문맥 전환 비용이 증가한다.

## 7. 게임 서버·백엔드 실무 예시

게임 서버는 로그인·게임·DB 프록시를 프로세스로 격리하고, 한 게임 프로세스 안에서는 I/O와 작업 스레드를 사용한다. 연결마다 스레드를 만들기보다 스레드 풀과 작업 큐로 자원을 제한한다.

관찰할 때는 평균 CPU만 보지 않고 스레드 수, 실행 큐, 문맥 교환, 메모리, 락 대기와 꼬리 지연을 같은 시간축에서 확인한다.

### 스레드 풀의 크기

CPU 작업용 풀은 코어 수와 작업 특성을 기준으로 제한한다. 스레드가 지나치게 많으면 실행 가능한 스레드끼리 CPU를 다투고 문맥 교환과 캐시 손실이 늘어난다. 반대로 동기 I/O로 오래 막히는 작업을 같은 작은 풀에 넣으면 요청을 실행할 스레드가 고갈될 수 있다. 가능하면 I/O는 비동기로 처리하고, 불가피한 블로킹 작업과 CPU 작업의 풀을 분리한다.

작업 큐에도 상한과 거절 정책이 필요하다. 생산 속도가 소비 속도를 계속 넘는데 큐만 늘리면 응답 시간이 길어지고 결국 메모리가 부족해진다. 서버가 감당할 수 없는 요청은 빠르게 거절하고 클라이언트가 백오프하도록 하는 편이 전체 장애를 줄일 수 있다.

### 장애 격리와 배포

모듈을 프로세스로 나누면 개별 재시작과 자원 제한이 쉬워진다. 하지만 호출이 네트워크 경계를 넘으면서 지연, 부분 실패, 직렬화, 버전 호환 문제가 생긴다. 따라서 "프로세스가 스레드보다 안전하므로 무조건 서비스로 분리한다"는 결론은 적절하지 않다. 장애 격리의 가치가 통신 복잡도보다 큰 경계에 적용한다.

## 8. 자주 하는 오해

- **"프로세스와 스레드는 모두 실행 단위이므로 같은 개념이다"**: 프로세스는 자원(주소 공간·파일) 컨테이너이고 스레드가 그 안에서 CPU를 실행하는 단위다. 역할과 격리 수준이 다르다.
- **"스레드를 늘리면 처리량이 항상 증가한다"**: 코어 수를 넘는 스레드는 문맥 교환과 캐시 손실을 만든다. 블로킹 I/O가 많으면 적당히 늘리는 것이 효과적일 수 있지만 무제한 증가는 역효과다.
- **"비동기 = 멀티스레드 = 병렬 실행"**: 비동기는 대기 중 스레드를 놓아주는 실행 모델이다. 단일 스레드 이벤트 루프도 비동기다. 병렬은 여러 코어에서 동시 실행되는 물리적 특성이다.
- **"CPU 사용률이 낮으면 병목이 없다"**: 락 경쟁·I/O 대기·GC 중단 때문에 CPU는 낮아도 응답 지연이 클 수 있다. 실행 큐·락 대기·꼬리 지연을 함께 확인해야 한다.
- **"지역 변수는 스레드 안전하다"**: 지역 변수 자체는 스택에 있어 스레드마다 독립이다. 하지만 지역 변수가 가리키는 힙 객체는 다른 스레드와 공유될 수 있다.
- **"프로세스를 분리하면 무조건 안전하고 좋다"**: 프로세스 분리는 IPC 비용·부분 실패·직렬화·버전 호환 문제를 만든다. 장애 격리 가치가 통신 복잡도를 넘는 경계에서만 적용한다.
- **"스레드가 공유 메모리로 통신하면 IPC 없이 안전하다"**: 공유 메모리 접근에도 동기화가 필요하다. 락·원자 연산·메모리 순서 보장 없이 공유 객체를 수정하면 경쟁 상태가 발생한다.

## 9. 면접 질문

### Q1. 프로그램, 프로세스, 스레드는 각각 무엇인가요?

프로그램은 디스크에 저장된 실행 파일이다. 프로세스는 프로그램이 실행되어 운영체제로부터 가상 주소 공간, 파일 디스크립터, 권한 등 자원을 할당받은 상태다. 스레드는 프로세스 안에서 CPU를 실행하는 독립적인 흐름으로, 같은 프로세스의 스레드들은 코드·힙·파일을 공유하고 각자 스택과 레지스터를 가진다.

### Q2. 스레드가 공유하는 것과 독립적인 것은 무엇인가요?

공유하는 것은 코드 영역, 힙, 전역 데이터, 열린 파일·소켓이다. 독립적인 것은 스택, 레지스터, 실행 위치(PC), 스레드 로컬 스토리지다. 지역 변수 자체는 스택에 속하지만 지역 변수가 가리키는 힙 객체는 공유될 수 있다.

### Q3. 프로세스와 스레드 중 무엇을 선택하는 기준은 무엇인가요?

장애 격리가 중요하거나 서로 다른 자원 제한이 필요한 경계에는 프로세스를 사용한다. 같은 데이터에 빠르게 접근하고 통신 오버헤드를 줄이려면 스레드를 사용한다. 프로세스 분리는 IPC 비용·부분 실패·직렬화 복잡도가 따르므로 격리 가치가 더 클 때만 적용한다.

### Q4. 스레드 풀 크기는 어떻게 결정하나요?

CPU 바운드 작업은 코어 수 ± 여유분으로 제한한다. 스레드를 많이 만들어도 코어 수를 초과하면 문맥 전환 비용이 늘어난다. I/O 바운드 블로킹 작업은 대기 비율에 따라 더 많은 스레드가 필요하다. I/O와 CPU 작업의 풀을 분리하고 작업 큐에 상한을 두어 과부하 시 빠르게 거절한다.

### Q5. 연결마다 스레드를 생성하면 어떤 문제가 있나요?

연결 수만큼 스택 메모리와 스케줄링 대상이 늘어난다. 많은 스레드가 동시에 실행 가능해지면 문맥 교환과 캐시 손실이 커지고, 블로킹 작업 때문에 스레드가 고갈되면 새 연결을 처리할 수 없다. 비동기 I/O와 제한된 작업 풀로 처리하는 방식이 필요하다.

### Q6. 게임 룸에서 스레드 안전성을 어떻게 설계하나요?

Room Owner 패턴을 사용한다. 룸 상태(플레이어 맵, 게임 로직)는 단일 스레드(roomExecutor)만 수정하고, 외부에서 오는 입력은 큐에 넣어 직렬 처리한다. 공유 객체를 락으로 보호하는 대신 단일 스레드에 소유권을 집중하면 동기화 복잡도를 줄일 수 있다.

## 10. 예상 꼬리질문

- 문맥 교환 시 저장하고 복원하는 것은 무엇인가요?
  > 프로그램 카운터(PC), 스택 포인터, 범용 레지스터, 상태 레지스터가 저장·복원된다. 부동소수점·벡터 레지스터도 포함될 수 있고, 프로세스 전환 시에는 페이지 테이블 관련 정보도 달라진다.
- 코어 수보다 스레드가 많으면 어떻게 되나요?
  > 실행 가능한 스레드가 코어 수를 초과하면 스케줄러가 시간을 나눠 실행하므로 문맥 교환 횟수가 늘어난다. 전환마다 캐시·TLB 지역성 손실이 생겨 CPU 바운드 작업에서는 처리량이 오히려 감소할 수 있다.
- I/O 작업과 CPU 작업의 풀을 왜 분리하나요?
  > I/O 블로킹 작업이 CPU 바운드 풀에 섞이면 스레드가 대기 중에도 슬롯을 차지해 실제 계산할 스레드가 고갈될 수 있다. 풀을 분리하면 CPU 작업은 코어 수 기준으로 제한하고 I/O 대기는 별도로 관리해 자원을 효율적으로 쓸 수 있다.
- `fork()`와 `exec()`의 역할은 어떻게 다른가요?
  > `fork()`는 부모 프로세스의 주소 공간과 실행 상태를 복제해 자식 프로세스를 만들고, `exec()`는 현재 프로세스의 프로그램 이미지를 새 실행 파일로 교체한다. 보통 `fork()` 후 자식에서 `exec()`를 호출해 새 프로그램을 실행한다.
- 프로세스 간 통신 방법에는 무엇이 있나요?
  > 파이프, 소켓, 공유 메모리, 메시지 큐 등이 있다. 소켓과 메시지 큐는 경계와 소유권이 명확하지만 직렬화·복사 비용이 있고, 공유 메모리는 대용량 교환에 유리하지만 접근 동기화를 직접 설계해야 한다.
- 좀비 프로세스는 어떤 상태인가요?
  > 자식 프로세스가 종료했지만 부모가 아직 종료 상태를 수거(`wait()` 호출)하지 않아 프로세스 테이블에 항목만 남은 상태다. 실행 중인 프로세스가 아니라 종료 정보를 담은 껍데기이며, 부모가 수거하거나 부모가 먼저 종료되면 init 프로세스가 수거한다.
- 작업 큐에 상한을 두지 않으면 어떤 문제가 생기나요?
  > 생산 속도가 소비 속도를 지속적으로 넘으면 큐가 계속 커져 메모리가 고갈되고, 큐에 쌓인 요청의 응답 지연이 무한정 늘어난다. 상한을 두고 초과 시 빠르게 거절해 클라이언트가 백오프하도록 하는 편이 전체 장애를 줄일 수 있다.

## 11. 30초 모범답변

> 프로세스는 운영체제가 자원을 격리해 관리하는 실행 환경이고, 스레드는 프로세스 안에서 코드·힙·파일을 공유하며 CPU를 실행하는 흐름입니다. 프로세스는 격리가 강하지만 IPC 비용이 크고, 스레드는 공유가 쉬운 대신 경쟁 상태를 동기화해야 합니다. 게임 서버에서는 서비스를 프로세스로 격리하고, 한 프로세스 안에서는 Room Owner 패턴으로 스레드 소유권을 명확히 해 동기화 복잡도를 줄입니다.

## 12. 1~2분 확장답변

> 프로세스는 실행 중인 프로그램이고 스레드는 프로세스 자원을 공유하는 실행 흐름입니다. 프로세스는 격리가 강하지만 생성·통신 비용이 크고, 스레드는 공유가 쉬운 대신 경쟁 상태를 동기화해야 합니다. 운영체제는 제한된 자원을 보호하면서 여러 작업을 진행시키고, 대기와 실행 상태를 전환합니다. 이 과정에는 스케줄링과 캐시 지역성 손실 같은 비용이 있습니다. 게임 서버에서는 I/O 대기와 CPU 계산을 구분하고, 공유 상태 범위를 줄이며, 평균값뿐 아니라 락 대기와 꼬리 지연을 함께 관찰해야 합니다.

## 13. 핵심 요약

- 프로그램은 디스크의 실행 파일, 프로세스는 자원을 할당받은 실행 환경, 스레드는 프로세스 안의 CPU 실행 흐름이다.
- 스레드는 코드·힙·파일을 공유하고, 스택·레지스터·PC(Program Counter)는 독립적으로 가진다.
- 지역 변수는 스택에 있어 스레드별로 독립이지만, 지역 변수가 가리키는 힙 객체는 공유될 수 있다.
- 프로세스는 격리가 강하고 스레드는 통신이 빠르다. 공유 상태에는 반드시 동기화가 필요하다.
- 스레드를 늘린다고 처리량이 항상 증가하지 않는다. 코어 수 초과 시 문맥 전환 비용이 커진다.
- CPU 바운드 풀과 I/O 블로킹 풀을 분리하고, 작업 큐에 상한과 거절 정책을 둔다.
- Room Owner 패턴: 공유 상태를 락으로 보호하는 대신 단일 스레드에 소유권을 집중한다.
- 병목 진단은 CPU 평균이 아니라 실행 큐·락 대기·꼬리 지연(p99)을 시간축으로 맞춰 확인한다.

## 한 줄 정리

> 프로세스는 격리된 자원 컨테이너, 스레드는 그 안에서 공유하며 실행되는 흐름이다. 공유할수록 빠르지만 동기화 책임이 생긴다.
