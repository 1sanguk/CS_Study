# 06. Mutex, Semaphore, SpinLock


## 학습 목표

- Mutex, Semaphore, SpinLock의 개념과 대기 방식 차이를 설명할 수 있다.
- Mutex와 이진 세마포어의 소유권 의미 차이를 설명할 수 있다.
- SpinLock이 CPU를 낭비하는 조건과 적합한 사용 시점을 설명할 수 있다.
- 게임 서버에서 룸 상태와 DB 연결 풀에 적합한 동기화 도구를 선택하고 그 이유를 설명할 수 있다.

## 1. 개요

Mutex는 한 실행 흐름만 진입시키고 Semaphore는 N개의 접근을 허용하며 SpinLock은 CPU(Central Processing Unit)에서 반복 대기하는 락이다.

세 도구는 모두 동시 접근을 조절하지만 표현하는 의도가 다르다. 뮤텍스(Mutex)는 공유 상태에 대한 상호 배제를 표현한다. 세마포어(Semaphore)는 사용 가능한 허가(Permit)의 개수를 세어 제한된 자원의 동시 사용량을 조절한다. 스핀락(SpinLock)은 락을 얻을 때까지 실행 스레드를 재우지 않고 짧게 반복 확인한다. 이름만 바꿔 쓸 수 있는 동일한 도구가 아니다.

## 2. 왜 필요한가

상호 배제와 제한된 연결·작업 슬롯의 수 제어에는 다른 도구가 필요하다.

플레이어 상태처럼 한 시점에 하나의 실행 흐름만 변경해야 하는 데이터가 있다. 반면 DB 연결 풀처럼 전체 20개까지는 동시에 사용해도 되지만 21번째 요청은 기다려야 하는 자원도 있다. 대기 시간이 매우 짧고 스레드를 재웠다가 깨우는 비용이 더 큰 저수준 구간도 있다. 문제의 의미와 예상 대기 시간에 맞는 도구를 선택해야 한다.

## 3. 핵심 동작 원리

```text
Mutex: lock→work→unlock / Semaphore: wait→work→release
```

Mutex는 긴 대기에, SpinLock은 매우 짧은 경쟁에, Semaphore는 동시 허용량 관리에 적합하다.

### Mutex

뮤텍스는 잠금 상태와 소유자를 관리한다. 한 스레드가 획득한 동안 다른 스레드는 진입할 수 없다. 경쟁이 없으면 원자 연산만으로 빠르게 획득할 수 있고, 경쟁이 길어지면 구현에 따라 대기 큐에 들어가 스레드가 잠들 수 있다. 잠든 스레드는 CPU를 소비하지 않지만 커널 스케줄링과 깨우기 비용이 생긴다.

```text
Thread A: lock 획득 ───── Critical Section ───── unlock
Thread B:          lock 시도 ── Waiting ──────── 획득
```

일반적인 뮤텍스는 획득한 소유자가 해제해야 한다. 재귀 뮤텍스는 같은 스레드의 중복 획득을 허용하고 횟수만큼 해제해야 하지만, 호출 구조의 잘못된 락 설계를 감출 수 있으므로 필요성을 분명히 한다. 락은 보호하는 데이터와 함께 설계한다. 예외나 조기 반환에서도 반드시 해제되도록 범위 기반 구조를 사용한다. 잠금 후 네트워크 호출이나 외부 I/O(Input/Output)를 실행하면 대기 시간이 예측 불가능해지고 상대 서비스 장애가 락 정체로 확대된다.

### Semaphore

카운팅 세마포어는 초기 허가 수 N을 가진다. `acquire`는 허가 하나를 가져가며 0이면 기다린다. `release`는 허가를 돌려주고 대기자를 깨울 수 있다.

```text
DB Connection Permits = 2

Request A: acquire(2→1) ─ query ─ release(1→2)
Request B: acquire(1→0) ─ query ─ release(0→1)
Request C: acquire(0) ─── wait ─── acquire 후 실행
```

이진 세마포어는 값이 0과 1이라 뮤텍스처럼 보일 수 있지만 일반적으로 소유권 의미가 약하다. 한 실행 흐름이 기다리고 다른 실행 흐름이 `release`하여 사건을 알리는 용도로도 사용할 수 있다. 세마포어 해제를 빠뜨리면 허가가 누수되어 시간이 지나며 처리량이 줄고 결국 모든 요청이 기다린다.

### SpinLock

스핀락 대기자는 원자적 비교·교환으로 잠금 상태를 반복 확인한다.

```text
while (!try_lock()) {
    // 짧게 반복하거나 CPU에 spin hint 전달
}
```

락이 수십 나노초처럼 매우 짧게 유지되고 곧 풀릴 가능성이 높다면 스레드 수면·깨우기보다 유리할 수 있다. 그러나 보유자가 I/O를 하거나 선점되어 오래 실행되지 못하면 대기자는 코어를 계속 소비한다. 일반 애플리케이션에서는 런타임의 적응형 락이 짧게 스핀한 뒤 블로킹하는 전략을 이미 사용할 수 있다.

## 4. 쉬운 예시

```java
// Mutex: 인벤토리 불변식 보호 — 아이템 추가와 무게 갱신이 원자적으로 보호
ReentrantLock inventoryLock = new ReentrantLock();

public boolean addItem(String itemId, int weight) {
    inventoryLock.lock();
    try {
        if (currentWeight + weight > MAX_WEIGHT) return false;
        items.add(itemId);
        currentWeight += weight; // 두 필드를 함께 보호
        return true;
    } finally {
        inventoryLock.unlock(); // 예외 발생해도 반드시 해제
    }
    // 주의: try 블록 내 외부 DB 호출 금지 — 락 보유 중 외부 I/O는 대기 시간 예측 불가
}
```

```java
// Semaphore: DB 연결 동시 20개로 제한
Semaphore dbPermits = new Semaphore(20);

public QueryResult query(String sql) throws InterruptedException {
    if (!dbPermits.tryAcquire(500, TimeUnit.MILLISECONDS)) {
        throw new ServiceUnavailableException("DB permit timeout"); // 빠른 실패
    }
    try {
        return db.execute(sql);
    } finally {
        dbPermits.release(); // 반드시 반환 — 빠뜨리면 허가 누수
    }
}
// 주의: 세마포어가 20이어도 대기 큐는 무한 → 큐 상한과 전체 요청 기한 별도 설정 필요
// 세마포어 수는 DB가 감당하는 질의 부하 기준으로 정함 (풀 크기와 다를 수 있음)
```

```java
// SpinLock: Java에서는 직접 구현보다 ReentrantLock의 적응형 락 권장
// AtomicBoolean 스핀락 예시 (매우 짧은 저수준 구간 전용)
AtomicBoolean locked = new AtomicBoolean(false);

public void spinLock() {
    while (!locked.compareAndSet(false, true)) {
        Thread.onSpinWait(); // CPU spin hint (JDK 9+): 하이퍼스레딩 파트너에게 자원 양보
    }
}
public void spinUnlock() { locked.set(false); }
// 경고: 보유자가 선점되거나 I/O 실행 시 대기자가 코어를 낭비
```

## 5. 비슷한 개념과 비교

| 구분 | Mutex | Semaphore | SpinLock |
|---|---|---|---|
| 주 목적 | 한 소유자의 상호 배제 | N개 자원·동시성 제한 | 매우 짧은 상호 배제 |
| 대기 방식 | 블로킹(잠들 수 있음) | 허가 없으면 블로킹 | CPU에서 반복 |
| 소유권 | 일반적으로 있음 | 일반적으로 약함 | 구현에 따라 다름 |
| 적합 예시 | 인벤토리 불변식 | DB 동시 질의 20개 | 저수준 짧은 메타데이터 갱신 |
| 주요 위험 | Deadlock·Contention | Permit 누수·큐 무한 증가 | CPU 낭비·Starvation |

| 구분 | Mutex | Binary Semaphore |
|---|---|---|
| 소유권 | 획득 스레드만 해제 가능 | 다른 스레드가 release 가능 |
| 주 용도 | 임계 구역 상호 배제 | 이벤트 신호·생산자-소비자 |
| 재귀 획득 | 재귀 뮤텍스 지원 가능 | 일반적으로 미지원 |

조건 변수(Condition Variable)는 특정 상태가 될 때까지 뮤텍스를 풀고 잠드는 도구다. "큐가 비어 있지 않다" 같은 조건을 공유 상태와 함께 기다릴 때 사용한다. 깨어난 뒤에도 조건을 반복 검사해야 한다.

## 6. 장점과 단점

**Mutex의 장점**

- 복합 불변식을 명확하게 보호하고 소유권 의미로 오용을 줄인다.
- 대기 중 CPU를 소비하지 않아 경쟁이 길어져도 시스템 자원 낭비가 없다.

**Mutex의 단점**

- 오래 잡거나 획득 순서가 엇갈리면 지연과 교착 상태가 생긴다.
- 락 보유 중 외부 I/O가 포함되면 장애 전파 경로가 된다.

**Semaphore의 장점**

- 외부 자원에 대한 동시성을 제한해 과부하를 막는다.
- 이벤트 신호와 생산자-소비자 패턴에 자연스럽다.

**Semaphore의 단점**

- Permit 해제를 빠뜨리면 허가가 누수되어 처리량이 줄고 결국 모든 요청이 대기한다.
- 대기 큐 상한을 별도로 설계해야 한다.

**SpinLock의 장점**

- 매우 짧은 임계 구역에서 스케줄링 지연 없이 낮은 지연을 제공할 수 있다.

**SpinLock의 단점**

- 보유자가 선점되거나 I/O를 하면 대기자가 코어를 낭비한다.
- 공정성과 우선순위 역전을 별도로 다뤄야 한다.

## 7. 게임 서버·백엔드 실무 예시

룸 상태는 Mutex나 단일 스레드 소유로 보호하고 DB 연결 20개는 Semaphore로 제한한다. 락 대기 시간, 큐 길이, 타임아웃과 p99 지연을 함께 관찰한다.

DB 세마포어를 20으로 제한해도 요청 큐가 무제한이면 장애 시 수천 요청이 메모리에 대기할 수 있다. 획득 타임아웃, 전체 요청 기한, 큐 상한을 두고 빠른 실패를 반환한다. 세마포어 수는 DB 풀 크기뿐 아니라 DB가 감당할 수 있는 질의 부하를 기준으로 정한다.

룸 뮤텍스의 p99 보유 시간이 갑자기 늘었다면 락 안에서 로그 출력, 직렬화, 외부 호출이 실행되는지 프로파일링한다. 평균 대기만 보면 드문 긴 임계 구역을 놓칠 수 있다. 획득 시도 횟수, 경쟁 비율, 대기와 보유 시간, 타임아웃을 구분해 기록한다.

## 8. 자주 하는 오해

- **"뮤텍스와 이진 세마포어는 완전히 같다"**: 뮤텍스는 획득한 스레드만 해제할 수 있는 소유권이 있고 임계 구역 보호가 목적이다. 이진 세마포어는 다른 스레드가 신호를 보낼 수 있어 이벤트 통보 용도에도 쓰인다.
- **"세마포어가 과부하를 완전히 막아준다"**: 실행 중인 작업 수는 제한하지만 앞의 대기 큐가 무한하면 메모리와 지연이 계속 증가한다. 큐 상한·타임아웃·빠른 실패를 함께 적용해야 한다.
- **"SpinLock이 Mutex보다 항상 빠르다"**: 보유자가 I/O를 하거나 선점되면 대기자가 코어를 낭비한다. 경쟁이 심하거나 보유 시간이 길면 오히려 더 느릴 수 있다.
- **"세마포어 release를 빠뜨려도 자동으로 복구된다"**: 허가가 누수되어 시간이 지나며 처리량이 줄고 결국 모든 요청이 기다린다. finally 블록에서 반드시 반환해야 한다.
- **"ReentrantLock은 재진입 허용이므로 항상 안전하다"**: 재귀 획득 횟수만큼 해제하지 않으면 교착 상태가 생긴다. 또한 잘못된 락 설계를 감추는 도구가 될 수 있다.
- **"락 보유 중 외부 API(Application Programming Interface)를 호출해도 된다"**: 외부 호출 중 락을 잡으면 대기 시간이 예측 불가능해지고 상대 서비스 장애가 로컬 락 정체로 확대된다. 외부 I/O는 락 밖으로 분리한다.
- **"세마포어 수는 DB 연결 풀 크기와 같으면 된다"**: DB가 감당할 수 있는 질의 부하를 기준으로 정해야 한다. 쿼리가 무거우면 연결 수보다 낮은 값이 적합할 수 있다.

## 9. 면접 질문

### Q1. Mutex, Semaphore, SpinLock의 차이는 무엇인가요?

Mutex는 한 실행 흐름만 임계 구역에 진입시키고 획득한 스레드가 해제하는 소유권이 있다. Semaphore는 N개의 허가를 관리해 제한된 자원의 동시 접근 수를 조절하며 소유권이 약하다. SpinLock은 락을 얻을 때까지 CPU에서 반복 확인하므로 보유 시간이 매우 짧은 구간에서만 유리하다.

### Q2. Mutex와 이진 세마포어는 어떻게 다른가요?

둘 다 한 번에 하나만 통과시키지만 뮤텍스는 획득한 스레드가 해제하는 소유권이 있고 임계 구역 상호 배제가 목적이다. 이진 세마포어는 다른 스레드가 신호를 보낼 수 있어 생산자-소비자나 이벤트 통보 패턴에 쓴다. 임계 구역 보호에는 뮤텍스가 의미가 더 명확하다.

### Q3. SpinLock은 언제 사용하나요?

락 보유 시간이 매우 짧고(수십 나노초 수준), 경쟁이 낮으며, 코어 여유가 있어 스레드 수면·깨우기 비용이 더 클 때 측정 후 고려한다. 보유자가 I/O를 하거나 선점될 수 있고 대기가 길다면 CPU를 낭비하므로 블로킹 락이 적합하다. Java에서는 ReentrantLock의 적응형 락이 이미 짧게 스핀한 뒤 블로킹한다.

### Q4. 세마포어에서 Permit을 빠뜨리면 어떻게 되나요?

허가가 누수되어 시간이 지날수록 사용 가능한 허가 수가 줄어든다. 결국 모든 요청이 허가를 기다리게 되어 처리량이 0이 된다. 예외 경로에서도 반드시 반환되도록 finally 블록을 사용해야 한다.

### Q5. Semaphore가 과부하를 완전히 막아 주나요?

실행 중인 작업 수는 제한하지만 앞의 대기 큐가 무한하면 메모리와 지연이 계속 증가한다. 큐 상한, 획득 타임아웃, 취소와 요청 전체 기한을 함께 적용해야 한다. 세마포어 수도 DB가 감당할 수 있는 질의 부하를 기준으로 정해야 한다.

### Q6. 게임 서버에서 룸 상태와 DB 연결 풀에 각각 어떤 동기화 도구를 쓰나요?

룸 상태는 Mutex나 Room Owner 단일 스레드 소유로 보호한다. 단일 스레드 소유는 락 없이도 안전하며 임계 구역 복잡도를 줄인다. DB 연결 풀은 Semaphore로 동시 접근 수를 제한하되, 세마포어 수는 DB가 감당하는 질의 부하를 기준으로 정하고 타임아웃과 큐 상한을 함께 설정한다.

## 10. 예상 꼬리질문

- 원자성과 가시성은 어떻게 다른가요?
  > 원자성(Atomicity)은 연산이 중간 상태 없이 한 번에 완료되는 성질이고, 가시성(Visibility)은 한 스레드의 변경이 다른 스레드에 즉시 보이는 성질이다. 원자 연산이 보장되어도 가시성이 없으면 다른 코어의 캐시에 오래된 값이 남을 수 있으며, 락이나 volatile 같은 동기화 수단으로 둘 다 확보해야 한다.
- 락 범위가 길면 어떤 문제가 생기나요?
  > 락을 오래 보유하면 다른 스레드가 오래 대기하여 경쟁(Contention)이 심해지고 처리량이 낮아진다. 특히 락 보유 중 외부 I/O나 네트워크 호출이 포함되면 대기 시간이 예측 불가능해지고, 상대 서비스 장애가 로컬 락 정체로 확산된다.
- 조건 변수는 세마포어와 어떻게 다른가요?
  > 조건 변수(Condition Variable)는 뮤텍스와 함께 사용하며, 특정 상태가 될 때까지 락을 해제하고 잠든다. 상태 변경 시 signal/broadcast로 대기자를 깨우며, 깨어난 뒤 조건을 반드시 재검사해야 한다. 세마포어는 허가 수를 카운팅하여 접근 수를 제한하는 범용 도구로, 조건 기반 대기보다 자원 수 제어에 적합하다.
- 운영에서 락 경쟁 원인을 어떻게 찾나요?
  > 스레드 덤프(jstack)로 BLOCKED 상태 스레드와 보유자를 확인하고, APM이나 프로파일러로 락 대기 시간·경쟁 비율을 측정한다. 평균 대기만 보지 않고 p99, p999 꼬리 지연을 함께 확인해 드문 긴 임계 구역을 찾는다.
- 적응형 Mutex는 어떤 방식으로 대기하나요?
  > 먼저 짧게 스핀하며 락 해제를 기다리고, 일정 횟수 이후에도 획득하지 못하면 블로킹 대기로 전환하여 스레드를 재운다. 짧은 경쟁에서는 스핀의 낮은 지연을 활용하고, 경쟁이 길어지면 CPU 낭비를 막는 두 가지 방식의 장점을 결합한다.
- Mutex는 반드시 획득한 스레드가 해제해야 하나요?
  > 일반 Mutex의 의미상 그렇다. 소유권이 있어 획득한 스레드만 해제할 수 있으며, 이를 통해 임계 구역의 오용과 혼란을 방지한다. 이진 세마포어는 소유권 의미가 약해 다른 스레드가 신호를 보낼 수 있으므로, 이벤트 통보 용도에는 세마포어가 더 적합하다.
- 재귀 뮤텍스는 언제 문제가 되나요?
  > 같은 스레드가 중복 획득한 횟수만큼 정확히 해제하지 않으면 교착 상태가 발생한다. 또한 재귀 허용이 잘못된 락 설계를 감추는 도구가 되어, 호출 구조 내의 중첩 임계 구역 문제를 발견하기 어렵게 만든다.

## 11. 30초 모범답변

> Mutex는 한 스레드의 진입을, Semaphore는 N개의 동시 접근을 제한하며 SpinLock은 짧은 대기를 CPU 반복으로 처리합니다. 뮤텍스는 획득한 스레드가 해제하는 소유권이 있어 임계 구역 보호에 적합하고, 이진 세마포어는 다른 스레드가 신호를 보낼 수 있어 이벤트 통보에도 씁니다. 게임 서버에서 룸 상태는 Mutex나 단일 스레드 소유, DB 연결은 Semaphore로 분리해 적용합니다.

## 12. 1~2분 확장답변

> Mutex는 한 스레드의 진입을, Semaphore는 N개의 동시 접근을 제한하며 SpinLock은 짧은 대기를 CPU 반복으로 처리합니다. 뮤텍스와 이진 세마포어는 모두 한 번에 하나만 통과시키지만 소유권 의미가 다릅니다. 세마포어가 실행 수를 제한해도 대기 큐가 무한하면 메모리와 지연이 늘어나므로 타임아웃과 큐 상한이 함께 필요합니다. 세마포어 Permit를 finally 없이 반환하면 누수가 생겨 처리량이 서서히 0이 됩니다. 게임 서버에서는 룸 단위 소유권으로 락 복잡도를 줄이고 외부 DB에는 세마포어로 부하를 제한합니다.

## 13. 핵심 요약

- Mutex는 한 실행 흐름만 임계 구역에 진입시키고 획득한 스레드가 해제하는 소유권이 있다.
- Semaphore는 N개의 허가를 관리해 제한된 자원의 동시 접근 수를 조절하며 소유권은 일반적으로 약하다.
- SpinLock은 락을 얻을 때까지 CPU에서 반복 확인한다. 보유 시간이 매우 짧고 코어 여유가 있을 때만 이점이 있다.
- 뮤텍스와 이진 세마포어는 겉으로 비슷하지만 소유권 의미가 다르다. 이진 세마포어는 다른 스레드가 신호를 보내는 이벤트 통보에도 쓴다.
- 세마포어 Permit를 빠뜨리면 허가가 누수되어 처리량이 서서히 줄다가 모든 요청이 기다린다.
- 세마포어가 실행 수를 제한해도 대기 큐가 무한하면 메모리와 지연이 계속 증가한다. 큐 상한과 타임아웃이 함께 필요하다.
- 락 보유 중 외부 I/O나 네트워크 호출이 포함되면 보유 시간이 예측 불가능해지고 상대 장애가 락 정체로 확대된다.
- 게임 서버에서 룸 상태는 Mutex나 단일 스레드 소유, DB 연결은 Semaphore로 분리해 적용한다. 세마포어 수는 DB가 감당하는 질의 부하를 기준으로 정한다.

## 한 줄 정리

> Mutex는 한 스레드의 진입을, Semaphore는 N개의 동시 접근을 제한하며 SpinLock은 짧은 대기를 CPU 반복으로 처리합니다.
