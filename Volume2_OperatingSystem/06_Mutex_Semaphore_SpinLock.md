# 06. Mutex, Semaphore, SpinLock

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 정의와 발생 원인을 설명할 수 있다.
- 대표 해결 도구와 차이를 설명할 수 있다.
- 게임 서버의 안전한 설계에 적용할 수 있다.

## 1. 개요

Mutex는 한 실행 흐름만 진입시키고 Semaphore는 N개의 접근을 허용하며 SpinLock은 CPU에서 반복 대기하는 락이다.

세 도구는 모두 동시 접근을 조절하지만 표현하는 의도가 다르다. 뮤텍스(Mutex)는 공유 상태에 대한 상호 배제를 표현한다. 세마포어(Semaphore)는 사용 가능한 허가(Permit)의 개수를 세어 제한된 자원의 동시 사용량을 조절한다. 스핀락(SpinLock)은 락을 얻을 때까지 실행 스레드를 재우지 않고 짧게 반복 확인한다. 이름만 바꿔 쓸 수 있는 동일한 도구가 아니다.

## 2. 왜 필요한가

상호 배제와 제한된 연결·작업 슬롯의 수 제어에는 다른 도구가 필요하다. 동시성 버그는 실행 순서와 부하에 따라 간헐적으로 나타나므로 불변식과 소유권을 설계 단계에서 명시해야 한다.

플레이어 상태처럼 한 시점에 하나의 실행 흐름만 변경해야 하는 데이터가 있다. 반면 DB 연결 풀처럼 전체 20개까지는 동시에 사용해도 되지만 21번째 요청은 기다려야 하는 자원도 있다. 대기 시간이 매우 짧고 스레드를 재웠다가 깨우는 비용이 더 큰 저수준 구간도 있다. 문제의 의미와 예상 대기 시간에 맞는 도구를 선택해야 한다.

## 3. 핵심 동작 원리

```text
Mutex: lock→work→unlock / Semaphore: wait→work→release
```

Mutex는 긴 대기에, SpinLock은 매우 짧은 경쟁에, Semaphore는 동시 허용량 관리에 적합하다. 동기화의 목적은 모든 실행을 막는 것이 아니라 필요한 원자성과 관찰 순서를 최소 범위에 제공하는 것이다.

### Mutex

뮤텍스는 잠금 상태와 소유자를 관리한다. 한 스레드가 획득한 동안 다른 스레드는 진입할 수 없다. 경쟁이 없으면 원자 연산만으로 빠르게 획득할 수 있고, 경쟁이 길어지면 구현에 따라 대기 큐에 들어가 스레드가 잠들 수 있다. 잠든 스레드는 CPU를 소비하지 않지만 커널 스케줄링과 깨우기 비용이 생긴다.

```text
Thread A: lock 획득 ───── Critical Section ───── unlock
Thread B:          lock 시도 ── Waiting ──────── 획득
```

일반적인 뮤텍스는 획득한 소유자가 해제해야 한다. 재귀 뮤텍스는 같은 스레드의 중복 획득을 허용하고 횟수만큼 해제해야 하지만, 호출 구조의 잘못된 락 설계를 감출 수 있으므로 필요성을 분명히 한다. 모든 구현이 대기 순서의 공정성을 보장하지 않으며 새로 온 스레드가 먼저 획득할 수도 있다.

락은 보호하는 데이터와 함께 설계한다. 예외나 조기 반환에서도 반드시 해제되도록 C++의 RAII 잠금 객체나 C#의 `lock` 문처럼 범위 기반 구조를 사용한다. 잠금 후 네트워크 호출이나 사용자 콜백을 실행하면 대기 시간이 예측 불가능해지고 재진입 문제가 생길 수 있다.

### Semaphore

카운팅 세마포어는 초기 허가 수 N을 가진다. `wait` 또는 `acquire`는 허가 하나를 가져가며 0이면 기다린다. `release`는 허가를 돌려주고 대기자를 깨울 수 있다.

```text
DB Connection Permits = 2

Request A: acquire(2→1) ─ query ─ release(1→2)
Request B: acquire(1→0) ─ query ─ release(0→1)
Request C: acquire(0) ─── wait ─── acquire 후 실행
```

이진 세마포어는 값이 0과 1이라 뮤텍스처럼 보일 수 있지만 일반적으로 소유권 의미가 약하다. 한 실행 흐름이 기다리고 다른 실행 흐름이 `release`하여 사건을 알리는 용도로도 사용할 수 있다. 반면 뮤텍스는 공유 임계 구역의 소유권과 상호 배제를 표현하는 데 더 자연스럽다.

세마포어 해제를 빠뜨리면 허가가 누수되어 시간이 지나며 처리량이 줄고 결국 모든 요청이 기다린다. 반대로 획득하지 않은 허가를 추가 반환하면 실제 자원 수보다 많은 요청이 통과할 수 있다. 예외 경로에서 반환을 보장하고 현재 사용량과 대기 시간을 관찰한다.

### SpinLock

스핀락 대기자는 원자적 비교·교환으로 잠금 상태를 반복 확인한다.

```text
while (!try_lock()) {
    // 짧게 반복하거나 CPU에 spin hint 전달
}
```

락이 수십 나노초처럼 매우 짧게 유지되고 곧 풀릴 가능성이 높다면 스레드 수면·깨우기보다 유리할 수 있다. 그러나 보유자가 I/O를 하거나 선점되어 오래 실행되지 못하면 대기자는 코어를 계속 소비한다. 단일 코어에서 보유자를 실행해야 하는데 대기자가 스핀하면 특히 비효율적이다.

일반 애플리케이션에서는 런타임의 적응형 락이 짧게 스핀한 뒤 블로킹하는 전략을 이미 사용할 수 있다. 직접 스핀락을 구현하면 메모리 순서, 선점, 공정성과 예외 안전성을 모두 다뤄야 하므로 측정된 저수준 병목이 아니라면 표준 동기화 도구를 우선한다.

### 대기 방식과 성능

블로킹 락은 CPU 사용을 줄이지만 잠들고 깨는 지연이 있다. 스핀락은 스케줄링 지연을 피하지만 대기 시간만큼 CPU를 태운다. “몇 마이크로초 이하면 무조건 스핀” 같은 고정 기준은 없다. 경쟁 빈도, 코어 여유, 임계 구역 분포, 선점 가능성을 실제 환경에서 측정해야 한다.

락 경쟁이 심하면 임계 구역 코드 자체보다 락을 둘러싼 캐시 라인의 소유권 이동이 병목이 될 수 있다. 공유 상태를 샤딩하거나 스레드별 집계를 한 뒤 합치는 방식이 락 종류 교체보다 효과적일 수 있다.

## 4. 쉬운 예시

두 요청이 같은 잔액을 읽고 각각 차감하면 둘 다 성공할 수 있다. 읽기, 조건 검사, 쓰기를 하나의 보호 단위로 만들거나 상태 소유 스레드에 명령을 직렬화한다.

화장실 열쇠 하나는 뮤텍스와 비슷하다. 열쇠를 가진 사람이 사용하고 같은 사람이 반납한다. 주차장 20자리의 입장권은 세마포어와 비슷하다. 어느 차량이 특정 허가를 반납하는지보다 전체 빈자리 수가 중요하다. 다만 실제 기술에서는 뮤텍스가 메모리 접근 순서와 스레드 대기를 제공하고 세마포어가 원자적인 허가 수를 관리한다는 동작을 이해해야 한다.

## 5. 비슷한 개념과 비교

| 방식 | 적합한 대상 | 비용·주의점 |
|---|---|---|
| Lock | 복합 불변식 | 대기와 Deadlock |
| Atomic | 단일 값 갱신 | 복합 상태 한계 |
| 메시지 전달 | 소유권 분리 | 큐 지연과 역압력 |

| 구분 | Mutex | Semaphore | SpinLock |
|---|---|---|---|
| 주 목적 | 한 소유자의 상호 배제 | N개 자원·동시성 제한 | 매우 짧은 상호 배제 |
| 대기 | 보통 블로킹 가능 | 허가가 없으면 블로킹 | CPU에서 반복 |
| 소유권 | 일반적으로 있음 | 일반적으로 약함 | 구현상 락 소유 규칙 필요 |
| 적합 예시 | 인벤토리 불변식 | DB 동시 질의 20개 | 저수준 짧은 메타데이터 갱신 |
| 주요 위험 | Deadlock·Contention | Permit 누수·과다 반환 | CPU 낭비·Starvation |

조건 변수(Condition Variable)는 특정 상태가 될 때까지 뮤텍스를 풀고 잠드는 도구다. 세마포어처럼 단순 허가 수를 표현하기보다 “큐가 비어 있지 않다” 같은 조건을 공유 상태와 함께 기다릴 때 사용한다. 깨어난 뒤에도 조건을 반복 검사해야 한다.

## 6. 장점과 단점

동기화는 정합성을 지키지만 경쟁, 문맥 전환, 캐시 무효화 비용을 만든다. 공유를 줄인 뒤 단순한 도구를 적용하고 측정 결과로 세분화한다.

뮤텍스는 복합 불변식을 명확하게 보호하지만 오래 잡거나 획득 순서가 엇갈리면 지연과 교착 상태가 생긴다. 세마포어는 외부 자원에 대한 동시성을 제한해 과부하를 막지만 대기 큐가 무한히 자라지 않도록 타임아웃과 입구 제한도 필요하다. 스핀락은 짧은 구간에서 낮은 지연을 줄 수 있지만 잘못 선택하면 높은 CPU 사용률과 우선순위 역전을 만든다.

## 7. 게임 서버·백엔드 실무 예시

룸 상태는 Mutex나 단일 스레드 소유로 보호하고 DB 연결 20개는 Semaphore로 제한한다. 락 대기 시간, 큐 길이, 타임아웃과 p99 지연을 함께 관찰한다.

DB 세마포어를 20으로 제한해도 요청 큐가 무제한이면 장애 시 수천 요청이 메모리에 대기할 수 있다. 획득 타임아웃, 전체 요청 기한, 큐 상한을 두고 빠른 실패를 반환한다. 세마포어 수는 DB 풀 크기뿐 아니라 DB가 감당할 수 있는 질의 부하를 기준으로 정한다.

룸 뮤텍스의 p99 보유 시간이 갑자기 늘었다면 락 안에서 로그 출력, 직렬화, 외부 호출이 실행되는지 프로파일링한다. 평균 대기만 보면 드문 긴 임계 구역을 놓칠 수 있다. 획득 시도 횟수, 경쟁 비율, 대기와 보유 시간, 타임아웃을 구분해 기록한다.

## 8. 자주 하는 오해

- 스레드 안전 컬렉션이면 복합 비즈니스 연산도 안전하다고 본다.
- Atomic이나 volatile이 모든 경쟁을 해결한다고 본다.
- 락 범위를 크게 만들수록 좋다고 생각한다.
- 재시도를 무제한 적용한다.
- Deadlock만 없으면 안전하다고 본다.

### Q2. 대표 해결 원칙은 무엇인가요?

보호할 불변식과 소유권을 정하고 Lock, Atomic 또는 메시지 전달을 선택한다.

### Q3. 실무에서는 어떻게 적용하나요?

룸 상태는 Mutex나 단일 스레드 소유로 보호하고 DB 연결 20개는 Semaphore로 제한한다.

### Q4. 성능과 정확성을 어떻게 균형 잡나요?

공유 범위를 줄이고 단순한 동기화를 적용한 뒤 경쟁과 꼬리 지연을 측정한다.

### Q5. Mutex와 Binary Semaphore는 어떻게 다른가요?

둘 다 한 번에 하나만 통과시킬 수 있지만 뮤텍스는 일반적으로 획득한 스레드가 해제하는 소유권과 임계 구역 보호 의미가 있다. 이진 세마포어는 한 실행 흐름이 기다리고 다른 흐름이 신호를 보내는 용도로도 쓰며 허가 수 제어의 의미가 중심이다.

### Q6. SpinLock은 언제 사용하나요?

락 보유 시간이 매우 짧고 경쟁이 낮으며 코어 여유가 있어 수면·깨우기 비용이 더 클 때 측정 후 고려한다. 보유자가 I/O를 하거나 선점될 수 있고 대기가 길다면 CPU를 낭비하므로 블로킹 락이 적합하다.

### Q7. Semaphore가 과부하를 완전히 막아 주나요?

실행 중인 작업 수는 제한하지만 앞의 대기 큐가 무한하면 메모리와 지연은 계속 증가한다. 큐 상한, 획득 타임아웃, 취소와 요청 전체 기한을 함께 적용해야 한다.

> Mutex는 한 스레드의 진입을, Semaphore는 N개의 동시 접근을 제한하며 SpinLock은 짧은 대기를 CPU 반복으로 처리합니다.
