# 03. Context Switch와 CPU Scheduling


## 학습 목표

- 문맥 교환에서 저장·복원하는 내용과 실제 비용(캐시·TLB(Translation Lookaside Buffer) 손실 포함)을 설명할 수 있다.
- 자발적·비자발적 문맥 교환의 차이와 지표로 병목 원인을 구분할 수 있다.
- 대표 스케줄링 알고리즘(Round Robin·Priority·다단계 피드백 큐)의 장단점을 설명할 수 있다.
- 게임 틱 스레드 지연을 문맥 교환·실행 큐·락 대기 지표로 진단할 수 있다.

## 1. 개요

문맥 교환은 CPU(Central Processing Unit)가 현재 실행 문맥을 저장하고 다른 스레드의 문맥을 복원하는 과정이며, 스케줄링은 다음 실행 대상을 선택하는 정책이다.

## 2. 왜 필요한가

실행 가능한 작업이 CPU보다 많으므로 응답성, 처리량, 공정성, 우선순위를 조절해야 한다.

스케줄러가 없다면 CPU를 오래 사용하는 작업 하나가 다른 입력 처리와 화면 갱신을 막을 수 있다. 운영체제는 짧은 대화형 작업의 응답 시간, 전체 처리량, 장기적인 공정성, 실시간 작업의 기한처럼 서로 충돌할 수 있는 목표를 조정한다. 모든 상황에 가장 좋은 단일 정책은 없고 시스템 목적에 따라 우선순위가 달라진다.

## 3. 핵심 동작 원리

```text
실행 스레드 중단 → 레지스터·PC·스택 포인터 저장 → 스케줄러 선택 → 다음 문맥 복원 → 실행
```

선점형 스케줄링은 타이머나 우선순위로 실행을 빼앗을 수 있다. 문맥 교환 자체와 캐시·TLB 지역성 손실이 비용이며, 모드 전환이 언제나 문맥 교환을 뜻하지는 않는다.

### 문맥에는 무엇이 포함되는가

실행을 정확히 이어가려면 프로그램 카운터, 스택 포인터, 범용 레지스터, 상태 레지스터 등이 보존되어야 한다. 부동소수점과 벡터 레지스터도 작업이 사용했다면 관리 대상이 될 수 있다. 프로세스가 바뀌면 주소 공간과 관련된 페이지 테이블 문맥도 달라질 수 있다. 같은 프로세스의 스레드 교환은 주소 공간을 공유하지만 스택과 레지스터는 별도다.

문맥 교환 비용은 저장·복원 명령의 시간만이 아니다. 새 작업의 코드와 데이터가 CPU 캐시에 없으면 캐시 미스가 늘고, 주소 변환 정보가 TLB에 없으면 페이지 테이블 탐색이 필요하다. 이전 작업의 분기 예측 상태도 새 작업에 유용하지 않을 수 있다. 따라서 전환 횟수와 실제 성능의 관계는 하드웨어와 작업 집합에 따라 달라진다.

### 선점과 자발적 전환

실행 중인 스레드가 I/O(Input/Output), 조건 변수, 락을 기다리며 스스로 대기 상태가 되면 다른 스레드로 전환할 수 있다. 이를 자발적 문맥 교환으로 분류할 수 있다. 시간 할당량 만료나 더 높은 우선순위 작업 때문에 실행권을 빼앗기면 비자발적 전환이다. 두 수치를 구분하면 블로킹이 많은지 CPU 경쟁이 심한지 추론하는 데 도움이 된다.

```text
Thread A Running
   ├─ read() 대기 ─────────> Waiting ── I/O 완료 ──> Ready
   └─ Time slice 만료 ─────────────────────────────> Ready

Ready Queue ── Scheduler 선택 ──> Running
```

대기에서 깨어난 스레드는 보통 즉시 실행을 보장받는 것이 아니라 준비 상태가 되어 스케줄러 선택을 기다린다.

### 대표 스케줄링 관점

- FCFS(First-Come, First-Served): 먼저 온 작업을 먼저 처리한다. 단순하지만 긴 작업 뒤에서 짧은 작업이 오래 기다리는 Convoy Effect가 생길 수 있다.
- SJF(Shortest Job First): 실행 시간이 짧은 작업을 먼저 처리하면 평균 대기 시간을 줄일 수 있지만 실제 실행 시간을 정확히 알기 어렵고 긴 작업이 굶을 수 있다.
- Round Robin: 일정 시간 할당량만 실행한 뒤 준비 큐 뒤로 보낸다. 응답성을 높이지만 할당량이 지나치게 작으면 문맥 교환이 늘어난다.
- Priority Scheduling: 높은 우선순위 작업을 먼저 실행한다. 낮은 우선순위의 기아를 막기 위해 오래 기다린 작업의 우선순위를 높이는 Aging을 적용할 수 있다.
- 다단계 피드백 큐: 행동에 따라 작업을 여러 우선순위 큐 사이에서 이동시켜 짧고 대화형인 작업에 빠르게 반응한다.

현대 범용 운영체제는 이 교과서 알고리즘 하나만 그대로 쓰기보다 공정성, 우선순위, CPU 친화도와 다중 코어를 함께 고려한다. 면접에서는 알고리즘 이름보다 평가 기준과 트레이드오프를 설명하는 것이 중요하다.

### CPU 친화도와 다중 코어

스레드를 이전에 실행한 코어에서 계속 실행하면 따뜻한 캐시를 활용할 가능성이 있다. 이를 CPU 친화도(Affinity) 관점에서 고려한다. 그러나 특정 코어에 지나치게 고정하면 다른 코어가 놀아도 작업을 옮기지 못해 부하가 불균형해질 수 있다. 운영체제는 캐시 지역성과 부하 분산 사이에서 선택한다.

## 4. 쉬운 예시

4코어 서버에 CPU를 계속 쓰는 작업 스레드가 100개 있다면 어느 순간 실제 실행되는 스레드는 제한적이고 나머지는 준비 큐에서 기다린다. 스레드를 200개로 늘려도 코어가 늘지 않으므로 처리량이 두 배가 되지 않는다. 오히려 시간 할당 경쟁과 캐시 교체가 늘 수 있다.

```bash
# 문맥 교환 횟수 모니터링
vmstat 1 5
# cs 컬럼: 초당 문맥 교환 횟수 (급격히 높으면 스레드 경쟁 의심)

cat /proc/<pid>/status | grep ctxt_switches
# voluntary_ctxt_switches:    → I/O·락 대기 자발적 전환
# nonvoluntary_ctxt_switches: → 시간 할당 만료·선점 비자발적 전환
# 비자발적 ↑ → CPU 경쟁 심함 / 자발적 ↑ → 블로킹 작업 많음

pidstat -w -p <pid> 1  # 스레드별 문맥 교환 통계 (procps 패키지)
```

```java
// 게임 틱 루프: 틱 실행 시간 측정 + 지연 경고
public class GameTickThread extends Thread {
    private static final long TICK_BUDGET_MS = 50;  // 20 TPS
    private static final long WARN_THRESHOLD_MS = 40; // 예산의 80%

    @Override
    public void run() {
        while (!Thread.currentThread().isInterrupted()) {
            long tickStart = System.nanoTime();

            processNetworkInput();  // 네트워크 수신 큐 처리
            updateGameState();      // 물리·충돌·스킬 처리
            broadcastSnapshot();    // 클라이언트 전송

            long elapsed = (System.nanoTime() - tickStart) / 1_000_000L;

            if (elapsed > WARN_THRESHOLD_MS) {
                // 지연 원인 추적: 아래 중 하나
                // 1. CPU 과부하 → vmstat cs ↑, 실행 큐 ↑
                // 2. 락 대기    → jstack에서 BLOCKED 스레드 확인
                // 3. GC 중단   → GC 로그에서 STW 구간 확인
                log.warn("Tick overrun: {}ms / budget {}ms", elapsed, TICK_BUDGET_MS);
            }

            long sleepMs = TICK_BUDGET_MS - elapsed;
            if (sleepMs > 0) {
                try { Thread.sleep(sleepMs); } catch (InterruptedException e) { break; }
            }
        }
    }
}
```

## 5. 비슷한 개념과 비교

| 개념 | 의미 | 같은가? |
|---|---|---|
| Mode Switch | 사용자 모드 ↔ 커널 모드 권한 전환 | 같은 스레드로 복귀 가능 |
| Context Switch | 실행 주체의 문맥을 바꿈 | 다른 스레드·프로세스 실행 |
| System Call | 프로그램이 커널 기능을 요청 | 모드 전환이지만 항상 문맥 교환 아님 |
| Interrupt | 장치·타이머 등이 CPU 실행에 개입 | 처리 후 원래 작업으로 돌아갈 수 있음 |

| 스케줄링 | 장점 | 단점 |
|---|---|---|
| FCFS | 단순 | Convoy Effect (긴 작업 뒤 짧은 작업 대기) |
| Round Robin | 응답성 | 작은 할당량 → 문맥 교환 증가 |
| Priority | 중요 작업 우선 | 기아·우선순위 역전 |
| 다단계 피드백 큐 | 짧은 작업 빠른 응답 | 복잡한 구현·튜닝 |

## 6. 장점과 단점

**문맥 교환의 장점**

- 여러 작업이 CPU를 나눠 사용할 수 있어 응답성과 동시 실행이 가능하다.
- I/O 대기 중인 작업을 기다리지 않고 다른 작업을 실행해 CPU 활용률을 높인다.

**문맥 교환의 단점**

- 레지스터 저장·복원 시간 외에 CPU 캐시·TLB·분기 예측 상태 손실 비용이 크다.
- 스레드 수가 코어 수를 크게 초과하면 교환 비용이 처리량 증가를 상쇄한다.

**스케줄링 정책의 장점**

- 응답 시간·처리량·공정성·우선순위 목표에 맞게 조정할 수 있다.

**스케줄링 정책의 단점**

- 우선순위 설계 미흡 시 기아(Starvation)·우선순위 역전(Priority Inversion)이 발생한다.
- 실제 실행 시간 예측이 어려워 최적 알고리즘 선택이 복잡하다.

## 7. 게임 서버·백엔드 실무 예시

게임 틱 스레드가 과도한 작업이나 락 대기로 밀리면 틱 지연이 생긴다. CPU 사용률뿐 아니라 실행 큐, 문맥 교환률, 코어별 부하와 p99 틱 시간을 함께 본다.

틱 스레드의 기한이 50ms라면 평균 10ms보다 최악 구간이 기한을 넘는지가 중요하다. 코어별 CPU가 꽉 차고 비자발적 전환과 실행 큐가 증가하면 CPU 경쟁을 의심한다. CPU는 낮은데 자발적 전환과 락 대기가 많다면 공유 자원이나 I/O 대기가 원인일 수 있다. 프로파일러로 실제 CPU 함수와 대기 스택을 함께 확인한다.

우선순위를 높이면 중요한 스레드가 빨리 실행될 가능성은 커지지만 과도한 우선순위는 다른 필수 작업을 굶길 수 있다. 높은 우선순위 스레드가 낮은 우선순위 스레드의 락을 기다리는 우선순위 역전도 생길 수 있다. 따라서 우선순위만 조정하기 전에 긴 임계 구역과 작업 분배를 개선한다.

## 8. 자주 하는 오해

- **"CPU 사용률이 낮으면 서버에 병목이 없다"**: 락 대기·I/O 대기·GC 중단 때문에 CPU는 낮아도 응답 지연이 클 수 있다. 실행 큐·자발적 문맥 교환·꼬리 지연을 함께 확인해야 한다.
- **"스레드를 늘리면 처리량이 항상 증가한다"**: 코어 수를 초과한 스레드는 CPU를 다투고 문맥 교환과 캐시 손실을 늘린다. CPU 바운드 작업은 코어 수 기준으로 제한한다.
- **"모든 시스템 콜이 문맥 교환을 일으킨다"**: 시스템 콜은 모드 전환이지 문맥 교환이 아니다. 처리 후 같은 스레드가 계속 실행될 수 있다. I/O 블로킹 같이 대기가 필요할 때 문맥 교환이 발생한다.
- **"우선순위를 높이면 항상 빨리 실행된다"**: 높은 우선순위 스레드가 낮은 우선순위 스레드가 보유한 락을 기다리면 우선순위 역전이 발생한다. 우선순위 조정 전에 임계 구역 길이를 먼저 줄인다.
- **"문맥 교환 비용은 레지스터 저장·복원 시간뿐이다"**: 새 스레드의 코드·데이터가 캐시에 없는 Cold Cache, TLB 미스, 분기 예측 오염이 레지스터 조작보다 더 큰 비용이 될 수 있다.
- **"자발적·비자발적 문맥 교환은 같은 현상이다"**: 자발적(블로킹·I/O 대기)은 공유 자원 경쟁이나 I/O 설계 문제이고, 비자발적(시간 할당 만료·선점)은 CPU 경쟁 심화를 의미한다. 원인이 달라 대응 방법이 다르다.
- **"Round Robin은 항상 공정하다"**: 시간 할당량 단위로 공정하지만 처리 비용이 크게 다른 작업에서는 짧은 작업이 불필요하게 오래 기다린다. 처리량 관점에서는 작업 특성에 맞는 알고리즘이 필요하다.

## 9. 면접 질문

### Q1. 문맥 교환에서 저장·복원하는 것은 무엇인가요?

프로그램 카운터(PC), 스택 포인터, 범용 레지스터, 상태 레지스터다. 부동소수점·벡터 레지스터도 포함될 수 있다. 프로세스 교환 시에는 페이지 테이블 관련 정보도 전환된다. 이 외에 캐시·TLB 지역성 손실이 추가 비용으로 발생한다.

### Q2. 자발적·비자발적 문맥 교환의 차이는 무엇인가요?

자발적 전환은 I/O·락·조건 변수 대기처럼 스레드 스스로 CPU를 놓을 때 발생한다. 비자발적 전환은 시간 할당량 만료나 더 높은 우선순위 작업에 의해 실행권을 빼앗길 때 발생한다. 비자발적 전환이 많으면 CPU 경쟁, 자발적 전환이 많으면 블로킹 작업이 원인이다.

### Q3. 모드 전환과 문맥 교환은 같은가요?

아니다. 시스템 콜로 사용자 모드에서 커널 모드로 바뀌어도 처리 후 같은 스레드가 계속 실행될 수 있다. 문맥 교환은 현재 실행 주체의 상태를 저장하고 다른 스레드나 프로세스의 상태를 복원해 실행 대상을 바꾸는 과정이다.

### Q4. Round Robin의 시간 할당량이 너무 작거나 크면 어떻게 되나요?

너무 작으면 응답성은 좋아질 수 있지만 문맥 교환 오버헤드가 커진다. 너무 크면 FCFS에 가까워져 CPU를 오래 쓰는 작업 뒤의 짧은 작업이 기다린다. 작업 특성과 응답 목표에 맞춰 균형을 잡는다.

### Q5. 게임 틱 스레드 지연의 원인을 어떻게 구분하나요?

비자발적 문맥 교환 증가 + 실행 큐 증가 → CPU 경쟁. 자발적 전환 증가 + CPU 낮음 → 락 대기·I/O. GC 중단 시간과 틱 지연 시간이 겹치면 GC가 원인. 프로파일러로 CPU 함수와 대기 스택을 동시에 확인한다.

### Q6. 우선순위 역전이란 무엇이며 어떻게 대응하나요?

높은 우선순위 스레드가 낮은 우선순위 스레드가 보유한 락을 기다려 실질적으로 낮은 우선순위로 실행되는 현상이다. 우선순위 상속(Priority Inheritance)으로 락 보유 스레드에 일시적으로 높은 우선순위를 부여하거나, 임계 구역을 짧게 유지해 발생 자체를 줄인다.

## 10. 예상 꼬리질문

- CPU 친화도(Affinity)의 장단점은 무엇인가요?
  > 특정 코어에 고정하면 이전 실행에서 데워진 캐시를 재사용할 가능성이 높아 캐시 미스가 줄어든다. 단, 과도하게 고정하면 다른 코어가 유휴 상태여도 작업을 이동하지 못해 부하가 불균형해지고 전체 처리량이 낮아진다.
- Convoy Effect는 어떤 상황에서 발생하나요?
  > FCFS(First-Come, First-Served) 스케줄링에서 CPU 사용 시간이 긴 작업이 먼저 실행될 때, 뒤에 대기 중인 짧은 작업들이 오랫동안 기다리는 현상이다. 긴 작업이 CPU를 독점하는 동안 I/O 장치도 유휴 상태가 되어 자원 활용률도 낮아진다.
- 다단계 피드백 큐는 어떻게 작동하나요?
  > 새 작업은 높은 우선순위 큐에 진입하고, 할당된 시간을 다 사용하면 우선순위가 낮은 큐로 이동한다. 짧게 끝나는 대화형 작업은 높은 우선순위 큐에 머물러 빠르게 처리되고, CPU를 오래 사용하는 배치 작업은 아래 큐로 내려가 낮은 우선순위로 실행된다.
- 선점형과 비선점형 스케줄링의 차이는 무엇인가요?
  > 선점형(Preemptive)은 타이머나 높은 우선순위 작업이 현재 실행 중인 프로세스를 강제로 중단시킬 수 있다. 비선점형(Non-preemptive)은 실행 중인 프로세스가 스스로 CPU를 반납하거나 종료할 때까지 기다려야 한다. 현대 OS는 응답성을 위해 대부분 선점형을 사용한다.
- Aging은 왜 필요한가요?
  > 우선순위 기반 스케줄링에서 낮은 우선순위 작업이 높은 우선순위 작업에 계속 밀려 CPU를 받지 못하는 기아(Starvation)를 방지하기 위해서다. 대기 시간이 길어질수록 우선순위를 점진적으로 높여 결국 실행 기회를 보장한다.
- 자발적 문맥 교환이 많을 때 무엇을 확인하나요?
  > I/O 대기, 락 경합, 조건 변수 대기 등 블로킹 원인을 확인한다. jstack으로 WAITING·TIMED_WAITING 상태 스레드를 파악하고, DB 응답 시간과 외부 API 지연, 공유 자원 경쟁 여부를 점검한다.
- 문맥 교환 비용이 캐시·TLB에서 오는 이유는 무엇인가요?
  > 새 스레드로 전환하면 이전 스레드가 데워놓은 L1·L2 캐시와 TLB 항목이 새 스레드의 코드·데이터와 맞지 않아 미스가 증가한다. 레지스터 저장·복원은 수십 사이클이지만, 캐시와 TLB 워밍업은 수천 사이클의 추가 지연을 만들 수 있어 전체 문맥 교환 비용에서 더 큰 비중을 차지한다.

## 11. 30초 모범답변

> CPU 스케줄러는 준비 큐에서 다음 스레드를 선택하고 문맥 교환으로 실행 상태를 바꿉니다. 문맥 교환 비용은 레지스터 저장·복원만이 아니라 캐시·TLB 지역성 손실이 더 크므로, 스레드를 무작정 늘리면 처리량이 오히려 낮아질 수 있습니다. 게임 틱 스레드 지연은 자발적·비자발적 문맥 교환 수치로 블로킹 또는 CPU 경쟁을 구분해 진단합니다.

## 12. 1~2분 확장답변

> CPU 스케줄러는 준비 큐에서 다음 스레드를 선택하고 문맥 교환으로 실행 상태를 바꿉니다. 문맥 교환에는 레지스터 저장·복원 외에 새 스레드의 캐시 미스·TLB 미스 비용이 추가됩니다. 스레드가 I/O·락을 기다리면 자발적으로 CPU를 내놓고, 시간 할당량이 만료되거나 더 높은 우선순위 작업이 오면 비자발적으로 빼앗깁니다. 게임 서버에서는 비자발적 전환이 급증하면 CPU 경쟁, 자발적 전환이 많으면 블로킹을 의심합니다. 우선순위를 높이기 전에 임계 구역을 줄이고 작업을 분리하는 것이 더 근본적인 해결입니다.

## 13. 핵심 요약

- 문맥 교환은 PC·레지스터·스택 포인터를 저장하고 다음 스레드의 문맥을 복원한다.
- 문맥 교환 비용은 저장·복원만이 아니다. 캐시·TLB·분기 예측 손실이 더 크다.
- 자발적 전환(I/O·락 대기)은 블로킹 원인, 비자발적 전환(선점)은 CPU 경쟁 원인을 나타낸다.
- 모드 전환(System Call)은 문맥 교환과 다르다. 처리 후 같은 스레드로 복귀 가능하다.
- 스케줄링 알고리즘은 응답 시간·처리량·공정성을 동시에 최적화할 수 없다. 목표에 맞게 선택한다.
- 우선순위 역전: 높은 우선순위 스레드가 낮은 쪽의 락을 기다리는 현상. 임계 구역 단축이 근본 해결이다.
- 틱 지연 진단: 비자발적 전환 ↑ → CPU 경쟁 / 자발적 전환 ↑ → 블로킹 / GC 중단과 겹침 → GC 원인.
- CPU 사용률이 낮아도 지연이 크다면 락 대기·I/O·GC 중단을 실행 큐·꼬리 지연과 함께 확인한다.

## 한 줄 정리

> 문맥 교환의 진짜 비용은 레지스터 저장이 아니라 캐시·TLB 손실이며, 자발적·비자발적 교환 수치로 병목 원인을 구분한다.
