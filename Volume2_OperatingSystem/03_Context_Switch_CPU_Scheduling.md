# 03. Context Switch와 CPU Scheduling

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 핵심 정의와 등장 이유를 설명할 수 있다.
- 대표 동작 과정과 유사 개념의 차이를 설명할 수 있다.
- 게임 서버 장애와 설계에 적용할 수 있다.

## 1. 개요

문맥 교환은 CPU가 현재 실행 문맥을 저장하고 다른 스레드의 문맥을 복원하는 과정이며, 스케줄링은 다음 실행 대상을 선택하는 정책이다.

## 2. 왜 필요한가

실행 가능한 작업이 CPU보다 많으므로 응답성, 처리량, 공정성, 우선순위를 조절해야 한다.

운영체제는 제한된 CPU와 메모리를 여러 작업에 안전하고 효율적으로 나누어야 한다. 개발자는 추상화가 감추는 비용과 공유 범위를 알아야 성능 저하와 동시성 버그를 진단할 수 있다.

스케줄러가 없다면 CPU를 오래 사용하는 작업 하나가 다른 입력 처리와 화면 갱신을 막을 수 있다. 운영체제는 짧은 대화형 작업의 응답 시간, 전체 처리량, 장기적인 공정성, 실시간 작업의 기한처럼 서로 충돌할 수 있는 목표를 조정한다. 모든 상황에 가장 좋은 단일 정책은 없고 시스템 목적에 따라 우선순위가 달라진다.

## 3. 핵심 동작 원리

```text
실행 스레드 중단 → 레지스터·PC·스택 포인터 저장 → 스케줄러 선택 → 다음 문맥 복원 → 실행
```

운영체제는 사용자 프로그램이 직접 하드웨어와 다른 프로세스의 자원을 침범하지 않도록 권한과 상태를 관리한다. 실행 단위가 대기하면 다른 준비 작업을 실행하고, 다시 실행할 때 필요한 문맥을 복원한다.

선점형 스케줄링은 타이머나 우선순위로 실행을 빼앗을 수 있다. 문맥 교환 자체와 캐시·TLB 지역성 손실이 비용이며, 모드 전환이 언제나 문맥 교환을 뜻하지는 않는다.

### 문맥에는 무엇이 포함되는가

실행을 정확히 이어가려면 프로그램 카운터, 스택 포인터, 범용 레지스터, 상태 레지스터 등이 보존되어야 한다. 부동소수점과 벡터 레지스터도 작업이 사용했다면 관리 대상이 될 수 있다. 프로세스가 바뀌면 주소 공간과 관련된 페이지 테이블 문맥도 달라질 수 있다. 같은 프로세스의 스레드 교환은 주소 공간을 공유하지만 스택과 레지스터는 별도다.

문맥 교환 비용은 저장·복원 명령의 시간만이 아니다. 새 작업의 코드와 데이터가 CPU 캐시에 없으면 캐시 미스가 늘고, 주소 변환 정보가 TLB에 없으면 페이지 테이블 탐색이 필요하다. 이전 작업의 분기 예측 상태도 새 작업에 유용하지 않을 수 있다. 따라서 전환 횟수와 실제 성능의 관계는 하드웨어와 작업 집합에 따라 달라진다.

### 선점과 자발적 전환

실행 중인 스레드가 I/O, 조건 변수, 락을 기다리며 스스로 대기 상태가 되면 다른 스레드로 전환할 수 있다. 이를 자발적 문맥 교환으로 분류할 수 있다. 시간 할당량 만료나 더 높은 우선순위 작업 때문에 실행권을 빼앗기면 비자발적 전환이다. 두 수치를 구분하면 블로킹이 많은지 CPU 경쟁이 심한지 추론하는 데 도움이 된다.

```text
Thread A Running
   ├─ read() 대기 ─────────> Waiting ── I/O 완료 ──> Ready
   └─ Time slice 만료 ─────────────────────────────> Ready

Ready Queue ── Scheduler 선택 ──> Running
```

대기에서 깨어난 스레드는 보통 즉시 실행을 보장받는 것이 아니라 준비 상태가 되어 스케줄러 선택을 기다린다.

### 대표 스케줄링 관점

- FCFS(First-Come, First-Served): 먼저 온 작업을 먼저 처리한다. 단순하지만 긴 작업 뒤에서 짧은 작업이 오래 기다리는 Convoy Effect가 생길 수 있다.
- SJF(Shortest Job First): 실행 시간이 짧은 작업을 먼저 처리하면 평균 대기 시간을 줄일 수 있지만 실제 실행 시간을 정확히 알기 어렵고 긴 작업이 굶을 수 있다.
- Round Robin: 일정 시간 할당량만 실행한 뒤 준비 큐 뒤로 보낸다. 응답성을 높이지만 할당량이 지나치게 작으면 문맥 교환이 늘어난다.
- Priority Scheduling: 높은 우선순위 작업을 먼저 실행한다. 낮은 우선순위의 기아를 막기 위해 오래 기다린 작업의 우선순위를 높이는 Aging을 적용할 수 있다.
- 다단계 피드백 큐: 행동에 따라 작업을 여러 우선순위 큐 사이에서 이동시켜 짧고 대화형인 작업에 빠르게 반응한다.

현대 범용 운영체제는 이 교과서 알고리즘 하나만 그대로 쓰기보다 공정성, 우선순위, CPU 친화도와 다중 코어를 함께 고려한다. 면접에서는 알고리즘 이름보다 평가 기준과 트레이드오프를 설명하는 것이 중요하다.

### CPU 친화도와 다중 코어

스레드를 이전에 실행한 코어에서 계속 실행하면 따뜻한 캐시를 활용할 가능성이 있다. 이를 CPU 친화도(Affinity) 관점에서 고려한다. 그러나 특정 코어에 지나치게 고정하면 다른 코어가 놀아도 작업을 옮기지 못해 부하가 불균형해질 수 있다. 운영체제는 캐시 지역성과 부하 분산 사이에서 선택한다.

## 4. 쉬운 예시

게임 서버가 네트워크 입력을 기다리는 동안 랭킹 요청을 처리하면 여러 작업이 진전된다. CPU 계산을 여러 코어에 분배하면 실제 동시 실행도 가능하다. 다만 같은 플레이어 상태를 함께 변경한다면 순서와 동기화를 정의해야 한다.

4코어 서버에 CPU를 계속 쓰는 작업 스레드가 100개 있다면 어느 순간 실제 실행되는 스레드는 제한적이고 나머지는 준비 큐에서 기다린다. 스레드를 200개로 늘려도 코어가 늘지 않으므로 처리량이 두 배가 되지 않는다. 오히려 시간 할당 경쟁과 캐시 교체가 늘 수 있다. 반면 대부분의 작업이 외부 DB 응답을 기다린다면 CPU 사용률은 낮아도 대기 때문에 요청 지연이 커질 수 있다.

## 5. 비슷한 개념과 비교

| 구분 | 핵심 | 주의점 |
|---|---|---|
| 프로세스 수준 | 주소 공간과 자원 격리 | 생성·통신 비용 |
| 스레드 수준 | 자원 공유와 실행 흐름 | 경쟁 상태·동기화 |
| 운영체제 관리 | 보호와 스케줄링 | 전환·캐시 비용 |

개념 이름보다 무엇을 공유하고 누가 실행 순서를 결정하는지 설명하는 것이 중요하다.

| 개념 | 의미 | 같은가? |
|---|---|---|
| Mode Switch | 사용자 모드와 커널 모드 권한 전환 | 같은 스레드로 복귀할 수 있음 |
| Context Switch | 실행 주체의 문맥을 바꿈 | 다른 스레드·프로세스 실행 |
| System Call | 프로그램이 커널 기능을 요청 | 모드 전환은 있지만 항상 문맥 교환은 아님 |
| Interrupt | 장치·타이머 등이 CPU 실행에 개입 | 처리 후 원래 작업으로 돌아갈 수 있음 |

## 6. 장점과 단점

운영체제 추상화는 격리, 자원 공유, 응답성과 처리량을 제공한다. 반면 관리 구조, 스케줄링, 문맥 교환, 동기화에는 비용이 있다. 작업 수를 늘리는 것만으로 성능이 비례해 증가하지 않는다.

## 7. 게임 서버·백엔드 실무 예시

게임 틱 스레드가 과도한 작업이나 락 대기로 밀리면 틱 지연이 생긴다. CPU 사용률뿐 아니라 실행 큐, 문맥 교환률, 코어별 부하와 p99 틱 시간을 함께 본다.

관찰할 때는 평균 CPU만 보지 않고 스레드 수, 실행 큐, 문맥 교환, 메모리, 락 대기와 꼬리 지연을 같은 시간축에서 확인한다.

틱 스레드의 기한이 50ms라면 평균 10ms보다 최악 구간이 기한을 넘는지가 중요하다. 코어별 CPU가 꽉 차고 비자발적 전환과 실행 큐가 증가하면 CPU 경쟁을 의심한다. CPU는 낮은데 자발적 전환과 락 대기가 많다면 공유 자원이나 I/O 대기가 원인일 수 있다. 프로파일러로 실제 CPU 함수와 대기 스택을 함께 확인한다.

우선순위를 높이면 중요한 스레드가 빨리 실행될 가능성은 커지지만 과도한 우선순위는 다른 필수 작업을 굶길 수 있다. 높은 우선순위 스레드가 낮은 우선순위 스레드의 락을 기다리는 우선순위 역전도 생길 수 있다. 따라서 우선순위만 조정하기 전에 긴 임계 구역과 작업 분배를 개선한다.

## 8. 자주 하는 오해

- 실행 단위와 자원 소유 단위를 같은 개념으로 본다.
- 스레드를 늘리면 처리량이 항상 증가한다고 생각한다.
- 비동기와 병렬 실행을 같은 의미로 사용한다.
- CPU 사용률이 낮으면 서버에 병목이 없다고 단정한다.
- 운영체제 추상화의 비용은 무시해도 된다고 생각한다.

### 최종 실무 판단 기준

- **요구 확인**: 문맥 교환은 CPU가 현재 실행 문맥을 저장하고 다른 스레드의 문맥을 복원하는 과정이며, 스케줄링은 다음 실행 대상을 선택하는 정책이다. 이 내용을 적용하기 전에 데이터 규모, 호출 빈도와 허용 지연을 수치로 확인한다. 같은 기술도 요청량과 정확성 요구가 달라지면 적합한 선택이 달라질 수 있다.
- **정확성 경계**: 필요한 이유는 제한된 자원의 보호와 효율적 사용이다. 정상 흐름만 설명하지 않고 중복, 역순, 동시 실행과 부분 실패에서 어떤 불변식을 지켜야 하는지 함께 명시한다.
- **비용 비교**: 공유 범위와 실행 단위를 구분해야 한다. 평균 복잡도나 처리량 하나만 보지 않고 Memory, CPU, I/O, Lock 대기와 구현 복잡도까지 비교한다.
- **장애 대응**: Context Switch와 CPU Scheduling 관련 구성 요소가 느려지거나 중단됐을 때 Timeout, Retry 상한, Backpressure와 복구 순서를 정한다. Retry가 중복 부작용이나 연쇄 부하를 만들지 검증한다.
- **운영 검증**: Context Switch와 CPU Scheduling에서는 기능 Test와 함께 경계값, Peak 부하와 장애 주입 Test를 수행한다. 처리 시간 p95·p99, 오류율, Queue와 Resource 사용량을 관찰하고 변경 전후 결과를 비교한다.

Context Switch와 CPU Scheduling 답변에서는 이 기준으로 답하면 개념 정의에 그치지 않고 선택 조건, Trade-off와 실무 검증 방법까지 논리적으로 연결할 수 있다.

## 9. 면접 질문

### Q1. 핵심 개념을 한 문장으로 설명해 주세요.

문맥 교환은 CPU가 현재 실행 문맥을 저장하고 다른 스레드의 문맥을 복원하는 과정이며, 스케줄링은 다음 실행 대상을 선택하는 정책이다.

### Q2. 왜 필요한가요?

실행 가능한 작업이 CPU보다 많으므로 응답성, 처리량, 공정성, 우선순위를 조절해야 한다.

### Q3. 게임 서버에서는 어떻게 적용하나요?

게임 틱 스레드가 과도한 작업이나 락 대기로 밀리면 틱 지연이 생긴다. CPU 사용률뿐 아니라 실행 큐, 문맥 교환률, 코어별 부하와 p99 틱 시간을 함께 본다.

### Q4. 성능 문제는 무엇을 확인하나요?

CPU 사용률과 함께 실행 큐, 전환 횟수, 대기 원인, 메모리와 p95·p99 지연을 확인한다.

### Q5. 모드 전환과 문맥 교환은 같은가요?

아니다. 시스템 콜로 사용자 모드에서 커널 모드로 바뀌어도 처리 후 같은 스레드가 계속 실행될 수 있다. 문맥 교환은 현재 실행 주체의 상태를 저장하고 다른 스레드나 프로세스의 상태를 복원해 실행 대상을 바꾸는 과정이다.

### Q6. Round Robin의 시간 할당량이 너무 작거나 크면 어떻게 되나요?

너무 작으면 응답성은 좋아질 수 있지만 문맥 교환 오버헤드가 커진다. 너무 크면 FCFS에 가까워져 CPU를 오래 쓰는 작업 뒤의 짧은 작업이 기다린다. 작업 특성과 응답 목표에 맞춰 균형을 잡는다.

## 13. 핵심 요약

- 문맥 교환은 CPU가 현재 실행 문맥을 저장하고 다른 스레드의 문맥을 복원하는 과정이며, 스케줄링은 다음 실행 대상을 선택하는 정책이다.
- 필요한 이유는 제한된 자원의 보호와 효율적 사용이다.
- 공유 범위와 실행 단위를 구분해야 한다.
- 동시 실행에는 전환과 동기화 비용이 따른다.
- 게임 서버에서는 지표와 꼬리 지연으로 실제 병목을 확인한다.
- 모드 전환, 시스템 콜, 문맥 교환은 서로 관련되지만 같은 사건은 아니다.
