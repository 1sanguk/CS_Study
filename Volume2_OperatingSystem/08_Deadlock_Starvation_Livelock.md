# 08. Deadlock, Starvation, Livelock


## 학습 목표

- Deadlock, Starvation, Livelock의 차이와 각각의 특징적인 증상을 설명할 수 있다.
- Deadlock의 네 가지 필요조건과 각각 깨는 방법을 설명할 수 있다.
- 타임아웃만으로 Deadlock을 해결할 수 없는 이유와 올바른 설계를 설명할 수 있다.
- 게임 서버에서 플레이어 간 거래 시 Deadlock을 방지하기 위한 락 순서 설계를 설명할 수 있다.

## 1. 개요

Deadlock은 순환 대기로 멈추고 Starvation은 특정 작업이 기회를 못 얻으며 Livelock은 상태만 바뀌고 진전이 없는 문제이다.

교착 상태(Deadlock)는 작업 집합이 서로가 가진 자원이나 사건을 기다려 어느 작업도 진행할 수 없는 상태다. 기아(Starvation)는 시스템 전체는 계속 진행하지만 특정 작업이 자원이나 CPU 기회를 오랫동안 얻지 못하는 상태다. 라이브락(Livelock)은 작업들이 멈춰 있지는 않고 서로에게 반응해 상태를 계속 바꾸지만 유용한 완료 상태에 도달하지 못하는 현상이다.

세 문제는 모두 "요청이 끝나지 않는다"로 보일 수 있지만 원인과 해결이 다르다. 스레드 덤프, CPU 사용량, 상태 변화와 완료율을 함께 봐야 구분할 수 있다.

## 2. 왜 필요한가

여러 락과 재시도가 상호작용하면 CPU가 살아 있어도 요청이 끝나지 않는다.

게임 서버는 플레이어, 길드, 거래소, DB 연결처럼 여러 자원을 한 요청에서 다룬다. 각 자원을 개별적으로 안전하게 잠갔더라도 획득 순서가 다르면 전체 시스템이 멈출 수 있다. 장애를 피하려고 모든 충돌에서 즉시 양보하고 재시도하면 라이브락이 될 수 있고, 높은 우선순위 요청만 계속 통과시키면 낮은 우선순위 작업이 굶을 수 있다.

## 3. 핵심 동작 원리

```text
Thread A: Lock1 획득 → Lock2 대기
Thread B: Lock2 획득 → Lock1 대기
→ 순환 대기: 두 스레드 모두 진행 불가
```

락 순서를 고정하고 임계 구역을 줄이며 타임아웃과 제한된 백오프를 둔다.

### Deadlock의 네 가지 필요조건

교착 상태에는 네 조건이 동시에 필요하다 (Coffman 조건).

1. 상호 배제(Mutual Exclusion): 자원을 한 번에 한 작업만 사용할 수 있다.
2. 점유 대기(Hold and Wait): 이미 자원을 가진 채 다른 자원을 기다린다.
3. 비선점(No Preemption): 다른 작업이 가진 자원을 강제로 빼앗을 수 없다.
4. 순환 대기(Circular Wait): 작업과 자원의 대기 관계가 원을 이룬다.

이 중 하나를 구조적으로 깨면 교착 상태를 예방할 수 있다. 전역 락 순서 고정은 순환 대기를 없애는 가장 실용적인 방법이다.

### 예방, 회피, 탐지와 복구

- 예방(Prevention): 네 필요조건 중 하나가 성립하지 않게 설계한다. 전역 락 순서 규칙이 실무에서 자주 쓰인다.
- 회피(Avoidance): 자원 할당 후에도 안전 상태인지 판단해 위험한 할당을 미룬다. 은행원 알고리즘이 교과서 예지만 일반 애플리케이션 락에 그대로 적용하는 경우는 드물다.
- 탐지와 복구: 대기 그래프의 순환을 찾고 작업 하나를 취소하거나 트랜잭션을 롤백해 순환을 끊는다. DB가 교착 트랜잭션 하나를 희생자로 선택하는 방식이 대표적이다.

### 타임아웃은 완전한 예방이 아니다

락 획득 타임아웃은 영구 대기를 끊고 오류를 드러내는 데 유용하다. 하지만 이미 변경한 상태를 되돌리지 않고 중간에 포기하면 정합성이 깨질 수 있다. 두 작업이 같은 주기로 타임아웃되고 즉시 다시 시도하면 라이브락이나 부하 증폭이 생긴다. 타임아웃은 취소 가능한 경계, 롤백, 제한된 재시도와 함께 설계한다.

### Starvation

불공정한 락에서 같은 빠른 스레드가 반복 획득하거나, 우선순위 스케줄링에서 높은 우선순위 작업이 계속 들어오면 낮은 우선순위 작업이 기아 상태가 될 수 있다. Readers-Writer Lock이 읽기를 계속 우선하면 쓰기 작업이 오래 기다릴 수도 있다. 공정한 큐, Aging, 읽기·쓰기 우선 정책 조정, 작업별 할당량으로 완화한다.

### Livelock

두 트랜잭션이 충돌을 감지할 때마다 동시에 롤백하고 같은 간격으로 즉시 재시도해 계속 충돌하는 경우다. CPU와 로그는 활발하지만 완료율이 낮다.

```text
A 충돌 → 양보 → 즉시 재시도 ─┐
B 충돌 → 양보 → 즉시 재시도 ─┴─ 같은 패턴 반복, 완료 0
```

무작위 지연이 포함된 지수 백오프, 우선순위나 승자 결정 규칙, 재시도 횟수 제한으로 대칭을 깨뜨린다.

## 4. 쉬운 예시

```java
// BAD: 획득 순서가 달라 교착 상태 발생
// Thread 1: player10 → player20 순서로 획득 시도
lockA.lock(); // player10 획득
// Thread 2: player20 → player10 순서로 획득 시도
lockB.lock(); // player20 획득
// Thread 1: player20 대기 (Thread 2가 보유 중)
// Thread 2: player10 대기 (Thread 1이 보유 중)
// → 순환 대기: 두 스레드 모두 영원히 진행 불가
```

```java
// GOOD: 락 순서 고정으로 순환 대기 제거
public boolean tradeItems(String fromId, String toId, Item item) {
    // 항상 ID가 작은 쪽을 먼저 획득 → 두 스레드가 같은 순서로 시도 → 순환 없음
    String firstId = fromId.compareTo(toId) < 0 ? fromId : toId;
    String secondId = fromId.compareTo(toId) < 0 ? toId : fromId;

    ReentrantLock first = playerLocks.get(firstId);
    ReentrantLock second = playerLocks.get(secondId);

    boolean gotFirst = false, gotSecond = false;
    try {
        gotFirst = first.tryLock(500, TimeUnit.MILLISECONDS);
        if (!gotFirst) return false;  // 빠른 실패, 중간 상태 없음
        gotSecond = second.tryLock(500, TimeUnit.MILLISECONDS);
        if (!gotSecond) return false;

        return executeTransfer(fromId, toId, item);
    } finally {
        if (gotSecond) second.unlock(); // 역순 해제
        if (gotFirst) first.unlock();
    }
}
```

```java
// Livelock 예시: 지수 백오프 없이 즉시 재시도 → 같은 충돌 반복
// BAD: 무제한 즉시 재시도
while (true) {
    if (tryAcquireBoth(lockA, lockB)) break;
    // 둘 다 즉시 재시도 → Thread A와 B가 동시에 재시도해 계속 충돌
}

// GOOD: 지수 백오프 + 무작위 지연 + 재시도 상한
int attempts = 0;
while (attempts++ < MAX_RETRIES) {
    if (tryAcquireBoth(lockA, lockB)) break;
    long backoff = (1L << attempts) * 10 + ThreadLocalRandom.current().nextLong(10);
    Thread.sleep(Math.min(backoff, 1000)); // 상한 1초
}
if (attempts >= MAX_RETRIES) throw new DeadlineExceededException();
```

## 5. 비슷한 개념과 비교

| 구분 | 작업 상태 | 시스템 전체 | 대표 징후 |
|---|---|---|---|
| Deadlock | 대기하며 멈춤 | 관련 작업 집합 정지 | 스레드 덤프 순환, 낮은 CPU |
| Starvation | 특정 작업이 기회 없음 | 다른 작업은 완료 | 일부 요청 대기 시간 지속 증가 |
| Livelock | 계속 반응·재시도 | 유용한 완료 없음 | 높은 CPU·로그 활발, 완료율 저하 |
| Contention | 결국 획득 가능 | 느리지만 진행 | 락 대기 증가, 순환 없음 |

| Deadlock 예방 방법 | 깨는 조건 | 비용 |
|---|---|---|
| 전역 락 순서 고정 | 순환 대기 | 규칙 유지 부담 |
| 모든 락 한 번에 요청 | 점유 대기 | 보유 범위·경쟁 증가 |
| 타임아웃 + 롤백 | 비선점 완화 | 복잡한 취소 로직 |
| DB 트랜잭션 희생자 선택 | 탐지 후 복구 | 롤백된 작업 재처리 |

## 6. 장점과 단점

**전역 락 순서 고정의 장점**

- 순환 대기를 구조적으로 없애 교착 상태를 예방한다.
- 이해하기 쉽고 추가 런타임 비용이 없다.

**전역 락 순서 고정의 단점**

- 모든 팀과 코드 경로가 규칙을 지켜야 한다. 규칙을 어기는 경로 하나가 교착을 만든다.
- 자원 집합이 동적으로 늘어나면 순서 유지가 복잡해진다.

**타임아웃의 장점**

- 영구 대기를 끊고 복구 기회를 준다.

**타임아웃의 단점**

- 원인을 없애지 않는다. 타임아웃 후 롤백 없이 포기하면 정합성이 깨진다.
- 양쪽이 동시에 재시도하면 Livelock이 된다.

## 7. 게임 서버·백엔드 실무 예시

거래 시 두 인벤토리 락을 플레이어 ID 순으로 얻고 DB 데드락 재시도에는 상한을 둔다. 락 대기 시간, 큐 길이, 타임아웃과 p99 지연을 함께 관찰한다.

DB가 교착 트랜잭션을 롤백하면 애플리케이션은 전체 트랜잭션을 처음부터 재시도해야 한다. 동일한 레코드를 같은 순서로 갱신하고 트랜잭션을 짧게 유지하면 빈도를 줄일 수 있다. 재시도에는 지수 백오프와 무작위 지연, 최대 횟수와 전체 요청 기한을 둔다. 외부 결제 호출을 DB 트랜잭션 안에서 기다리지 않는다.

운영에서는 스레드 덤프를 한 번만 보기보다 일정 간격으로 여러 번 수집해 같은 대기가 지속되는지 확인한다. CPU가 높다면 재시도 루프와 Livelock을, 낮은데 요청이 멈췄다면 Deadlock을 우선 의심하되 스레드 덤프로 확인한다.

## 8. 자주 하는 오해

- **"타임아웃을 두면 Deadlock이 해결된다"**: 영구 대기를 끊지만 원인을 없애지 않는다. 타임아웃 후 중간 상태 롤백 없이 포기하면 정합성이 깨지고, 양쪽이 동시에 재시도하면 Livelock이 된다.
- **"Deadlock만 없으면 동시성이 안전하다"**: Starvation, Livelock, 경쟁 상태, 메모리 가시성 문제가 여전히 발생할 수 있다.
- **"CPU가 높으면 Deadlock이 아니다"**: Livelock에서는 CPU가 높고 계속 재시도하지만 완료 상태에 도달하지 못한다. CPU 상태만으로 구분하면 오진할 수 있다.
- **"재시도하면 결국 성공한다"**: 백오프 상한과 전체 기한 없이 무제한 재시도하면 Livelock이나 부하 증폭이 생긴다.
- **"락 타임아웃만 걸면 정합성이 유지된다"**: 타임아웃 시 이미 변경한 상태를 되돌리지 않으면 중간 상태가 남는다. 롤백 설계가 함께 필요하다.
- **"Reader 우선 Lock은 성능이 좋다"**: 읽기가 계속 들어오면 쓰기 작업이 오랫동안 기회를 얻지 못하는 Writer Starvation이 생긴다.
- **"전역 락 순서 규칙으로 모든 Deadlock을 막을 수 있다"**: 락 순서로 순환 대기는 깨지만 DB 호출 중 다른 락을 획득하는 패턴처럼 규칙이 닿지 않는 곳에서 교착이 생길 수 있다.

## 9. 면접 질문

### Q1. Deadlock, Starvation, Livelock의 차이는 무엇인가요?

Deadlock은 관련 작업 집합이 순환 대기로 모두 멈추는 상태다. Starvation은 시스템 전체는 진행하지만 특정 작업이 자원 기회를 오랫동안 얻지 못하는 상태다. Livelock은 작업들이 계속 상태를 바꾸고 재시도하지만 유용한 완료에 도달하지 못하는 현상이다.

### Q2. Deadlock의 네 가지 필요조건은 무엇인가요?

상호 배제, 점유 대기, 비선점, 순환 대기다. 네 조건이 동시에 성립해야 하며, 하나를 구조적으로 깨면 교착 상태를 예방할 수 있다. 전역 락 순서 고정은 순환 대기를 없애는 가장 실용적인 방법이다.

### Q3. 타임아웃을 두면 Deadlock이 해결되나요?

영구 대기를 끊고 복구 기회를 주지만 발생 원인을 없애지는 않는다. 타임아웃 시 중간 상태를 롤백해야 하고, 양쪽이 동시에 재시도하면 Livelock이 될 수 있다. 락 순서와 짧은 트랜잭션이 우선이며 타임아웃은 안전망이다.

### Q4. Starvation과 Livelock을 어떻게 구분하나요?

Starvation에서는 다른 작업은 완료하지만 특정 작업이 실행 기회를 얻지 못한다. 대기 시간이 지속 증가하지만 CPU 낭비는 없다. Livelock에서는 관련 작업들이 계속 상태를 바꾸고 재시도하지만 누구도 완료에 도달하지 못한다. CPU와 로그는 활발하지만 완료율이 낮다.

### Q5. DB Deadlock이 발생했을 때 애플리케이션은 어떻게 해야 하나요?

DB가 교착 트랜잭션을 롤백하면 애플리케이션은 전체 트랜잭션을 처음부터 재시도해야 한다. 재시도에는 지수 백오프와 무작위 지연, 최대 횟수와 전체 요청 기한을 둔다. 동일 레코드를 같은 순서로 갱신하고 트랜잭션을 짧게 유지하면 교착 빈도를 줄일 수 있다.

### Q6. 게임 서버에서 플레이어 간 거래 시 Deadlock을 어떻게 방지하나요?

두 플레이어 인벤토리 락을 항상 플레이어 ID가 작은 순서대로 획득한다. 이렇게 하면 어떤 두 요청도 항상 같은 순서로 락을 시도해 순환 대기가 불가능하다. 더 단순하게는 거래 작업 전체를 하나의 소유 큐에서 직렬 처리하는 설계도 가능하다.

> Deadlock은 순환 대기로 관련 작업이 모두 멈추고, Starvation은 특정 작업이 기회를 얻지 못하며, Livelock은 계속 재시도하지만 완료에 도달하지 못하는 문제입니다. 게임 서버에서 플레이어 간 거래 시 두 인벤토리 락을 플레이어 ID 순서로 획득하면 순환 대기를 구조적으로 막을 수 있습니다. 타임아웃만으로는 충분하지 않고 롤백과 제한된 재시도를 함께 설계해야 합니다.

## 12. 1~2분 확장답변

> Deadlock은 순환 대기로 멈추고 Starvation은 특정 작업이 굶으며 Livelock은 상태만 바뀌고 진전이 없습니다. Deadlock을 예방하는 가장 실용적인 방법은 전역 락 순서 고정으로 순환 대기 조건을 깨는 것입니다. 타임아웃은 영구 대기를 끊지만 원인을 없애지 않으며, 롤백 없이 포기하면 정합성이 깨지고 동시 재시도하면 Livelock이 됩니다. 운영에서 CPU가 높으면 재시도 루프와 Livelock, 낮은데 요청이 멈추면 Deadlock을 의심하고 스레드 덤프로 순환 대기를 확인합니다.

## 13. 핵심 요약

- Deadlock은 순환 대기로 관련 작업 집합이 멈추고, Starvation은 특정 작업만 기회를 못 얻으며, Livelock은 상태는 바뀌지만 유용한 완료가 없다.
- Deadlock의 네 필요조건: 상호 배제, 점유 대기, 비선점, 순환 대기. 하나를 구조적으로 깨면 예방할 수 있다.
- 전역 락 순서 고정은 순환 대기를 없애는 가장 실용적인 예방책이다. 모든 코드 경로가 규칙을 지켜야 한다.
- 타임아웃은 영구 대기를 끊지만 원인을 없애지 않는다. 중간 상태 롤백과 제한된 재시도를 함께 설계해야 한다.
- Livelock에서는 CPU가 높고 로그가 활발하지만 완료율이 낮다. 무작위 지연과 재시도 상한으로 대칭을 깨야 한다.
- Reader 우선 Lock은 읽기가 계속 들어오면 Writer Starvation을 만들 수 있다.
- DB가 교착 트랜잭션을 롤백하면 애플리케이션은 전체 트랜잭션을 처음부터 재시도해야 한다. 지수 백오프와 상한을 둔다.
- 운영에서 CPU가 높으면 재시도 루프·Livelock, 낮은데 요청이 멈추면 Deadlock을 우선 의심하고 스레드 덤프로 확인한다.

## 한 줄 정리

> Deadlock은 서로 기다려 모두 멈추고 Starvation은 한 작업이 굶으며 Livelock은 반응만 반복하고 진전하지 못합니다.
