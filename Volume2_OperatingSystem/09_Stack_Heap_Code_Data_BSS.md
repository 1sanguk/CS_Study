# 09. Stack, Heap, Code, Data, BSS

> 게임 서버·백엔드 개발자를 위한 CS 면접 교재

## 학습 목표

- 정의와 필요성을 설명할 수 있다.
- 핵심 동작과 비교 개념을 설명할 수 있다.
- 게임 서버 성능 진단에 적용할 수 있다.

## 1. 개요

Code는 명령, Data·BSS는 전역 상태, Heap은 동적 할당, Stack은 호출 문맥을 저장한다.

이 영역들은 프로그램의 가상 주소 공간을 용도와 권한, 수명에 따라 이해하기 위한 대표 분류다. 실제 배치는 운영체제, 실행 파일 형식, 런타임과 컴파일러에 따라 달라질 수 있다. 모든 지역 변수는 반드시 스택, 모든 객체는 반드시 힙이라는 식의 규칙으로 외우기보다 누가 수명을 관리하고 메모리가 어떻게 사용되는지 설명해야 한다.

## 2. 왜 필요한가

데이터 수명과 권한, 할당 방식을 분리한다. 추상화의 편리함에도 실제 전환과 메모리 비용은 남는다.

실행 명령은 쓰기보다 읽기와 실행 권한이 필요하고, 전역 데이터는 프로그램 수명 동안 유지되어야 한다. 함수 호출의 임시 상태는 중첩된 호출 순서대로 빠르게 만들고 제거하는 것이 유리하다. 실행 중 크기와 수명이 결정되는 객체는 호출이 끝난 뒤에도 살아남을 수 있어 별도 동적 저장 공간이 필요하다.

운영체제는 페이지마다 읽기·쓰기·실행 권한을 다르게 설정할 수 있다. 코드 영역을 일반적으로 쓰기 불가능하게 하고 데이터 영역을 실행 불가능하게 하는 것은 실수와 공격의 범위를 줄인다. 영역 구분은 단순한 그림이 아니라 수명, 보호와 로딩 방식의 차이를 반영한다.

## 3. 핵심 동작 원리

```text
낮은 주소(전형적 예시)
┌────────────────────┐
│ Code / Text        │ 기계 명령, 읽기·실행
├────────────────────┤
│ Read-only Data     │ 문자열 상수 등
├────────────────────┤
│ Data               │ 초기값 있는 전역·정적 변수
│ BSS                │ 0 초기화 전역·정적 변수
├────────────────────┤
│ Heap        ↓      │ 동적 할당
│                    │
│ Memory Mappings    │ Library, File, 익명 Mapping
│                    │
│              ↑     │
│ Thread Stack       │ 호출 Frame, Thread마다 존재
└────────────────────┘
높은 주소
```

위 성장 방향과 위치는 흔한 설명을 단순화한 것이며 보장된 규칙은 아니다. ASLR(Address Space Layout Randomization)은 보안을 위해 영역의 실제 주소를 바꾼다.

### Code 영역

컴파일된 기계 명령을 담는다. 같은 실행 파일을 실행하는 여러 프로세스는 변경되지 않는 코드 페이지를 물리적으로 공유할 수 있다. 일반적으로 읽기와 실행 권한을 주고 쓰기는 제한한다. 코드와 함께 읽기 전용 상수 데이터가 별도 영역에 매핑될 수 있다.

### Data와 BSS

Data 영역에는 명시적인 0이 아닌 초기값을 가진 전역·정적 변수가 들어갈 수 있다. BSS에는 초기값이 없거나 0으로 초기화되는 전역·정적 변수가 배치된다. BSS의 큰 0 배열을 실행 파일에 같은 수의 0바이트로 저장할 필요 없이 필요한 크기만 기록하고 로더가 0으로 보이는 메모리를 준비할 수 있다.

```cpp
int initialized = 42;       // Data 영역의 전형적 예
int zeroInitialized[1024];  // BSS 영역의 전형적 예
static const char* message = "hello";
```

정확한 배치는 최적화, 링커와 상수 표현에 따라 달라질 수 있으므로 이 코드는 개념적 예시다. 전역·정적이라는 저장 기간과 어느 세그먼트에 놓이는지는 관련되지만 언어 수준 개념과 실행 파일의 실제 섹션을 완전히 동일시하지 않는다.

### Stack

스택은 스레드마다 있으며 함수 호출 프레임을 관리한다. 프레임에는 반환 위치, 보존할 레지스터, 일부 매개변수와 지역 변수 등이 들어갈 수 있다. 호출 시 스택 포인터를 조정하고 반환 시 되돌리는 방식이라 일반적인 할당과 해제가 빠르다. 컴파일러는 지역 변수를 레지스터에만 두거나 최적화로 없앨 수 있으므로 모든 지역 변수가 실제 스택 메모리에 존재하는 것은 아니다.

스택 크기는 제한되어 있다. 종료 조건 없는 재귀, 지나치게 큰 지역 배열, 깊은 호출 구조는 스택 오버플로를 일으킬 수 있다. 스레드마다 스택 주소 공간을 예약하므로 스레드를 수천 개 만들면 실제 사용 페이지 외에도 주소 공간과 관리 비용이 늘어난다.

함수 반환 후 해당 스택 프레임의 지역 변수 주소를 사용하면 수명이 끝난 메모리를 참조한다. C++에서는 댕글링 포인터와 정의되지 않은 동작을 만들 수 있다. C#에서는 안전한 일반 코드가 이런 참조 탈출을 제한하지만 `Span<T>` 같은 스택 관련 타입에는 수명 규칙이 있다.

### Heap

힙은 실행 중 동적으로 요청한 메모리를 관리한다. 객체가 생성 함수보다 오래 살아야 하거나 크기가 런타임에 결정될 때 사용한다. C++에서는 개발자가 RAII와 스마트 포인터로 수명을 관리하고, C# 같은 관리형 환경에서는 도달 가능성을 기준으로 가비지 컬렉터가 회수한다.

일반적인 할당자는 운영체제에 매번 시스템 콜을 하지 않는다. 큰 메모리 영역을 받아 크기별 목록과 스레드 로컬 캐시로 나눠 작은 할당을 처리한다. 따라서 “힙 할당은 항상 시스템 콜이라 느리다”는 설명은 부정확하다. 그래도 메타데이터 관리, 동기화, 캐시 지역성, 회수와 단편화 비용은 남는다.

외부 단편화는 사용 가능한 총 공간은 충분하지만 필요한 연속 블록을 찾기 어려운 상태다. 내부 단편화는 할당 단위가 요청보다 커 블록 내부가 낭비되는 상태다. 관리형 힙은 객체 이동과 압축으로 일부 외부 단편화를 줄일 수 있지만 고정된 객체, 대형 객체와 런타임 정책에 따른 비용이 있다.

### 수명과 저장 위치

값 형식은 무조건 스택, 참조 형식은 무조건 힙이라는 표현은 피한다. C# 값 형식은 다른 힙 객체의 필드나 배열 요소로 포함될 수 있고, JIT가 지역 값을 레지스터에 둘 수도 있다. 참조 변수 자체는 스택 프레임에 있을 수 있지만 가리키는 객체는 관리형 힙에 있다. C++ 객체도 선언 방식, 포함 관계와 최적화에 따라 자동 저장 기간이나 동적 저장 기간을 가진다.

## 4. 쉬운 예시

Stack, Heap, Code, Data, BSS에서는 같은 결과의 코드라도 연속 메모리 순회와 흩어진 객체 접근은 실제 시간이 다르다. 데이터 수명과 호출 횟수를 함께 본다.

백만 개 위치를 연속 배열에 저장하면 CPU가 다음 데이터를 예측해 캐시 라인 단위로 가져오기 쉽다. 각 위치가 개별 힙 객체이고 포인터로 흩어져 있으면 포인터 추적과 캐시 미스가 늘 수 있다. 둘 다 논리적으로 같은 정보를 표현하지만 데이터 배치가 틱 처리 시간에 영향을 준다.

함수 안에서 잠깐 쓰는 4KB 버퍼를 매 패킷마다 힙에 만들기보다 범위가 명확한 임시 버퍼나 재사용 전략을 고려할 수 있다. 다만 큰 버퍼를 무작정 스택에 두면 동시 호출과 재귀 깊이에 따라 스택 오버플로 위험이 있으므로 크기와 호출 패턴을 기준으로 선택한다.

## 5. 비슷한 개념과 비교

| 관점 | 역할 | 비용 |
|---|---|---|
| OS 추상화 | 보호·자원 관리 | 전환 |
| 메모리 | 주소·수명 관리 | Fault·할당 |
| 하드웨어 | 접근 가속 | Cache Miss |

| 영역 | 대표 내용 | 수명·관리 | 주요 위험 |
|---|---|---|---|
| Code | 실행 명령 | 실행 파일·Loader | 잘못된 실행 권한 |
| Data/BSS | 전역·정적 상태 | 프로세스 수명 | 전역 공유 상태 경쟁 |
| Stack | 호출 Frame·일부 지역 값 | Thread와 호출 구조 | Overflow·수명 종료 참조 |
| Heap | 동적 객체·Buffer | Allocator·GC·개발자 | 누수·단편화·GC 지연 |

스택과 자료구조 스택은 구분한다. 호출 스택은 함수 실행 문맥을 후입선출 방식으로 관리하는 메모리 사용 구조다. `std::stack`이나 `Stack<T>`는 힙을 포함한 어디에든 내부 저장소를 둘 수 있는 추상 자료구조다.

## 6. 장점과 단점

Stack, Heap, Code, Data, BSS에서는 보호와 추상화는 안정성을 높이지만 Fault, Miss, System Call과 할당 지연을 만든다. 측정된 병목만 최적화한다.

스택은 범위 기반 수명과 저렴한 포인터 조정이 장점이지만 크기가 제한되고 호출 수명 밖으로 데이터를 유지하기 어렵다. 힙은 유연한 크기와 수명을 제공하지만 소유권, 회수, 단편화와 지역성을 고려해야 한다. 전역 데이터는 접근하기 쉽지만 테스트와 동시성 경계를 숨기므로 필요한 범위로 캡슐화한다.

## 7. 게임 서버·백엔드 실무 예시

틱마다 Heap 객체를 만들면 GC 지연이 생길 수 있어 할당률을 측정하고 풀을 선택한다. 평균 CPU뿐 아니라 할당률, RSS, Fault, 호출 수와 p99를 본다.

객체 풀은 할당을 줄일 수 있지만 만능 최적화는 아니다. 반환 누락, 이전 사용자 데이터 초기화 실패, 동시 접근과 풀 자체의 메모리 유지 비용을 만든다. 작고 수명이 짧은 관리형 객체는 세대별 GC가 효율적으로 처리할 수도 있다. 실제 할당 프로파일과 GC 일시 정지에서 병목이 확인될 때 적용한다.

C++ 서버에서는 누수뿐 아니라 해제 후 사용, 이중 해제와 소유권 순환을 확인한다. `unique_ptr`로 단일 소유권을 표현하고 공유가 필요한 곳만 `shared_ptr`를 고려한다. C# 서버에서는 살아남은 객체의 참조 경로, 대형 객체, 고정(Pinning), 네이티브 자원 해제를 함께 본다. 관리형 GC가 소켓과 파일 핸들의 즉시 반환까지 자동 보장하는 것은 아니므로 `Dispose` 패턴을 사용한다.

메모리 장애에서는 관리형 힙 크기만 보지 않는다. RSS, 가상 메모리, 스레드 수와 스택, 네이티브 버퍼, 메모리 매핑을 나눠 본다. 컨테이너 제한에 가까워지면 GC가 회수 가능한 객체가 적어도 프로세스가 종료될 수 있다.

## 8. 자주 하는 오해
- 가상 주소와 물리 사용량을 같다고 본다.
- Heap은 언제나 느리다고 단정한다.
- Page Fault는 모두 디스크 I/O라고 본다.
- TLB와 CPU Cache를 혼동한다.
- System Call과 Context Switch를 같다고 본다.
- 지역 변수는 모두 물리적으로 Stack에 존재한다고 본다.
- 값 형식은 항상 Stack, 참조 형식은 항상 Heap이라고 단정한다.
- BSS가 실행 파일 안에 같은 크기의 0으로 저장된다고 생각한다.
- 객체 풀은 언제나 GC보다 빠르고 메모리를 줄인다고 생각한다.

## 9. 면접 질문
### Q1. 핵심 개념은 무엇인가요?
Code는 명령, Data·BSS는 전역 상태, Heap은 동적 할당, Stack은 호출 문맥을 저장한다.
### Q2. 왜 필요한가요?
데이터 수명과 권한, 할당 방식을 분리한다.
### Q3. 실무 적용은 무엇인가요?
틱마다 Heap 객체를 만들면 GC 지연이 생길 수 있어 할당률을 측정하고 풀을 선택한다.

### Q4. Data와 BSS의 차이는 무엇인가요?

Data에는 명시적인 초기값이 있는 전역·정적 데이터가, BSS에는 초기값이 없거나 0으로 초기화되는 데이터가 배치되는 것이 전형적이다. BSS는 실행 파일에 전체 0바이트를 저장하지 않고 크기 정보로 표현할 수 있다.

### Q5. Stack 할당이 일반적으로 빠른 이유는 무엇인가요?

함수 호출 규칙에 따라 스택 포인터를 이동해 공간을 확보하고 반환 시 되돌릴 수 있기 때문이다. 다만 크기가 제한되고 스레드마다 존재하며, 모든 지역 변수가 실제 스택에 저장되는 것은 아니다.

### Q6. Heap은 항상 느린가요?

아니다. 현대 할당자는 스레드 로컬 캐시와 크기별 목록으로 작은 할당을 빠르게 처리한다. 다만 수명 관리, 단편화, 동기화, 캐시 지역성과 GC·해제 비용이 있으므로 할당률과 지연을 측정해야 한다.

> Stack은 호출 문맥, Heap은 동적 객체, Code·Data·BSS는 프로그램의 정적 영역을 관리합니다. Stack, Heap, Code, Data, BSS을 선택하거나 적용할 때는 정확성, 성능과 구현 복잡도의 균형을 함께 봐야 합니다. 틱마다 Heap 객체를 만들면 GC 지연이 생길 수 있어 할당률을 측정하고 풀을 선택한다.

## 12. 1~2분 확장답변
> Stack은 호출 문맥, Heap은 동적 객체, Code·Data·BSS는 프로그램의 정적 영역을 관리합니다. 보호와 추상화에는 Fault, Miss와 전환 비용이 있으므로 게임 서버에서는 데이터 수명과 배치를 설계하고 p99 지연과 OS 지표를 함께 확인합니다.
