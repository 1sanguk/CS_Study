# 09. Stack, Heap, Code, Data, BSS


## 학습 목표

- Stack, Heap, Code, Data, BSS 각 영역의 목적과 수명 관리 주체를 설명할 수 있다.
- Data와 BSS의 차이와 BSS가 실행 파일 크기에 영향을 주지 않는 이유를 설명할 수 있다.
- Stack 크기 제한과 Heap 단편화의 원인 및 게임 서버에서 미치는 영향을 설명할 수 있다.
- 틱마다 Heap 객체를 만들 때의 GC 영향과 객체 풀 적용 판단 기준을 설명할 수 있다.

## 1. 개요

Code는 명령, Data·BSS(Block Started by Symbol)는 전역 상태, Heap은 동적 할당, Stack은 호출 문맥을 저장한다.

이 영역들은 프로그램의 가상 주소 공간을 용도와 권한, 수명에 따라 이해하기 위한 대표 분류다. 실제 배치는 운영체제, 실행 파일 형식, 런타임과 컴파일러에 따라 달라질 수 있다. 모든 지역 변수는 반드시 스택, 모든 객체는 반드시 힙이라는 식의 규칙으로 외우기보다 누가 수명을 관리하고 메모리가 어떻게 사용되는지 설명해야 한다.

## 2. 왜 필요한가

데이터 수명과 권한, 할당 방식을 분리한다.

실행 명령은 쓰기보다 읽기와 실행 권한이 필요하고, 전역 데이터는 프로그램 수명 동안 유지되어야 한다. 함수 호출의 임시 상태는 중첩된 호출 순서대로 빠르게 만들고 제거하는 것이 유리하다. 실행 중 크기와 수명이 결정되는 객체는 호출이 끝난 뒤에도 살아남을 수 있어 별도 동적 저장 공간이 필요하다.

운영체제는 페이지마다 읽기·쓰기·실행 권한을 다르게 설정할 수 있다. 코드 영역을 쓰기 불가능하게 하고 데이터 영역을 실행 불가능하게 하는 것은 실수와 공격의 범위를 줄인다.

## 3. 핵심 동작 원리

```text
낮은 주소(전형적 예시)
┌────────────────────┐
│ Code / Text        │ 기계 명령, 읽기·실행
├────────────────────┤
│ Read-only Data     │ 문자열 상수 등
├────────────────────┤
│ Data               │ 초기값 있는 전역·정적 변수
│ BSS                │ 0 초기화 전역·정적 변수
├────────────────────┤
│ Heap        ↓      │ 동적 할당
│                    │
│ Memory Mappings    │ Library, File, 익명 Mapping
│                    │
│              ↑     │
│ Thread Stack       │ 호출 Frame, Thread마다 존재
└────────────────────┘
높은 주소
```

위 성장 방향과 위치는 흔한 설명을 단순화한 것이며 보장된 규칙은 아니다. ASLR은 보안을 위해 영역의 실제 주소를 바꾼다.

### Code 영역

컴파일된 기계 명령을 담는다. 같은 실행 파일을 실행하는 여러 프로세스는 변경되지 않는 코드 페이지를 물리적으로 공유할 수 있다. 일반적으로 읽기와 실행 권한을 주고 쓰기는 제한한다.

### Data와 BSS

Data 영역에는 명시적인 초기값을 가진 전역·정적 변수가 들어갈 수 있다. BSS에는 초기값이 없거나 0으로 초기화되는 전역·정적 변수가 배치된다. BSS의 큰 0 배열을 실행 파일에 같은 수의 0바이트로 저장할 필요 없이 필요한 크기만 기록하고 로더가 0으로 보이는 메모리를 준비할 수 있다.

```cpp
int initialized = 42;       // Data 영역의 전형적 예
int zeroInitialized[1024];  // BSS 영역의 전형적 예 — 실행 파일에 4KB를 저장하지 않음
```

### Stack

스택은 스레드마다 있으며 함수 호출 프레임을 관리한다. 프레임에는 반환 위치, 보존할 레지스터, 일부 매개변수와 지역 변수 등이 들어갈 수 있다. 호출 시 스택 포인터를 조정하고 반환 시 되돌리는 방식이라 일반적인 할당과 해제가 빠르다. 컴파일러는 지역 변수를 레지스터에만 두거나 최적화로 없앨 수 있으므로 모든 지역 변수가 실제 스택 메모리에 존재하는 것은 아니다.

스택 크기는 제한되어 있다. 종료 조건 없는 재귀, 지나치게 큰 지역 배열, 깊은 호출 구조는 스택 오버플로를 일으킬 수 있다. 스레드마다 스택 주소 공간을 예약하므로 스레드를 수천 개 만들면 주소 공간과 관리 비용이 늘어난다.

### Heap

힙은 실행 중 동적으로 요청한 메모리를 관리한다. 객체가 생성 함수보다 오래 살아야 하거나 크기가 런타임에 결정될 때 사용한다. 관리형 환경에서는 가비지 컬렉터가, C++에서는 개발자가 수명을 관리한다.

일반적인 할당자는 운영체제에 매번 시스템 콜을 하지 않는다. 큰 메모리 영역을 받아 크기별 목록과 스레드 로컬 캐시로 나눠 작은 할당을 처리한다. 그래도 메타데이터 관리, 동기화, 캐시 지역성, 회수와 단편화 비용은 남는다.

외부 단편화는 사용 가능한 총 공간은 충분하지만 필요한 연속 블록을 찾기 어려운 상태다. 내부 단편화는 할당 단위가 요청보다 커 블록 내부가 낭비되는 상태다.

## 4. 쉬운 예시

```java
// 스택 오버플로: 종료 조건 없는 재귀
public int infiniteRecursion(int n) {
    return infiniteRecursion(n - 1); // 종료 조건 없음 → StackOverflowError
}
// 게임 서버에서 방 탐색, 경로탐색을 재귀로 구현할 때 깊이 제한 필요
```

```java
// BAD: 틱마다 객체 생성 → GC 부하
public void onTick() {
    List<PlayerUpdate> updates = new ArrayList<>(); // 매 틱마다 힙 할당
    for (Player p : players) {
        updates.add(new PlayerUpdate(p.x, p.y));   // 객체마다 힙 할당
    }
    broadcast(updates);
    // 틱 종료 → ArrayList, PlayerUpdate가 가비지로 → Young GC 빈번 → 지연 스파이크
}
```

```java
// GOOD: 객체 풀로 재사용
private final ArrayDeque<PlayerUpdate> updatePool = new ArrayDeque<>();

public PlayerUpdate borrowUpdate() {
    PlayerUpdate u = updatePool.poll();
    return u != null ? u : new PlayerUpdate(); // 풀이 비면 새로 생성
}

public void returnUpdate(PlayerUpdate u) {
    u.reset(); // 반드시 초기화 (이전 사용자 데이터 노출 방지)
    updatePool.offer(u);
}
// 주의: 반환 누락 시 메모리 누수. 동시 접근 시 ConcurrentLinkedDeque 또는 별도 동기화 필요
// 단수명 객체는 세대별 GC가 효율적 처리 가능 → 프로파일 먼저, 풀은 측정 후 적용
```

```bash
# RSS, 힙, 스레드 스택 분리해 확인 (02번 파일 기법 재사용)
cat /proc/<pid>/status | grep -E "VmRSS|VmSize|Threads"
```

## 5. 비슷한 개념과 비교

| 영역 | 대표 내용 | 수명·관리 주체 | 주요 위험 |
|---|---|---|---|
| Code | 실행 명령 | 실행 파일·Loader | 잘못된 실행 권한 |
| Data | 초기값 있는 전역·정적 변수 | 프로세스 수명 | 전역 상태 경쟁 |
| BSS | 0초기화 전역·정적 변수 | 프로세스 수명 | 전역 상태 경쟁 |
| Stack | 호출 프레임·일부 지역 값 | 스레드와 호출 구조 | Overflow·수명 종료 참조 |
| Heap | 동적 객체·Buffer | Allocator·GC·개발자 | 누수·단편화·GC 지연 |

| Stack vs Heap | Stack | Heap |
|---|---|---|
| 할당 방식 | 포인터 조정 (빠름) | Allocator 탐색 (상대적으로 느림) |
| 크기 제한 | 있음 (보통 수 MB) | 가상 주소 공간 한도까지 |
| 수명 관리 | 자동 (호출 복귀 시 해제) | 개발자·GC |
| 스레드 | 스레드마다 독립 | 프로세스 공유 (동기화 필요) |
| 위험 | 오버플로·댕글링 참조 | 누수·단편화·GC 일시 정지 |

## 6. 장점과 단점

**Stack의 장점**

- 포인터 조정만으로 빠르게 할당·해제한다.
- 범위 기반 수명으로 관리가 단순하다.

**Stack의 단점**

- 크기가 제한되어 깊은 재귀나 큰 지역 배열은 오버플로를 만든다.
- 스레드마다 주소 공간을 예약하므로 스레드 수가 많으면 비용이 늘어난다.

**Heap의 장점**

- 유연한 크기와 수명을 제공한다.
- 스레드 간 공유가 가능하다.

**Heap의 단점**

- 단편화, 수명 관리, 캐시 지역성과 GC 일시 정지 비용이 있다.
- 할당률이 높으면 GC 빈도가 늘어 지연 스파이크가 생긴다.

## 7. 게임 서버·백엔드 실무 예시

틱마다 Heap 객체를 만들면 GC 지연이 생길 수 있어 할당률을 측정하고 풀을 선택한다. 평균 CPU(Central Processing Unit)뿐 아니라 할당률, RSS, Fault, 호출 수와 p99를 본다.

객체 풀은 할당을 줄일 수 있지만 만능 최적화는 아니다. 반환 누락, 이전 사용자 데이터 초기화 실패, 동시 접근과 풀 자체의 메모리 유지 비용을 만든다. 작고 수명이 짧은 관리형 객체는 세대별 GC가 효율적으로 처리할 수도 있다. 실제 할당 프로파일과 GC 일시 정지에서 병목이 확인될 때 적용한다.

메모리 장애에서는 관리형 힙 크기만 보지 않는다. RSS, 가상 메모리, 스레드 수와 스택, 네이티브 버퍼, 메모리 매핑을 나눠 본다. 컨테이너 제한에 가까워지면 GC가 회수 가능한 객체가 적어도 프로세스가 종료될 수 있다.

## 8. 자주 하는 오해

- **"지역 변수는 모두 물리적으로 스택에 존재한다"**: 컴파일러가 레지스터에만 두거나 최적화로 없앨 수 있다. 소스 코드에 지역 변수가 있어도 스택 메모리에 실제로 할당되지 않을 수 있다.
- **"값 형식은 항상 스택, 참조 형식은 항상 힙이다"**: C# 값 형식도 다른 힙 객체의 필드가 되면 힙에 있다. 참조 변수 자체는 스택 프레임에 있을 수 있지만 가리키는 객체는 힙에 있다.
- **"BSS가 실행 파일에 같은 크기의 0으로 저장된다"**: BSS는 크기만 기록하고 로더가 0으로 초기화한다. 대형 0 배열도 실행 파일 크기를 늘리지 않는다.
- **"Heap 할당은 항상 시스템 콜이라 느리다"**: 현대 할당자는 스레드 로컬 캐시와 크기별 목록으로 작은 할당을 시스템 콜 없이 빠르게 처리한다. 수명 관리, 단편화, 캐시 지역성 비용은 남는다.
- **"객체 풀은 GC보다 항상 빠르다"**: 반환 누락, 초기화 실패, 동시 접근 동기화 비용이 있다. 세대별 GC가 단수명 객체를 효율적으로 처리할 수 있다. 프로파일로 확인한 뒤 적용한다.
- **"관리형 GC가 소켓·DB 연결·파일 핸들을 자동으로 즉시 해제한다"**: GC는 관리형 메모리만 처리한다. 네이티브 자원은 `Dispose` 패턴이나 `try-with-resources`로 명시적으로 해제해야 한다.
- **"힙 메모리가 정상 범위이면 메모리 누수가 없다"**: 스레드 스택, 네이티브 버퍼, 메모리 매핑, 코드 캐시 등이 관리형 힙 외부에 있다. RSS와 가상 메모리를 함께 봐야 한다.

## 9. 면접 질문

### Q1. Stack, Heap, Code, Data, BSS 각 영역의 역할은 무엇인가요?

Code는 컴파일된 기계 명령, Data는 초기값 있는 전역·정적 변수, BSS는 0초기화 전역·정적 변수, Heap은 동적 할당 객체, Stack은 호출 프레임과 일부 지역 값을 저장한다. 각 영역은 목적, 수명, 권한이 달라 별도 관리된다.

### Q2. 스택 오버플로는 어떤 상황에서 발생하나요?

스택 크기가 제한되어 있어 종료 조건 없는 재귀, 지나치게 큰 지역 배열, 깊은 호출 구조로 스택이 한도를 넘으면 발생한다. 게임 서버에서 경로 탐색이나 방 구조 탐색을 재귀로 구현할 때 깊이 제한을 함께 설계해야 한다.

### Q3. Data와 BSS의 차이는 무엇인가요?

Data에는 명시적인 초기값이 있는 전역·정적 데이터가, BSS에는 초기값이 없거나 0으로 초기화되는 데이터가 배치되는 것이 전형적이다. BSS는 실행 파일에 전체 0바이트를 저장하지 않고 크기 정보로 표현하여 실행 파일 크기를 줄인다.

### Q4. 스택 할당이 일반적으로 빠른 이유는 무엇인가요?

함수 호출 규칙에 따라 스택 포인터를 이동해 공간을 확보하고 반환 시 되돌릴 수 있기 때문이다. 다만 크기가 제한되고 스레드마다 존재하며, 모든 지역 변수가 실제 스택에 저장되는 것은 아니다.

### Q5. Heap은 항상 느린가요?

아니다. 현대 할당자는 스레드 로컬 캐시와 크기별 목록으로 작은 할당을 시스템 콜 없이 빠르게 처리한다. 다만 수명 관리, 단편화, 동기화, 캐시 지역성과 GC 비용이 있으므로 할당률과 지연을 측정해야 한다.

### Q6. 게임 서버에서 틱마다 객체를 만들면 어떤 문제가 생기나요?

매 틱마다 대량의 객체가 생성·폐기되어 Young GC 빈도가 높아지고 지연 스파이크가 생길 수 있다. 할당률과 GC 일시 정지를 프로파일로 확인한 뒤, 반환 누락과 초기화 실패에 주의하면서 객체 풀 적용을 판단한다.

## 10. 예상 꼬리질문

- 가상 주소와 물리 주소의 차이는 무엇인가요?
  > 가상 주소는 프로세스가 사용하는 논리적 주소이고 물리 주소는 실제 RAM에서의 위치다. 운영체제와 MMU가 페이지 테이블을 통해 가상 주소를 물리 주소로 변환한다. 이 추상화 덕분에 프로세스마다 독립적인 주소 공간을 가질 수 있고 물리 메모리 단편화 없이 연속된 가상 공간을 제공할 수 있다.
- 데이터 지역성이 성능에 어떤 영향을 주나요?
  > 공간 지역성이 좋으면 캐시 라인 한 번 로드로 인접 데이터를 함께 가져와 Cache Miss를 줄인다. 시간 지역성이 좋으면 최근 사용한 데이터가 캐시에 머물러 재접근 속도가 빠르다. 힙에 흩어진 객체 참조를 반복적으로 추적하면 지역성이 나빠져 Cache Miss와 TLB Miss가 늘고 성능이 저하된다.
- Stack Overflow가 발생하면 어떻게 처리하나요?
  > 스택 포인터가 스택 영역의 하한을 넘으면 운영체제가 Guard Page를 감지해 프로세스에 신호(SIGSEGV 또는 StackOverflowError)를 전달한다. 대부분의 경우 복구하기 어렵고 프로세스가 종료된다. 예방책으로는 재귀 깊이 제한, 큰 지역 배열은 힙으로 이동, 비재귀 알고리즘 사용 등이 있다.
- 내부 단편화와 외부 단편화의 차이는 무엇인가요?
  > 내부 단편화는 할당 단위가 요청 크기보다 커 블록 내부가 낭비되는 상태다. 예를 들어 5바이트를 요청했을 때 8바이트 블록이 할당되면 3바이트가 낭비된다. 외부 단편화는 사용 가능한 총 공간은 충분하지만 요청한 크기의 연속 블록이 없는 상태로, 메모리가 여러 작은 조각으로 나뉘어 있을 때 발생한다.
- 같은 실행 파일의 Code 페이지를 여러 Process가 공유할 수 있나요?
  > 그렇다. Code 영역은 읽기 전용이므로 같은 실행 파일을 실행하는 여러 프로세스가 동일한 물리 코드 페이지를 공유할 수 있다. 각 프로세스의 가상 주소는 다를 수 있지만 페이지 테이블이 같은 물리 프레임을 가리켜 메모리를 절약한다. 공유 라이브러리(*.so, *.dll)도 같은 방식으로 코드 페이지를 공유한다.
- C++에서 댕글링 포인터는 어떻게 생기나요?
  > 이미 해제된 메모리를 가리키는 포인터를 댕글링 포인터라 한다. `delete`로 객체를 해제한 뒤 포인터를 null로 초기화하지 않거나, 스택 프레임이 복귀된 뒤 그 안의 지역 변수 주소를 참조하거나, 컨테이너 재할당 후 이전 주소를 저장한 이터레이터를 사용하면 발생한다. 해제된 메모리에 접근하면 undefined behavior가 발생한다.
- 세대별 GC가 단수명 객체에 효율적인 이유는 무엇인가요?
  > 세대별 GC는 대부분의 객체가 생성 직후 곧 사라진다는 약세대 가설(Weak Generational Hypothesis)에 기반한다. Young 영역은 작고 자주 GC를 수행하는데, 이때 살아남은 객체만 Old 영역으로 승격한다. 단수명 객체는 Young GC에서 회수되어 전체 힙 탐색 없이 빠르게 처리되므로 GC 일시 정지 시간이 짧아진다.

## 11. 30초 모범답변

> Code는 기계 명령, Data·BSS는 전역 상태, Heap은 동적 할당, Stack은 호출 프레임을 저장합니다. BSS는 실행 파일에 크기만 기록해 0 배열이 파일 크기를 늘리지 않습니다. 게임 서버에서 틱마다 객체를 만들면 GC 빈도가 높아지므로 할당률을 측정한 뒤 객체 풀 적용을 판단합니다.

## 12. 1~2분 확장답변

> Stack은 호출 문맥, Heap은 동적 객체, Code·Data·BSS는 프로그램의 정적 영역을 관리합니다. Stack은 포인터 조정으로 빠르지만 크기가 제한되어 깊은 재귀는 오버플로를 만듭니다. Heap 할당자는 스레드 로컬 캐시로 빠르게 처리하지만 단편화와 GC 비용이 있습니다. 지역 변수가 반드시 스택에 있는 것은 아니고, 값 형식이 항상 스택에 있다는 규칙도 언어마다 다릅니다. 게임 서버에서는 틱 루프 할당률과 GC 일시 정지를 측정하고, 관리형 GC가 소켓·DB 연결을 자동 해제하지 않으므로 Dispose 패턴을 사용합니다.

## 13. 핵심 요약

- Code는 기계 명령, Data는 초기값 있는 전역·정적 변수, BSS는 0초기화 전역·정적 변수, Heap은 동적 할당, Stack은 호출 프레임을 저장한다.
- BSS는 실행 파일에 크기만 기록하고 로더가 0으로 초기화한다. 대형 0 배열도 실행 파일 크기를 늘리지 않는다.
- 스택은 스레드마다 있으며 포인터 조정으로 빠르게 할당·해제한다. 크기가 제한되어 깊은 재귀나 큰 지역 배열은 스택 오버플로를 만든다.
- 현대 힙 할당자는 스레드 로컬 캐시로 작은 할당을 시스템 콜 없이 처리한다. 수명 관리·단편화·캐시 지역성 비용은 남는다.
- 지역 변수가 반드시 스택에 있는 것은 아니다. 컴파일러가 레지스터에 두거나 최적화로 없앨 수 있다.
- 값 형식이 항상 스택, 참조 형식이 항상 힙이라는 규칙은 언어마다 다르다. C# 값 형식도 힙 객체의 필드가 되면 힙에 있다.
- 틱마다 객체를 만들면 GC 빈도가 높아져 지연 스파이크가 생길 수 있다. 할당률과 GC 일시 정지를 측정한 뒤 객체 풀 적용을 판단한다.
- 관리형 GC는 관리형 메모리만 처리한다. 소켓·DB 연결·파일 핸들은 Dispose 패턴으로 명시적으로 해제해야 한다.
